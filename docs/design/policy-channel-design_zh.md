# ONNX策略通道 — 来自Hub的策略

状态: 草案 · 日期: 2026-08-31 · 负责人: pierre

ONNX策略的来源，有人尝试一个他们没有训练过的策略，以及“重置”会做什么。

**目前构建完成**（2026-08-31）：§3，§4，§5，§9，§9.1 和 §9.2 — 除了§7中的`check`，涵盖了社区条目的全部内容。板上的策略可以尝试和撤销而无需编辑文件或重启任何东西；官方策略集是从Hub获取的，而不是随发行版携带的；重新训练的步伐可以到达机器人而无需daemon的发布。

**尚未实现**：`policy check`仅覆盖官方策略集 — 从移动分支获取的社区策略记录了它来自的提交，但尚未有机制将这些提交与分支进行比较以确定分支是否已移动。本页中的其他内容均已构建完成。

本页与[更新机制设计.md](updater-design_zh.md)相配套，后者负责更新引擎 — 组件、来源、签名、健康门、回滚 — 以及与[机器人守护程序设计.md](robotd-design_zh.md) §2.3 相配套，后者负责策略的验证和运行。本页负责 **通道**：哪个文件填充了空缺，谁发布了它，以及改变这一点的命令。如果某个机制属于上述任一页面，则本页面会用一句话并指明。

## 1. 今天的问题

所有九个`.onnx`文件都随daemon的软件包一起提供，`robotd`从`/opt/robot/daemon/current/policies/`加载它们。三个后果，从该文件自编写之日起就由`policies/README.md`命名：

- 重新训练步伐需要daemon的发布；
- daemon修复会重新下载6MB未更改的权重；
- 在笔记本上训练的策略只能通过CI或整个daemon的侧载到达鸭子。

由此产生了两个要求，它们 **不是同一个功能**：

1. 我们的策略版本独立于daemon；
2. 有人可以尝试一个他们没有训练过的策略，发现它是否有效，然后撤销。

第一个是一个普通的组件（更新机制设计中的§5.5），不需要新的概念。第二个是本页主要讨论的内容，因为它正是组件模型尚未覆盖的部分。

## 2. 三种来源，一个空缺

一个空缺 — `walk`，`stand`，`sitstand`，`ground_pick`，`kick_left`，`kick_right`，`roulade` — 仅从三个来源之一填充：

| | 来源 | 出处 | 签名 | 自动更新 | 重置目标 |
|---|---|---|---|---|---|
| **官方** | `policies` 组件 | manifest, semver | 是 | 是，根据 `auto_apply` | **是** |
| **社区** | 任何其他 HF 仓库 | repo + revision + commit sha | 否 | 否 — 仅报告 | 否 |
| **本地** | 板上的路径 | 无 | 否 | 否 — 无法确定 | 否 |

组织决定来源：**`pollen-robotics/*` 是官方，其他一切为社区**。一个常量，一个地方。这不是一个配置键 — 一个可以被告诉信任哪个组织的机器人，其“官方”标识毫无意义。

来源决定了行为，而不仅仅是标签：

- **官方** 是 `policy reset` 返回的目标，也是周期性检查可能自行应用的唯一来源；
- **社区和本地** 从不自动应用，也不是重置目标，它们携带其来源出现在所有显示的地方 — `policy list`、`policy check` 以及 `robotctl monitor` 打印的策略名称 `robotctl monitor` 今天显示为 `walk`，而这些策略除了槽位外没有任何共同之处。

**社区策略的签名验证故意不被要求**。除了组件路径规则外，引擎安装的其他所有文件都根据可信密钥进行验证，这是第一个例外。其论点在于，策略不是一个二进制文件：`robotd` 拥有唯一写入关节钳后方总线的权限，一个跌倒→跛行反射和意图死锁（`robotd-design.md` §2.4），而 `obs[1,61] → actions[1,14]` 网关在机器人静止时会拒绝一个形状不匹配的图。这个沙盒是边界，而不是签名。一个守护进程二进制文件没有这样的沙盒，这就是为什么组件路径规则没有改变的原因。

## 3. 槽位是配置，因此 `load` 和 `reset` 是配置编辑

`policy.walk` 已经是 `robotd.toml` 中的 `Option<PathBuf>`，未设置意味着“解析为此模式的默认值”（`robotd-params/src/lib.rs`，`PolicyParams::resolved`）。`robotctl configure` 通过 `toml_edit` 设置或移除它所触及的键，而不干扰注释。因此：

- `policy load <槽位> <x>` 写入 `policy.<槽位>`，然后重新加载；
- `policy reset <槽位>` 移除键，然后重新加载；
- `policy reset` 移除所有七个键 — “把它恢复到最初的样子”。
**`robotd`写入键值，而不是调用者。**`robot.loadPolicy`在记录槽位到`robotd.toml`后才将交换入队列，因此上述持久性是方法的属性，而非调用它的命令。最初则相反——`robotctl`写入文件，守护进程仅更改自身内存——这在相同名称下悄无声息地为本节所拒绝的临时模式提供了支持。写入者位于`robotd_params::edit`中，紧邻其验证的模式，每个写入者在整个读取-修改-写入过程中都会锁定文件：现在有四个进程编辑它，包括守护进程。

这就是整个持久性模型，且并非新机制。加载在重启后仍然有效，正如[`updater-design.md`](updater-design_zh.md)§5.7所要求的那样：“活动模式选择”是一种**用户偏好**，保存在更新程序从不覆盖的配置文件中，并且在更新和回滚过程中均得以保留。

**考虑过一种临时的“尝试直到重启”的模式，但最终被拒绝了。**它读起来更安全——一次步态错误就可能造成永久性损失——但会在配置文件旁边引入另一种真相来源，关于机器人正在运行的内容，并且会使`reset`几乎失去意义，因为重启本身就已经是撤销操作。一个持久的答案加上一个撤销命令更容易解释和确保。它所防范的风险已在§5中处理，那里才是它应处之地。

## 4. 实时重载

`robot.setMode`已经在运行中的50 Hz循环中交换了每个ONNX会话，而策略加载则是同一条路径，但范围更窄。流程（`robotd/src/main.rs`，模式切换处理程序及其在起始姿态的完成）：
```text
IPC call        → validate what this side can, set an intent, answer accepted
loop            → re-resolve the params, start loading the controller on a worker thread
                  (load + warm-up), and decide whether the change touches the network
                  that is driving
  if it does    → home the robot with torque on; swap in at home, fresh
  if it does not→ swap in wherever the robot is, carrying the running state across
on success      → publish the new policy names, resume
```
Three 与模式切换的不同之处。

**范围。** 加载会覆盖 `policy_params` 中的一个字段并重新解析，与模式切换将 `policy_params.mode` 设置为某个值并重新解析完全相同。重建控制器会重新加载所有七个会话，而不仅仅是更改的那个——在工作线程中完成，因为现在可以在移动的机器人下进行切换，循环不能因加载而停滞。

**只有网络的变化才会驱动机器人。** 首次针对此设计的反馈是：加载一个行走指令，行走，坐下，`policy reset walk` — 机器人返回到起始位置并站立起来。重置正确地反映了配置，但错误地反映了机器人：`sitstand` 已经包含了这个指令，而重置并没有触及 `sitstand`。因此，循环会将变化与上一个时间步的指令进行比较，通过该网络的解析路径（当一个技能驱动时，是整个技能列表，因为技能是列表中的一个索引）。如果未发生变化，新的控制器会在机器人所在的位置替换旧控制器，接管其座位、技能和过滤状态，因此下一个时间步将从相同的位置和相同的网络开始。如果发生变化，机器人会先返回到起始位置，就像所有变化之前那样，直到加载完成。加载总是被视为驱动因素的变化：它用于处理路径未变但字节已变的情况，因此路径无法给出答案。

**一个已经是真值的请求不会做任何工作。** 重置一个没有被覆盖的槽位，或者加载一个槽位已经运行的文件，会返回一个队列中未做任何事情的确认——与 `robot.setMode` 对于“已经在那种模式下”的情况给出相同答案，原因相同：调用者请求了一个状态并且已经拥有它。如果没有这个特性，对于一个未被更改的机器人，`policy reset` 会将其送回起始位置，重新加载七个网络并回到它原本运行的状态，这看起来像是一个故障。

唯一一个永远不会已经完成的槽位是携带错误信息的那个。在启动时失败的覆盖会在内存中被丢弃（§5），因此它会被读作未被覆盖并运行默认值——与任何未被触碰的槽位无法区分。重置它是为了清除错误及其背后的配置，因此这个请求必须通过。
**失败不应剥夺你应有的步伐。**今天，一个控制器失败未能构建时会设置`policy_error`，健康状态标记为不健康，并使机器人保持其姿态——这适用于模式切换，表示机器人配置状态，而在试验中则是错误的，因为试验本质上是推测性的。尝试一个51-D文件不应使机器人失去步伐，直到有人重启它。因此，加载**保持运行中的控制器**当新的控制器失败时，并将原因返回给调用者。生成原因的门已经存在，并在任何东西上线之前在起始姿态运行；这关乎如何处理其错误。

## 5. 无效的覆盖不应阻止守护进程更新

持久性有一个锋利的边缘。一个在尝试时加载的社区或本地策略可能在下一次启动时失败——文件被删除，库被清空，板子被重新烧录恢复配置。`robotd`将在每次启动时报告**不健康**，`updaterd`的健康门将因一个文件缺失而回滚守护进程发布，而这个原因并非任何发布所导致：这是由于一个缺少文件而引发的更新循环，而这个文件任何更新都无法提供。

解决此问题的规则：

- 一个**社区或本地**策略加载失败会回退到该插槽的**官方默认值**并报告**降级**，并命名该文件；
- 一个**官方**策略加载失败保持**不健康**。

这是`HealthResult::degraded`存在的意义。缺少的覆盖是板子的属性，而不是被门控的发布所固有的——回滚守护进程无法修复它，只会增加启动计数。一个真正的官方策略出错确实是一个损坏的捆绑包，回滚它是正确的响应。

请注意，这**不会**默默地修复配置。覆盖仍然存在，`robotctl health`会指出哪个文件未能加载，因此状态是可见的，`policy reset <插槽>`是修复方法。一个在坏启动时默默地重写配置的守护进程会比一个说明原因的降级机器人更令人惊讶。

## 6. 版本检查

一个作为“库中的一个文件”持有的社区策略没有版本，也没有可供比较的内容，因此库为每个条目保留了一个小型的侧车：仓库、修订版本、解析的提交SHA、文件名、获取时间。这些记录使得检查成为可能，而读取这些记录的大部分内容已经存在——`source/hf_hub.rs`已经解析引用API为`RepoRefs { tags }`，`api/models/{repo}`提供了`sha`和`lastModified`。
要求由出版者实际提供的版本来呈现，而不是假装每个人都使用 semver：

| 来源 | 显示为 |
|---|---|
| 正式发布 | manifest 的 semver — `1.2.0`，就像任何组件一样 |
| 社区，仓库有 `v*` 标签 | 标签 |
| 社区，跟踪分支 | 短 sha + 日期 |
| 本地 | `local`，且 `check` 报告未知 |

**`policy check` 是唯一查看的地方。** 它内部路由 —— 正式槽位询问 `updaterd` 关于 `policies` 组件，社区槽位询问 Hub —— 因为“哪个命令告诉我我的行走是否过时”有两个答案正是值得通过稍微的路由来避免的混淆。

周期性检查（`check_interval`，6 小时）也覆盖了社区策略，并且 **不应用只报告**。这已经是 `auto_apply` 对普通版本的处理方式：可用性是一个需要呈现的事实，安装是一个决定。这也使得应用能够说“一个更新已为你的弹跳行走可用”而无需新的基础设施。

## 7. 命令界面
```text
robotctl policy list                      slot · current · origin · version
robotctl policy check [slot]              is anything newer at the source
robotctl policy load <slot> <repo|name|path>
robotctl policy update <slot>             fetch the newest and load it
robotctl policy reset [slot]              back to official; no slot = all seven
robotctl policy search <query>            Hub models matching a query
```
`load` 采取一个 HF 仓库 (`org/name[@rev]`)、库中已有的名称或 **板上的路径**。路径形式是训练者的 `scp`-然后尝试循环，也是为什么整个功能值得在工作站上存在的原因；这也是唯一一个没有来源输入，因此 `local` 在第 2 节中作为一级源头而不是偶然存在的原因。

没有单独的 `fetch`：`load` 在需要时下载，并且库会累积，因此加载 A，然后加载 B，然后再次加载 A 只会花费一次下载。`search` 很薄 —— `api/models?search=` 对查询的搜索 —— 在 `microduck` 标签存在之前，通过搜索单词来查找就是全部内容。

## 8. 电线，以及它的成本

`robotd` 上的两个新方法：`robot.loadPolicy`（插槽 + 源，回答方式类似于 `robot.setMode` —— 接受、拒绝并附带原因，或无操作）和 `robot.policies`（每个插槽运行的内容，包括来源和版本）。`updaterd` 上的一个新命名空间 `policy.*`，用于获取。

`API_VERSION` 从 17 升级到 18。`robotctl` 和 `btd` 与 `robotd` 一起打包在同一个二进制文件中，因此它们一起移动；一个绑定到 v17 的客户端会收到 `METHOD_NOT_FOUND`，这是设计中的偏差行为，而不是握手拒绝（[`duck-ipc-proto/src/lib.rs`](../../duck-ipc-proto/src/lib.rs)，`API_VERSION`）。

**获取操作在 `updaterd` 中进行，而不是在 `robotctl` 中。** `robotctl/Cargo.toml` 中声明了这条规则：一个在恢复路径上的支持工具不会链接更新引擎的 http/tar/zstd/crypto 树，从结构上来说现在也不能。`updaterd` 已经具备了 HF URL 解析、`reqwest` 客户端以及应用程序所需的进度通知。成本是诚实的 —— 它是第一个在守护进程内部的未签名下载，其不变性是没有任何未签名的字节到达活动路径 —— 因此 `policy.*` 命名空间只能写入库目录，而绝不会写入组件的安装目录，从而在关键位置保持该不变性的真实。
- 库存放在 `/var/lib/robot/policies/`，每个发布目录之外，根据 [`updater-design.md`](updater-design_zh.md) §5.7 规则1。它为每个仓库保留两个版本——刚刚获取的一个和之前的那个，官方集使用的是§9.1中的规则，因为没有其他方式清理它，而且 `policy.fetch` 以及其背后的命令都通过两种无线电传输提供。机器人正在使用的版本，无论其多旧，都会被保留；一个不响应的机器人不会修剪任何内容，因为沉默表示机器人宕机，而不是不使用任何策略的机器人。

## 9. 留下成品

`robotd` 从 `/opt/robot/policies/current` 读取其策略，而不是从发布内部读取。这已经完成了，重要的是这一点：策略的运行时来源只有一个，没有发布副本与其他任何内容之间的优先级规则。

**填充该目录的是 `scripts/seed-policies.sh`，并且它会下载。**
由 `hooks/postinstall` 在每次更新时运行，以及由 `install.sh` 在新板上运行，它从 Hub 获取锁定的集合到 `/opt/robot/policies/releases/seed-<pin>/`，并将 `current` 指向它——与更新器已经交换的相同 `releases/` + `current` 符号链接布局（更新器设计的§7.1）。

通过下载而不是复制：这是 `setup-board.sh` 为 ONNX Runtime 和 `setup-gstreamer.sh` 为插件已经使用的安排，这两者是板子需要而发布没有理由携带的其他两种东西。鸭子检测器也遵循了同样的道路离开发布——`scripts/seed-detector.sh`，`/opt/robot/detector/current`，`robotctl duck-detector check/update`，一个固定文件列表代替了清单，因为它的两个文件具有固定的名称（`docs/project/npu-bringup.md`）。该固定版本位于 `[workspace.metadata.detector]` 中，并作为脚本中的字面量存在，有一个测试断言它们一致——`setup-gstreamer.sh` 的陷阱，因为从发布内部运行的脚本无法读取清单。
**钉子是一个最低要求，而不是上限**，这一点区别至关重要。它包含在守护进程发布中，因此提升它*确实*需要一个守护进程发布——早期版本的这一部分内容声称并非如此，实际上是错误的。钉子决定两件事：新部署的板子安装的内容，以及守护进程运行的最旧官方版本。如果板子的版本来自我们的仓库且低于钉子，安装后挂钩会将其更新至钉子版本——守护进程的插槽默认命名文件，一个仅由更新版本携带的文件名（v5的`velstand.onnx`）的默认设置会导致单独更新守护进程的板子无法加载其步态，从而变得不健康并被回滚。超过钉子版本的集合、来自其他仓库或没有`.source`记录的集合将被忽略。跨越钉子版本是通过`robotctl policy update`（第9.1节）实现的，这是使重新训练的步态能够不依赖守护进程发布就到达机器人的方式，也是使整个渠道有价值的原因。

钉子不做三件事。它不会重新下载已经拥有的集合，因此如果钉子未变，更新不会触及任何网络——这很重要，因为安装后挂钩在120秒超时内运行，超时的挂钩会回滚更新。它从不安装部分下载的内容：所有内容都暂存在一个暂存目录中，直到整个集合到达后才会移动到`current`目录。它也不会在下载失败时用较旧版本替换当前工作版本——半发布的修订版会让板子保持原有的步态，钉子会在下次更新时重试。

没有内容被签名，这遵循了第2节的内容，而不是与其相矛盾：这是一个人可以下载的内容，放入一个`robotd`目录中进行校验。形状校验也会捕获截断的文件，这就是为什么这里没有固定哈希值，不会在每次重新训练时失效。

一条规则使这成为一次启动而不是第二个家：**已经安装的集合无论钉子如何指示都不会被替换**。有两种状态——某物已安装或未安装——只有后者会进行下载。所有在首次安装后的操作都属于第9.1节。
That 规则在某个委员会证明较宽松的规则错误后变得更严格。它过去曾用以替换较旧的
`seed-*`，理由是守护进程更新仍然是重新训练的步伐如何达到机器人的方式。现在，`policy update` 是这种方式，而旧规则变成了一个陷阱：手动将板子更新到 `v2` 后
`current -> releases/seed-v2`，这与播种者称为自己模式的模式匹配，因此下一个无关的守护进程更新会将 `v1` 回滚 —— 作为二进制更新的无声副作用，撤销了某人选择的步伐。

**策略不再与守护进程一起回滚**，这一点值得明确说明，因为过去这是免费的。当它们生活在发行版内部时，回滚发行版也会回滚策略；现在 `current` 由后安装挂钩重新指向，回滚不会运行挂钩
(`post_swap` 仅在应用路径上）。因此，因为发行版中的策略有误而回滚发行版会留下那个策略运行。两步回退，第一步是普通的方式：向前运行 `robotctl update apply daemon --version <older>` 会运行挂钩并重新播种。如果失败，被发行版替换的种子仍然在板子上 —— 播种者保留了上一个版本，就是为了这个目的 —— 并且可以手动将 `current` 指向它。

这是预期的形状而不是倒退：两个各自有自己的版本行的东西不会一起回滚。当发行版仍然是策略的唯一来源时，这才会显得尖锐，这也是为什么不要让这种状态长时间存在的另一个原因。

**如果板子在首次安装时无法连接到 Hub，它就没有步伐**，这是接受的形状而不是疏忽。`robotd` 保持其姿态并报告 *降级*，因此更新闸门通过并且不会回滚；下一个更新会获取。这与 `setup-board.sh` 为 ONNX Runtime 和 `setup-gstreamer.sh` 为插件所做的交易相同 —— 板子需要网络一次，而这是它需要网络的另一件事，而不是一个理由让每个守护进程发行版永远携带六兆字节。

播种者绝不能失败：后安装挂钩的非零退出会回滚更新，因此网络问题会撤销与它无关的发行版。每个错误路径退出零并在 stderr 上说明这一点。

**一套组件用于整个集合，而不是每个插槽一个。**更新设计草图中的`model-walk`、`model-jump`等（§5.5），以及每个插槽的组件是其自身机制最自然的产物。与此相反：这九个文件是由一次训练运行生成的一个*家族*，插槽→文件映射取决于模式（`walk`在腿上是`alpha_walking.onnx`，在轮子上是`roller.onnx`，这发生在那一节之后），并且九个组件意味着九个仓库、九个签名、九个配置块、九次检查往返，以及一个九维偏斜矩阵，在其中没有任何记录表明某个行走和站立曾一起训练过。一个组件意味着模式切换不会下载任何内容，且该集合是按构建方式版本化的。

一个缺失的策略是降级的，而不是不健康的，根据同一§5规则：一个刚刚配置的板还没有获取该集合，因此没有步态，且这必须不会导致每个后续守护进程更新的健康门失败。配置安装了启动集，其中`setup-board.sh`已经安装了ONNX运行时，`setup-gstreamer.sh`安装了插件——网络依赖项落在存在之处，且在运行时，对于没有优先级规则的策略，从发布副本到Hub副本只有一个来源。

### 9.1 超越限制

`robotctl policy check`询问Hub该集合的仓库提供了哪些版本，与板上的版本相比。`robotctl policy update`安装一个——默认安装最新版本，或使用`--version v1`回退到特定版本——并告诉`robotd`重新读取其插槽。

两者都由`updaterd`（§8）提供服务，而三个细节就是为什么这不仅仅是种子的第二个副本的原因：

**仓库来自集合，而不是来自配置。**每个安装的集合都携带一个`.source`记录，指明其来源的仓库和版本，该记录由安装它的工具写入。因此没有第二个配置仓库的地方，也没有任何漂移；由某些未来工具安装的集合会以同样的方式回答同样的问题。
**最新版本指的是仓库自身的最新版本，而不是semver排序后的版本。**策略仓库不必使用semver，将`bouncy-2`与`v10`进行比较会是一种猜测被当作事实。Hub按最古老的第一顺序列出引用，因此最新版本是其逆序，`check`会打印整个列表而不是仅打印其自身的判断结果——向**回**走与向前走一样重要。

**`robot.reloadPolicies`存在是因为路径不会改变。**安装一组策略会在每个插槽下交换`current`，因此每个插槽仍然解析为相同的字符串，`robot.loadPolicy`会正确地得出无需执行任何操作的结论。它关于路径是对的，但关于字节流是错的，这正是需要单独的方法——并且这个方法从不短路，因为“已经加载”是它存在的理由。

重新加载会替换所有网络，因此当一个网络**在移动**时，它会首先回家——这是每个引起干扰变化都遵循的规则。**静坐的机器人并不在移动**：当一个静坐于替补席上的机器人执行`policy update`时，它会先被提升到起始位置并站立起来，因为坐立网络是驱动因素，而重新加载被视作干扰。座位是一个静态姿态，基于一个恒定标志，所以交换现在发生在原地，座位也会随之转移，就像对一个非驱动网络的更改一样。

重新加载不改变任何配置，因此**你自行加载的插槽在重新加载后仍然存在**。这不仅仅是一个细节：重新加载在每次`policy update`结束时都会运行，如果安装过程默默地丢弃了某人的步态实验，那么重新加载时发现两者被混淆将是最糟糕的时机。

无法访问的Hub会被报告，而不是抛出异常。无论机器人是否行走，调用者都会知道“无法访问Hub”旁边显示的已安装内容比显示错误信息知道得更多。这与一个没有任何安装内容的板子不同：这不是一个网络故障，通过同一字段传达这种信息会使健康的Hub看起来无法访问。

安装会修剪到当前集和它所替换的集——每个集都是七兆字节，有人比较两种步态时会来回切换。前任集被保留的原因是：回滚不会运行挂钩，因此重新加载守护进程不会回滚其策略，将`current`指回保留的集是当策略出错时的恢复手段。

### 9.2 别人的策略
`robotctl policy load walk RemiFabre/microduck-flamingo-cycle` 从任何 Hub 仓库中加载一个策略到 `/var/lib/robot/policies/<org>/<name>/<revision>/` 目录，并将其放置在相应的槽位中。根据更新器设计 §5.7 外部的每个发布目录中：一个策略在更新和回滚后仍然存在。

**路径是由答案构成的**，这使得 `origin` 能够诚实而不需查找：发布策略的组织是策略所在位置的一部分，因此 `robot.policies` 报告陌生人的策略为 `community`，而报告我们自己的策略为 `official`。这是一个标签而不是边界——任何可以编辑 `robotd.toml` 的人都可以将目录命名为他们喜欢的任何内容，而任何可以做到这一点的人也可以运行他们喜欢的任何内容。阻止一个不良策略导致机器人损坏的是 §2 的沙箱。

**一个仓库携带一个 `policy.onnx`。** 这种约定在构建此功能之前已经在 Hub 上存在——每个发布的 microduck 策略旁边都有一个 `.onnx` 文件和一个 README 以及一个清单文件——因此，获取操作会选择唯一的 `.onnx` 文件，并通过命名多个 `.onnx` 文件来拒绝一个仓库。选择错误意味着在实际的机器人上运行错误的网络，这不是一个可以掷硬币决定的事情；`<repo>:<file>` 指明了具体的选择。

**并且它携带一个 `manifest.json`**，结果证明这是一种比此设计所指定的任何内容都要丰富的约定：`obs_len`，`action_len`，`model_api`，`robot.model`，加上一个名称、一种类型和一个描述。读取它使得策略可以在下载前的 800 KB 之前被拒绝，并在机器人被要求运行它之前——“其清单文件说明观测宽度为 51，而此机器人构建的是 61”——这是 `robotd` 在加载时会得出的相同结论，而此时有人可以采取行动。这也是 `model_api` 最终发挥作用的地方：根据更新器设计 §5.5 的规定，它被指定，但双方都没有使用它，而现在一个需要更新 daemon 的策略将因这一点而被拒绝，这将作为解决方案。
Three 规则阻止这种情况变成陷阱。manifest 是 **不可信赖的** — 一个陌生人的文件描述 — 因此它是一个拒绝的理由，而不是一个信任的理由；一个撒谎的 manifest 会在形状门被捕捉，而真正的检查一直都在这里。**缺席不等于证据**：一个没有 manifest 的仓库，或者一个省略了我们操作的字段的 manifest，会被接受，因为大多数的 Hub 遵循的不是我们的任何惯例，拒绝沉默会拒绝大多数的它。而它被检查的数字发表在 `duck_ipc_proto` 中，而不是重复，`duck_control` 中有一个编译时断言，确保两者一致 —— 这是一个与发布策略的人的合同，双方都能看到。

**一个插槽可以被关闭**，使用 `none` — 实际上已经使用了 `policy] <插槽> = "none"`。除了 `walk` 插槽外，其他插槽都依赖于它，因此不能为空；询问会被拒绝，一个已经声明了这一点的配置会在启动时被修复并报告为降级。这不是一个事后想法：任何尝试的第一个社区策略都会自己进行一次两脚站立，而 `will_stand` 会在命令幅度为零时将机器人交给站立网络，这正是策略站立在两条腿上的状态。没有说 `stand none` 的方式，运行它意味着编辑这个命令存在的文件，以停止编辑文件。

`robotctl policy search microduck` 列出当前有哪些策略，标记每个命中点的来源。没有标签过滤器：一个共享名称是已发布的策略共有的，而一个标签只有在有东西要标记时才值得添加。

### 9.3 集合描述自身

策略仓库的根目录下的 `manifest.json` 说明了集合包含的内容以及每个策略是什么。它 **仅存在于 Hub 上** — 这里没有副本，这是有意为之的。这里的一个副本会成为 Hub 上版本控制的东西的第二个真相来源，而对它的测试会锁定副本而不是机器人下载的东西，这比没有测试还要糟糕：它通过了测试，而一块电路板却得到了其他的东西。

两个列表以前是硬编码的，它们意味着集合中的十分之一策略是一个守护进程发布而不是一个标签：
- `scripts/seed-policies.sh` 知道要下载哪些文件。现在它从清单中读取这些文件，保留它知道的九个文件作为在清单存在之前标记的修订版本的备用方案。
- `robotd-params` 知道哪些策略是一次性的技能以及每个技能运行多长时间。现在它从清单中获取这些信息，同样以同样的方式作为备用方案。

**并且 `policy.install` 安装了清单中的设置**，遵循相同的两条规则。它最初从已经显示在板上的列表中获取下载列表，这使得第十个策略成为播种者会尊重而 `robotctl policy update` 无法安装的标签——只能通过守护程序版本安装，而这正是整个通道存在的目的。此外，新设置中没有 `manifest.json`，因此 `robotd` 落回使用编译时提供的三个技能名称，而每种技能数量的声明在命令中被默默地丢失了，该命令唯一的任务是版本之间的切换。现在，修订版本的清单就是列表，文件被写入描述其所描述策略的设置旁边；板的自身 `.onnx` 名称仍然是没有清单的修订版本的备用方案。一个不是普通名称的 `file` 被丢弃而不是下载——在脚本和守护程序中都是如此——因为它是他人的文档，而它选择自己的路径。

**逐字段的合同是 [`../policy-manifest.md`](../policy-manifest_zh.md)** —— 两个轴，每个字段，每个字段在机器人上的变化。这里没有重复这些内容，本节仅是机制存在的理由。

值得重申的一点，因为这是机制的目的：`kind` 和 `command.encoding` 是两个轴，一个分时策略只有在恒定命令下才会成为一个技能。一个 `phase` 或 `posture_flag` 条目为守护程序驱动的臂提供时间贡献——这就是为什么重新训练的地面拾取具有更长的周期是一个标签而不是守护程序版本。

**每个策略的字段与单策略仓库使用的字段相同**，加上 `file`。这就是为什么对社区发布者的要求是“添加这些字段”而不是“采用我们的格式”，这意味着一个读者可以理解这两种形状。

## 10. 技能：机器人可以被要求做的事情

一个槽位是机器人默认运行的内容。**技能**是当被要求时运行的内容——踢腿、旋踢以及其他相同形状的动作。
添加一个功能点通常会触及七个地方：`Skill` 枚举、`Net`、`PolicyPaths`、一个 `Policy` 字段及其 `has_*`、一个带有配置键和注册条目的 `Slot`、控制循环中的一个分支，以及 padd 的按钮表。因此，一个社区策略——就像ROLAND一样——没有命令，四秒后自动触发，无法在不发布守护进程的情况下添加。

因为它不需要是单一的改动。这两个分支其实是同一条臂：
- `Skill` 枚举
- `Net`
- `PolicyPaths`
- 一个 `Policy` 字段及其 `has_*`
- 一个带有配置键和注册条目的 `Slot`
- 控制循环中的一个分支
- padd 的按钮表
```rust
} else if let Some((left, _)) = self.kick {
    let net = if left { Net::KickLeft } else { Net::KickRight };
    (net, Command::default(), label)
} else if self.roulade.is_some() {
    (Net::Roulade, Command::default(), "roulade")
```
Kicks 和 roulade 在四个方面有所不同——持续时间、动作规模、收益比，以及按住按钮是否连击——除此之外别无不同。所以它们就是四个数字：
Kicks 和 roulade 在四个方面有所不同——持续时间、动作规模、收益比，以及按住按钮是否连击——除此之外别无不同。所以它们就是四个数字：
```toml
[[policy.skill]]
name = "polite-bow"
path = "/var/lib/robot/policies/fffiloni/microduck-polite-bow-b1d864/main/policy.onnx"
duration = 4.0
```
`robotctl policy add polite-bow <repo>` 从 repo 的 manifest 中获取长度。缺失则使用内置的三个，且条目按名称合并，因此一块电路板会更新到此配置，无需配置文件也无需迁移——添加一个条目不会通过省略另一个而默默移除它。“none”移除一个内置条目，与关闭一个策略槽位使用相同的词。

### 10.1 谁来结束

manifest 中的 `kind` 并不是指策略运行的长度，而是指 **谁来结束它**。

一个 *episodic* 策略会回到一个安全姿态 —— `polite-bow` 在四秒后又站了起来 —— 因此窗口可以简单地过期，步态接管一个直立的机器人。一个 *perpetual* 策略则会一直持续到被明确告知停止，如果在它上面让窗口过期，步态会得到一个一只脚着地的机器人。因此一个技能可以声明两者的结合：
```toml
command  = [1.0, 1.0, 0.0]   # the twist while it runs — flamingo reads [flag, side, 0]
unwind   = [0.0, 1.0, 0.0]   # what it drives on the way back
unwind_s = 3.0
```
That 是供应策略所缺乏的守护程序提供的结尾，也是 sit
toggle 已经具有的形态：锁定，然后是定时上升再交还，因为移除标志并不能立即让机器人站立。两者都默认为空，因此在常见情况下既不声明头部也不声明身体。——每次技能的头和身体都被初始化为零，无论处于哪个阶段 —— 到目前为止发布的每个一次性技能都声明它们未使用，而使用 `zero_command_padding` 训练的策略正好期望这一点。唯一不同的只是扭曲，而且对于大多数技能来说，扭曲也是零。

**技能的扭曲在构造上是未经平滑处理的。** EMA 会应用于客户端的命令进入过程中，但技能从不读取这个命令 —— 循环会构建一个新的命令块。这就是为什么读取标志而不是速度的策略不需要 `cmd_alpha` 作为技能，而在它蹲在行走槽位时需要将其设置为全局值。

### 10.2 守护程序中保留的内容

`walk` 和 `stand` 是默认对选对的一对，由命令幅度选择，而它们之下没有其他可以返回的内容。`sitstand` 是锁定的，并由关闭坐姿和坐起上升内部驱动，不仅由按钮驱动 —— 在清单的术语中称为 `scripted`。`ground_pick` 写入一个阶段而不是一个常量。这四个中没有一个是通用的一次性技能，一个设置入口可能不会响应 `ground_pick` 或 `sit_toggle` —— 在任何一个名称之后的第二个网络会收到一个它从未训练过的全零命令。保护不仅在名称上，也在编码上：无论以何种方式调用，`phase` 或 `posture_flag` 入口都不会被加载为技能。设置可以对这些手臂说的唯一事情是它们的时机（§9.3） —— 选择的周期和截止点，上升和坐下的稳定 —— 因为这些是训练网络的属性，而不是构建的属性。

**运行中的技能在整个持续时间内都有跌倒反射关闭**：跌倒预测器只在控制器不 `busy()` 时被咨询，而任何活跃的技能都会使其忙碌。当每个一次性技能都少于一秒钟时，这一点是无争议的。可以配置为保持十秒的技能是一个没有跌倒反射的机器人，持续十秒，这需要决定而不是继承。

### 10.3 按钮

`[pad]` 指定了哪个一次性按钮运行哪个技能：
```toml
[pad]
x = "polite-bow"
```
`robotctl pad bindings` 显示它们，`pad bind` 更改一个，`pad reset` 重置它们。默认值是原型的映射，因此没有 `[pad]` 的机器人会像以往一样行为，而 `padd` 会在一秒钟内重新读取文件 —— 没有重启。

只有这五个。`Start`，两个杆模式切换，按住 `Select` 和按住 `D-pad up` 不是 `robot.do` 调用，而使机器人关机的按钮是唯一一个不能因配置编辑而丢失的绑定。

**通过网络，`pad.bindings` 和 `pad.bind` 是 `robotd` 的，而不是 `configd` 的，后者拥有 `pad.*` 的其余部分。配对涉及无线电；一个绑定涉及按钮对机器人的作用，而回答它需要知道机器人拥有的技能列表，以便可以拒绝一个名称而不是使其成为一个死按钮。路由是按方法进行的 —— `policy.*` 发送到 `updaterd` 而 `robot.loadPolicy` 发送到 `robotd` 对于相同的概念 —— 因此这种划分在机械上没有任何成本，仅因命名空间暗示了这一点才值得命名。

一个绑定会与 `do_names` 进行检查，**而不是 `policy.skills`** ：`ground_pick` 和 `sit_toggle` 有自己的级联分支，而不是作为配置条目，因此它们不在那个列表中，但完全可以作为请求的对象。仅验证 `skills` 就排除了五个初始绑定中的两个，这在测试中被发现。

**技能表可以通过两种传输方式访问**，这也闭合了路径：获取陌生人的策略，为其命名并指定长度，通过该名称询问它，将其放在按钮上 —— 无需在机器人上使用终端。`robot.setSkill` 写入配置并在同一调用中重新加载，而 `robot.skills` 报告 `built_in` 单独，因为 `ground_pick` 和 `sit_toggle` 不是表条目，客户端仅读取表时会得出它们不存在的结论。

`padd` 仍然不知道一个技能 *是什么*。它读取哪个按钮被按下，查找其旁边的名称并发送该名称；`robotd` 决定机器人是否具有此类事物，并在没有时用它拥有的列表回答。检查应位于答案所在之处，这就是为什么 `robotctl pad bind` 向机器人询问并用实际列表拒绝拼写错误的原因。

### 10.4 从手机访问

---

注意：这里的翻译尽量保持了原文的结构和术语，但部分术语可能需要根据具体上下文进行调整以确保准确性和流畅性。
`robot.do`, `robot.policies`, `robot.loadPolicy` 和 `robot.reloadPolicies` 既通过 BLE 也通过 WebRTC 提供服务。变化之处并不在于任何安全性的改变——形状闸门、关节夹钳和跌落反射都是一样的，无论谁提出要求——而是现在存在了一个客户端，这正是所有这些拒绝等待的东西。

**一项技能并非遥操作。** `robot.do` 曾经与 `robot.move` 及其同类一起在 BLE 的传输参数下分组——一个 20 字节的通知预算和在启动后的前约 73 秒内不存在的连接。该参数涉及的是一个 *流*：每秒五十次小更新。一项技能只是一次请求，根本不需要任何控制连接，因为死人机制会自动归零扭转，而没有驱动的机器人会保持静止并鞠躬。

**BLE 是最符合观看条件的传输方式，**这正是这里大多数拒绝所开启的条件。它的无线电波可以达到大约十米，因此无论谁按了按钮，按构造来说都在机器人的同一房间内——并且通过 `encrypt_authenticated_write` 的 PIN 检查建立了连接。WebRTC 以不同的方式回答了相同的条件：对方正在观看视频，这已经是允许 `robot.init` 和 `robot.shutdown` 的论据，并且比覆盖站立更好，因为对方正在观看即将移动的事物。

值得记住的不对称性与直觉相反。**BLE 是经过认证的；WebRTC 并非如此**——`remote-webrtc.md` 的第 4 条意味着任何局域网对等方继承了已打开的内容，而 BLE 则在十米范围内由 PIN 绑定的呼叫者携带相同的呼叫。这是加强第 4 条的原因，而不是从能够展示结果的传输中剥夺呼叫的原因。

**从手机中选择的步伐是机器人启动时的步伐。** `robot.loadPolicy` 会自己写入槽键，因此第 3 条的持久性模型属于 *方法* 而不是调用它的命令。最初并非如此——`robotctl` 写入文件，而守护程序仅更改自己的内存——这意味着同样的两个词根据谁提出要求而有不同的含义，并且给了远程调用者临时的“尝试直到重启”模式，第 3 条考虑了但 **拒绝了** 这种模式。撤销的方法是相同的调用但没有路径，可以从同一部手机访问。
**`robot.policies` 携带技能列表**，而这正是使其余部分可用的关键。客户端无法提供一个不存在的鞠躬，因为现在技能的存在是配置的一部分——无需编译。这些名称已经在 `robot.subscribe` 的确认中出现过，但那是一个每秒 50 次的流，回答一个仅被询问一次的问题，而 BLE 特意不转发它。

## 12. 命名
The 更新器说 `model`；`robotd` 说 `policy`。统一使用 **policy** —— 组件是 `policies`，命名空间是 `policy.*`，命令是 `robotctl policy …`。`models/` 保留其含义，用于真正是模型而不是控制策略的事物，例如 `pet_detect.onnx` 和鸭子检测器。

## 14. 延迟，故意

- **一个社区政策的竞争版本。** 一个槽位只存储一个文件；库中存储了许多文件，但只有配置文件指明哪个是当前使用的。在 `updater-design.md` §17 中，一个真正的 `(name, version)` 存储键被估价为约 14 个文件和一个 `API_VERSION` 版本更新，而 A/B 测试案例则是通过依次加载每个文件来实现的。
- **一次性加载整个集合。** 目前仅限于每个槽位。如果在训练运行家族之间进行切换成为常规操作，而混合一个运行中的行走与另一个运行中的站立是一个没有人训练过的组合，那么这将是一个重要的考虑因素。
- **Hub 上的 `microduck` 标签。** 在有需要之前，仅通过搜索单词即可满足需求。
- **签署社区政策**，以及任何需要签署的受托管组织方案。

## 15. 开放

- **一个运行中的技能在其整个持续时间内没有下落反射**（§10.2）。对于半秒的踢击来说是合适的；一个配置为持续十秒的技能在十秒内没有下落反射。
- **`robotctl configure` 列出技能表并无法编辑它。** 一个重复的表不是带有光标位置的键，因此编辑器指向 `robotctl policy`。关于重复部分的教学是这项工作的最大部分，但它带来的收益最少。

- **官方集是否最终会成为更新组件。** 交付不再需要一个：§9 从 Hub 直接获取固定集，就像其他先决条件一样。因此，这更多是一个组件会带来什么的问题——回滚、固定、黄金、已知不良的历史记录和周期性检查——而不是关于政策的问题。组件路径安装的每个文件都无条件地由与安装守护程序二进制文件相同的代码进行签名验证。因此，以这种方式交付的官方集必须被签署，不是因为政策需要签名，而是因为该路径从未有过未签名模式，而给它一个这样的模式将会扩大漏洞，远远超出政策本身。如果每个集合的回滚最终成为任何人的需求，那么值得重新考虑；目前没有任何需求。
- 该应用是否展示任何与此相关的内容，以及它需要多少 §7 的内容。所有这些内容都可以通过 `btd` 已经转发的同一套接字访问，因此答案是一个 UI 问题，而不是一个协议问题。
- 每次加载时的七次会话重建是否在板上是可测量的坏处（§4）。这是模式切换的现状，因此在任何工作之前需要进行测量。
