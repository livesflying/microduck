# `robotd` — 控制循环

状态: 草案 · 日期: 2026-08-20 · 负责人: pierre

实现了 [`architecture.md`](architecture_zh.md) 第1节中的 `robotd` 行，并涵盖了 [`roadmap.md`](../project/roadmap_zh.md) M3。被吸收的原型是 [`apirrone/microduck_runtime`](https://github.com/apirrone/microduck_runtime)，在整个文档中称为 *运行时*。

仅 alpha 版本，仅 Radxa，仅 v2 `imu_to_dxl` 板。v1/v1.5/v1.6、其他四个 IMU、三个摄像头和 Pi 均被舍弃，所有发布的策略均为 `alpha_*`。轮式配置作为单一参数开关 — `policy.mode = "roller"` (第4.2节) — 存在，因为它选择的是一个策略集和一个调校预设，而不是硬件变体。

## 1. 形状

一个进程，一个串行总线，一个 50 Hz 循环。该循环在一个事务中读取总线上的所有十六个设备，决定十五个关节目标，并将它们写回。其他一切 — 客户端、健康、遥测 — 都依赖于该循环，从不阻塞它。

### 1.1 总线，以及谁拥有端口

十五个伺服和 `imu_to_dxl` 板共享一个 UART。没有第二个总线和第二个端口：
```text
                     robotd — control thread
                              │
                              │  duck_control::bus::DynamixelIo
                              │  serialport · TIOCEXCL
                              ▼
         /dev/ttyS2 · 1 Mbps · Dynamixel protocol v2
                              │
    ┌────────────┬────────────┴───────┬──────────────────┐
    │            │                    │                  │
  id 200       20–24                30–34             10–14
 imu_to_dxl   left leg        neck · head · mouth     right leg
  v2 board    5 servos             5 servos           5 servos
```
The IMU是`id 200`，并且与伺服电机在同一`sync_read`中读取，因为硬件就是这样做的：v2板卡位于Dynamixel总线上，并从同一寄存器块中提供芯片内的SFLP四元数，伺服电机也是从这个寄存器块中回答。一块板卡，一条代码路径，没有IMU抽象。IMU在id向量中被列在首位，因此它会在伺服电机突发数据之前作出响应。

**一次只有一个所有者；TTY独占性并不能单独强制执行这一点。**`serialport`设置`TIOCEXCL`，这将使第二个未授权的打开操作变为`EBUSY`——但`robotd.service`以root身份运行，因为电机控制需要字符设备，而root不会被那个标志所阻止。因此，守护进程和独立的`init`共享一个建议锁，其他申索者则分别被排除在端口之外：

- **控制循环**在守护进程运行期间一直拥有它。
- **`robotd init`**自己打开端口，但必须首先获取守护进程的端点锁。它在整个启动过程中都持有该锁：运行中的守护进程拒绝`init`，而正在移动机器人的`init`也拒绝守护进程启动或另一个`init`。`robot.init`和`robot.relax`仍然是运行中的守护进程的IPC方法（§3.3），而独立的`init`则是机器人的守护进程未运行时的逃生出口。
- **`serial-getty@ttyS2`** — Armbian默认在UART2上运行登录控制台，并且一个持有端口的`agetty`使所有伺服电机对其他一切不可见。`scripts/setup-board.sh`遮蔽了该单元；`fuser -v /dev/ttyS2`指出`agetty`是通过这种方式找到的，而它仍然是回答“谁拥有总线”的命令。
- **运行时**，以更粗粒度的方式：它驱动相同的总线，因此一块板卡要么运行运行时，要么运行`robotd`，但不会两者都运行，而单位通过`Conflicts=`（§5.2）说明了这一点。

**套接字所有权。**两个入口点在发布`/run/robotd/identity.json`或打开总线之前都会获取`<socket>.lock`（通常为`/run/robotd.sock.lock`）。守护进程也在启动控制线程之前绑定其监听器，并在整个控制线程关闭和套接字清理过程中保持锁。被拒绝的重复项不得覆盖所有者的PID和构建：`robotctl health`和更新器启动检查会读取该身份信息。对于没有锁的老守护进程遗留的监听器，守护进程的绑定路径仅移除实际拒绝绑定连接探测的套接字；活的监听器和模糊路径将被保留。独立的`init`仅锁定套接字，但从不绑定或清理套接字。
**Never unlink the lock file, 即使在关机时也不可删除。**内核会在文件关闭或进程退出（包括 `SIGKILL`）时释放建议性锁定；文件本身会保持原位。删除并重新创建它可能会导致竞争者在同一个名称下锁定两个不同的inode。文件存在并不意味着锁被持有。锁是针对 `--socket` 的，因此使用相同物理总线的调用者必须使用相同的socket设置；不同的端点对于独立的假想守护进程仍然有用。较旧的二进制文件和其他工具不参与此锁，因此在独立的 `init` 接管总线之前仍需停止它们。

   └──────────┘                                │                     │
                                               │                     │
   ┌──────────┐   robot.health                 │                     │

   │          │  robot.modelApi                └──────────┬──────────┘

        │                                                 │

        └─────────────────────────────────────────────────┘

   ┌ the two transports ────────────────────────┐
   │  mediad — WebRTC + JSON-RPC relay          │  phone, browser and LLM

Every one of those 用相同的两种词汇进行交流 — 输入意图，输出状态 — 所以 `mediad` **转发** 帧而不是翻译它们（§3.1, §3.2）。`updaterd` 只会提问：更新路径中没有任何内容可以命令电机。

### 1.3 箱子边界
```text
duck-ipc-proto/  wire contract — serde only; no tokio, no http, no crypto
duck-control/    robot model · bus · IMU · RobotIo · obs · policy · safety
                 everything between reading the bus and writing it
                 no tokio, no sockets, no systemd
robotd/          the process: socket, JSON-RPC, systemd, health reporting
robotd-params/   the startup parameters: schema, defaults, validation (§4.2)
kinematics/      the MJCF model, forward kinematics, head and hand chains
odometry/        where the robot is, from foot contacts and the IMU
sounds/          the voice: synthesis, per-robot personality, the chorale's score
pet-detect/      the camera-side detector robotd polls, off the loop
robotctl/        CLI
padd/            gamepad → intents
updater/         engine + updaterd
```
Everything below `robotd/` 在该列表中是它驱动的 **库**，而不是服务：没有自己的 tokio 运行时，没有 socket，也没有 systemd 启动。它们是出于相同的原因独立的 crate —— 编译器保持了守护进程相关问题的隔离，特别是 `kinematics` 有两个消费者 (`odometry` 和 `robotd` 的头 FK)，否则每个消费者都会各自复制一份模型。

`duck-control` 包含从读取总线到写入总线之间的所有内容；`robotd` 是其周围的过程。编译器强制执行这个边界，这就是为什么守护进程相关问题不会泄露到控制代码中 —— 这也意味着在运行时需要在过渡期间消费它时，可以将 crate 提升到自己的仓库中，而不需要进行重写。

`safety` 包含 `RobotIo`，因此策略、控制器和每个客户端都可以 *提出* 目标，但没有任何一方可以发送。这是借用检查器，而不是一种约定（§2.4）。

### 1.4 跳跃点

50 Hz，一个 `tokio` 任务在其自己的运行时中，因此 IPC 工作不能在其前面阻塞。每跳两次总线事务，再加上每秒一次：

```
```text
read()          one sync_read  · IMU board + 15 servos · registers 124–136   (§2.1)
decide          observation → policy → targets → clamp                 (§2.2–§2.4)
write()         one sync_write · goal positions
publish         atomics always; a state frame only if someone subscribed     (§4.1)

every 1 s       slow_sensors() · registers 144–146 · voltage + temperature   (§2.1)

数据在每个周期去向何处：
```text
  Dynamixel bus
       │  one sync_read: IMU board + 15 servos, one transaction
       ▼
   Sensors ──────────┬──────────────────────► safety.observe ──► fallen? (debounced)
   joints, IMU       │
                     ▼
              Observation::build  ◄──── Command ◄── gate(deadman) ◄── intent snapshot
                     │              (twist, head, body = nominal)
                     │  [f32; 61]
                     ▼
              Policy::infer ──── roulade > kick > ground pick > sit/rise >
                     │           stand (by |twist|, or forced) > walk
                     │  [f32; 14]   — mouth excluded
                     ▼
              home pose + scale × action ──► low-pass on head and legs
                     │
                     │  [f64; 15] proposed targets
                     ▼
        ╔═════════════════════════════════════════════╗
        ║  safety.apply   ← owns the only RobotIo      ║
        ║  · refuse non-finite                         ║
        ║  · clamp to actuator range                   ║
        ║  · no fall gate — the verdict only reports   ║
        ╚═════════════════════════════════════════════╝
                     │  sync_write goal positions
                     ▼
              Dynamixel bus
```
And 关于这些决策，数据流上面并未显示：
```text
  startup
    ├─ open the bus, waiting              an unpowered board is fixed with a switch,
    │                                     not by abandoning the loop
    ├─ Safety::new(io)                    safety takes the RobotIo; nothing else can write
    ├─ read() → hold = the pose the robot is already in    ── never move on start
    └─ policy
         disabled ─────────────► controller = None                    healthy
         loaded   ─────────────► controller = Some
         failed   ─────────────► controller = None + policy_error   unhealthy

  each tick
    read ─┬─ ok  ─► clear the consecutive-error count
          └─ err ─► count++, sensors = None   (the tick still runs)

    observe → fallen?     published; gates nothing

    driving = enabled ∧ policy loaded ∧ sensors this tick ∧ ¬limp-fall

    edges ─┬─ started driving ──► controller.reset()
           │                      else a stale last action, or a filter anchored to
           │                      where the robot was a minute ago, shows up as a lurch
           └─ stopped driving ──► hold = current pose, captured once
                                  re-reading each tick would sag under gravity

    driving ─┬─ limp-fall ─► the sequence's own targets and gain    (§2.4.1)
             ├─ yes ──────► step() → targets, gain, the active net's name
             └─ no  ──────► targets = hold, default gain, "held"

    safety.apply(targets, hold, gain)

    publish ─┬─ atomics            always      → robot.health, safeToRestart
             └─ state frame        only if subscribed   → robot.state
```
要求 `driving` 的四个条件各自承载重量。`sensors this tick` 是不那么显而易见的一个条件：一次读取失败会留下 nothing 可以用来构建观察，而凭空捏造一个则会向策略提供一个不存在的机器人。`¬limp-fall` 是那个不是拒绝的条件——虽然在 `limp-fall` 序列中机器人被拥有（§2.4.1），但策略故意不进行驱动，目标则来自该序列。

循环保持为一个 `tokio` 任务，带有 `interval`。它没有被设置为实时（§5.4）。从运行时的一个变化值得命名：**`MissedTickBehavior::Skip`**。`Burst` 会连续地触发回执并将电机命令堆叠在一起。`Delay` 的错误则不那么明显——它在每次唤醒后将下一个 tick 的调度时间设置为 *现在 + 周期*，因此每次唤醒的延迟都会被添加到周期中而不是被吸收，导致循环的进度比其配置的速率更慢。`Skip` 保持原始的调度并丢弃未完成的 tick，这是控制循环所希望的。将感知移出到 `mediad` 去除了大部分与循环竞争资源的部分。

### 1.5 不变性

围绕着其他一切安排的五个属性。每个属性都在某个地方得到了保证，而不仅仅是意图：

1. **`safety` 以上的一切都不能写入电机。** 它拥有唯一的 `RobotIo`；借用检查是执行手段（§2.4）。
2. **`robotd` 从不因为一个进程启动而移动机器人。** 更新重启会留下一个站立的机器人（§3.3）。
3. **控制循环从不等待客户端。** 意图是原子加载，遥测数据是丢包时丢弃（§4.1）。
4. **健康状态是发布的，从不被请求。** 卡住的循环会报告自身为不健康而不是挂起调用者（§3.4）。
5. **只有可以归咎于发布的内容才能到达健康判决。** 电池和温度是描述，从不作为回滚输入（§3.4）。

## 2. 控制路径

### 2.1 总线层和 `RobotIo`

一层薄薄的 `rustypot` 层：打开，一个综合的 `sync_read` 和 `sync_write` 目标位置，扭矩启用，增益，缓慢的传感器读取，以及启动寄存器检查。它是新鲜编写的而不是从运行时提取的，但 **数字是从运行时借用的**，每个数字旁边都有一个注释说明这一点：
- `RAD_PER_SEC_PER_COUNT = 0.229 × 2π/60`, 和位置计数↔弧度转换。
- 从 `check_and_fix_config` 断言并在启动时纠正的 EEPROM 寄存器：
  `return_delay_time=0`, `baud_rate=3`, `pwm_slope=255`, `shutdown=52`。第一个是
  承载项 — 在 XL330 默认的 250 下，每次设备的来回时间为 500 µs，所以十六个设备的成本约为每拍 8 ms，占预算的 40%。一个工厂重置或替换的伺服到达时速率为 250，因此检查是为了消除一类“为什么这个机器人运行得慢”的原因。`shutdown = 52` 是在过载、过热和输入电压故障时锁定的错误掩码。
- **替换的伺服被采用，而不是手动配置。** 新的 XL330 在 57 600 波特率下作为 ID 1 回应，且两者均未在该总线上使用。因此，在寄存器检查之前，`open_bus` 会向十五个预期的 ID 发送 ping；如果 *恰好有一个* 沉默，它会寻找 ID 1 — 首先在 1 Mbps 下，然后通过重新打开端口在 57 600 波特率下 — 写入缺失的 ID 和总线的波特率，重新打开在 1 Mbps 下，对它运行相同的寄存器检查，然后重启它。重启会清除闪存留下的硬件错误警报，否则会一直阻止扭矩，直到有人拔掉电池。一个完整的总线为此花费十五次 ping，除此之外没有任何其他开销 — 57 600 探测器除非有伺服缺失，否则从不运行。两个缺失的伺服被忽略：无法确定哪个伺服被新伺服替换，日志也如此记录。
- 位置 P 增益以 **零** 写入 I 和 D，即运行时的 `--ki`/`--kd` 默认值。这些是 RAM 寄存器，因此断电恢复后伺服恢复出厂设置值，且出厂 D 不为零：留置在此会阻尼伺服的内部 PID，机器人在 *相同的* kP 下运行得更柔和。这不是任何人做出的调谐选择，因此被固定而不是暴露。

**每拍两次总线事务，每秒三次。** 每拍读取 124–136 连续块（pwm、电流、速度、位置）。电压和温度位于 144–146，其末端之后的八个字节，中间有八个不希望的轨迹寄存器 — 因此它们每秒在一个事务中（约 1 ms）一起采样，而不是将每伺服的读取时间扩大到 50 Hz 下的 22 字节。采样间隔是测量实际速率的同一窗口，因此一个时钟驱动两者。
电压在舵机上进行平均：所有十五个舵机都连接在一个电池包上，因此单次读取就是一个测量值但噪声更多，且那些返回零值的设备会被过滤掉而不是像电池包半空时那样进行平均。温度**不**进行平均——调用者会得到每个关节的温度，并报告最热的那个**名称**，因为膝盖在蹲姿时的温度远高于嘴巴，而十五个舵机的平均温度会掩盖即将过热关机的那个。

静默的舵机不会产生简短的回答：`rustypot` 的 `sync_read` 会等待每个ID的响应，如果有一个不回复则整个交易失败。因此，两次读取都是要么全部成功要么全部失败，调用者会保留之前的样本而不是将一次缺失视为新信息。

**电路板温度是一个独立的来源，并不在总线上。** 从 `sysfs` 读取 SoC 的最热的热区，在每秒一次的样本中读取（`robotd/src/soc.rs`）。它位于 `robotd` 而不是 `duck-control`，因为它是 Linux 电路板的属性，而不是机器人的属性——这也是为什么即使电机总线不响应它也会继续回答的原因，而这也是它存在的原因：电路板在通风口堵塞时和机器人舵机失效时的症状相同，直到你能看到两个数字。它显示的是各热区中的最高温度而不是某个特定热区的温度，因此即使传感器连接方式不同，也不会默默地省略那个正在上升的温度。

**IMU 的过时状态会永久跟踪。**“读取成功但电路板返回了相同的样本”会向策略提供无效的方向信息，除非有人统计它，否则是看不见的，并且已知会发生这种情况。总线层会记住最后的一块数据，统计连续相同的后续块，并在一次运行足够长以有意义时在日志中说明——半秒，与 SFLP 解码器等待芯片输出成为测量值的时间相同。首次重复块的警告会教会所有人忽略这条消息；超过阈值后会进行速率限制，因为停止刷新的电路板每跳一次脉冲会产生一个相同的警告，50 Hz 的相同警告会清空日志。

分界线：
```rust
trait RobotIo {
    fn read(&mut self) -> Result<Sensors>;                 // joints + IMU, one transaction
    fn write(&mut self, targets: &JointTargets) -> Result<()>;
    fn set_gain(&mut self, kp: u16) -> Result<()>;         // one write per joint, not per tick
    fn set_torque(&mut self, on: bool) -> Result<()>;      // idem
    fn slow_sensors(&mut self) -> Result<SlowSensors>;     // voltage + per-joint temperature
    fn imu_stale(&self) -> ImuStale;                       // defaulted
    fn imu_ready(&self) -> bool;                           // defaulted
}
```
`set_gain` 和 `set_torque` 是每个关节的一个事务，因此它们都不是每次节拍的调用，这也是启动过程是一个状态机而不是循环一直应用标志的原因（§3.3）。两个内置方法因为只有 `init` 使用它们而位于特质之外：`present_positions`（一个较轻的读取操作，在启动时仅使用一次，以采用机器人当前所处的姿态）和 `interpolate_to`（一个阻塞的线性斜坡——故意阻塞，因为在此运行时不应有其他内容与总线通信）。

有两种实现：`DynamixelIo` 和 `FakeIo`（脚本化的样本，可选地冻结或按需失败）。`FakeIo` 是测试套件运行的对象，这也是为什么 `cargo test` 不需要硬件、网络和 Docker。

**macOS 上也没有 `cfg` 门控。** 该门控原本是为了防止 `serialport` 进入笔记本电脑的依赖树，但 `rustypot` 和 `serialport` 都可以在 macOS 上干净地构建，因此它什么也没买到，却失去了在没有板卡的情况下检查总线层的能力——这正是最有可能被没有板卡的人编辑的代码。只有打开实际端口的入口点被门控，因此 macOS 构建仍然拒绝假装有机器人：`robotd --fake` 是笔记本电脑的路径，且必须显式请求，而不是默认使用。

### 2.2 一个观察构建器

每个 alpha 策略都是 `obs[1,61] → actions[1,14]`——在行走、站立、地面拾取、球踢和坐下过程中均得到验证。因此，恰好只有一个布局：
```
[ gyro(3) | projected_gravity(3) | joint_pos(14) | joint_vel(14) | last_action(14) | command(13) ]
                                                                    command = vel(3) + head(4) + body(6)
```
Joints outhexclude 咀嚼 throughout; actions 映射 back into 15 动作槽位，索引 9 保持为零。51/54D legacy, 49D 轮式和 85D 跟踪布局在变体中消失。

命令块，唯一存有疑问的部分，现已确定 —— 从原型的 `control_step` 中读取，而非猜测：
```text
48..51   vx, vy, vyaw
51..55   neck_pitch, head_pitch, head_yaw, head_roll
55..57   body x, y      — hardcoded zero, unbound in training
57..60   body z, roll, pitch
60       body yaw       — hardcoded zero, unbound in training
```
三个关于它的说法单独来看都是合理的但错误的：

1. **全零体态是名义编码**，而不是占位符——x、y 和 yaw 实际上是硬编码为“未绑定”的零值，除非处于体态模式，否则 z/roll/pitch 为零。
2. **头部目标在命令中传输，并未叠加在策略输出之上**。原型在不同模式下两者都做，并且在 `if !new_cmd_obs` 后面通过注释“头部偏移量是通过 obs 向量馈入的命令——不要在此重复添加”来闸控后置叠加。两者同时做会导致头部被弯曲两次。
3. **体态块的顺序是 `z, roll, pitch`** — 而不是 `z, pitch, roll`。将最后两个参数互换会导致机器人在被要求前倾时侧倾。

### 2.3 策略

设计得像运行时的那样，故意如此。`robotd/src/control.rs` 包含优先级链和从 `control_step` 替换过来的所有数值默认值：
```text
skill windows ← advance / expire (roulade window, kick timer, ground-pick phase, sit↔stand rise)
command       ← the caller's smoothed command, re-encoded for the active skill
net           ← roulade > kick > ground pick > sit/rise > stand-by-magnitude (or forced) > walk
action        ← ONNX
targets       ← home pose + action_scale × action
filters       ← first-order low-pass on head and legs
```
Two 模型的细微之处值得命名，因为它们很容易通过“修复”来掩盖。
- 在站立调谐时运行一个踢窗**——踢的动作携带一个全零命令**，而站立过渡正好在这一点上触发，因此踢会在 `standing_action_scale` 和软化的站立增益下运行。保留，因为踢的动作是针对这一点进行调谐的。**坐下站立的上升也运行在站立增益下**（其命令为全零），而坐下则不运行（其姿态标志使扭曲幅度为1）。同样的机制，同样的原因。一个故意的分歧在于，原型通过在过渡中保存和恢复 `action_scale` 来跟踪站立动作比例，这可能会在坐→站循环后留下一个过时的值，直到下一次行走；在这里，每一步都会从活跃状态重新计算比例和增益。

策略文件来自参数文件中的路径，默认情况下会进入发布目录——因此，正常的更新会携带针对二进制文件训练的策略，而开发人员会指向自己的 `.onnx` 并迭代而无需发布。

哪个文件填充一个槽位——是发布的副本，来自 Hub 的组件，还是开发人员放置在板上的东西——由 [`policy-channel-design.md`](policy-channel-design_zh.md) 说明，以及改变它的命令和加载失败时会发生什么。这一部分说明了策略是什么以及如何验证和运行它，但仅限于此。

所有内容都在**加载**时验证，而不是在推理时验证：观察宽度、动作数量以及是否安装了 ONNX 运行时。每个网络都必须是61输入、14输出，在加载时而不是在中途发现时进行验证。运行时还提供了一个51维的家庭，使用的是遗留的3值命令；这些只在 `--new-cmd-obs=false` 路径下加载，并且 `robotd` 会用 `观察宽度为51，预期为61` 拒绝它们。在循环开始前运行一个预热推理，这既可以在热路径上提前支付第一次调用的成本——在那里它看起来与错过时间片的效果相同——又可以证明 dylib 已正确解析。
**`ort`在缺少ONNX Runtime时会panic。**它在`setup_api`内部`expect`，位于任何API调用的懒加载路径上，因此无法将其捕获为错误。若任其自然，会杀死控制线程：从未收到心跳，并报告“循环尚未完成一个周期”，因此守护进程看起来像是卡住了而不是指出原因——比这种设计所拒绝的崩溃循环更糟糕。因此，`policy::ensure_runtime`在触及`ort`之前会探测使用相同加载器和搜索规则的dylib，这样缺少的库就会变成一个普通的错误。

**`policy.enabled`将“无策略需求”与“策略失效”区分开来。**前者是健康的，是基准更新器测试的正确配置；后者是不健康的，因此更新器会回滚发布。将它们合并在一起要么会使一个基准机器人看起来不正常，要么让一个不可用的捆绑包通过检查。`robotd --no-policy`设置了它，门测试也使用它，因为既没有CI也没有笔记本安装了ONNX Runtime。

ONNX Runtime是一个**板载先决条件**，由`scripts/install.sh`安装，不在发布的捆绑包中。它比守护进程变化得少，每个制品中包含20 MB会毫无意义地增加每次更新的大小。因此，一个缺少它的板子可以安装并启动，但无法行走——这就是为什么健康报告搜索路径的原因。

尚未完成，且故意如此：预绑定ONNX的输入/输出张量。当前路径在每次推理时分配一个包含61个浮点数的向量，大约在50 Hz时为244字节。在板子上测量之前优化之前值得测量。

**因为有效而从运行时继承而来**——头部和腿部的低通滤波器，动作缩放，电压自适应缩放，站立过渡增益变化。这些都是可调参数（§4.2），不是需要重新考虑的决策。特别是低通滤波器的alpha值是alpha策略训练时使用的值，因此必须匹配训练以避免性能下降。规则是不要退化已经运行的代码。

### 2.4 安全性

`safety`拥有唯一的`RobotIo`写入句柄。没有策略和客户端拥有它，因此没有任何东西可以在上面命令电机——这个不变量是结构性的而不是记忆性的。与更新器关于其恢复路径的论点相同：只在已经出错的情况下运行的代码最有可能是静默失效的代码，因此应使失效状态不可表示。

两条无条件的规则：
- **非有限拒绝。**一个 `NaN` 目标不会被限制，而是直接拒绝。
- **范围限制。**每个节拍中，目标都会被限制在执行器的行程范围内，无论策略要求如何。这是 *执行器* 的范围，而不是每个关节的解剖学限制——它会捕捉 `NaN`、荒谬的动作尺度和垃圾张量；它不会阻止关节被驱动到机械上不明智的位置（§9.3）。

命令中还设有一个死锁机制：如果意图停止到达，速度会归零。**停止** 不是惰性状态，这一点很重要——通信中断会让机器人 *原地不动*，因为站立是双足机器人安全的状态；失去平衡是不同的事件，这一层不会处理它。

**跌倒判决是一个报告，而不是规则。**它每节拍都会被计算——基于躯干坐标系中的投影重力，经过 0.2 秒的去抖动处理，以确保稳定的足部着地不会被误判为跌倒——然后发布，但它 **不控制任何事情**：一个跌倒的机器人会被启用、初始化、驱动，并发送技能，就像一个直立的机器人一样。这是有意为之。机器人在地板上时正是需要这些调用发挥作用的时候，一个在重力误判倾斜时就放弃的机器人会在有人处理它时一直保持坐着。这也使得跌倒的答案可以在这个层面上存在，没有任何特殊情况的豁免：早期版本有一个 `fall_limp` 门和一个 `fall_recover` 自动站立机制，但它们都被移除了，因为一个必须绕过安全规则才能工作的恢复机制不是一个安全规则。

#### 2.4.1 跌倒是一个第三类事件

上述跌倒判决回答了“机器人是否倒下”的问题。对于报告机器人侧躺的情况，这是正确的；但对于软着陆，这个问题是错误的：重力超过 `fall_gravity_z` 持续 200 毫秒 *确实* 表明机器人在地板上，而此时已经错过了采取行动的窗口。

因此，`limp_fall`（默认关闭：默认的步行姿态加载不回传站立网络）会运行一个独立的第二检测器——`duck_control::fall`——基于速率而不是位置。投影重力会随着躯干旋转，因此 `ġ = −ω × g` 是精确的，并直接来自同一 12 字节的 IMU 模块中的陀螺仪；在约 0.3 秒内外推它会指出重力将要指向的位置。当机器人已经倾斜（≈26°），还在继续倾斜而不是恢复，并且预测将超过跌倒阈值时，它会触发——经过三次节拍的去抖动处理。相反，对 SFLP 四元数进行微分会增加滤波器的滞后，而整个数值的早期判断只有一个数值。
要求的并非是着陆本身，而是着陆后的站立。站立策略能够将一个静止的机器人以已知姿势干净利落地立起，而一个挣扎的机器人则需要经过多次尝试重新获得行走能力后才能立起，这也是电机负载的来源。因此，该序列将跌倒从策略中移除：在`gain_limp`下摇晃关节，等待陀螺仪静止，然后在约1秒内逐步恢复到站立姿势，最后交由系统处理。交由处理的过程就是——整个旋转过程中扭力保持为零，因此命令幅度选择站立网络，这就是站立的过程。

该过程是通过策略路径构建的：在整个序列中`driving`始终为假（§1.4），因此目标来自序列而非控制器，它们通过`apply`传递给电机——没有豁免，没有后门。`safety`中的任何内容都不需要特别说明，因为裁决不会影响任何内容：姿态斜坡移动一个躺在地上的机器人就像其他任何一格一样。

调优是关键，而且是不对称的：一个假阳性意味着机器人自己导致了一次跌倒，这比它试图避免的僵硬着陆更糟糕。默认值故意偏向较晚的设置。

另一个无需请求就能移动机器人的因素是电量耗尽：通过`safety.battery_empty_shutdown`（默认启用），当平滑后的电压达到空闲地板时，机器人会坐下并关闭电路板。EMA在约10秒内移动，因此负载下降不会触发它——达到6.6V需要一个真正空闲的电池包。

### 2.5 机器人模型

仅对alpha使用Rust常量：15个关节，Dynamixel ID `20–24 / 30–34 / 10–14`，名称，`DEFAULT_POSITION`，以及执行器范围。这些表格与运行时的`motor.rs`相同，只是缺少三个死变体。只有一个机器人；第二个修订版可以是一个新的表格。

其中两个表格超出了它们所在模块的范围。`JOINT_NAMES`来自`duck-ipc-proto`，因为线上的`joints`和`targets`按位置索引，两个顺序不能允许漂移——一个`const`断言使“不允许”变为现实。而`DEFAULT_POSITION`必须与训练环境中的`HOME_FRAME`匹配：策略观察关节位置相对于起始姿势的差异，因此这里的一致性差异会在14个观察槽中产生一个恒定的偏移。

## 3. API

### 3.1 输入意图

有两种词汇——输入意图，输出状态——以及JSON-RPC的两种消息家族完全对应它们。
```jsonc
// continuous: notifications, no id, no reply, last-writer-wins
{"jsonrpc":"2.0","method":"robot.move","params":{"vx":0.2,"vy":0.0,"vyaw":0.4}}
{"jsonrpc":"2.0","method":"robot.head","params":{"neck_pitch":0.35,"head_pitch":0.35,
                                                 "head_yaw":0.0,"head_roll":0.0}}

// discrete: requests, answered
{"jsonrpc":"2.0","id":7,"method":"robot.stop"}
{"jsonrpc":"2.0","id":8,"method":"robot.enable","params":{"on":true}}
```
Everything 是弧度，树干坐标系，右手系，符号固定在协议定义中。运行时携带 `--laser-track-yaw-sign`，`--laser-track-pitch-sign`，`--laser-fk-pitch-sign`，`--laser-fk-neck-sign` 和 `--imu-z-rotation-deg`，因为这种约定从未写下来，每个消费者都是通过经验重新发现的。将其写入协议会删除这一类别。

以 50 Hz 的频率，连续意图作为通知意味着没有响应流量。当它们后来通过 WebRTC 传输时，通知路由到不可靠的 `teleop` 通道，请求则路由到可靠的 `control` 通道——这正是 `architecture.md` §5.2 所要求的，属于消息家族而非需要记住的规则。

**Twist 和 head 是故意分开的槽位。** 如果有一个结合的槽位，更新一个字段需要读-修改-写操作，并且两个客户端——一个游戏手柄控制身体，另一个控制头部——会默默地丢失对方的更新。分开的槽位实际上每个都是单写者，因此最后写者获胜意味着其所说的内容。每个槽位都有时间戳，因为循环的实际问题是“当前的值是什么”而不是“它有多旧”；这就是死锁读取的内容。

`look`（注视方向）是延迟的；两种注视形式都将被暴露，并且它们之间的仲裁是最后写者获胜，没有混合。

### 3.2 状态输出

一个流，可订阅，每个订阅者一个采样。它必须报告被 **拒绝** 的内容，而不仅仅是发生了什么——一个显示摇杆向前但机器人仍然不动的遥控界面，没有任何解释，是不可用的，而且安全机制会不断限制：

```
```jsonc
{"method":"robot.state","params":{
  "t":1234.567,
  "move":{"requested":[0.4,0,0],"applied":[0.15,0,0],"limited_by":["max_velocity"]},
  "policy":"walk", "safety":{"fallen":false,"limp":false},
  "loop":{"hz":49.8,"missed":0},
  "battery":{"volts":7.62,"percent":64}
}}
```
**电池既携带伏特也携带百分比**，这里以及在 `robot.health` 中是如此。这种映射——空载时6.6伏，满载时8.2伏，适用于NP-F550——存在于 `duck_control::model::battery_percent` 中，并且已经应用。原型仅发送了伏特，而应用程序则从自身的常量中重新推导出百分比，这就是为什么同一个电池包在两个屏幕上显示不同数字的原因。绘制电池图标的应用程序不应知道这个机器人搭载的是哪个电池包。没有燃油表：测量的是舵机自身的供电电压（§2.1），因此在负载下会下降，在空闲时恢复。

`robotctl monitor` 和稍后应用程序中的负载相同。这将取代9870上的180字节的运行时帧、9871上的JPEG流、9872上的UDP命令套接字、9874/9875上的maploc端口以及web hub的`/state.json`。今天添加一个字段意味着要编辑四个地方，这些地方可能会默默地不一致；在这里，这意味着一个结构体，而较旧的客户端会忽略它们不认识的内容。

`robot.subscribe` 将一个连接转换为一个流；循环会发布到一个有界广播中，并且永远不会等待订阅者，因此一个慢速客户端会得到一个间隙而不是反压——这是更新者已经用于进度的规则。降采样是服务器端的，并且针对每个订阅者，因此一个10赫兹的仪表盘实际上比一个50赫兹的数字孪生体对机器人造成的负担更小。

**确认消息命名了策略**。`robot.subscribe` 回复 `SubscribeResult`：此进程配置的网络，以文件名为基础，以及当没有驱动时的一句话——在参数中禁用，或者想要但无法加载。这应该在握手过程中而不是帧中，因为它在进程存活期间不会改变，而帧上的 `policy` 回答的是不同的问题：这次心跳由哪个网络驱动。两个具有不同步态的发布版本都会报告 `walk`，而“这是哪个网络？”是任何人比较它们时首先会问的问题。将它放在帧上会为控制线程上的每次心跳分配两个字符串，而答案从未不同。

两个容易出错的细节。**没有人订阅时没有组装**——这是机器人正常状态——因为构建一个帧会在没有理由访问分配器的线程上分配内存。并且，限制名称是**明确写在通信协议中**，而不是从Rust枚举派生，因此重命名一个变体不会默默地破坏分支在 `limited_by` 上的客户端。

### 3.3 启动：`enable`，`init`，`relax`
**`robotd`**从不自行移动机器人。启动时，它会读取当前位置并将其设为目标，而不改变扭矩。在进程停止期间，Dynamixels 会保持其最后一个命令的目标位置，因此重启后姿态不变，没有间隙——机器人在更新过程中不会察觉。在启动时插值到默认姿态会使每次更新重启时移动站立的机器人：这会增加跌倒的风险，并在测试对象是更新器时造成干扰。

`robot.enable` 以前只是切换一个标志，除此之外不做其他事情。扭矩来自 `robotd init`，这是一个单独的子命令，用于打开电机总线——因此它需要停止守护进程，且未出现在任何文档中，在新启动的机器人上按下“开始”按钮没有任何可见效果：策略运行，循环写入位置，而伺服却忽略了这些位置。因此循环有一个初始化状态，显式的 `robot.enable` 是使其前进的关键：

```
Limp ──enable (policy loaded, a fresh sample)──▶ Homing (torque on, 2 s ramp) ──▶ Ready ──▶ policy drives
```
**旧规则保护的不变量依然存在：这里发生的一切都不是因为某个进程启动的。**一个由更新重启的`robotd`会找到`Limp`，请求不施加扭矩，并让站立的机器人保持站立状态——`a_restart_asks_for_no_torque`正是在没有任何写操作的情况下断言这一点。变化在于，“永不触碰扭矩”这条规则比它所保护的属性要宽泛，而且它在每次启动驱动前都设定了一个手动步骤。

启动的两个条件各自出于不同的原因：

- **加载的策略。**`enable`意味着“启用策略”；如果启动一个被禁用或无法加载的策略，机器人可能会在故障版本上站立并保持不动。
- **新鲜的样本。**斜坡从关节当前的位置开始。从无人读取的位置开始是斜坡存在的目的，以避免突然的移动。

**机器人处于停机状态并不是其中之一。**早期的一个版本在那时拒绝了这一点，当时`apply`保持机器人处于下垂状态，斜坡会尝试写入一个站立状态，但这个状态无法实现；当判决不再控制任何事情时（§2.4），从地面站立起来正好是要求机器人站立的方式——斜坡像其他情况一样运行，站立策略从那里接管。

当策略再次被禁用时，扭矩不会被释放：机器人保持其姿态，这也是“站立的机器人保持站立”在这边的意义。

`robot.init`和`robot.relax`是相同的两个转换，直接请求——因为“站立”和“放手”是它们自己的决定，直到现在，“站立”是一个子命令，它会打开电机总线本身（§1.1），而“放手”根本不存在。两者都由`robotd`提供服务，因此都不需要停止守护进程，而且在控制循环执行相同操作时，两者都不能写入总线。`init`明确不需要策略：对于没有行走网络的机器人，要求站立是合理的，这也是使启动测试成为可能的原因，因为CI没有ONNX Runtime。

它们作为请求到达，循环每跳一次处理一次，而不是保持一个标志：一次`set_torque`是一个关节一次总线事务，因此一个级别会在每次跳动中放入十六次写入。后来的请求会替换先前未读取的请求——要求站立并在20毫秒内放手，第二次请求才是正确的。而`relax`会清除`enabled`，否则在下一次跳动中会看到一个被要求驱动的机器人被直接立起来。

Neither是通过BLE不可达的。一个可以让机器人掉到地板上的手机按钮不值得提供，而站立动作会一次性移动所有关节，这需要请求者在机器人旁边观察。

### 3.4 健康状况，以及可能影响裁决的因素

| 方法 | 回答 |
|---|---|
| `robot.health` | **循环正在满足其截止时间** — 从实现率和未满足截止时间的计数中得出 — 以及循环裁决从不咨询的描述：循环、总线、IMU、电池、伺服和板温 |
| `robot.safeToRestart` | 在策略启用且机器人移动时为 `false` |
| `robot.modelApi` | 常量 |
| `robot.remoteSessionActive` | `false` — `mediad` 拥有真实的答案 |

健康状况由IPC侧从循环发布的原子数据计算得出 — 包括最后的时钟戳和计数器 — 而不是询问循环。这使得一个 *卡住* 的循环能够报告自身为不健康，而不是挂起调用者。

运行速度为目标速度60%的循环是活着的，回答每个请求，并且严重损坏。做出这种区别的现实性正是为什么在任何行走之前构建了控制循环（§5.1）。

**可能和不可能影响裁决的因素。** `healthy` 和 `degraded` 是更新系统的输入，因此只有更新系统可以归咎于的条件才能设置它们 — 这正是 `degraded` 存在的原因，以确保未供电的测试板不会被归咎。答案中的其他一切都是 **描述**，没有任何自动决策可以读取它们：电池、电机温度以及循环/总线/IMU 计数器。基于电池的决策意味着一个在电量低的电池上更新的机器人会回滚更新，然后在相同的电量低的电池上评估其替代品，直到有人找出原因之前都无法更新。在炎热的下午，基于电机温度的决策也会产生同样的问题。

**为什么它们会一起移动。** 一个方法，因为问题只出现一次：当机器人行为异常时，会问“发生了什么”，而没有数字支持的裁决只会引发新一轮的问题。循环部分携带了裁决计算所用的数字，因此 `unhealthy: 控制循环在 43.9 Hz` 可以与 `missed = 0` 并列阅读 — 这区分了循环延迟唤醒和循环处理过多，而这两者需要不同的修复。`robotctl health` 会从 `updaterd` 添加软件部分并打印两者。

`safeToRestart` 在策略启用且机器人移动时为 `false`：在行进中重启电机控制会导致机器人摔倒（`updater-design.md` §7.2）。
### 3.5 维护是一个单独的命名空间

`init`、紧急断扭矩、校准和原始关节写入不是意图。它们生活在自己的命名空间中，这样继电器的每种传输允许列表可以将它们隔离在远程传输之外。
信号门控决定 *谁可以连接*；它并不意味着电信操作员也是机械师——而 `update.*` 达到数据通道意味着远程对等方可以触发回滚。

## 4. 循环周围

### 4.1 循环读取快照，从不等待

意图和参数由 IPC 线程发布，并由循环作为一个单一的原子加载来读取。
没有任何东西可以对循环施加回压，也没有请求以同步方式进入循环。遥测数据通过有界广播发送出去，其中缓慢的订阅者会收到一个缺口——这是更新者的 IPC 层已经使用并记录的模式。
```text
   IPC tasks (tokio, multi-thread)        control thread (own runtime, 50 Hz)
   ═══════════════════════════════        ═══════════════════════════════════

     robot.move  ──► ┌────────────┐
     robot.head  ──► │intent slots│ ──atomic load, once per tick──►  read
                     │ twist│head │
                     └────────────┘
                     ArcSwap, stamped

     robot.init  ──► ┌────────────┐
     robot.relax ──► │power req.  │ ──taken once per tick──────────►  bring-up
     skills      ──► │skill flags │
                     └────────────┘
                     last request wins

     robot.health ◄── ┌──────────┐ ◄────────── publish ───────────  atomics
     safeToRestart    │ atomics  │              ticks, hz, missed,
                      └──────────┘              fallen, moving

     robot.state  ◄── ┌──────────┐ ◄─── send, only if subscribed ──  frame
                      │broadcast │
                      └──────────┘
                      bounded, drop-on-lag
```
**没有一个通道是双向的。**健康状态是**发布的**，而不是被请求的，这使得一个卡死的循环能够报告自身为不健康状态，而不是挂起调用者。

技能标志是布尔值而不是队列：在一个20毫秒的时钟周期内，同一按钮的第二次按下没有任何额外意义，而两个**不同的**请求都值得被看到——这单个最后写入的槽位会丢失。

### 4.2 参数

在启动时读取一个TOML文件，并且，大多数情况下，**不监视**。它位于`releases/<ver>/`之外，因此在更新和回滚时都能生存，并且紧邻更新器自己的配置文件`/etc/robot/robotd.toml`。

其中的两部分被监视，而且都是例外情况，因为重启的成本比监视整个文件更值得。`padd`每秒统计一次文件，并在mtime变化时重新读取`[pad]`和`[pad_imu_head_control]`：一个绑定从手机更改，重启`padd`来应用它会导致手柄会话中断，并且`robotd`的死人机制会让站立机器人停止行走。`robotd`在被请求时重新读取`[policy]`——除了`mode`和`enabled`之外的所有内容——这是如何通过`robotctl policy add`在不从站立机器人那里移除电机控制的情况下添加一个技能。在运行循环下重新读取`[safety]`或`[control]`是一个不同的并且更大的承诺，而且这个承诺还没有实现。`robotctl configure`知道一个键想要的三个答案中的哪一个，一个什么都没有说的键会在`robotctl`中失败。

属于板卡而不是发布的是为什么手动编辑的策略路径能够坚持：默认值指向`releases/<ver>/`内部，因此一次普通的更新会保留与之对应的策略，而删除覆盖会回到默认。文件可能完全不存在——一个未配置的板卡会以内置默认值启动，而不是拒绝启动，这比一个无法运行的守护进程更容易远程诊断。这个推论，是通过痛苦的经验学到的：一个**未注释**的值会永远冻结在该板卡上，而发布则在前进，这就是一个机群最终以kP 120而发布默认值为160的情况。

大约十个值，而不是142个：控制速率、增益、动作缩放、低通滤波器系数、最大速度、死人机制超时、策略路径和更新门限。运行时的标志爆炸主要是变体、死掉的技能和死掉的传感器，所有这些都已经消失了。
One switch是其中最粗糙的一个。`policy.mode` — `walk` 或 `roller` — 选择加载哪些策略
以及调优默认值，因此每个未设置的字段都会根据模式进行解析，将机器人移动到轮子上只需一行代码加上重启。这是一个预设，而不是一个变体：滚轮行是原型的，基于alpha默认值进行重定位。

### 4.3 游戏手柄是一个客户端

`padd` 读取 `gilrs` 并通过 `robotd` 的套接字发送意图。它是一个独立的crate，因此游戏手柄堆栈不会干扰 `robotctl` — 这是一个在故障机器人上必须工作的工具。

一次套接字跳转，仅需数十微秒。它带来的好处：应用程序、SDK 和任何远程客户端所使用的输入路径是开发人员每天都在练习的，因此它不能默默腐烂。对于开发人员来说，`ssh -L /tmp/robotd.sock:/run/robotd.sock` 可以让笔记本上的手柄与板上的机器人进行连接，无需任何代码。

在机器人上，`padd.service` 从启动时运行并驱动任何连接的手柄 —— 即使没有手柄也是安全的，因为它发送的内容为空，且死人按钮可以保持机器人静止。它保持 **非特权状态**，这是“游戏手柄是一个客户端”这一说法的核心部分：它的 `input` 和 `robot` 组成员资格就是它所拥有的全部。因此，将手柄配对属于 `configd` (`architecture.md` §1) 的职责，而不是在这里 —— 绑定设备需要 root 权限和 BlueZ，而一个持有这些权限的 `padd` 将不再在使用应用程序将要使用的API。

### 4.4 里程计，已经在样本循环中处理过的

`odometry::Odometry::alpha()` 每次循环从关节位置和循环刚刚读取的IMU四元数中递进一次，并将其估计值作为 `odom: { position, yaw }` 发送到状态流中。`robotctl monitor` 会在3D视图下将其绘制为路径图。

**基于接触**，从原型运行时移植而来：唯一的角落是地面锚点，躯干的世界姿态通过 `kinematics` crate 的模型由前向运动学从它推导而来，当另一个角落低于它时，锚点会移动 —— 所以一步从不会使估计值跳跃。航向是IMU的集成航向，因此世界坐标系是机器人启动时所面对的方向。没有磁力计，也没有任何东西来纠正漂移；这是相对运动，每个消费者都必须以这种方式处理。

它每次循环需要两次链式评估，但没有额外的总线流量，这就是为什么它以循环自身的速率而不是原型的单独100 Hz运行的原因。这个成本是“没有里程计”决策在§7中被逆转而不是重新争论的原因：反对意见从来不是算术问题，而是没有人读取答案。
### 4.5 除此之外，循环还驱动了哪些部分，以及为何它们都没有设计页面

`robotd` 在第 2 个切片之后增长了四个非控制且非安全的子系统。它们共享一种形态：每个子系统都依赖于 tick，没有一个会阻塞它，也没有一个可以直接访问总线，除非通过循环已经仲裁的意图。

| 在过程中 | 是什么 | 原因所在 |
|---|---|---|
| `sound.rs` | 播放时间的声音——一个 `aplay` 子进程，新的声音会杀死旧的声音，因为编解码器的 PCM 是独占的 | 模块头部 |
| `theremin.rs` | 从 `tofd` 深度（15 Hz）→ 一个音符，一张嘴的张开程度，以及一条状态线，由 50 Hz 的循环采样且从不等待 | 模块头部 |
| `chorale.rs` | 几只鸭子合唱一首曲子：最低的 id 指挥，指挥员拥有座位安排，`btd` 携带信标且不做思考 | 模块头部 |
| `pet-detect/` | 来自机载麦克风的约 20 KB 的 CNN，基于 40 带对数梅尔窗口，在自己的工作进程中运行 | 箱子头部 |

此外，`soc.rs` 会从 `sysfs` 读取板载的热区信息 —— 不通过 `RobotIo`，因为必须在电机总线不响应时也能持续回答。

**它们都没有设计页面，这并不是一个缺口，而是规则在起作用。** 一个服务只有在第二个读者需要从代码中推导出其合约（`../README.md`）时才会获得一个设计页面。这些服务每个只有一个实现和一个消费者，它们的决策足够本地化，可以生活在模块头部，紧挨着它们所约束的内容。它们需要的是能够 *操作*，而这正是速查表的职责：[声音]、[合唱]、[ theremin]。

## 5. 它为何存在，以及它的起源

### 5.1 目标，不是“一个良好的 `robotd`”

有两个目标，而第二个目标重新安排了工作顺序：

1. **快速迭代控制内核。**
2. **实际测试更新程序。**

更新引擎已经完成，但从未在硬件上运行过。因此，其最重要的路径尚未得到验证：`on_apply` 中的 `systemctl restart` 从未遇到过真实的 systemd，30 秒的健康门限超时是一个承认的猜测，更糟糕的是，**自动回滚只有在 `robot.health` 有意义时才有意义。** 它曾经意味着“控制循环运行了一次”，因此迄今为止的每次回滚都测试的是一个占位符。
That 是为什么第一次增量没有行走。它存在是为了在真实的板子上发出真实的健康信号（§3.4）。

### 5.2 `robotd` 替代的内容

`robotd` 替代了运行时，但不是一步到位 — 运行时执行了五个可分离的任务，其中只有一个是由 `robotd` 完成的：

| 运行时任务 | 目的地 | 时间 |
|---|---|---|
| 控制环路，策略，电机，IMU | `robotd` | 完成 |
| 游戏手柄 | 意图客户端 (`padd`) | 完成 |
| 摄像头，球/激光/宠物检测，JPEG | `mediad` | M5 |
| 网站中心，PWA，大脑命令套接字 | `mediad` / 应用 | M5+ |
| maploc — 映射，MCL，规划 | 未拥有 | — |

所以这两个任务会并行一段时间。它们不能同时运行 — 一个串行总线，一个所有者（§1.1） — 因此一块板子上只能运行其中一个，systemd 单元文件会用 `Conflicts=` 来说明这一点。

远程/应用层在这里没有设计。这是 `reachy_mini` 架构 — 媒体通过 WebRTC，控制通过 DataChannel 的 JSON-RPC 2.0 — 用 Rust 重写，超出了本文档的范围。它对 `robotd` 的唯一要求在 §3.5 中。

### 5.3 两个切片，以及“完成”的含义

**切片 1 — 保持姿态。** 每一帧，总线，模型，`RobotIo`，以及诚实的健康信号。没有任何东西进行了计算：`held_pose` 是在启动时采用的一个常量。这就是它的目的 — 它将实际负载以实际速率加载到总线上，因此循环时间和健康信号都是诚实的，当一个故意破坏的版本发布时，没有任何东西会崩溃。你可以在工作台上全天进行安装/回滚/断电循环。完成时间：`robotd` 保持姿态一小时且无总线错误；`robotctl update apply` 安装了一个版本，重启后通过了门限，机器人没有移动；一个构建为不健康的版本会自动回滚；并且在更新过程中断电会通过启动计数器恢复。

**切片 2 — 行走和站立。** 观察，ONNX 策略，安全层，意图，以及游戏手柄客户端。完成时间：它在一块板子上行走，通过意图 API 驱动；使用 `robotctl` 更新后干净地重启并通过了门限；并且 `--unhealthy` 仍然会回滚。

自那之后的一切 — 技能链，启动状态机，滚轮预设，跛行跌落 — 都是在此基础上添加的，而不是改变它。

### 5.4 不倒退是接受标准
测量已经存在：`bench_dynamixel_bus` 报告了实现速率、抖动、读取时间、总线时间、利用率、错误和 IMU 样本新鲜度，频率分别为 50Hz 和 100Hz。记录今天的数值作为基线；`robotd` 必须匹配它们。这并不是一个实时工程项目——没有使用 `SCHED_FIFO`，没有进程绑定，也没有 `mlockall`。循环今天是可靠的，任务是在保持其可靠性的前提下，使周围的代码变得更简单。

## 6. 测试

使用脚本化的样本，不使用硬件：

- 当时间片被错过时，健康状态变为 false；
- 启动时采用当前姿态，从不命令运动；
- 安全机制拒绝非有限的目标值，并将超出执行器范围的目标值钳位，跌落不会中断策略或调用者的增益；
- 跌落预测器在跌落时触发，而不是在脚落地或静态倾斜时触发，其姿态斜坡结束于站立姿态；
- 死机状态在意图停止时归零速度；
- **黄金观测向量** — `(输入，预期 61 个浮点数组)` 对，从 `mjlab` 导出并提交。观测中的错误索引不会引发错误；它会产生一个可能倒下的机器人。依赖于 `microduck_brain` 的导出（§9.2）。

每个测试的注释说明了它旨在防止哪种失败，符合仓库的约定。

## 9. 开放

1. **在 Radxa 上控制速率。** 50 Hz 继承自 Pi Zero 2W。现在由于存在电路板——`bench_dynamixel_bus` 和循环自身的五分钟总结报告了相同的数据。
2. **黄金向量** 从 `microduck_brain` 中会很有价值——作为与训练环境的回归检查，而不是作为它们原本要成为的真相来源。这不是任何已发货内容的先决条件。
3. **每个关节的限制不存在。** 安全限位器对 *执行器* 的行程进行限制，可以捕捉到 `NaN`、不良的动作比例和垃圾张量——但它不会阻止关节被驱动到机械上不智的地方。实际的限制在 alpha MJCF（31 KB）中，而不是在此处引入。一个看似解剖学上的但实际上是不正确的限制将暗示没有人会受到保护。
4. **如果将来需要进行模拟/现实一致性测试，alpha MJCF 存在于何处** —— 31 KB 的 XML，19 MB 的网格，目前在运行时的 `scripts/alpha_assets/` 中。
5. **C 依赖的成本。** `gilrs` 在 Linux 上无条件地拉取 `libudev-sys`，因此 CI 和板载交叉构建会安装它。同样的开销会再次出现，直到下一个需要到达板载的 C 依赖，因此在那条路径上更倾向于纯 Rust 库。*未经验证的 macOS:* 交叉构建需要一个 aarch64 系统根目录，而 Mac 无法提供，因此 `cargo board --bins` 在那里会失败——使用 `-p updater -p robotd -p robotctl` 构建已发货的集合，或者在 Linux 上构建。

## 映射遥测数据（API v24）

视频远端的一个映射器——今天是台笔记本电脑，将来是台服务器——需要从 `robot.state` 没有携带的三件事情：与 `tof.frame` 共享的时钟、超出其投影重力的 IMU，以及相机和 ToF 传感器的位置。所有三件事情都是附加的。
- **`t_ns`** 在 `robot.state` 和 `tof.frame` 上是 `CLOCK_MONOTONIC`，单位为纳秒（`proto::clock`）。`t` 和 `at_us` 保持不变：它们分别是每个守护进程的累积时间，一个只有一条流的读取者仍然希望从零开始的数字。`mediad` 的 `media.video` 回答在某一瞬间读取 `mono_ns` 和 `real_ns`，因此 RTP 时间戳——RTCP 发送者报告的是墙钟时间——可以放在同一个轴上。
- **`imu: {gyro, quat}`** 是循环读取的 `ImuData`：主 IMU，采样率为 50 Hz，没有更高级别的数据（`docs/design/robotd-design.md` §IMU）。原型 HAT 上的头部 IMU 目前还没有被任何东西读取；当它被读取时，它会与 `tof.frame` 并行流式传输，而不是在这里。
- **`frames: {camera, tof}`** 是此刻测得的头部关节的主坐标系姿态，来自 `kinematics::head::HeadFk`——与 `robot.look` 解决的问题相同——以及 **`robot.model`** 回答静态几何信息（主高度、关节顺序、ToF 光束方向、头部零位的姿态）。运动学保持在一个 crate 中；客户端询问而不是转录。

成本：每个发布的 tick 只有少量订阅者时，会有三个小型结构体；FK 大约需要 50 ns。
