# 重启恢复网络

当机器人启动的版本无法启动其守护进程时，如何将其恢复到已知的良好发布版本。

此页面负责启动截止时间及其谓词，即它所监控的单元的成员资格规则，`robot-rescue`，`golden` 符号链接，以及循环保护。`[restart-order.md](restart-order_zh.md)` 负责它所在的序列——包括 `updaterd` 在启动时读取的面包屑位置——而 `[updater-design.md](updater-design_zh.md)` 负责存储、健康门和启动计数器。

## 它填补的空白

`updaterd` 在更新过程中不会重新启动自身，因为它就是执行更新的进程。三个层次限制了这种成本，并且所有这些都运行在一个完全启动的板子上：

- `self_test_updaterd` 在提交前运行发布自身的 `updaterd --self-test`，因此一个错误架构的二进制文件、缺失的库或被拒绝的 `updater.toml` 会在旧发布仍然有效时失败；
- 延迟重启在更新响应后五秒将 `updaterd` 和 `btd` 放置在新二进制文件上；
- 启动校正是从继任者的角度进行的，确保这些重启确实发生了。

一个在运行中的板子上启动的二进制文件仍然可能在 **启动** 时失败，那时网络尚未启动，外围设备尚未枚举，或者单元顺序不同。而校正则在 `updaterd` 启动时运行，因此它假设已经启动了 `updaterd`。

这一点正是这个存在的原因。`BootCounter::record_boot` 从 `Engine::recover_on_start` 在 `updaterd` 内部运行，并统计 `updaterd` 的 **启动** 而不是实际的启动次数——因此一个未启动的 `updaterd` 不会被计入，从而通过可能成为受害者的过程来实现永不砖死的保证。如果这样，板子上有一个好的发布版本在磁盘上，一个试验可以回退到它，而没有任何可以作用于任何一方的运行程序。

启动计数器处理的是另一种失败：一个可以启动并运行但从未报告健康的发布版本。这种情况处理的是其守护进程根本未启动的发布版本。
| | |
|---|---|
| `robot-boot-check.timer` | 每次启动后180秒触发 |
| `robot-boot-check.service` | 一次性服务：询问是否启动成功，若未成功则转交控制 |
| `scripts/robot-boot-check` | 判断条件。安装在 `/usr/local/sbin/robot-boot-check` |
| `scripts/robot-rescue` | 交换 `current` 为黄金版，记录此操作，然后重启。`/usr/local/sbin/robot-rescue` |
| `<install_dir>/golden` | 由 `updaterd` 发布的带有永久担保的符号链接 |
| `<state_dir>/rescued` | 面包屑：最后一次尝试，也是循环的保护 |

这两个脚本都是 `/bin/sh`，并且都是通过 `scripts/install.sh` 和 `hooks/postinstall` 复制到 `/usr/local/sbin` — 与这些单元文件的行为相同，出于同样的原因，而不是通过 `current` 读取。一个作为发布负载中的二进制文件打包的救援，会被它存在的目的要解决的发行版破坏：错误的架构、缺失的共享库、启动时的崩溃。通过 `current` 读取的救援会将恢复路由到正在恢复的对象。

## 触发器：一个截止时间，而不是 `OnFailure=` 

`OnFailure=` 看起来是自然的选择 —— systemd 在一个单元用尽重启次数并进入 `failed` 状态时立即触发它，无需轮询和驻留看门狗。但这些单元的配置并未使其达到这种状态：

| 单元 | 策略 | `RestartSec` |
|---|---|---|
| `btd` | `Restart=always` | 5 秒 |
| `padd` | `Restart=always` | 5 秒 |
| `configd` | `Restart=always` | 2 秒 |
| `robotd` | `Restart=always` | 2 秒 |
| `updaterd` | `Restart=on-failure` | — |

`Restart=always` 在每个情况下都是故意的，并在单元文件中进行了论证。没有单元覆盖 `StartLimitIntervalSec`/`StartLimitBurst`，因此 systemd 的默认值（10秒内5次启动）适用 —— 而 `btd` 每5秒重启一次从未接近这个限制。它无限期地崩溃循环，从未进入 `failed` 状态，这是 `OnFailure=` 等待的状态。使 `OnFailure=` 触发意味着将这些单元重新配置为使守护进程放弃：将正常情况降级以启用救援情况。

一个截止时间将问题倒转，无需更改单元文件，并捕获无限重启的守护进程。`OnBootSec=180` 因为板子比看起来的要慢 —— `hci0` 直到电源接通后大约73秒才存在，其中 `bluetooth.service` 在 `dbus` 后面阻塞了26秒 —— 守护进程等待其硬件而不是退出，因此慢启动不是失败的启动。

### 判断条件
Two 条件，都是 systemd 尝试运行一个守护进程但无法保持其运行的正向证据。任何一个条件在任何成员中都成立：

- `ActiveState` 是 `failed`；
- `NRestarts` 是 3 或更多。

其余部分保持不变，不对称性是关键。一个操作员停止的单元是 `inactive` 且没有重启，且不应影响板卡的发布——这与启动重合时的做法相同，即当它留下一个停止的单元停止时。一个在发布之前加载的单元没有回答，这读起来是一样的。一个仍在等待硬件的守护进程是 `active`。并且一次崩溃后恢复只留下一到两次重启，而不是三次。**假阴性会令操作员错过诊断；假阳性会令一个好版本发布失败。**

三次重启而不是一次，因为 `Restart=always` 与 `RestartSec` 为 2–5 秒意味着一个真正的循环会在截止时间前的三次内通过，而一个在瞬态错误中一次死亡的守护进程不会。

### 它拒绝触发的三种方式

- **`Conflicts=shutdown.target`** 在 oneshot 上。一个在关闭过程中被杀死的守护进程可以记录为 `failed`；如果没有这个，`systemctl poweroff` 在错误的时刻最终会重启机器人进入黄金状态。
- **一个运行时间守护。** 超过十分钟，除了计时器之外的其他东西启动了它，答案是这个问题不属于这个脚本的业务范围。
- **没有 `[Install]` 部分** 在 oneshot 上，两个安装程序都将其解读为“不要启用此内容”。没有它，`hooks/postinstall` 运行 `enable --now` 覆盖它刚刚写入的单元时会在更新过程中进行回滚检查——此时守护进程正处于合法的重启中，这正是回滚检查读作一个无法启动的发布的方式。计时器被启用但从未启动的原因相同：一个 `OnBootSec=` 计时器在错过其截止时间后会立即触发。

## 成员资格规则

“任何守护进程失败 → 回滚”的反对意见是，守护进程可能因回滚无法修复的原因失败——缺少的无线电、未供电的总线——在硬件故障上回滚一个好版本比什么都不做更糟。

这归结为一个规则，用于接纳单元加入集合：**一个单元只能加入集合，如果它等待其硬件，而不是退出。** 然后一个下线的成员意味着 *二进制* 破坏了——错误的架构、缺少的库、启动时的内核崩溃、它拒绝的配置——这些都是回滚可以修复的。
| 服务端 | 在集合中 | 当其依赖缺失时 |
|---|---|---|
| `robotd` | 是 | 等待电机总线，处于“等待，不执行任何命令”状态 |
| `updaterd` | 是 | 无论何时都提供服务；它是恢复路径，当一切出问题时必须可访问 |
| `btd` | 是 | 每 5 秒重试一次适配器，如果出现适配器则重新运行整个启动过程并停止响应 |
| `configd` | 是 | 提供 `system.*` 和 `pad.*`，并报告 `net.state=unavailable` |
| `padd` | 否 | 通过设计，没有 `robotd` 套接字干净退出 |

`btd` 因其 merits 而获得其位置，而不是对称性：如果没有网络，BLE 是唯一的接入方式，因此一个 boot 时没有 `btd` 且没有已知 wifi 的机器人将完全无法访问。`configd` 也因其同样的方式而获得其位置 —— `system.pin` 是 `btd` 获取手机认证 PIN 的地方，因此 `configd` 停止运行会连同手机路径一起失效。

如果未来的服务因缺少硬件而退出，请修复该服务或将其从集合中移除。不要削弱这条规则。

## 救援

`robot-rescue` 读取两个符号链接并解析 nothing。

这并不是为了节省。它最可能救援的是一个被 `updaterd` 拒绝的 `updater.toml` 的发布 —— 这是操作员的文件，跨安装保留，而发布可以自由更改其期望。一个解析相同文件的救援会因它要治疗的疾病而死亡。

`golden` 是该文件中的一个版本（`ComponentConfig::golden`），因此 `Engine::refresh_golden_links` 在每次 `updaterd` 启动时将其发布为 `updaterd` 启动时每个 `updaterd` 旁边的 `golden` 符号链接：一个 `readlink`，没有拒绝。一个缓存而不是第二个真相来源，并且它会安全失败 —— 如果 `updaterd` 停止启动，链接仍然命名了最后一次写入时的 golden 版本，即一个已知良好的版本。一个配置的 golden 如果 *未安装* 将不发布任何链接，因为一个悬空链接会告诉救援它有一个目标而实际上没有。

**golden，而不是先前的：** 当失效的是恢复路径本身时，先前的也可能失效。golden 是唯一一个有持续保证的发布，`prune` 从不移除它。

它会拒绝，说明原因，当没有金色链接时，当“金色”指的是未安装的发布版本时，以及当 `current` 已经是金色时。最后一个情况最重要：此时守护进程会在承载有效保证的发布版本上失败，因此这不是发布版本的问题，切换也不会有任何改变，除了增加一次重启——这就是硬件故障如何变成重启循环的。

切换会将临时符号链接重命名为 `current`，与 `Store::link_to` 一致，因为 `ln -sfn` 会解除链接并重新创建，留下一个守护进程无法执行的窗口。`rename(2)` 不跟随符号链接，但 `mv` 的路径解析会，因此简单的 `mv tmp current` 将链接移动到 `releases/<version>`，并使 `current` 保持不变；GNU 使用 `-T` 来表示这个修复，而 BSD 使用 `-h`。

`--reboot` 是可选的。每个单元通过 `current` 执行，因此切换在它们重启之前不会做任何事情，而当机器人在守护进程死亡时站立，它就会倒下——由谁来决定。启动检查会传递这个标志；在控制台的人会收到命令的打印。

## 重启循环的防护，以及如何打开它

两个独立的因素防止“切换并重启”发生两次：

1. 当 `current` 已经是金色时的拒绝，这涵盖了普通情况，因为成功的救援会留下这种状态；
2. 面包屑，它覆盖了第一个情况遗漏的情况——更新移动了 `current` 使其远离金色，并再次失败。

`Engine::record_rescue` 会在 `updaterd` 下一次启动时清除面包屑，将其复制到更新日志中。因此，防护在板子证明它可以再次运行更新守护进程时打开，并在无法运行时保持关闭：一个坐着不动且日志清晰的机器人比永远重启的机器人更好。`robot-rescue --force` 是手动通过的方法。

清除发生在启动计数器之前，顺序至关重要。武装的试验会回退到 `previous`；救援已经更进一步，到达了金色。如果保持武装状态，`record_boot` 会推进试验，并最终将 `current` 移离救援选择的发布版本——恢复网络和永不砖死的保证在一次启动间隔内相互抵消。

面包屑是 `key=value` 格式，尽管 `updaterd` 会解析它：
```text
at=1786453421
install_dir=/opt/robot/daemon
from=1.2.0
to=1.0.0
because=boot check: robotd.service (failed, 7 restarts)
```
The writer 是一个在板子上运行的 shell 脚本，而板子上已经出了问题，因此在 `sh` 中正确引用 JSON 是一种无法被任何东西读取的记录方式。`journal::Breadcrumb` 也是如此——每个字段都是可选的，因为无法解析的面包屑相当于一个永远无法打开的门。`install_dir` 是将条目归属于组件的一种方式，而无需另一个地方同意 `updater.toml` 中的组件名称 `daemon`。

## 证据

静默回滚是怎样的一个过程，使得一天变成了“在我的板子上可以工作”，因此交换留下了三个痕迹：

- **日志**，来自两个脚本，通过 `logger`（当存在时）和 stderr；
- **更新日志**，作为 `Outcome::RolledBack`，其中失败的单元在原因中被命名——这就是 `robotctl update log` 所显示的内容，它是永久性的，而面包屑会被清除；
- **`robotctl version`**，间接但有用：一个运行旧版本的板子，恰好就是它所报告的内容。

## 未测试的内容

这些决定是：`xtask/tests/rescue.rs` 要求两个脚本针对临时目录中的每一个问题，使用一个 stub `systemctl` 来提供单元状态并记录是否请求了重启，而 `scripts/board-test.sh` 则在真实的 ARM64 Linux 上覆盖安装器的一半。

**systemd 未被测试。** 在 `OnBootSec=180` 时定时器是否触发，`Conflicts=shutdown.target` 是否阻止了 oneshot 在关机时运行，以及 `NRestarts` 在崩溃循环单元上是否按假设的方式读取——所有这些都没有被验证。除了真实的 systemd —— `systemd-nspawn`，或以它作为 pid 1 的特权容器——都无法回答这些问题，而相关论据可以在 `../project/install-path-gap.md` 中找到。这又是另一个理由：恢复网络是当所有其他部分都失效时必须工作的代码，而最难以测试的代码之一就是它。

在此之前，这种机制仅在测试板子上或根本不进行验证，验证的方法是给板子一个 `robotd` 无法启动的版本。

其中没有任何内容在硬件上运行，而有趣的路径需要一个无法启动的板子。
