# 机器人守护进程更新系统 — 设计

状态: 草稿 · 日期: 2026-07-22 · 负责人: pierre

## 1. 背景

机器人在Raspberry-Pi级别的板子上运行Rust守护进程（Raspberry Pi OS / Debian）。该守护进程处理电机控制、运动学、小型ML步态模型，并通过HTTP/WebRTC流式传输视频/音频。蓝牙（BLE）服务暴露配置和预配。机器人发往非开发人员客户；更新必须可以通过伴侣移动应用几下就能触发。

我们需要一种在现场安全更新发货软件的方法。

更新的顺序和里程碑存放在[`roadmap.md`](../project/roadmap_zh.md)中。

周围的系统——服务拆分、进程间通信、状态所有权、机器人API和远程/WebRTC访问——在[`architecture.md`](architecture_zh.md)中有所涵盖。本文件仅涵盖更新系统。

## 2. 目标 / 非目标

**目标**
- 独立更新**守护进程二进制文件**和**ML步态模型+配置**（它们几乎永远不会一起发货）。
- 支持**多种模型**（行走、跳跃、站立等），这些模型可以独立版本化和更新，并且一次性加载，每个模型都由守护进程兼容性（§5.5）控制。
- 从移动应用触发和监控更新。
- 通过最小版本门槛强制升级到已知不良版本。
- 从不砖死机器人：原子化应用，自动回滚，签名的文件。
- 简单易用；没有舰队后端。
- 能在团队其他机器人的开发中**重复使用**，只需少量适应。
- 支持每个组件的**安装后钩子**，用于迁移/一次性步骤。

**非目标（目前）**
- OTA操作系统/内核/驱动程序的更新（由外部处理，参见§11）。
- 舰队管理：分阶段部署、单设备遥测、仪表板。模型是“最新版本，所有机器人”。
- 差分/增量更新。在我们的更新频率下，完整文件足够小。

## 3. 关键决策及理由
| 决策 | 选择 | 为什么 |
|---|---|---|
| 更新粒度 | 应用级（非A/B镜像） | 仅daemon+模型变更；操作系统是静态的。A/B（RAUC/Mender）则会过度工程化。 |
| 传输 | 机器人 **拉取** CDN上的内容，通过自身的WiFi | 机器人有互联网连接；手机仅作为触发器和进度指示。大容量数据从不通过BLE传输。 |
| 主机 | **GitHub Releases**（daemon）+ **HF Hub**（模型） | 没有后端服务；每个都是其构件的自然存放地。引擎将“源代码”视为可插拔的。 |
| 签名 | **minisign**（CI签名，机器人验证） | 经实战验证的格式，小巧的验证库，简单的密钥管理。 |
| 通道 | 每个独立版本的组件一个通道：`daemon`，加上每个模型一个通道 | 不同的发布节奏；模型可以无需完全重启即可重新加载。 |
| 回滚 | 版本目录+原子符号链接替换+健康门限 | 简单且可靠，无需分区。 |
| 重用 | 配置驱动的通用引擎 | 每个机器人使用相同的引擎；每个机器人声明其组件。 |

面向客户端的发布节奏预期：前几个月每个daemon版本大约每2-3周发布一次，之后每2-3个月发布一次。模型更新则遵循独立的节奏。

但 **内部** 迭代速度更快（原型在3天内生成了约8个标签），因此系统必须支持两种节奏：一个快速的内部 `staging` 流和一个缓慢且经过精心筛选的 `stable` 流（§16.3）。这就是为什么 `staging` 通道和脚本化的回滚机制是必要的，而不是可选的润色。

### 3.1 先决条件：机器人需要独立的互联网访问

上述传输决策有一个设置后果，值得明确指出：**更新需要机器人在网络接口上拥有有效的互联网连接。** 因此，WiFi配置是更新的前提条件，而不是独立的功能——启动顺序是 *BLE配对 → 配置WiFi → 更新* ——而从未配置过WiFi的机器人将无法进行更新。

手机自身的连接性不能替代。实际的持续BLE应用吞吐量在考虑连接间隔和iOS的调度后大约为10-30 kB/s，这意味着一个daemon构件需要几分钟，一个模型包则需要数小时。这也是为什么数据包从不通过BLE传输（§13）的原因：限制在于链路，而不是协议，因此无论多少次的封装工作都无法恢复它。
- 无需总结、省略或添加内容，忠实翻译全文。
没有任何网络也能正常工作的命令有 `rollback` 和 `reset-to-golden`（§8.2），它们仅在磁盘上的发布版本上运行。它们不需要 manifest 和源代码，并且不移动任何字节，因此可以轻松地将它们包含在 BLE 中，即使 `robotd` 死机，`btd` 也能提供服务（§4.1）。**因此，一个未配置或离线的机器人是可以恢复的，只是不能升级** —— 这是权衡的正确方向。

如果通过电话传输文件作为备用方案是可行的，但这不是正常路径，并且仍然需要一个实际的连接（如 Wi-Fi 或 USB，绝不是 BLE）。请参阅 §17。

## 4. 架构

`systemd` 是监督程序（生命周期管理、崩溃重启、顺序控制、看门狗机制）。
```
systemd
├── robotd     motor control · kinematics · gait ML · sensor loop   [RT-ish core]
├── mediad     video/audio capture · WebRTC/HTTP                     [isolated: media crash ≠ dead motors]
├── btd        BLE GATT server (bluer): wifi provisioning, naming, update trigger/progress
└── updaterd   the update engine (this document)
                    ↕ local IPC (unix socket) with robotd + btd
```
**结构规则:** 更新器是一个与它要更新的单元**分离的单元**。一个进程不能干净地替换其自身的运行二进制文件，更新器必须在守护程序崩溃时存活下来以执行回滚。

**推论 —— `updaterd` 必须驻留，并且必须将其自身排除在重启集之外。** `updaterd` 和 `btd` 都包含在守护程序的包中，因此简单的“重启一切”会导致在交换或健康门中运行的执行器被杀死。`on_apply` 因此会重启发布中包含的 **所有** 项，**除了** 这两个。

**不在飞行重启中排除并不等同于跳过**，而将它们解释为跳过是错误的。将它们推迟到“下次启动或显式稍后的重启”会导致两个守护程序无限期地运行旧的二进制文件：驻留的 `updaterd` 拒绝了更新的 `robotctl`，提示“客户端使用 API v4，守护程序使用 v3”（这种拒绝已经消失——是陈旧的二进制文件的错误，而不是意见不合），而 `btd` 的修复是在从未运行过的二进制文件上进行的。因此，`RESTART_AFTER_REPLYING` 通过 systemd 临时计时器在结果上线后 5 秒重新启动每个项——足够长以完成一次写入，但又不会让任何人等待。每个排除的原因在那一刻就失效了：更新已完成，`btd` 携带的回复也已送达。

这里没有任何内容等待重启，`robotctl health` 的单元块是确认这一点的地方：它打印每个进程 **正在运行的发布**，这是唯一一个未成功重启的延迟重启会显示的地方。

该集合是从发布的 `systemd/*.service` 文件中派生出来的，而不是从板卡的配置中读取的，这两个排除项在代码中 (`NEVER_RESTART`) 而不是在配置中：它们是这些守护程序 **是什么** 的属性，而不是操作员可以出错的选择。早期的设计将列表放在 `/etc/robot/updater.toml` 中，`install.sh` 保留了它——因此在守护程序存在之前预置的板卡从未重启它，更新仍然报告成功（`install-path-gap.md` §4）。
**这不涵盖的内容，以及答案的形状。**不停止 `updaterd` 保护了 *在途* 的更新。这并没有说明新的 `updaterd` 是否正常工作，而是将验证推迟到下次启动时——到那时更新已经提交，没有人关注，恢复则位于 `Engine::recover_on_start` 中，即 **在导致启动失败的进程中**。`Restart=on-failure` 然后会循环几次重启并放弃，留下一个没有更新守护进程且无法从中更新的机器人。这与恢复在机器人已经损坏时有效这一承诺相矛盾。

两层机制可以实现这一点，但它们捕获的内容不同。**第一层已经实现**；第二层则是其自身的 PR。

1. **在提交前对新二进制文件进行自测**，并在回复发送后重启 `updaterd`。只读模式——配置加载完毕，引擎构建完成，但在恢复之前退出——可以捕捉错误的架构、缺失的库、即时崩溃以及最有可能的情况：一个新版本的 `updaterd` 拒绝了板子现有的 `updater.toml`，这是操作员的文件且跨安装保持不变。在那里的失败可以廉价地回滚，无需重启。重启必须 **分离**，因为引擎运行在 `update.apply` RPC 内，否则会向客户端发送一个断开的管道而不是其结果。同样的“回复后重启”的逻辑也适用于 `btd`。

   注意现有的 `--check-only` 并不是这样：它在真正执行 `recover_on_start` 之前运行该标志，因此会增加每次武装试验的启动计数并可以撤销更新。它是一个操作员工具，而不是一个探针，且在更新过程中使用它会导致第一个引擎在工作的同时第二个引擎在修改存储。

   如构建：`self_test_updaterd` 在已启动单元重启和健康门之后运行，仅在 `on_apply` 是重启的情况下——一个模型组件没有 `updaterd`，而初始安装强制 `on_apply=none` 正是因为还没有安装任何内容。`Error::SelfTest` 携带二进制文件的最后一条 stderr，因此“配置错误：未知字段 `foo`”会到达回滚原因而不是被压平为“不可达”。
   重启通过 `systemd-run --on-active=5s` 完成，其中有两个细节至关重要。一个
*子进程* 会驻留在 `updaterd` 的 cgroup 中，在重启其自身父进程的过程中被中途杀死；而临时单元则不会。并且在任何内容被生成之前，更新锁会被释放，因为 fork 会复制进程中的每个打开描述符——包括同一进程中的其他引擎持有的锁，这在测试套件中表现为无关操作失败并带有 `Busy` 错误。

2. **在 `updaterd` 之外的启动时网络连接**，用于处理那些漏网之鱼：每次启动后三分钟的定时器会检查本次发布是否启动了其守护进程，如果未启动，则在基础安装中使用 `/bin/sh` 救援模式将 `current` 切换到 `golden`。它必须驻留在这个进程和发布之外，因为其存在的失败情况是 `updaterd` 未启动——此时 `recover_on_start` 和下面的启动计数器都不可用。它无法修复硬件：一个因缺乏伺服电源而失败的 `robotd` 在 `golden` 状态下也会以相同的方式失败，这与健康门将不健康状态和降级状态区分开来的区别相同。[`boot-recovery-net.md`](boot-recovery-net_zh.md) 拥有它。

这也是为什么更新逻辑不能驻留在 `btd` 中的原因：作为更新的客户端，`btd` 不能执行更新——它会在更新过程中中途杀死自己。`btd` 保持为一个轻量级传输，而驻留的 `updaterd` 拥有状态机、单次飞行锁、启动恢复以及任何没有客户端存在的周期性/强制性检查（§8.1）。

`btd` 是一个轻量级中继器：它将“检查”/“应用”转发给 `updaterd`，并将进度流回手机。它从不移动负载本身。

### 4.1 不变性：`btd` 和 `updaterd` 在 `robotd` 死亡时仍能生存

**`btd` 和 `updaterd` 必须在 `robotd` 被崩溃、崩溃循环或不存在的情况下启动、运行并保持完全可用。** 它们是恢复路径——如果它们只能在机器人健康时工作，那么客户端真正需要它们的情况就是它们无法工作的那种情况。这是确保在现场不砖死机器人时最重要的结构属性。
Concretely:
- **不依赖systemd的`robotd`。**没有`Requires=`/`After=robotd`，没有共享命运。`btd`和`updaterd`在启动时独立启动并保持运行。
- **没有硬性IPC依赖。**每一个对`robotd`的调用（“是否可以重启？”检查、健康探测、模型重载）都是*可选的且超时限制的*。死掉的套接字是一个正常的、预期的答案——从不会导致阻塞，从不会导致程序崩溃，从不会导致拒绝服务。
- **降级模式的语义。**当`robotd`宕机时，安全重启检查会轻易通过（没有东西在移动）并且`updaterd`继续运行。健康探测会退回到“新的`robotd`是否启动并报告健康”——这正是从坏版本恢复时需要检查的内容。
- **`btd`报告真相。**应用程序必须能够看到“守护进程不健康，版本X，上次更新失败”并从该状态提供*更新* / *回滚* / *恢复到出厂设置*（§8.2）选项。一个不能行走的机器人仍然必须能够解释自己并接受修复。
- **最小的依赖面。**这两个是最后的防线，所以要让它们简单：依赖项少，不包含机器学习运行时，不包含媒体堆栈，不访问GPU/摄像头。有趣的代码中的一个错误不能导致恢复路径的崩溃。
- **保守地单独可更新。**`btd`/`updaterd`与守护进程一起打包，因此一个坏版本理论上也可能破坏它们——这就是为什么黄金版本（§8.2）和启动计数器回滚（§8）存在的原因。将这些两个组件的变化视为比`robotd`变化更高的风险。

`updaterd`的附带结论：它也不应该*需要*`btd`。即使BLE本身已损坏，本地的`robotctl`（§15）通过Unix套接字也能驱动恢复。

## 5. 更新模型

### 5.1 通道

两个逻辑通道，每个通道有自己的清单和版本行：

- `daemon` — `robotd` / `mediad` / `btd`二进制文件及其支持文件。
- `model`  — 步态模型权重 + 行为/配置捆绑包。

这两个通道存在于**不同的主机**上，引擎通过每个组件的可插拔`source`来处理：
- `daemon` → **GitHub Releases**，标签`daemon-v1.4.2`，资产 = 构件 + `.minisig` + 清单。
- `model` → **HF Hub**仓库，通过git修订/标签版本化；文件在`https://huggingface.co/ORG/MODEL/resolve/<rev>/<file>`处解析。“最新” = 一个移动的标签/分支或最新的标签。我们仍然自己`minisign`模型构件，并将`.minisig`存储在一起——HF不为我们签名。
### 5.2 构件

每个发布版本一个压缩的 tarball，例如 `daemon-1.4.2.tar.zst`，包含：
```
bin/robotd  bin/mediad  bin/btd        # (daemon channel)
model/gait.onnx  config/…              # (model channel)
version.toml                           # semver, min_hw_rev, schema_version
hooks/postinstall                      # optional, executable, versioned+signed
```
### 5.3 构建说明

一个小型的 JSON 文件，作为发布资源发布（并通过稳定的 URL 引用，见 §6），并使用 minisign 签名。
```json
{
  "channel": "daemon",
  "version": "1.4.2",
  "url": "https://github.com/ORG/REPO/releases/download/daemon-v1.4.2/daemon-1.4.2.tar.zst",
  "sha256": "…",
  "sig_url": "https://github.com/ORG/REPO/releases/download/daemon-v1.4.2/daemon-1.4.2.tar.zst.minisig",
  "min_hw_rev": 3,
  "schema_version": 2,
  "min_supported": "1.5.1",
  "changelog": "…"
}
```
`schema_version` 是 **迁移上下文，而不是兼容性门**。基于它进行限制是自相矛盾的：判断清单的引擎总是上一版本的引擎，因此拒绝 `schema_version > supported` 会使每个模式更新不可交付——包括携带理解它的引擎的发布。
安装后挂钩执行迁移；引擎只是传递这些数字（§9）。

`min_supported` 是 **最小版本门槛**（§8.1）。即使最初未使用，从 v1 起也包含在模式中——它无法回装到从未学会查找它的机器人上。

目前故意没有 `not_valid_after` 字段：清单过期是防止冻结攻击的防御措施，其操作成本的承担决定在 §8.4.2 中推迟。以后添加它是可叠加的（缺省值表示没有过期），与 `min_supported` 不同，因此现在不需要预留。`model` 清单还携带 `model_api`（§5.5）。

### 5.4 签名 / 信任

- CI 使用私有的 minisign 私钥（保存在 CI 秘密中，理想情况下是离线主服务器）对 **制品** 和 **清单** 进行签名。
- 机器人随附一组可信的 minisign 公钥（`/etc/robot/trusted_keys/`），而不是单一的公钥。如果签名能够验证通过任何可信公钥，则该签名有效。这是信任锚点——不需要 PKI。
- **密钥轮换**：从第一天起就提供一组密钥意味着丢失或泄露的密钥是可生存的——发布一个由现有密钥签名的更新，该更新添加新的密钥并在稍后退役旧的密钥。嵌入一个固定的密钥会使丢失的密钥成为不可恢复的死更新路径。
- 可选地在组中预留一个 **开发密钥**，通过一个标志进行保护，用于团队的本地侧载路径（§15）。
- 机器人上的验证顺序：验证清单签名 → 下载制品 → 验证 sha256 → 验证制品签名。**从未执行或提取到活动路径中的未签名字节。**

#### 密钥保管

使用 `cargo xtask keygen` 生成密钥，该工具拒绝写入仓库，并将秘密密钥写为 `0600` 权限。
| key | 加密 | 私有半生命周期 | 在受信任集合中 |
|---|---|---|---|
| `release-1.pub/.key` | 是 | 密码管理器 **和** CI 密钥 | 每个机器人 |
| `release-2.pub/.key` | 是，**不同的密码短语** | 仅密码管理器 — **从不 CI** | 每个机器人 |
| `release-3.pub/.key` | 是，**不同的密码短语** | 离线；理想情况下从不连接到网络 | 每个机器人 |
| `team.dev.pub/.key` | 否 | 团队存储 + CI | 仅开发板 |

此表编码了三件事，每件事都很容易出错：

1. **备用必须来自第一个图像。** 机器人验证其内置的密钥集，因此不能通过空中更新引入备用密钥——丢失唯一的密钥意味着必须手动重新刷写每个机器人。
2. **备用必须在密码短语和暴露方面有所不同。** 它的目的是在第一个密钥被破坏时生存；`release.key` 必须在 CI 中，因此 `release-2.key` 不得在 CI 中。共享相同的密码短语会将两者合并为一个。
3. **密码短语是生成的，不是选择的。** 它们从不手动输入——它们存在于密码管理器和秘密存储中——因此记忆力毫无价值，而 minisign 的 scrypt 参数（32 MiB，opslimit 2²⁰）仅对泄露密钥文件的离线攻击起到轻微的阻碍作用。≥128位，例如 `openssl rand -base64 24`。

发布在 CI 中签名，而不是本地——这是一个故意的选择，文档在 [`ci-setup.md`](../project/ci-setup_zh.md) 中。

开发密钥未加密：CI 以非交互方式签名，保护密钥旁存储的密码短语增加的保护很少。其真正的保护是结构上的——它不在客户机器人的受信任集合中，并通过 `allow_dev_keys = false` 在那里被封锁。

### 5.5 模型：每个组件一个

有几种模型——行走、跳跃、站立、地面拾取——**每个独立版本化**，并且所有组件同时加载，而不是从多个组件中选择一个。

**控制策略采取了相反的方式，本节是通用规则而不是它们所做的事情。** 它们由一次训练运行生成，并且插槽→文件映射取决于驱动模式，因此它们作为一个 `policies` 组件一起发送，每个插槽的覆盖设置覆盖其余部分——参见 [`policy-channel-design.md`](policy-channel-design_zh.md) §9。这里保持不变的是结构：一个组件是一个具有自己版本号的事物，机器人可以拥有任意数量这样的事物。
That 是一个 *组件* 的确切定义：一个有自己的版本号的实体。因此，每个模型都是 `updater.toml` 中的一项独立条目，并不需要特殊的存储布局：
```toml
[component.model-walk]
install_dir = "/opt/robot/model/walk"
source      = { type = "hf_hub", repo = "ORG/gait-walk", revision = "main" }
on_apply    = { action = "reload", unit = "robotd", signal = "SIGHUP" }

[component.model-jump]
install_dir = "/opt/robot/model/jump"
source      = { type = "hf_hub", repo = "ORG/gait-jump", revision = "main" }
on_apply    = { action = "reload", unit = "robotd", signal = "SIGHUP" }
```
Each then gets, 免费且独立地：自己的回滚目标、黄金发布版本、启动计数器试验，以及已知错误历史记录。`robotctl update apply model-walk` 更新一个模型而不影响其他模型。尝试一个较旧版本的命令是 `robotctl update select model-walk 1.1.0` — `select` 会重新指向任何已安装的发布版本而无需下载。

模型使用 `reload`（SIGHUP → 重新 `mmap` 权重）而不是 `restart`，因此权重交换从不中断电机控制。每个组件的 `on_apply` 是实现这一点的关键，也是模型和守护进程保持为独立组件的核心原因之一。

**尝试过一种“库布局”但已被移除。** 早期的一个草稿中有一个 `Layout::Library` 模式（`library/<ver>/` + 一个 `active` 符号链接），旨在容纳多个命名的捆绑包并选择其中一个。实际上它并不能做到这一点 — 它只改变了两个目录名称，因此在功能上与正常布局相同，只是看起来像是一个功能。更糟糕的是，“多个已安装，一个激活”并不是模型的形状：它们同时全部激活。已删除。

如果某个 *单一* 插槽需要竞争的替代品（两种不同的 walk 模型，用户选择其中一个），那是一个真正的 `(name, version)` 存储键和实际的变化 — 请参阅第 17 节。当前设计中没有任何内容假装支持它。

**兼容性（保持轻量）。** 守护进程宣传一个 **模型 API 版本**（`model_api`，例如 `1`），描述它实现的传感器输入 / 执行器输出合约。每个模型清单声明它所需的 `model_api`。规则：只有当 `model.model_api <= daemon.model_api` 时，模型才会加载。

API 版本在接口更改时提升 — 例如，一个模型开始消费 **新的传感器输入** 或发出 **新的输出**。这意味着：
- 需要 API `2` 的模型在只支持 `1` 的守护进程上被拒绝 → 应用程序会提示先更新守护进程。
- 旧模型可以在更新后的守护进程上继续工作（向后兼容），因此在守护进程升级时不会有任何中断。

无法连接的 `robotd` 使这变得 *未知* 而不是不兼容，这是等待模型而不是守护进程的原因 — 请参阅第 5.4 节的 `兼容性` 注释。

### 5.6 硬件：单一目标

**当前目标：Radxa Zero 3**（RK3566，Cortex-A55 → `aarch64`）运行 **Armbian 26.2.x**，带有 **Debian 13 (Trixie)** 用户空间，Rockchip BSP 内核 6.1.115。
暂定 — 最近手边的最接近的板子而不是最终选择 — 但这是构建和测试工具链的目标。
Build和验证: `scripts/board-test.sh` 使用 `cargo-zigbuild`（`zig cc` 提供交叉sysroot和`zstd`所需的C编译器）进行交叉编译，并在容器中运行实际的ARM64 Linux二进制文件。

glibc的最低版本固定在**2.31**（实际为2.30），而不是Trixie的2.41，脚本仅在**Trixie**中运行——这是我们要提供的用户空间。Armbian为该板提供了其他选项；测试那些无人运行的配置会浪费工作时间来捍卫一个我们不需要的主张，`BOARD_IMAGES=`可以为此进行一次性的检查。

这个固定值不是关于那些替代品的，它是为了防御构建主机：未固定时，构建会链接到开发者的机器或CI运行器所拥有的glibc版本，这比板上的版本新，构建可以顺利进行，但在机器人上加载时会失败，而构建输出中没有任何内容指向原因。2.31已经远远低于目标版本，这没有任何成本。

内核版本不是限制：`flock`、`SO_PEERCRED`和`statvfs`都早于6.1版本。

容器无法覆盖，硬件必须完成的部分：真实的`systemctl restart`（`on_apply`从未针对systemd运行过）、eMMC写入行为和时间、`statvfs`针对实际文件系统，以及健康门限是否适合一个启动需要数十秒的机器人。

**v1针对一个明确的硬件配置。**没有板卡/变体/IMU/相机矩阵，没有针对每个设备的硬件配置，也没有选择补丁的逻辑。原型的硬件差异是探索的结果，而不是需要延续的要求。

我们保留的内容是故意最小化的：
- 表现清单中的`min_hw_rev`（§5.3）作为单一的前向兼容保护，未来板卡的修订可以拒绝不兼容的补丁。一个整数，没有矩阵。
- 更新日志（§8.3）和任何未来电话回家的**稳定设备ID**。SoC序列号（`/proc/device-tree/serial-number`）有效且在 reflashes 后仍然存在——无需任何配置步骤即可获取它。

如果出现第二个硬件目标，表现清单将获得约束，引擎将获得匹配步骤。在此之前——这正是要避免的投机性复杂度。

### 5.7 机器人特定的状态必须在更新中存活

保留下来的唯一要求：某些文件属于**这个**机器人，更新或回滚绝不能破坏它们。分为三类，处理方式不同：
| 类别 | 示例 | 生命周期 |
|---|---|---|
| **已发货**（替换） | 二进制文件，策略捆绑包，默认配置，静态systemd单元 | 存在于`releases/<ver>/`；原子替换 |
| **机器人特定**（从未更改） | 校准数据，每设备生成的资产，学习/持久化状态（地图，个性，习惯） | 位于发布目录之外；**在更新和回滚过程中均保留** |
| **用户偏好**（保留，迁移） | 机器人名称，WiFi凭据，活动模型选择，应用设置 | 自身配置文件；通过钩子（§9）在`schema_version`版本更新时迁移 |

两条规则：
1. 发布目录是**可抛弃的**。任何必须生存下来的内容应存放在`/etc/robot/`或`/var/lib/robot/`。回滚时不应丢失用户数据，也不应迫使客户端重新校准。
2. **运行时配置存放在配置文件中，而不是systemd单元中**。单元是预装且静态的；它们读取一个配置文件，而更新程序从不覆盖该文件。（原型在安装时将CLI标志嵌入生成的单元文件中，因此重新安装会默默地重置设置——这是一个值得命名的陷阱。）

附注：每次设备特定的资产重新生成必须基于稳定的种子，并且仅在真正需要时进行，而绝不能在每次更新时无条件地进行。

## 6. 在GitHub Releases托管

- 构件 + `.minisig` + `manifest.json`是每个版本的资产。
- “最新的是什么？”通过以下方式之一解决：
  - **稳定重定向URL** `…/releases/latest/download/<资产>` — 但GitHub的“最新”是针对整个仓库的，因此仅当每个仓库只有一个通道时才能干净地工作。
  - **GitHub API** 查询以查找匹配通道前缀（`daemon-v*`）的新标签 — 适用于共享一个仓库的情况。如果我们将两个通道保留在一个仓库中，则这是首选方法。
- CI端：`cargo-dist`可以构建并发布签名的构件到GitHub Releases；我们以附加资产的形式托管manifest。

### 6.1 私有仓库无法为整个车队服务 — 因此这个仓库不会保持私有

**决定（2026-08-26）：发布`pollen-robotics/microduck`。** 在私有仓库中，即使在有令牌的情况下，机器人也无法下载任何内容，这是因为私有仓库的`releases/download/<tag>/<asset>`URL返回**404，无论是否有令牌**。直接验证如下：

| URL | 私有仓库 |
|---|---|
| `https://github.com/<repo>/releases/download/<tag>/<asset>` | 404，认证与否皆是 |
| `https://api.github.com/repos/<repo>/releases/assets/<id>` + `Accept: application/octet-stream` | 有令牌时返回200 |
So 引擎通过API端点解析每个资源，这适用于 开发者的板 — `GITHUB_TOKEN` 在环境中，并且 `--ref` 安装分支构建 — 以及公共仓库，但不适用于客户机器人，后者没有令牌且不应有令牌：fleet范围内的凭证嵌入到镜像中，无法在不重新刷写的情况下进行轮换，这也是分级的签名密钥旨在避免的问题。

还有三个其他选项，记录下来以防将来需要重新考虑此决定：

| 选项 | 保持零后端 | 备注 |
|---|---|---|
| 仅包含发布制品的公共仓库 | 是 | 签名才是使制品安全的关键，而不是隐秘性 —— 一个制品仓库泄露构建元数据而不会泄露其他内容。源代码保持私有。这是如果此仓库将来再次私有化时的备用方案。 |
| 一个带有普通HTTP源的对象存储或CDN | 大部分 | 又多了一项需要拥有和付费的内容；源特性已经抽象了这一点。 |
| 镜像中的只读令牌 | 是 | 拒绝：无法轮换的fleet凭证。 |

**公开变更不涉及任何代码。** API路径保持正确 — 它是私有和公共仓库共用的唯一路径，这也是为什么它被这样编写的原因。

**它所改变的是预算。** 未认证的GitHub API请求每小时每个IP限制为60次，而令牌可以提升这一限制；一个家中的机器人没有令牌，因此其检查会从与该地址后方所有内容共享的匿名池中消耗。在 `check_interval = "6h"` 和每次检查中几次调用的情况下，一只鸭子远未达到这一限制 — 二十只鸭子在同一WiFi下更新时可以达到。这不是一个正确性问题：`http.rs` 已经读取403和429作为“稍后再试”，并在消息中说明了这一点。因此，在仓库公开后，为了从 `objects.githubusercontent.com` 下载对象时不会从该池中消耗资源，更倾向于使用 `browser_download_url` 获取字节，并且保留API路径用于私有仓库和开发板。在一群鸭子存在之前，值得在第一只鸭子发货之前就进行这项工作。

## 7. `updaterd` 状态机
```
receive trigger (from btd)  ── check | apply(version)
        │
        ▼
PREFLIGHT (§7.2):  single-flight lock · clock/NTP sane · robot stopped · disk space free
        │  (any fail → report + exit, no changes)
        ▼
fetch manifest ──► verify manifest signature ──► compare version, check min_hw_rev / model_api / pin / downgrade
        │                                                    │ (nothing to do / incompatible)
        ▼                                                    └─► report + exit
download artifact ──► verify sha256 ──► verify artifact signature
        │
        ▼
extract to releases/<ver>.tmp/  ──► orphaned-unit check (§7.3) ──► [pre_install hook]
        │                                    │ (an installed unit execs a binary this release lacks)
        │                                    └─► report + exit, nothing swapped
        ▼
atomic symlink swap:  current → releases/<ver>        (rename(2), same fs)
        │
        ▼
[post_install hook]  ──► apply: restart (daemon) | reload+SIGHUP (model)
        │
        ▼
HEALTH GATE (poll robotd over unix socket, timeout per component)
        │
   ┌────┴─────────────────────────┐
 healthy                        not healthy / hook failed / timeout
   │                                │
 prune old (keep_previous)      ROLLBACK: swap symlink back, re-apply, mark failed
   │                                │
 report success                 report failure
```
任何非零挂钩退出码、失败的健康探测或超时均被视为相同情况：
**中止并回滚。**

### 7.1 磁盘布局
```
/opt/robot/daemon/
├── releases/1.4.1/     ← previous (kept for rollback)
├── releases/1.4.2/     ← new
├── current → releases/1.4.2     ← systemd units point at current/
└── golden  → releases/1.4.1     ← never pruned; what the rescue reads
```
原子性是在同一文件系统上执行的单个 `rename(2)` 操作。绝不会存在半完成的状态。

`golden` 由 `Engine::refresh_golden_links` 在每次启动时从 `ComponentConfig::golden` 写入。它存在是为了让外部恢复过程无需解析器 —— 详见 [`boot-recovery-net.md`](boot-recovery-net_zh.md)。

### 7.2 下载前的预条件

在任何下载或更改之前都会进行检查；任何失败都会干净地中断，不会产生副作用：

- **单次飞行锁。** `updaterd` 持有一个锁文件/套接字，因此两个触发器（或重试）不会发生冲突。正在进行的更新会报告“忙”，从不启动第二个更新。
- **手机独立性。** 机器人会主动拉取更新，因此即使 BLE 断开连接，更新也会运行至完成。状态会在重新连接时持久化并重放至手机上 —— 手机从不需要保持连接。
- **时钟合理性。** 一个 Pi/eMMC 板没有电池供电的 RTC；错误的时钟会在任何下载之前失败 HTTPS 证书日期验证。需要 NTP 同步（或时钟合理性检查 + 有限重试）作为预条件。minisign 本身与时间无关。
- **机器人停止。** 假设应用程序仅在机器人停止/停放（电机安全）时提供更新。`updaterd` 仍然会向 `robotd` 发送一个轻量级的“安全重启？”查询，如果未通过则拒绝 —— 这是对在运动中意外重启电机控制的廉价保险。
- **无活动远程会话。** 在远程存在会话期间重启 `robotd`/`mediad` 会带来意外；拒绝，或警告并要求显式确认。参见 [`architecture.md`](architecture_zh.md) §5。
- **磁盘空间。** 存储是 eMMC（有限，磨损问题不如 SD 卡严重，但空间仍然重要）。在开始之前验证下载、解压及 `keep_previous` 所需的可用空间。

### 7.3 这次发布是否会弃用已安装的单元？

`hooks/postinstall` 安装了发布的单元并在回滚时留下它们（§9）。对于回滚来说这是正确的 — 下一次成功的更新会重新安装它所携带的任何内容。但对于 **回滚到引入了一个守护进程的版本之前** 的版本来说则不是：该单元会保留，其 `ExecStart` 指向的是旧版本不包含的二进制文件，systemd 会因 `203/EXEC` 错误而失败它，并且由于该守护进程在衍生的重启集中，失败的重启会失败更新，从而导致回滚。在已解决为稳定版 `0.2.0` 的板子上观察到此现象，而 `0.2.0` 版本早于 `configd`。
所以一个候选者如果缺少某个已安装单元的二进制文件则会被拒绝 — `updater/src/orphan.rs`, `Error::WouldOrphanUnit`。它读取 `/etc/systemd/system/*.service`，过滤出 `Exec*=` 指向组件 `current` 符号链接的单元：只有活动目录才是孤儿出现的地方，因为它超过了安装它的发布版本，而过滤器则排除了我们从未发布的单元。它无法解析的任何内容都不会产生结果 — 解析器不理解的单元文件导致拒绝更新是最糟糕的失败。

值得保留的三个放置决策：

- **不预检（§7.2）。** 两次预检都在下载包之前运行，所以候选者的文件列表尚不存在。这在解压后且在交换前运行，仍然没有副作用：暂存是可抛弃的，启动计数器未激活，`current` 没有移动。需要下载才能确定。
- **在干运行返回之前**，因为“这个降级会起作用吗？”正是干运行所问的问题。
- **没有目标可以豁免**，不像 `WouldDowngrade` 保护器仅在 `Latest` 上触发。那个是关于镜像提供过时的清单；而这个是关于无法启动的单元，这并不关心目标是如何命名的 —— 而 `Ref` 就是这种情况被观察到的方式。

不在回滚、重置为黄金状态或 `select` 中：这些故意向后移动，是让板卡摆脱不良版本的方法，因此任何可以拒绝的都不应出现在恢复路径中（`architecture.md` §1.1）。

拒绝会指出单元、缺失的二进制文件以及绕过它的方法 — 移除该单元：
```
systemctl disable --now configd.service && rm /etc/systemd/system/configd.service
```
Deliberately不使用`--force`标志。移除单位才是操作员的意思，
因为引入守护进程的版本发布后的电路板不应该运行该守护进程；这使情况变得正确而不是覆盖检查，该检查表明不应该运行；下次分发带有该单位的更新会重新安装它。

## 8. 健康门与回滚

- 在应用后，新的`robotd`必须在每个组件的超时时间内清除一个**健康标志**（电机确认，模型加载，媒体管道初始化）。
- 作为硬性停滞的保险措施（不仅仅是干净的失败）：
  - `systemd` `WatchdogSec` 用于`robotd`，以便停滞触发恢复。
  - 一个**启动计数器**文件`updaterd`在启动时检查：如果最后一次更新在两次启动中从未达到“健康”，则询问机器人并作出决定。这涵盖了“启动但病态”和“根本无法启动”的情况。

    **预算决定何时询问；机器人决定是否回滚。** 达到预算的末尾意味着从未有应用确认过试验——通常的原因不是糟糕的版本而是应用在门运行前被杀掉，而这正是版本自身的`hooks/postinstall`重启`updaterd`所导致的。因此，与健康门询问的三个问题相同：*健康*提交，*降级*提交，其他任何情况都会回滚。

    降级提交是因为§4中给出的启动网络无法修复硬件的原因：没有伺服电源的`robotd`在黄金版本上表现相同。在那里回滚会将硬件故障隐藏在软件更改之后，回滚下一个版本，而且——最糟糕的是——在没有说明的情况下替换了持有机器人的代码。这并非假设：一块安装了分支构建并配对了游戏手柄的电路板在两次启动后运行了稳定版本，之后的每一个命令都运行在没有人要求的代码上。

    仍然会回滚的是这个网络的目的：`robotd`不健康、不可达或以`updaterd`无法读取的格式回答。

- `keep_previous`（默认1）保留的发布目录限制了磁盘使用，同时总是保留了一个已知良好的目标用于回滚。

### 8.1 最小版本门槛 / 杀掉开关
**已实现**，包括使其工作的部分：在配置中设置 `check_interval` 可使居民 `updaterd` 按照定时器检查每个源，并且 `auto_apply` 决定在无需等待客户端的情况下安装这些更新。在另一项更新正在执行时，整个计划的检查将被完全跳过，而首次检查在启动后会延迟（通常网络尚未启动，且一群机器人同时重启会像羊群一样到来）。

若未设置 `check_interval`，则会禁用轮询——连同地板的检测，因为一个无人触碰更新的机器人永远不会得知地板的存在。`updaterd` 在启动时会发出警告，当 `auto_apply` 设置但没有运行计时器时，会发出不同的警告。

### 8.1.1 `auto_apply` — 无人值守更新策略

| | |
|---|---|
| `off` | 从不；可用性会被记录，强制版本会大声提醒 |
| `mandatory` | **默认** — 仅强制版本。普通版本会等待客户端 |
| `all` | 所有可用版本 |

这是一系列有序设置而非不同紧急程度的标志，因此配置文件无法表达“自动应用普通更新但不自动应用强制更新”——自动更新所有除了发布用于解救故障集群的版本之外的所有更新。

`mandatory` 是默认设置，因为其他选择会导致机器人卡在我们已撤回的版本上。普通版本会等待，因为 *何时重启机器人是机器人的所有者的决定*，这也是整个应用程序驱动更新流程存在的原因，以赋予他们这个决定权。

`all` 是金丝雀和测试设置，也是第 16.2 节第 2 级可配置性的基础：跟踪 `staging` 并安装每个候选版本的实验室机器人。将其发送给客户端机器人会将重启决定权从他们手中夺走。

无论策略如何，无人值守应用都是 **普通** 应用。它会运行相同的预检 —— 因此一个正在行走或有远程会话的机器人会在下一个间隔时拒绝并重试，而不是在某人的手中重启 —— 同样会运行相同的健康门，因此一个无法启动的版本会被回滚。这也是为什么不需要维护窗口的原因：`safeToRestart` 比时钟更能回答“现在是否是个好时机”这个问题，而且它在任何网络访问之前运行，因此忙碌的机器人不会产生任何成本。
**这属于守护进程，而不是在cron中。**一个systemd定时器或crontab调用`robotctl update apply`看起来等价，但并非如此：显式的应用故意绕过了下面已知的不良保护，因为操作员在重试发布时可能已经解决了根本原因。外部定时器会继承这种绕过并失去保护——每半边的错误——从而重新引入下一节所防止的循环。

**无人值守路径拒绝一个此机器人已经回滚的候选版本**，无论策略如何，即使该发布是强制性的。如果没有这种保护，一个有缺陷的发布会成为整个机群的陷阱，没有出路：检查显示可用 → 应用 → 网关失败 → 回滚 → 等待 `check_interval` → 重复。每个循环都会重新下载该文件，重新写入eMMC并重启 `robotd`，因此每台机器人都是既不可用又在耗损，处于电池供电状态，而没有任何客户端注意到。循环中的任何东西都不会收敛。

保护是 `known_bad`，源自每个版本日志的最新结果，因此如果发布最终成功，它会自动清除。它仅应用于无人值守路径：显式的 `robotctl update apply` 仍然会重试，因为操作员可能已经解决了根本原因，拒绝他们将移除显而易见的检查方式。当保护触发时，它会在 `error` 级别记录日志 —— 一个卡在强制最低版本之下的机器人需要一个修复的发布，而这一点应该大声提醒。

此测试通过日志中的尝试次数而不是检查当前版本来计数：在每个循环之后，符号链接都会回到正确的发布上，因此即使循环运行，机器人的状态看起来也是正确的。

---

该清单的 `min_supported` 允许我们在“最新版本对所有”策略下强制机器人脱离已知的不良发布（在这种情况下，机器人只有在被手动触发时才会更新）：
- 在检查/启动时，如果运行版本 `< min_supported`，则更新 **强制执行** — `updaterd` 不会等待用户点击即可应用该更新（并且运行的旧版本可以被拒绝）。
- 一个更直接的 **紧急关闭开关**（一个签名的“版本 X 已撤销”声明）是该机制的升级版。签名意味着攻击者无法伪造一个 —— 但请参阅 §8.4：签名表示该文件是 **我们的**，而不是 **当前的**，因此仅签名并不能防止重放一个旧的真正有效的清单。
- 现在在模式中加入该字段（§5.3）；以后无法回补。
- `min_supported` 只会在机器人成功获取携带该字段的清单后生效。因此它是一个 *补救工具*，而不是一种防御手段：一个被切断更新的机器人永远不会知道最低版本的存在。

### 8.2 金砖发布与恢复

- 保留一个已知良好的 **金砖** 发布，该发布 *永不被清理*（与 `keep_previous` 旋转分开）。
- 如果当前和之前的版本都无法启动并运行健康，则回退到金砖，如果这也失败，则回退到一个最小的 **恢复模式**，该模式仍然可以连接网络并重新获取。机器人必须始终能够与服务器通信，而无需进行 RMA / 送修。

### 8.3 设备上的更新日志和运行转录

将最近 N 次更新尝试（时间戳、渠道、从→到版本、结果、错误）持久化到磁盘，并通过 BLE/HTTP 可检索。这是当客户端报告“更新失败”时，支持人员需要的第一件事。

日志回答了 *是否* 发生了尝试以及它如何结束。但它无法回答尝试 **做了什么**，而这个问题也有一个诚实的答案。

**为什么不是日志。** `updaterd` 将其重要事件记录到 systemd 中，对于观察更新过程来说这是正确的位置 —— `journalctl -f` 不需要任何额外的机制。但它不适合保存这些日志。在该板上 `/var/log` 是一个 zram 设备，因此 `Storage=persistent` 插件可以保证在干净重启后日志的生存，但无法保证在断电后日志的生存 —— 而需要这种功能的更新往往是那些以断电告终的更新。这也是将更新日志放在日志之外的第一个原因；转录是其第二个应用。

更糟糕的是，阶段时间线从未被记录在日志中。阶段仅作为 `update.progress` 通知发出，因此状态机的自我记录仅存在客户端保持套接字打开的时间内，而无人观看的 `robotctl update apply` 命令仅留下一个中间部分缺失的轮廓。
**What 一个运行记录的内容。**每个运行一个文件，`runs/<id>.jsonl` 在 `state_dir` 中，每行 `fsync`，遵循日志相同的规则 —— 在每个 `install_dir` 之外，这样一次交换或回滚不会破坏交换或回滚的账户（§5.7）：

- 运行的开始：目标以调用者命名的方式，来源，当时是什么状态，以及谁询问，来自 `SO_PEERCRED`；
- 通过签名检查的清单 —— 版本、哈希、大小、URL，哪一把受信任的密钥接纳了它，以及它构建的版本；
- 每个阶段边界，如果有详细信息，则记录详细信息，因此记录每个阶段所花费的时间；
- 无论成功还是失败，附带输出的退出代码，原封不动地记录挂钩输出；
- 每个单元的重启、重新加载或延迟，以及系统守护程序所说的内容；
- 健康门的裁决，这是决定提交还是回滚的依据；
- 它是如何结束的。

一条日志条目携带运行编号，因此两者组合的方式类似于 `git log` 和 `git show`：`robotctl update log` 是索引，`robotctl update show` 是详细信息。

**记录从不失败更新。**每次写入都是尽力而为的，并将失败报告给日志。一个已完成但丢失日志条目的更新比被放弃以保持日志条目诚实的更新要好。

**在其他地方结束的运行。**守护进程更新会重启 `updaterd` 本身，因此其转录设计上会在中途停止，裁决几分钟后并通过启动计数器试验到达。该回滚会开启 **自己的运行** 而不是重新打开第一个 —— 第一个进程已经不存在，无法追加。配对是可读的：没有 `ended` 的转录是一些裁决在其他地方的运行，`show` 在裁决本应出现的地方说明这一点，下一个运行就是那个裁决。在 `updaterd` 启动前由一个 shell 脚本执行的救援到黄金路径，从它留下的面包屑重建了一个薄薄的运行，标记为二手。

**界限。** 保留 20 个运行，每运行 4000 个事件和 2 MiB，每个事件 64 KiB。超过上限时，写入器停止并记录它丢弃了多少内容，结束无论如何都会被记录 —— 缺少尾巴的转录不应读作在那里停止的运行。`hooks::MAX_OUTPUT` 已经限制了最大的贡献者为每个挂钩 8 KiB，因此一个普通的守护进程运行是几个千字节。
**客户端拼接日志，而不是守护程序。** `robotctl update show` 运行
`journalctl --utc` 在运行的窗口内，并且仅针对运行本身指出其操作的单位进行范围限定，然后追加日志。读取系统日志是 `updaterd` 所具有的特权，而不应通过一个读取端未受限制的套接字将其借出——并且这是覆盖 *其他* 守护程序的那一半，而转录中从未涉及。没有日志访问权限的操作员将获得转录以及用于运行其余部分的命令。

### 8.4 签名能买什么，不能买什么：降级和冻结

一个 minisign 签名证明一个文件 **来自我们且未被修改**。它
并未说明 *何时* 发布或是否仍然有效。两种
攻击即使在完全有效的签名面前也能存活，它们是任何签名文件方案的标准配对：

| | 是什么 | 状态 |
|---|---|---|
| **降级 / 回滚** | 服务一个 *更旧但真正签名* 的清单，使机器人倒退到我们已撤回的版本 | **已修复** |
| **冻结** | 无限期地服务 *当前* 的清单，使机器人永远无法得知存在修复 | **开放**（§8.4.2）|

两者都可以通过任何控制机器人所获取内容的人达到：过时或已回滚的 CDN/镜像、缓存的代理、DNS 拦截或恶意本地网络。两者都不需要被盗用的密钥。

#### 8.4.1 降级 — 封闭

`updaterd` 在目标为“最新版本”时拒绝候选版本，如果候选版本比已安装的版本更旧：

- `Target::Latest` → 拒绝并返回 `WOULD_DOWNGRADE`。`check` 会报告其不兼容而不是提供它作为一个可用更新。
- `Target::Exact` → **允许**。这是如何实现目标回滚的方式，且是操作员的有意行为，镜像无法诱导。
- `rollback` 和 `reset-to-golden` 由于设计原因会向后移动，并使用已安装的版本，因此它们从不咨询清单。

这种不对称性是关键：门卫阻止攻击者可以导致的行为，同时允许操作员可以选择的行为。

#### 8.4.2 冻结 — 开放，需要决策

目前没有任何东西将“没有更新”与“有人阻止我看到更新”区分开来。机器人无限期地停留在一个易受攻击的版本上是实际的危害——它已经运行的相同版本，因此不会触发任何完整性检查。

选项，从最便宜的开始：

1. **签名的清单过期时间。** 添加 `not_valid_after`（一个时间戳）到清单中；拒绝任何比那更早的清单，并在应用中显示“更新元数据已过期”的提示。成本：发布变得时间限制——即使没有版本变更，CI 也必须定期重新签名 `stable` 清单，否则每个机器人都会发出警告。这还依赖于机器人的时钟，而 §7.2 的时钟检查正是为了不信任这种时钟而存在的。
2. **单调递增的清单计数器。** 一个只递增的 `sequence`；机器人记录已见过的最大值，并拒绝任何更低的版本。无需依赖时钟即可稳健地检测元数据的回滚，但 **不** 能检测冻结（重放当前的清单具有预期的序列号）。
3. **报告过期而非强制执行。** 记录“上次成功的清单获取时间”并在 `status`/应用中显示： “上次检查 47 天前”。不进行任何加密检测，但使冻结的机器人对其所有者和支持人员可见。没有发布负担，也没有时钟依赖。
4. **电话回家**（§17）。报告的机器人让我们能够看到哪些机器人停止了检查——这是唯一一个能够集中检测冻结而非每个机器人单独检测的选项。需要后端支持。

**推荐：先实施 (3)，当有版本发布周期时再实施 (1)。** 过期时间报告几乎不产生成本，没有自身失败模式，并将无声的攻击转化为可见的攻击。过期时间是真正的防御手段，但其操作成本——如果错过，则会警告整个舰队的重新签名计划——在发布流水线成为常规之前不值得支付。选项 (2) 较为廉价，但解决的问题 §8.4.1 在版本级别已经覆盖了。

**明确接受 v1：** 如果网络敌对，可以防止机器人更新。它不能被强迫降级、安装未签名的文件或安装未通过健康检查的文件。这些才是我们真正依赖的属性。

## 9. 安装后钩子

与 dpkg `postinst` 类似，但钩子被包含在（已签名的）tarball 中，因此从不运行任何未签名的代码。可以是 Rust 二进制文件或 shell 脚本——引擎会直接 `exec` 运行它。
**合同**
- 在符号链接交换之后、`apply` 之前运行。（如果存在 `pre_install` 挂钩，则在交换之前运行。）
- `pre_install` 挂钩比 `post_install` 挂钩有更多的执行时间限制——前者为十分钟，后者为两分钟。`pre_install` 挂钩用于安装当前发布需要而板子可能没有的内容（例如 ONNX 运行时；`mediad` 所需的 GStreamer 依赖，大约为 100 MB 的 apt 包），并且它可以承受分钟级别的执行时间，因为此时还没有进行交换：旧版本仍然处于活动状态并提供服务，因此长时间的 `pre_install` 只是缓慢更新而不是机器人处于不确定状态。
- 非零退出码表示更新失败，将触发回滚。
- 提供的环境（缺失的值将被省略，而不是设置为空，因此挂钩可以区分“首次安装”与“未知”）：
  - `UPDATE_COMPONENT` / `UPDATE_CHANNEL` — 组件名称；两者均设置且值相同
  - `UPDATE_NEW_VERSION`，以及当存在先前发布时的 `UPDATE_OLD_VERSION`
  - `UPDATE_RELEASE_DIR` — 正在安装的发布版本，`<install_dir>/releases/<ver>/`。**这通常是迁移所需的内容**，也是挂钩的工作目录。
  - `UPDATE_INSTALL_DIR` — 组件根目录，例如 `/opt/robot/daemon`
  - `UPDATE_NEW_SCHEMA_VERSION`，以及当已知时的 `UPDATE_OLD_SCHEMA_VERSION`
- 挂钩以 **清除的环境** 和固定的 `PATH` 运行，因此行为不会依赖于 `updaterd` 如何由 systemd 启动。
- 输出被捕获并截断，并以任何方式到达更新日志：在失败时作为错误的一部分，在成功时逐行记录（`updater/src/hooks.rs`）。成功时记录日志，因为 `pre_install` 挂钩的报告——哪些插件、哪个运行时、这块板子是否有 NPU——是“在当前发布版本下，这个机器人实际上可以做什么”的答案，一次 `journalctl -u updaterd` 的 grep 在一个挂钩显然运行过的板子上返回了空结果。
- 典型用途：安装当前发布需要而板子可能没有的内容（§9.1）、配置模式迁移、`udev`/权限调整、`schema_version` 升级时的数据转换。

### 9.1 如果是全新安装，挂钩也会执行
**一个发布未安装直到它所需的一切都已就位。**将文件放入发布目录并不等于安装；将脚本放入发布目录并不等于运行。钩子是唯一在每次更新时在每个板上运行的东西，因此“此板在此次发布生效前必须具备X”应属于钩子——而不是在X存在之前仅运行一次的配置脚本，也不是在人类的记忆中。

**问题不在于发布是否需要它。而在于全新安装是否需要它。**“需要”是一个判断，它已经放过了一个案例：一个将机器人名称放入命令行提示的片段并不是发布 *需要* 的东西，因此它进入了`install.sh`，而没有出现在任何地方，而且从未更新过的板上也没有它。相反，应该提出机械性的问题——**`scripts/install.sh`是否写入了此文件或运行了此命令？**——因为这个问题可以通过grep单个文件来回答，并且一个非全新板上获得的正是钩子所做的事情，而没有其他东西。

这已经被搞错了四次，以四种不同的形式。
1. **单位。**一个增加了守护进程的发布在其.artifact中包含了`.service`文件，而systemd查找的地方没有。`btd`在一块板子上失败了，这块板子的发布是完整且正确的，`on_apply`无法重启一个尚未存在的单位。`docs/project/install-path-gap.md`是关于这个问题的文档；`hooks/postinstall`是修复方案。
2. **GStreamer堆栈和3A引擎。**预置安装了它们，因此在它们存在的之前被预置的板子没有这些，同样，一个插件比发布的构建版本更旧的板子也没有它们。`hooks/preinstall`在每次更新时运行发布的`setup-gstreamer.sh`和`setup-rkaiq.sh`，这正是解决问题的方法。
3. **NPU。**增加鸭子检测器的分支编写了`setup-npu.sh`，将其打包在发布中与模型一起——但从未调用过。直到有人通过SSH登录，每块板子都会发货一个无法访问NPU的检测器。找到这个问题的方法是`rknn_init`返回一个数字。
4. **登录shell。**`install.sh`增加了一个`/etc/profile.d`片段，将机器人的名字放在主机名旁边——`microduck@radxa-zero3 (coincoin):~$`——这样三个SSH窗口连接到三只鸭子就不会有三个相同的提示符。除了这个片段外，没有其他东西安装它，`install.sh`也没有被打包进发布中，因此没有钩子可以做到这一点。在`install.sh`编写之前被预置的板子在之后的每次更新中都没有获得它；找到这个问题的方法是在包含该功能的发布中，`ls: cannot access '/etc/profile.d/robot-name-prompt.sh'`。

每次的结构都是一样的：工作已经完成，但使工作到达板子的东西被遗漏了。在审查中是看不见的，因为添加脚本的差异看起来是完整的。

第四点增加了它看起来正确的可能性。`install.sh`中的两个邻居——登录横幅和`robotctl`补全——也有同样的缺口并且更旧，因此周围的代码看起来是遵循的模式。连续运行三次仅由全新安装运行的功能并不是先例；它们是三个实例。

**推论。**
- **任何`install.sh`对板子所做的操作，钩子也会做。**其他三个都是这种模式的实例，而错误实际上发生在`install.sh`增加了一个步骤，这个步骤在准备板子的过程中很容易测试，但更新路径却从未得知。`install.sh`不在制品中，钩子也无法调用它，因此共享的步骤应该放在`scripts/setup-*.sh`中——这就是`setup-gstreamer.sh`和`setup-login.sh`的作用。`every_install_sh_step_reaches_an_updated_board`会读取`install.sh`的调用点并失败，除非每个步骤要么由钩子执行，要么写明原因，说明这是仅在初次安装时才会执行的操作。这是一个强制机制而非证明——逃生出口是一张表格中的某一行——但所有四个实例都必须为此行辩护，而它们中的任何一个都无法做到。
- **钩子步骤必须是幂等的，并且在没有需要执行的操作时必须便宜。**因为这种步骤会在每次更新时在每个板子上运行，而不是只运行一次，所以“已经完成”是正常情况而不是例外。其次，因为每次更新的成本都会累积：一个已经安装了所有内容的板子上花费十秒的步骤会在每次未来的发布中增加十秒，而钩子阶段会因为每个功能增加一个步骤，而预算却没有增加。预安装阶段的预算为600秒（`UPDATE_MAX_SILENCE_SECONDS`，与每个客户签订的合同——这是apply可能保持静默的最长时间），而安装后的共享预算为120秒，与单元、账户和重启共享。有效的方式是一个印章：`setup-npu.sh`将运行时版本写入`/usr/lib/librknnrt.version`并进行比较，`setup-gstreamer.sh`进行印章比较和两次`dpkg -s`调用，两者在已经设置好的板子上都不会产生可测量的影响。
- **钩子运行的脚本必须被打包。**`every_script_the_hooks_run_is_packaged`会从钩子中读取`script=scripts/…`的赋值，并在任何打包站点遗漏一个时失败。
- **脚本需要的内容必须随脚本一起携带。**`setup-rkaiq.sh`从旁边的一个C文件编译一个LD_PRELOAD shim；`setup-npu.sh`从旁边的一个`.dts`文件编译一个设备树overlay。每个都有一个测试来说明这一点，因为失败是无声的：脚本运行，找不到其源代码，更新成功，日志中只有一个警告。
- **可选硬件的缺失永远不会致命。**从挂钩返回非零值会失败更新并回滚，因此挂钩只能因意味着发布不可安装的事情而失败。一块没有摄像头、没有蓝牙适配器或没有NPU的板子仍然是一个机器人；这些安装步骤说明了丢失了什么，命名了重试的命令，并返回成功。

**这就是为什么需要区分预配置和更新的原因。**`provision.sh` 和 `install.sh` 用于设置新板子，并且只会运行一次。在某物存在之前预配置的每块板子都可以通过普通的更新来修复——这意味着一个发布可以假设其板子的预配置时间点，而只由预配置执行的设置步骤对一半的设备来说都是无效的。

## 10. 可重用、配置驱动的引擎

引擎在所有机器人中是相同的；每个机器人都会提供一个声明其组件的配置。适应新机器人 = 新配置 + 新签名密钥 + （可能）一个新的健康探测。

权威且可解析的示例是
[`updater/updater.example.toml`](../../updater/updater.example.toml) — 一个单元测试会解析它，因此它不会偏离代码。简化如下：
```toml
# /etc/robot/updater.toml
trusted_keys_dir = "/etc/robot/trusted_keys"   # a *set* of keys (§5.4)
hw_rev           = 1
state_dir        = "/var/lib/robot/updater"    # must be outside every install_dir

[component.daemon]
install_dir   = "/opt/robot/daemon"
keep_previous = 1
golden        = "1.0.0"

[component.daemon.source]
type       = "github_releases"
repo       = "ORG/robot-daemon"
tag_prefix = "daemon-v"

[component.daemon.on_apply]
action = "restart"
units  = ["robotd", "mediad"]                  # never updaterd or btd — see §4

[component.daemon.health]
probe   = "socket"
path    = "/run/robotd.sock"
timeout = "30s"

# One component per model — each versions independently (§5.5).
[component.model-walk]
install_dir   = "/opt/robot/model/walk"
keep_previous = 3

[component.model-walk.source]
type     = "hf_hub"
repo     = "ORG/gait-walk"
revision = "main"

[component.model-walk.on_apply]
action = "reload"                              # never drops motor control
unit   = "robotd"
signal = "SIGHUP"
```
Config 在加载时会被验证，并且 `deny_unknown_fields` 为启用状态，因此一个拼写错误会响亮地失败，而不是默默地禁用原本打算更改的设置。值得注意的是，被拒绝的有：`state_dir` 在 `install_dir` 内（一个交换会破坏更新日志），两个组件共享一个 `install_dir`，相对路径，以及 `keep_previous = 0` 且没有金钥（没有回滚目标）。

注意，模型使用 `reload`（SIGHUP → 重新-mmap 权重）而不是 `restart`，因此在模型切换时不会中断电机控制。每个组件的 `on_apply` 是使这一过程自然进行的核心原因，也是两个通道保持分离的主要原因之一。

跨机器人的共有部分：引擎、minisign 管道、电话/BLE 触发协议、回滚逻辑。每个机器人的共有部分：配置文件、签名密钥、健康探测、钩子。这只是一个小型二进制文件加上一个模式，而不是一个框架。

## 11. 操作系统更新（有意排除在 OTA 之外）

跳过 A/B 测试有一个实际约束：我们不会通过 OTA 更新内核/系统库。
缓解措施：
- 仅针对 Debian 的 **安全** 包启用 `unattended-upgrades`，用于 CVE 修复。设置并忘记。
- 任何更大的更新（内核版本更新，新系统库，守护进程需要的）= **在服务时间重新刷写**。
- 尽量减少对基础操作系统的运行时依赖：静态链接，将尽可能多的内容打包到 tarball 中，这样即使使用默认操作系统也不会阻塞守护进程的更新。

### 11.1 周边 / MCU 固件 —— 有意排除在 OTA 之外

子板和伺服固件在生产时刷写，不在现场进行。不是 OTA 组件；没有为其预留空间。（如果将来有所改变，它会成为一个 `on_apply` 通过电机总线刷写的组件——这在回滚时会更加危险，因为回滚意味着重新刷写而不是简单的符号链接替换。）

## 12. 替代方案：apt / dpkg（自有签名仓库）

对于 Debian 上的 **守护进程** 通道，仍然值得保留这个选项：

**优点**
- 签名（GPG）、原子安装、版本控制，以及 **维护者脚本** (`preinst`/`postinst`/`prerm`/`postrm`) — 我们想要的安装后钩子 —— 全部免费且经过实战验证。
- 标准的 Debian 工具；易于推理；`apt` 处理依赖关系。

**我们的案例中的缺点**
- 没有健康监护回滚，也没有干净的“回滚到先前版本”的功能；我们无论如何都会构建这些功能。
- 对于分发 ML 模型作为普通版本化资产来说有点棘手。
- 不携带电话触发 / 进度 IPC —— 仍然需要封装。
- **可移植性**：在未来的非 Debian 机器人（Yocto 等）上不存在，这与“跨机器人使用共同工具”的目标相悖。
**当 apt 适用时：**如果决定未来一段时间内仅使用 Debian，并且愿意放弃自动健康门限回滚（或通过 `apt install pkg=old` 强制回滚），自签名 apt 仓库对于守护进程二进制文件来说确实是一个更简单的路径。该模型仍然需要一个侧通道。建议：从可移植性 + 回滚的自定义 Rust 引擎开始；如果 Rust 引擎的维护成本最终超过其带来的好处且舰队仍仅使用 Debian，则重新考虑 apt。

## 13. 电话 / BLE 触发协议（草图）

`btd` 每个通道暴露两个 GATT 特性（或一个带有通道字段的特性）：
- **触发**（写入）：`{ "cmd": "check" | "apply", "channel": "daemon", "version"? : "…" }`
- **状态**（读取/通知）：`{ "channel", "state": 空闲|检查中|下载中|应用中|健康|失败|已回滚, "progress": 0-100, "version", "error"? }`

`btd` 通过 Unix 套接字转发给 `updaterd`，并镜像其状态。
载荷从不通过 BLE 传输。

## 14. 实现草图

`updaterd`，一个小型 Rust 二进制文件（约几百行逻辑）：
- `reqwest` — 下载（带断点续传/重试） + GitHub API 用于查找最新标签。
- `minisign-verify` — 签名验证。
- `tar` + `zstd` — 解压。
- `serde` / `toml` — 配置；`serde_json` — 表现形式。
- 通过 `rename(2)` 进行原子符号链接替换；通过现有 Unix-socket IPC 进行健康检查。
- `systemd` 集成：`Type=notify`，`WatchdogSec`，单元模板。

CI（每个通道）：
1. 构建产物（可选地通过 `cargo-dist`）。
2. 使用 `minisign -S` 对产物和表现形式进行签名。
3. 创建一个带有产物、`.minisig` 和 `manifest.json` 作为资产的 GitHub 发行版 `daemon-vX` / `model-vX`。

## 15. 好邻居（在范围之内）

廉价的附加功能可以无缝集成到相同的 IPC / 引擎中，并带来好处：
- **可重用的健康自检模块。** 一个探测器（电机确认、模型加载、媒体初始化）被两个调用者调用：启动时和更新后作为健康门。这是“机器人是否正常”的单一来源。
- **`robotctl` 本地命令行界面。** 一个通过 `updaterd` 的 Unix 套接字实现的轻量客户端 —— 它的角色与 `btd` 相同，但传输方式不同；它自身不包含任何更新逻辑。用于支持、现场恢复和 CI。
  命令命名空间化（`robotctl update …`），后续命名空间是可叠加的：`check`，`apply [--version|--dry-run]`，`rollback`，`reset-to-golden`，`select`（如何切换模型捆绑包），`pin`，`status`，`log`，`watch`。仅实现了 `update` 命名空间。
- **开发侧载路径。** 接受一个用 **dev key** 签名的 artifact（该 key 在受信任集中但被一个标志 / 开发版构建所限制），这样团队可以不接触生产签名就刷写本地构建（参见 §5.4）。
  **构建。** `robotctl update apply --from <dir>` 为一次调用覆盖了源路径，因此发布物来自板上的一个目录，而其余所有关于应用的内容保持不变 —— 预检、签名、哈希、兼容性、健康门、自动回滚。`scripts/dev-push.sh` 是整个路径：跨编译、打包、签名、复制、应用。它不做两件事，都是故意为之：它不是 `updaterd install --from`，后者强制 `on_apply` 和门关闭，因此不能用于生产发布；它不放松验证，这就是为什么它需要在板上有一个 dev key 而不是跳过一个检查的标志。降级保护对 `--from` 的处理与对 `--version` 的处理相同 —— 操作者命名一个目录并不意味着镜像已经倒退，而本地构建是一个预发布版本，其排序低于板上运行的任何内容，因此保护它会拒绝每次推送。
  对目录有一个约束，而不是由引擎本身设置：`updaterd.service` 设置 `PrivateTmp=yes`，这为单元提供了一个独立的 `/tmp` **和** 独立的 `/var/tmp`，因此从 shell 复制到任一目录的发布物不是守护进程读取的发布物。这就是为什么侧载目录生活在板用户家中，以及为什么 `Check::SideloadDir` 存在 —— 没有它，失败的原因是一个目录中的清单缺失，而该目录的 `ls` 列出了它，这从外部是无法证伪的。
- **BLE  provisioning 安全性。** 相邻但同样重要：Wi-Fi凭据传递
- 在设置过程中通过BLE传输。该特性必须进行配对并加密，否则就会发生凭证泄露。更新文件是经过签名的，因此伪造的*触发器*风险较低，但*配置*写入必须经过认证。请确认`btd`已经强制执行这一点。

## 16. 发布测试与信心

**动机。** 在之前的机器人上，发布是通过手动验证——手动回滚到已知版本，手动应用新版本，手动检查。存在太多的人为错误空间。在此的设计目标是：**使更新路径可脚本化和自动测试，以便向客户发货是一个*决策*，而不是手动操作。**

关键构架：大部分的人为错误表面（回滚 → 应用 → 验证）存在于更新*机制*中，这是一个纯软件部分，并且可以在CI中通过**无需硬件**的方式进行测试。只有真正依赖硬件的行为才需要实际的板子。

### 16.1 测试设计

- **真实的代码路径针对测试数据。** `updaterd` 从配置中读取其源代码/清单文件，因此测试会将其指向本地目录或`staging`通道，并驱动*生产代码*——没有与现实脱节的模拟更新器。
- **可脚本化且幂等的基本操作**（通过`robotctl`，§15）：`apply --version X`，`rollback`，`pin <version>` / `unpin`，`model select`，**`reset-to-golden`**。之前的痛苦是没有一个干净的“直接跳转到具体版本”的命令——这些就是它。所有**非交互式**：没有提示，没有任何操作员需要回答的内容。
- **`--dry-run`：** 运行获取/验证/兼容性/空间检查并停止在交换之前。
- **故障注入挂钩：** 强制失败的健康探测、损坏的文件、非零挂钩或交换中途被杀掉的标志——这样回滚可以被*测试*，而不仅仅是假设。

### 16.2 两级测试

**第一级——机制测试（CI，无需硬件，快速）。** 每个PR都会运行；这本身就能消除大部分的手动回滚风险。覆盖自动：

- 签名有效/无效/错误密钥 → 接受/拒绝
- 哈希校验不匹配 → 拒绝
- `min_hw_rev` / `model_api` 不兼容 → 清晰标明状态后拒绝
- 有效签名但较旧的manifest被当作“最新”提供 → 作为降级拒绝处理（§8.4.1），而显式版本降级仍然允许
- `rollback` 从不会停留在刚刚失败的版本，也不会停留在日志记录中被回滚的版本
- 启动计数器试验按组件进行：一个组件的过渡不能消耗另一个组件的预算
- **机器人特定状态**在更新和回滚过程中保持一致：校准、生成的资产、学习状态、用户偏好均完好无损（§5.7）
- 健康更新 → 提交 + 清理
- 健康探测失败 → 自动回滚；机器人在旧版本上保持健康
- 挂起挂钩非零退出 → 回滚
- **交换中途被kill -9 / 模拟断电** → 重启后状态一致，从不会出现半生不熟的发布
- 磁盘满 → 在任何变更前中止
- 同时触发 → 单一飞行；第二个报告忙
- **`robotd`缺失/循环崩溃** → `btd`和`updaterd`仍然服务；更新、回滚和恢复到出厂设置全部完成（§4.1）。包含一个“从故意破坏的发布中恢复”的测试——它锻炼了最关键路径。
- `robotd` IPC 挂起（套接字打开，无回复） → 超时，而非停滞
- 版本矩阵：从A升级到B，跳过A直接到C，从B回滚到A，跨越`schema_version`跃迁时的迁移

一级驱动程序使用内置的`FakeRobot`实现`RobotClient`来驱动引擎。这是测试引擎*决策*的正确方式——一个假的机器人可以是不健康的、挂起的或缺失的，所有这些都不容易在现实中进行模拟。但它从不序列化任何内容，因此它完全看不到网络。

**一级B —— 针对一个真实的`robotd`进程**（`robotd/tests/updater_gate.rs`，仍然在CI中，仍然没有硬件）弥补了这一点。它启动实际的二进制文件，并让真实的`SocketRobotClient`通过一个真实的Unix套接字与它通信：引擎调用的每个方法都必须以它解析的形状返回，更新必须被门控并提交，`robotd --unhealthy`必须恢复`current`背后的*内容*，而不仅仅是符号链接。

没有任何其他内容覆盖这一点。协议库自身的往返测试无法检测偏差，因为双方共享了结构；`robotd`中的`dispatch`级别单元测试可以廉价地捕捉到改变的回复形状，但只有真实进程才能锻炼到套接字本身。
**Tier 2 — 本地设备接受（ Canary 机器人）。**依赖硬件的行为（步态、电机、媒体）需要真实的板卡。保留几台 **实验室/ Canary 机器人**，跟踪 `staging`，自动更新每个候选版本，运行一个脚本化的接受测试（电机扫描、步态烟雾测试、媒体初始化、健康自检），并报告通过/失败以及更新日志。因为可以通过脚本进行复位到黄金状态和 `apply --version`，所以是可重复的。

### 16.3 渠道与推广

**实现**为三个 GitHub Actions 工作流加上一个 `cargo xtask` 发布者（`.github/workflows/`，`xtask/`）：

| | |
|---|---|
| `ci.yml` | 格式化、clippy、测试，加上 `board-test.sh` —— 唯一证明二进制文件在 aarch64 Linux 上运行的作业 |
| `release.yml` | 在 `daemon-staging-v*` 标签上：交叉编译、打包、签名、**使用机器人的自身代码路径验证**，发布一个预发布版本 |
| `promote.yml` | 手动：重新签名一个 *稳定* 的清单，将验证过的文件复制到稳定发布版本，退役 staging |

发布者是一个 Rust `xtask` 而不是一个 shell 脚本，原因只有一个：它重用了更新器验证所需的 `minisign`、`tar`、`zstd` 和 `sha2` 箱子。一个 shell 版本会依赖于单独安装的二进制文件，其行为可能会与机器人接受的行为不同——这是不应该隐藏差异的最后地方。它还链接了 *完整* 的 `minisign` 箱子（可以签名）而守护进程只链接 `minisign-verify`（不能签名）。

三个值得陈述的属性，因为每个属性都是断言而不是假设：

- **推广从不重建。** 稳定的清单携带 staging 的 `sha256`，推广在检查该摘要后将 staging 的文件复制到稳定发布版本，因此客户端接收到的字节是 Canary 验证过的字节；一个测试断言摘要未变。
  用于指向 *预发布* 版本而不是复制的清单，原因是同一组字节在复制时可能会有所不同，而在预发布时不会。但忽略了一点，即机器人在安装前会验证 `sha256`，因此复制的字节如果不同，也无法无声地安装——而一个稳定的通道，其构件生活在以脚手架命名的标签下，只需一次清理操作就可能失效。它确实失效了：删除 `daemon-staging-v0.1.x` 发行版后，`daemon-v0.1.0`、`v0.1.1` 和 `v0.1.4` 正确地被签名并指向 404。稳定的发行版现在是自包含的，预发布版本由 `promote.yml` 本身废弃。
- **构件可重复生成。** 压缩包中的时间戳修复后，相同的输入会生成相同的存档，因此可以将重建的存档与已发布的存档进行比较；一个测试断言两个相同输入的包的哈希值完全相同。
- **`release.yml` 在发布前验证。** 它通过实际的引擎 (`updaterd install --from`，通过 `LocalDir` 源) 安装发布，并断言二进制文件可执行。如果更新器无法接受一个发布，那么没有人可以下载它。

存在两个防护措施，因为这两种错误都很容易发生：`package` 拒绝一个与 `Cargo.toml` 不匹配的 `--version`（未更新版本号就打标签），而 `promote` 拒绝一个与预发布清单不匹配的版本。

- 通道：`预发布` → `稳定`。CI 将候选版本发布到 `预发布`。
- 一个哨兵机器人以 **一个标志，对应一个命令** 的方式处理候选版本：

  ```
  sudo robotctl update apply daemon --staging
  ```

  早期的草稿中说哨兵“自动拉取预发布版本”，但按原样实现是不可行的：`newest_version` 会跳过 GitHub 标记为预发布的所有内容，以及任何带有 semver 预发布组件的内容。这个过滤器正是阻止客户机器人访问候选构建的原因，因此它仍然存在，`--staging` 是唯一的启用选项——在 `staging_tag_prefix` 下的第二次扫描，允许 GitHub 标记同时排除 semver 预发布版本，这样分支构建永远不会被误认为候选构建。`latest_manifest` 未受影响，因此 `auto_apply` 和周期性检查继续解决稳定问题：没有任何人和 root 的干预，不会有任何东西意外地漂移到候选版本中。

最初尝试的方式是将一个指向预发布的板子通过编辑 `tag_prefix` 来实现，它报告 `在 … 中没有带有标签前缀 "daemon-staging-v" 的发布`，而一个候选版本就坐在那里——前缀指明了要查找的位置，而预发布过滤器拒绝了查找。
  **`--staging` 拒绝当通道落后于板子。** 一个直接推广到稳定版的发布不发布候选版本 — 这是一个支持的路径，也是 `release.yml` 标注为“未 Canary 测试”的路径 — 因此， staging 扫描继续回答上次发布的版本。在板子已经过那个版本的情况下，`--staging` 以前会安装它：验证后，替换，然后当一个旧版发布不包含的守护进程无法启动时回滚。回滚是正确的，没有说明原因，所以解决的候选版本现在会与已安装的版本进行比较，并拒绝两个版本。`--staging --version X` 是未受保护的，是绕过的方式 — 操作员命名一个候选版本表示其意图，这也是板子刚刚回滚后重新安装的方式。
- 在绿灯情况下，**推广**：将 `stable` 重新指向已经验证过的 *相同字节* — 重新签署 `stable` 的清单以引用相同的 tarball + 哈希。无需重建，无需重新刷写，无需手动复制文件。推广只需一个命令 / 一次点击，并发送经过测试的完全相同的版本。
- 无效的 `stable` → 逆向操作：将 `stable` 重新指向先前已知良好的清单；`min_supported`（§8.1）会在修复提交后将机器人向前推进。
### 16.4 来源

`version.toml` 和更新日志记录每个文件的 git SHA + 哈希，因此“客户端正在运行的确切版本”在实验室中总是可以复现的。

这关闭了上次造成问题的循环：**人类决定是否进行推广；机器每次都以相同的方式回滚 / 应用 / 验证。**

### 16.5 启动状态 — 健康门之后，不是负载之后

`daemon` 文件仍然比最终版本少：`bin/updaterd`，`bin/robotctl`，`bin/robotd`，`version.toml`。尚未包含 `mediad` 或 `btd`。

这不是循环：§4.1 确立了 `updaterd` 和 `btd` 包含在 `daemon` 文件中，因此使用更新器更新更新器是最终的流程 — 也是最危险的流程。首先执行它是§9 构建顺序的目的。

`updater.example.toml` 中的两个设置直到有东西可以限制它们之前都是惰性的。现在它们都生效了：

| | 以前 | 现在 | 仍然待办 |
|---|---|---|---|
| `on_apply` | `none` | `restart` 附带 `["robotd", "configd"]` | — |
| `health` | `none` | `socket`，30s | 超时是一个猜测，直到 M4 测量出真正的启动时间 |
`mediad` 需要在旧的权威列表中添加一个条目，但现在不需要了：重启集是从发布的单元文件中导出的，跳过了没有 `[Install]` 部分的单元文件，而 `mediad.service` 有一个 `[Install]` 部分。因此，应用重启会启动它，而从未运行过的机器人会在下次安装时启用它——规则是单元文件，而不是任何人维护的名称。

**`health = none` 是设计中最弱的选项**：它在交换成功后立即提交，因此根本没有自动回滚机制，只剩下了启动计数器作为唯一的恢复机制。离开这种状态就是 M1 的用途。

将示例配置固定为惰性值的单元测试现在断言相反的情况：`on_apply` 必须重启 `robotd`，但必须 **不** 重启 `updaterd` 或 `btd`（§4.1），并且 `health` 必须是一个套接字探测。将 `health` 重置为 `probe = "none"` 会无声地禁用自动回滚，而看起来只是一次单字符的差异，这正是需要单元测试来阻止的更改类型。

**尚未测试的内容**：`on_apply` 中的 `systemctl restart` 从未在实际的 systemd 上运行过——开发笔记本上没有 systemd，而模拟它会测试模拟本身。健康门本身确实是在一个实际的 `robotd` 进程和一个实际的套接字（`robotd/tests/updater_gate.rs`）上进行了测试，因此未证明的是重启步骤和 30 秒的超时。两者都将在 M4 阶段在 Radxa 上实现。

## 17. 开放问题 / 未来

- **配置所有权。** 配置目前随模型捆绑包一起提供。是否应该将配置归属于守护进程通道，或者成为其自己的小型通道？无论哪种情况，模式迁移都由挂钩处理（§9）。
- **最小的“是否成功”回传。** 管理是延迟的，但每次更新时只需一次成功/失败回传，可以让我们及早发现不良版本，并且是 `min_supported`（§8.1）在实践中可操作的原因。值得吗？
- 阶段性发布 / 仪表板 / 仪表：明确推迟；如果 Fleet 扩展，则重新考虑。
- 差分更新：推迟；当前频率下，补丁包很小。

此文档与实现之间的已知差距，故意保持开放：
- **一个模型槽内不支持竞争的替代方案。**每个模型是一个组件，包含一条版本线（§5.5），这涵盖了“行走、跳跃和站立每个更新独立进行”。它不涵盖“安装两个不同的行走模型，用户选择一个”。这需要一个 `(name, version)` 存储键，这会波及大约14个文件——`Store` 的键值方法、`known_bad`、`PendingUpdate`、`Pins`、`golden`、`pinned` 以及网络类型（因此需要一个 `API_VERSION` 激增）。它还会将四个东西从每个捆绑包变为全局：修剪计数、回滚目标、“最新”和金色。直到确定需要时再进行；猜测这四个东西是如何导致删除的 `Layout::Library` 的。
- **无法发现可安装的模型。** 应用可以列出已安装的内容，但没有任何 `Source` 可以回答“可以安装什么”——添加一个模型意味着今天需要编辑配置。需要一个 `Source::list_*` 操作。
- **没有恢复模式。** §8.2 的链是 `current → previous → golden`，所有三个都已实现，包括对缺失或已知不良的先前版本的升级。最终的“最小恢复模式，仍然可以重新获取”并不存在。
- **一个 `RobotClient` 为所有组件服务。** 对于 *哪个探测要运行*，`HealthCheck::Socket { path }` 被尊重，但套接字路径本身来自 `main` 构造的内容。只要两个组件都探测 `robotd` 就没问题；如果一个组件需要不同的对等方，就会陷入陷阱。需要一个为每个组件的客户端。
Still open:
- **通过电话交付的替代品** — 对于没有可用互联网的机器人：从未预配、 captive portal、被封锁的 CDN、离线演示站点。引擎端几乎免费，因为 `LocalDir`（§15, §16.1）已经通过实际的验证路径应用了一个包含清单 + 艺术品 + 两者 `.minisig` 的目录，而签名使得交付传输在本质上是不可信的。成本完全在于链接，该链接必须是 wifi 或 USB（§3.1）。两种形态，它们解决了不同的问题：机器人托管一个 AP 供电话连接（不需要机器人的凭据，但电话必须在连接前通过蜂窝网络获取发布内容，而两种移动操作系统都抵制没有互联网的网络），或者——当 wifi 可用但 CDN 不可用时——电话通过局域网推送，这要便宜得多，但会增加一个面向网络的摄入监听器。该监听器的破坏范围由签名验证所限制（未签名的上传无法安装；最坏的情况是填满磁盘），但它仍然需要一个令牌和一个明确的绑定（`architecture.md` §2.2）。这是一个备用计划，而非 v1 版本。
- **清单陈旧报告**（§8.4.2）——在 `status` 和应用中显示“上次成功检查 N 天前”，将静默的冻结攻击转化为可见的攻击。成本低廉；推荐。签名清单过期是真正的防御手段，但会带来重新签名的时间表，直到发布成为常规。
- **配置所有权** — 配置是与模型捆绑包、守护进程一起携带，还是成为其自己的小型通道？（挂钩处理迁移方式，无论哪种情况，§9。）
- **最小成功/失败电话回传** — 每次更新一次 ping 可以让我们及早发现不良的发布内容，并使 `min_supported`（§8.1）在实践中变得可行。值得做，还是 v1 版本太多？
- **行为/大脑层** — 如果更高层次的行为层（驱动、情绪、习惯）最终以独立的文件形式发布，它将成为第三个通道，具有自己的兼容性约束。其学习状态也是 §5.7 的主要内容。

明确不做的：硬件变体矩阵（§5.6）、外设固件 OTA（§11.1）、分阶段发布 / 诊断、增量更新。

自首次草稿以来决定：分拆托管（GitHub + HF Hub）；`min_supported` 在模式中的底线；模型 *捆绑包带有命名插槽* + `model_api` 兼容性；多个可信签名密钥；单一硬件目标；机器人特定状态保存（§5.7）；配置存储在文件中而不是 systemd 单元中。
