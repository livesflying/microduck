# 应用路径 — `btd` 和 `configd`

状态: 草案 · 日期: 2026-08-04 · 负责人: pierre

手机如何配置机器人：WiFi、名称、重启、版本以及触发更新。

参见配套文件[`architecture.md`](architecture_zh.md)，它负责服务拆分和横切面契约。这部分涵盖了同时落地的两个服务，因为 **它们是一个功能**，每个决策都会相互制约：`btd` 没有拥有任何东西，因此 `configd` 存在；`configd` 提供了一个 PIN，因此 `btd` 可以配对；`btd` 中路由的方法是 `configd` 必须回答的方法。

这里指的是机器人的一端。另一端的手机是 [`mobile-app.md`](mobile-app_zh.md)。

标记为 **测量** 的部分是在 Radxa Zero 3W 上建立的，而不是通过推理得出的。

**路径在硬件上端到端工作**（2026-08-05）：一台 Mac 发现了机器人，进行了配对，读取了 API 版本，传递了 PIN，得到了真实的 `system.info` 回复 —— GATT 发现，双向分块 NDJSON，PIN 门，路由表以及通过其 Unix 套接字跳转到 `configd`。`configd` 也针对真实的 NetworkManager 做了回答，报告了实时的 SSID 和地址。

尚未实现的是：连接没有加密（§5.5），`net.connect` 还没有通过 BLE 驱动，也没有用手机而不是笔记本进行过测试。

## 1. 形状
```
        phone ──BLE──▸ btd ──┐
     robotctl ──unix socket──┼──▸ configd ──D-Bus──▸ NetworkManager   (wifi)
    (mediad) ──WebSocket────┘                    └──▸ logind          (reboot)
                             │                    └──▸ config file     (name, PIN)
                             └──▸ updaterd  (update.*)
                             └──▸ robotd    (robot.health)
```
Two 规则来自 `architecture.md`，产生这一结果，且没有其他自由变动的空间：

- **§4.1: `btd` 拥有 nothing。** 如果配置或配置项存于 BLE 服务中，其他每个服务都会依赖它，而一个 SDK 必须通过蓝牙来设置机器人的名称，这显然是荒谬的。
- **§3.1: 配置必须在 `robotd` 死亡时可访问。** 在机器人损坏时，配置 wifi 正是所需，因此配置不能存于控制守护进程之中。

两者之间没有服务可以放置 `net.*` 和 `system.*`，因此需要第五个服务。

**大部分工作并非蓝牙相关。** API 表面及其拥有者的服务在手机应用、SDK、`robotctl` 和 `mediad` 的远程网关之间是相同的。`btd` 只是一个薄薄的管道——而这一声明的测试是，添加七个 `net.*`/`system.*` 方法仅使 `btd` 在路由表中增加了每一行。

## 2. wifi: NetworkManager，以及为什么一个板子必须迁移到它  · **measured**

`architecture.md` §3 选择了 NetworkManager。板子上没有它。

Armbian 的无头镜像运行 netplan + `systemd-networkd` + `wpa_supplicant`。板子上的三个发现使其再次选择了 NetworkManager，而不是继承它：

- **D-Bus 启用的 `wpa_supplicant` 没有接口。** `fi.w1.wpa_supplicant1` 被声明且闲置（`Interfaces` 是一个空数组）；netplan 运行了一个 *第二* 个，通过 `-c` 配置的 supplicant，拥有 `wlan0` 且没有任何 D-Bus。因此直接驱动 `wpa_supplicant` 将意味着取代 netplan——而没有 NM 的故障报告。
- **netplan 无法报告手机所需的内容。** 它是一个配置 *生成器*：任何层都没有扫描 API，`netplan apply` 返回 "配置已应用" 而不是是否关联成功。"显示网络" 和 "那个密码错了" 是配置流程最需要的两件事，而它两者都不回答。
- **`RequiredForOnline=no` 使启动变得更糟，而不是更好。** Armbian 发行了一个 drop-in 将 `systemd-networkd-wait-online` 转换为 `--any`：当 *任何* 网络d链接上线时成功。一旦 wifi 属于 NM，网络d的唯一链接通常是无线缆的以太网端口，因此 `--any` 从不满足。标记该链接为非必需会移除唯一候选者并保证失败。屏蔽该单元是修复；`NetworkManager-wait-online` 是诚实的门。
`scripts/migrate-network.sh` 执行一次迁移，并且在将板子现有的凭证复制到 NM 配置文件之前拒绝切换——否则无用户界面的板子会离线并且无法恢复。它设置了一个启动时的后备机制，在 `wlan0` 90秒后没有地址时恢复 netplan 并重启，这是更新系统启动计数器的想法应用于网络更改的结果。

### 2.1 `BadKey` 是关键所在

`ConnectFailure::BadKey` 是 NM 值得迁移的原因。被拒绝的密码短语是最常见的配置失败，而一个无法说明这一点的客户端会把用户置于无所事事的境地。NM 报告它为设备状态原因 7；`configd` 将 NM 的原因映射为 `BadKey`、`NotFound`、`Timeout`、`Unsupported` 和 `Other`，未映射的原因绝不能成为 `BadKey`——这会让某人反复输入已经正确的密钥而陷入循环。

`configd` 在 `AddAndActivateConnection` 后轮询 NM 而不是在激活开始时返回，因为“配置已应用”是 netplan 给出的答案，也是我们拒绝的答案。

### 2.2 新网络的配置，这是整个路径的目的

支持 BLE 的场景是：一块板子到达了一个新的地方，它知道的 WiFi 并不在那里，而网络上的任何东西都无法到达它。三个特性使得这种情况得以实现，而只有第三个需要修复。
- **这些守护进程不会等待网络。**`btd` 是 `After=dbus.service bluetooth.service`，`configd` 是 `After=NetworkManager.service`，均未使用 `network-online.target`。即使没有可达的 AP，板子仍然会启动并提供 BLE 服务。
- **已配置的配置文件会在重启后存活。**`AddAndActivateConnection` 会留下一个带有 `autoconnect` 默认开启的保存配置文件，因此重新连接是 NetworkManager 的职责，`configd` 完全不参与重新连接的循环。
- **扫描会等待扫描。**  · **测量** `RequestScan` 返回时，NetworkManager 会接受请求，而不是当无线电已经扫描完信道时，NetworkManager 会修剪它最近没有看到的接入点——因此在关联状态下，缓存的列表通常只包含机器人已经连接的 AP。立即读取它会立即返回上一次的扫描结果：第一次调用时只有一个网络，第二次调用时有八个网络。`configd` 现在会等待 `LastScan` 属性更新，最多等待 10 秒，将频率受限的请求视为“缓存已经足够新鲜”而不是错误。对于一个整日都在选择网络的客户端来说，“问两次”不是一个值得发布的合同。
- **结果是从激活中读取，而不是从设备中读取。**  · **测量** 这条路径上的最严重 bug。`connect` 会轮询 *设备* 状态，而设备在使用当前网络时会保持 `ACTIVATED` 状态，即使新的激活失败——因此 `connect("Tehaupoo", psk: "lol")` 对于一个根本不在范围内的网络返回了 `{"outcome":"connected","ssid":"SFR-e994"}`，命名了机器人一直连接的网络。报告一个从未发生的连接成功的消息是最糟糕的答案：手机会认为机器人已经配置好并继续执行。

  现在 `AddAndActivateConnection` 返回的活动连接对象会被轮询，请求的 SSID 是返回的内容而不是 `status` 说什么，一个无线电看不到的 SSID 会立即被拒绝为 `NotFound`，失败的激活会删除 NetworkManager 添加的配置文件——否则自动连接会无限重试已知错误的密钥，`net.status` 会声称网络是 `saved`。
  隐藏SSID也会被那个预检拒绝。连接一个隐藏的SSID需要使用`802-11-wireless.hidden`和一个能够声明“这个SSID是隐藏的”客户端，而API目前还没有这种形状。
- **重新配置会替换，而不是累积。**  · **measured** `AddAndActivateConnection`总是添加，而NM可以容忍具有相同ID的两个配置文件。因此，普通路径——在手机上输入错误的密码，`BadKey`，然后输入正确的密码——会让机器人持有两个配置文件，但在下次重启后，无法保证哪个配置文件会在重新连接时被自动使用。`net.forget`会通过删除其中一个配置文件并报告成功而使情况变得更糟。现在，对于一个SSID，保存的配置文件被枚举为一个*集合*并在连接前删除，`net.forget`会删除所有这些配置文件。

  在添加前而不是添加后删除，因为这样可以避免在添加成功而清理失败时留下重复的配置文件。如果添加失败，SSID将没有配置文件，这是配置被替换后的诚实结果，并会报告给客户端。

  请注意，当被替换的配置文件是当前活动配置文件时，这会断开机器人连接。这是不可避免的——更改密钥意味着重新关联——而通过BLE的客户端不会受到影响，这也是整个设计的基础。

## 3. GATT界面：一个管道，而非API

只有一个服务，**一个特征值**。客户端仅在读取一次以获取机器人的API版本后，向其写入NDJSON请求字节并订阅以接收答案——与其他传输方式携带的JSON-RPC行相同。读取不是可选的；请参阅第5节以了解其存在的原因。
**它返回的版本仅用于说明，而非拒绝。**`API_VERSION` 表明两个对等体未一起构建；它并未说明哪些调用会停止工作，在此链路中通常它们中的任何一个也没有停止。——没有任何东西检查这个数字——`configd` 不会因版本而封堵任何 `net.*` 或 `system.*` 调用，`updaterd` 在调用 `update.status` 之前不需要握手，而 `updaterd` 的 `hello` 也不会在此处拒绝。因此，一个在偏移时拒绝调用的客户端实际上是在拒绝机器人本可以回答的调用——而它在机器人没有网络的传输中拒绝这些调用，`net.connect` 是从偏移中解脱出来的途径。`duckctl` 会警告并继续执行，应用程序也应这样做：表面显示不匹配，让调用继续，并在实际到达一个接口形状发生变化的方法时报告 JSON-RPC 错误。这些错误会自我命名——`METHOD_NOT_FOUND` 表示此版本的此发布中没有此路由，`INVALID_PARAMS` 表示它不认识此参数——这使得继续执行比仅仅乐观要安全。

**没有封装头。**NDJSON 消息之间的换行已经作为双向的帧分隔符。这比侥幸要安全：`serde_json` 会在字符串内部转义换行符为 `\n`，因此序列化对象内部永远不会出现原始的 `0x0A`——这也是为什么 NDJSON 在 Unix 套接字上可以工作的相同属性。长度前缀会成为一种仅 BLE 实现的方言；相反，手机会像 `robotctl` 一样：写入字节，读取直到换行。

重组限制在 8 KiB，因为这个缓冲区在任何无线电范围内的人都是可访问的。

**替代方案及其为何不行：**

| | 为何不行 |
|---|---|
| 按字段特性（名称、ssid、ip、连接等） | 可在通用 BLE 应用中浏览，但会成为 API 的同一方言的第二种：每个字段都变成一个 UUID 加上 `btd` 代码，`net.scan`（一个列表）和 `update.subscribe`（一个流）都难以适应 |
| 两个特性，写和通知 | 传统的形状，且最初就是这样书写的。BlueZ 将写入和订阅报告为 *单独的事件*，因此必须通过设备地址在它们之间匹配两个特性——猜测一个特性通过构造获得的关联 |

一个特性的成本在于，在 nRF Connect 中，同一行在其中看起来有些奇怪。

### 3.1 路由子集是安全边界
BLE 暴露了一部分功能（§4.1）。`btd/src/route.rs` 中的一个表格决定了 *是否* 允许一个调用，*哪个套接字* 回应它以及 *哪个连接到该套接字* 的调用。前两者是同一个问题 —— 一个调用被允许当且仅当表格为其指定了服务 —— 而第三个问题也在同一表格中，因此在添加新方法时必须回答它（§3.5）。

**对 `Call` 的匹配是故意详尽的。** 添加一个协议方法会失败 `btd` 的构建，直到有人决定如何处理。在那一刻，`_ => None` 的通配符是安全的默认值，但从长远来看则是错误的 —— 它会无声地拒绝新的方法，而第一个症状是一个手机应用程序缺少一个没有人记得路由的功能。这已经为自己赢得了回报：七个 `net.*`/`system.*` 方法以及 `updaterd` 的等效匹配都破坏了构建。

每个被拒绝的原因如下：

| 拒绝 | 原因 |
|---|---|
| `update.pin` | 一个因误击而被机器人锁定的更新拒绝所有后续更新，并报告自己为最新版本 — 这里唯一看起来正确的错误行为。`robotctl`，以及一个本意如此的人 |
| `update.resetToGolden` | 除了名称之外的工厂重置。从不通过无线电 |
| `robot.safeToRestart`, `robot.modelApi`, `robot.remoteSessionActive` | `updaterd` 对 `robotd` 的私有问题；手机读取它们无法采取任何行动 |
| `system.pairingPin`, `system.setPairingPin` | **承载主要功能的一个。** 一个未配对的对端可以读取或覆盖的配对密钥 —— 这会使配对成为一场戏法。`btd` 通过 Unix 套接字而不是通过此方式读取它 |

**`update.rollback` 和 `update.select` 曾在该列表中，但现在不在。** 它们被拒绝的原因是引擎会自行回滚错误的版本，而这正是它所做的 —— 那个在健康门限测试中失败的版本。这并不是用户会通过手机寻求帮助的情况，而是安装、通过门限测试并表现更差的版本：一个摇摇欲坠的政策而不是完全不执行，一个停止重新连接的平板。除了一个人之外，没有任何东西可以回滚它，而这个人正拿着手机且没有 SSH。两者都会移动到已经在该板上运行过的版本，下载 nothing，并像其他任何过渡一样被门限测试和自动回滚。`update.apply` 已经被路由并且是这三个中更关键的一个，因此这几乎不会增加在无线电范围内的一方可以做的事情。`docs/project/update-over-ble.md` §2.4 是该决定及其权衡。

## 4. 授权：两层，保持分离
| 层次 | 机制 | 决定 |
|---|---|---|
| 1 | socket模式 `0660`，组 `robot` | 谁可以 **连接和交流** |
| 2 | `allow_users` / `--allow-user` | 谁可以进行 **修改** 调用 |

只读调用跳过第2层，因此支持可以检查它可能无法更改的机器人。

由于 `btd` 必须在 `robot` 组中才能访问所有套接字，而加入该组不应意味着“可以替换固件”。因此，两个服务都授予更改权限给 **命名的服务** — `allow_users = ["btd"]` 在 `updater.toml` 中，`--allow-user btd` 在 `configd.service` 中 — 并且两者都有一个测试拒绝将 `robot` 作为组。

**通过名称，而不是通过uid。** `systemd-sysusers` 动态分配，因此写入的配置中的数字在写入时是正确的，但在下一个板上是错误的。名称在启动时解析；无法解析的名称会警告而不是中止，因为缺少可选服务的机器人仍然可以提供状态。

`SO_PEERCRED` 只报告对端的 **主** 组id，这就是陷阱所在：`SupplementaryGroups=` 让一个进程通过套接字模式并通过，但不再进一步。缺少这一点是导致所有通过蓝牙低功耗的修改调用返回 `PERMISSION_DENIED` 而所有只读操作都正常工作的原因 — 这是最糟糕的错误形式，因为它表现为一个谜团而不是配置错误。

### 4.1 权限，以及解析器的位置

`btd` 是无特权的；`configd` 以 root 运行。这看起来是反常的，但并非如此。

`btd` 是解析来自任何无线电范围内的人的字节的进程。`configd` 仅在本地凭据化本地套接字上接收经过类型化 JSON 的调用。**将解析器置于该边界的安全侧比加固调度器更重要。**

`configd` 需要 root 的原因是狭窄的：NM 的连接修改和 logind 的 `Reboot` 都是 polkit 保护的，而 **此镜像上没有 polkit**，systemd 拒绝来自无会话的非 root 调用者。替代方案是安装一个 JS 策略引擎来授权两个调用。与 `robotd` 不同，它不接触任何硬件，因此其单元正确地将其沙箱化 — `ProtectSystem=strict`，一个可写路径，`AF_UNIX` 仅限，空 `CapabilityBoundingSet`。`CAP_SYS_BOOT` 有意省略：logind 执行重启而 `configd` 只是询问，因此该能力将允许此设计旨在避免的不干净的 `reboot(2)`。

如果 polkit 由于其他原因到达，`configd` 应该降级到一个专用用户加上两条规则。
### 3.2 每个订阅一个会话，以及决定它的那个错误  · **measured**

`btd` 保持一个会话——一个重组缓冲区，一个出站队列，一个授权状态——并且
问题在于它能存活多久。最初的答案是“服务存活期间”，因为 BlueZ 的回调模型给订阅者不提供对等体身份，并且每次只持有 *一个* 通知状态，因此每个对等体的会话看起来像是一个不可能发生的案例中的机械装置。一个过时的不完整行最多只导致一次错误请求。

它反而让下一个客户端承担了成本，这更糟糕，直到在一块电路板上看到三个症状才得以发现：

| 症状 | 原因 |
|---|---|
| 一个请求被回答，然后下一个请求超时 | 第一个泵将出站接收器从共享槽位中移除，因此第二个订阅没有泵：回复被写入到没有人读取的通道中 |
| `":0,"result":{"authenticated":true}}` — 缺少开头的回复 | 那些孤儿块通过后来的通知器浮现 |
| `no robot found`，然后同样的命令生效 | 无关：客户端在固定睡眠后进行一次快照扫描，因此广告是否落在窗口内是靠运气 |

只有第三个是客户端错误。前两个是同一个缺陷：**超出对等体寿命的状态**。断开连接在这个模型中是不可见的，因此没有任何东西会重置它。

因此，当中央订阅时创建会话，并在中央消失时丢弃会话——重组器和队列随之消失，重新连接的手机以未认证状态开始，这正是第 5.2 节所声称的行为。两个细节是关键性的，最初都是错误的：

- 泵不仅等待 `notifier.stopped()`，还等待队列。仅从失败的通知学习到的对等体离开仅需要发送回复，因此一个在空闲状态下断开连接的客户端会持有槽位，直到有请求到来而无人接收。
- 拆除仅在槽位仍然持有 *自己的* 发送者时清除。通知给消失的中央需要花费与 BlueZ 相同的时间来放弃，到那时，一个重新连接的中央可能已经安装了一个更新的会话，盲目的清除会杀死它。

写入路径仍然拒绝没有活跃订阅的写入。接受一个这样的写入会是一个谎言：没有地方发送答案。

### 3.3 移动应用会遇到的一件事：不要使用服务过滤进行扫描  · **measured**
`duckctl` 是一个测试工具，而且功能并不复杂得多——真正的客户端是一个手机应用。但它的某个 bug 是由于 CoreBluetooth 而非工具本身导致的，因此在 iOS 上记录下来是有价值的。

`btd` 广告了服务 UUID 和主机名。使用服务过滤器进行扫描仍然只能偶尔找到机器人：**CoreBluetooth 严格遵守过滤器，而一个已配对的外设经常会以空的服务列表进行广告。** 过滤后，它就完全不会被报告——不是“没有服务的报告”，而是完全不存在。这在一次运行中表现为“未找到机器人”，而在下一次运行中成功，中间没有任何变化，并且这个 bug 因为基于名称的回退只能匹配过滤扫描已经返回的外设而幸存下来。

应用应该未过滤地进行扫描，并区分自己的候选者，优先级最高的是广告的 UUID，然后是已知名称或存储的外设标识符，将“提供我们的特征”视为唯一的权威身份测试——只有在连接后才能知道。iOS 应用在这方面比 `duckctl` 有更好的第三级，即 `retrievePeripherals(withIdentifiers:)`，而 `btleplug` 并未公开此方法；在首次成功连接后存储标识符是正确的选择，完全消除了猜测。

另外值得注意的是：单次在固定睡眠后拍摄的快照是不够的。广告是周期性的，适配器对已配对外设的看法也会随之变化，因此需要轮询直到候选者出现。

### 3.4 机器人必须频繁地进行广告以便被捕捉  · **实测**

`duckctl` 大约在一半的运行中报告“未找到机器人”，有一段时间这被解读为工具的不稳定性——或者游戏手柄，其 LE 链接共享了同一个无线电。这都不是问题所在。`btd` 没有设置广告间隔，因此 BlueZ 使用内核的默认值 **1.28 秒**，而一个低占空比的中心扫描无法可靠地捕捉到 1.28 秒的广告者。

从 Mac 连续扫描两分钟，按设备统计每分钟到达次数：

| 设备 | 信号 | 120 秒内到达次数 |
|---|---|---|
| 智能插座 | −66 dBm | 130 |
| 广播器 | −91 dBm | 159 |
| 机器人 | **−36 dBm** | **16** |
The 机器人是房间中最强的信号源，其出现的频率比其他任何东西低一个数量级，因此范围、干扰和客户端都被排除，而不是争论。它平均每7.5秒出现一次，静默期为9秒、14秒、17秒，有一次为31秒；较大的间隔接近1.28秒的整数倍，这便是从出现中识别出的间隔。八秒的扫描落在这些静默期内也找不到任何东西。

对于应用来说，有两点需要注意。

**一部手机不会因为是手机而逃脱这一规则。**首次连接是扫描，因此注册过程会遇到相同的静默期——而这正是机器人需要可被找到的时刻。§3.3的`retrievePeripherals(withIdentifiers:)`提供的功能远没有看起来那么好：存储的标识符可以让iOS在没有新发现的情况下连接，因此重新连接会退化为延迟而不是失败。它对首次连接没有任何帮助，而首次连接是最重要的连接。

**广告间隔是机器人的属性，因此这是`btd`的责任：**100-150毫秒，8-12倍于默认值，这是普通外围设备使用的间隔。而不是规范允许的20毫秒——一个天线承载这一任务，游戏手柄的LE连接和Wi-Fi，以及用于广播的时间会从机器人可用的时间中扣除。

`duckctl/examples/advwatch.rs`是测量工具，保留下来是因为该声明只有通过重新运行才能验证：每台设备的到达次数及其信号强度，然后是机器人的静默期。

**已在板上确认。**安装了100-150毫秒后，同一台Mac同一分钟内的观察结果：

| | 120秒内的到达次数 | 平均间隔 | 最长静默期 | 长度≥8秒的静默期 |
|---|---|---|---|---|
| 默认1.28秒 | 16 | 7.5秒 | 30.8秒 | 7 |
| 100-150毫秒 | 151 | 0.8秒 | 3.8秒 | **0** |

到达次数是默认值的九倍，而且——这才是关键的部分——在`duckctl`八秒窗口内的两倍以内，因此从诊断出的失败中无法发生。机器人从106个听到的设备中的第34位上升到74个中的第7位。

### 3.5 每条车道一个连接，因为守护进程一次只能处理一个请求
`btd` 根据需要向 `updaterd`、`robotd` 和 `configd` 打开套接字，并在整个会话期间保持这些连接（`btd/src/upstream.rs`）。它为每个服务保持一个连接，并且这两个后台守护进程一次只处理一个连接：读取一行，等待整个调用完成，然后读取下一行（`updater/src/ipc.rs::handle_connection`，`configd/src/main.rs::handle`）。因此，每次会话中的调用都会排队等待最慢的那个操作，而应用程序首先请求的两个顺序也因此被打乱了：

| 客户端操作 | 发生的情况 |
|---|---|
| `update.apply`，然后在运行时 `update.status` | 状态行在 `updaterd` 无法读取的套接字中等待了数分钟。客户端超时未听到任何消息，而机器人正在正常更新 |
| `update.subscribe`，然后 `update.apply` | 更糟。`stream_progress` 拥有其连接直到对端断开连接，并且从不读取另一个请求，因此 `apply` 被写入了一个无人读取的套接字：它从未运行，从未回复，也从未出错 |

第二个情况是需要记住的。当客户端发起“更新”请求时，机器人没有任何动作，而且没有任何错误可以找到——请求就坐在一个套接字缓冲区中。

因此，调用按 **它们保持连接的时间长短** 分组，每个组获得自己的连接。车道在 `route.rs` 中决定（§3.1），紧邻权限和服务，这也是为什么详尽匹配会覆盖它：不能随意添加一个长时间运行的方法。

| 车道 | 保持连接的时间 | 调用 |
|---|---|---|
| `Prompt` | 与查找时间相同 | `hello`，`update.status`，`update.log`，`update.listInstalled`，`robot.health`，`net.status`，`net.forget`，`system.*`，`pad.status`，`pad.forget` |
| `Slow` | 几秒钟——网络或无线电扫描 | `update.check`，`net.scan` |
| `Operation` | 与操作时间相同，并改变机器人状态 | `update.apply`，`update.rollback`，`update.select`，`net.connect`，`pad.pair` |
| `Stream` | 永远，且不回复 | `update.subscribe` |

共享车道就是排队，每个分组都是这样做的正确答案：`updaterd` 在文件锁后面单次处理突变并为第二个请求返回 `BUSY`，而 `configd` 同时进行两个无线电操作也不是想要的。`update.check` 特意不在 `Operation` 车道上——在更新期间它有一个即时答案，排队它会使 `BUSY` 变为一个几分钟后才解决的旋转图标。
- 每个服务每个会话最多四个套接字，实践中通常是两个。每次调用一个连接是更整洁的模型，需要 `btd` 知道调用结束的时间，这需要它解析回复——但它从未这样做（§3），正是这一特性使得路由子集保持为传输而非 API 的第二种实现。

### 3.6 回复比一次突发大，以及通知方无法询问的 MTU  · **测量**

`bluer` 的回调模型——在这里起作用的模型，原因见 `btd/src/bluez.rs` 的头部——既不给通知方提供发送方需要的两种信息。它无法询问已协商的链路信息，而 `notify` 一收到 D-Bus 信号就返回，因此泵无法得知无线电已赶上。这两个空白都通过将每个回复大小定为 20 字节的最低限并尽可能快地发送来弥补。

与来自 Mac 的板子进行测量，通过 `system.logs` 获取日志尾部：

| 回复 | 在最低限的通知数量 | 发生了什么 |
|---|---|---|
| 约 5 KiB（24 行） | ≈265 | 送达，耗时 1.83 秒 |
| 约 7 KiB（32 行） | ≈350 | 通知会话在 150 毫秒后被拆解 |

第二行是通过实际测试找到的。`btd` 记录了一条 INFO 级别的日志，说中心已取消订阅——实际上没有取消；CoreBluetooth 仍然保持连接——客户端在重新组装器中有一半的答案，但没有错误报告地等待了 60 秒的空闲预算。泵将 `notify` 的单个错误解释为“中心已离开”，而一个满队列和已离开的中心是 `bluer` 返回的相同 `Err`，只有 `is_stopped()` 才能区分它们。

三个变更，都不是真正的解决方案，因为该模型没有提供就绪信号：

- **负载来自写入方。** BlueZ 在每次入站写入时报告已协商的 MTU，一个 ATT MTU 适用于两个方向，且中心在有回复发送之前总是先写入——`system.authenticate` 是每个会话的第一个写入。因此，会话从最低限开始打开，并从第一个答案起正确地进行大小调整，大约减少了十分之九的通知。
- **泵每 16 个块暂停一次**，大约是一个连接间隔。一个小回复从不停止。
- **被拒绝的块会重试而不是被解释为断开连接**，并且现在放弃会记录一条警告。

真正解决这个问题的方法是 IO 模型的 `sendable()`，但这个方法仍然遥不可及：它仅服务于 `Acquire*` fd 路径，而 CoreBluetooth 中心不会驱动这些路径。

**一部手机协商了515，这改变了问题的规模**  · **测量**（2026-09-15）。
上述内容均是从Mac测量得出的。一部运行iOS 26.6.2的iPhone 17，通过`tauri-plugin-blec`报告ATT MTU为**515**——CoreBluetooth的`maximumWriteValueLength`为512加上三字节的头部，这与守护进程用于获取其负载的算术相同。因此，从会话的第一个入站写入开始，`btd`将通知的大小设置为**512字节而不是20字节**。

将上述两行应用于此：原本需要约265个通知和1.83秒的约5 KiB日志尾部，变为大约11个通知；原本需要约350个通知并导致通知会话崩溃的约7 KiB回复，变为大约14个。这种崩溃仍未得到解决——上述三个更改仍然是我们与之斗争的东西，但导致这种队列压力的根源在于向一个无法告知何时准备好的链接发送了数百个数据块，而手机无法接近这种情况。这就像`system.logs`是一个应用程序可能提供的调用，也可能不是。

## 5. 配对：即插即用，以及传输检查的PIN码

`configd`存储了一个六位数的PIN码，`btd`在提供任何服务之前会检查它。**不是**通过蓝牙绑定——这由规范强制执行，而非选择。

### 5.1 为什么BLE无法携带打印的PIN码  · **测量**

最初的设计是让机器人以存储的PIN码回应BlueZ的密钥请求。在硬件上，macOS显示了它自己的随机六位数代码，并等待有人将其输入到机器人中。

在LE密钥输入中，一侧显示密钥，另一侧输入密钥，角色取决于每侧声明的IO能力。实现`request_passkey`声明“此设备可以输入”，因此macOS承担了显示角色。一个没有键盘的机器人无法承担此角色。

相反的情况也不好。使用`DisplayPasskey`时，机器人承担了显示角色，但规范要求显示的一侧随机生成密钥——BlueZ选择它并交给代理。没有方法可以使其呈现我们存储的值，而且一个无头的机器人也没有显示它的屏幕。

因此，在BLE密钥输入中无法表达固定在机器人上的打印PIN码。只剩下三个选项：
| | |
|---|---|
| 仅工作 | 加密但未认证，无PIN。安全性依赖物理存在。大多数无头BLE设备的做法 |
| 出带外（QR） | 真正的认证且针对每个机器人真正有效。BlueZ的出带外支持薄弱且不存在用于驱动它的手机应用。对v1来说是一个重大提升 |
| **带有应用层PIN的仅工作** | **选择这种方式。** 配对以进行加密；在会话中检查PIN，我们在此定义规则 |

### 5.2 工作原理

配对是仅工作：每个代理处理器都是`None`，`bluer`将其发布为`NoInputNoOutput`。
对RPC特征的读取需要`encrypt_read`，这使得中心节点能够建立连接——纯加密，而不是`encrypt_authenticated_*`，因为仅工作的连接永远无法满足认证变体，要求它们会拒绝所有客户端。

然后`btd`在客户端发送`system.authenticate`之前什么也不提供。该调用由传输端而不是转发，这就是路由表有第三种结果（`Route::Local`）的原因，除了“转发”和“拒绝”。`hello`是唯一其他允许通过未认证的调用，因为它只报告版本——与GATT读取已经告诉未认证客户端的内容相同——拒绝它会让一个不匹配的客户端无法了解为什么什么都没工作。

三个关键细节，而不是无关紧要的：

- **每次尝试时从`configd`获取PIN**，而不是缓存，因此`robotctl system set-pin`在下一次尝试时生效而不是下一次重启。如果`configd`无法回答，会拒绝会话而不是接纳。
- **以字符串形式比较。** `042042`和`42042`是不同的密钥；数字解析会将它们视为相同。有一个针对这种情况的测试。
- **三次尝试后，会话关闭。** 六位数的PIN在一加密但未认证的链接上是一百万次猜测，因此配额是唯一让暴力破解昂贵的因素：重新连接需要完整的BLE连接和建立连接。`attempts_remaining`返回给客户端，它可以说“还剩两次”而不是默默地失去连接。
**PIN通过加密但未认证的链接传输**，因此，在配对时刻出现攻击者的情况下，攻击者可以捕获它。这就是交易的代价，这也是在威胁模型允许的情况下，应优先考虑OOB的原因。与“即插即用”相比，它购买的是即使在范围内任何人都可以轻易完成配对的设备仍然无法执行任何操作。

**工厂PIN为`000000`，并在本仓库中公开。**因此，出厂时仅证明了物理存在，而没有更多。`btd`在每次使用默认PIN进行认证时都会记录警告，`robotctl system pin`也会这么说。安全完全依赖于PIN是针对每个机器人的，这使其成为一个**配置义务**：必须生成它、打印它并记录所打印的内容。这就是`updater-design.md`第5.7节的每个设备状态，也是我们所欠的序列号所在的同一个槽位。

**没有配对窗口，这是决定而非推迟的。**只要机器人广播，它就是可配对的。针对每个机器人的PIN已经包含了窗口所能提供的所有内容：知道打印的PIN需要物理访问，而任何能够读取标签的人都可以获取机器人。一个按钮会增加一个可见的同意时刻、丢失PIN后的恢复路径，以及如果标签被拍摄时的多层次防御——对于v1来说这些都不是必需的，每个都可以在以后添加，因为一个带有按钮的外壳可以阻止`set_pairable`而不会改变此设计。

### 5.5 加密目前是关闭的，这还不确定  · **度量**

在特性上启用`encrypt_read`会使macOS上的读取操作**挂起**：CoreBluetooth发出读取请求，BlueZ因加密不足而拒绝，没有任何解决办法——没有提示，没有错误，没有重试。客户端会等待超时，直到与正常工作的机器人进行交互。当标志关闭时，读取会立即回答，因此要求是原因。

因此，测试板上的`btd`目前以`--insecure-no-pairing`运行，**PIN通过未加密的链接传输**。这比第5.3节描述的还要糟糕：它既不是“加密但未认证”，也不是两者。在交换期间，任何在无线电范围内的人都可以读取PIN，之后可以执行客户端可以执行的任何操作。
. Do not summarize, omit, or add new content.
.

未解决，接下来需要确定是否存在任何连接——`bluetoothctl info <mac>` 报告 `Paired: no` 会意味着永远无法建立加密，并且标志是症状而非原因。直到这一点被确认，将要求移动到写入是一个猜测：如果没有用于加密的连接，它会以相同的方式失败。

**默认是不安全的，出于目前的目的，这是有意为之的。** 标志是 `--require-pairing`，并且它是 **关闭** 的。因此，从发行版安装的板子提供了一个未加密的链接，并且可以开箱即用。

首先尝试了另一种替代方案并被拒绝：默认要求配对，首次安装是安全的但 **不可用** — 每个客户端在读取版本时都会挂起，因为这正是导致 CoreBluetooth 破坏的配置。没有什么可以保护一个无法与之交谈的机器人，而项目距离发布还很远；在无法使用的默认设置和可以使用的默认设置之间，开发工具选择了可使用的那个。

成本是明确声明的，而不是含糊其辞：**每台运行此代码的机器人具有可由旁观者读取的 Wi-Fi 密钥和 PIN。** `btd` 在每次启动时都会记录一个警告，指出这一点，因此选择保持可见而不是成为没有人记得的事情。旧的 `--insecure-no-pairing` 标志被接受并被忽略，纯粹是为了一个携带它的板子在移除它后不会因启动失败而停止工作。

在任何人收到任何东西之前，必须关闭此问题——标志被切换并默认设置——否则。一个其配置密钥可由旁观者读取的机器人不是一个你可以交给陌生人的机器人。

#### iOS 不是 macOS，这就是全部确定的内容  · **度量**（2026-09-14）

对 olducky 进行了简短的 A/B 测试，手机与板子，`btd` 在每次运行之间通过一个 systemd drop-in 重启，因此单元的 `SupplementaryGroups` 是真实的。

`--require-pairing` **关闭** — 这正是 Reachy Mini 的配置，见下文 — 时，一部 iPhone 连接并发现服务而没有任何抱怨。当它 **开启** 时，iOS 弹出配对提示。这是值得记录的部分：**手机上的 CoreBluetooth 从 SMP 开始，而笔记本上的 CoreBluetooth 不会**，因此第 5.5 节测量的挂起不是堆栈的总体属性，“没有建立连接”也不是发生的情况。
- 未建立，因为运行在此停止：加密读取是否完成，以及 `bluetoothctl info` 中关于绑定状态的说明。`version read` 从未出现在日志中——但该行是 `debug!` 级别，而单元设置 `RUST_LOG=info`，因此其缺失并非证据。接手此问题的人应首先在相同的插件中添加 `Environment=RUST_LOG=debug`，并连接设备，然后尝试读取而不是连接。

#### 参考实现完全不使用链路层加密

在任何人花费更多时间在该标志上之前，值得了解这一点。`reachy_mini` 的 BLE 配置服务（`daemon/app/services/bluetooth/bluetooth_service.py`）声明其特性为 `["write"]` 和 `["read", "notify"]` —— 无处提及加密标志。它注册了一个 `NoInputNoOutput` 代理，并设置了 `Pairable`，因此中心设备 *可能* 与之绑定，但从未有任何需求。这就是为什么它在 iOS 上可以工作的原因：手机从未被要求进行任何加密操作。

他们的推理与我们相同，但顺序不同：

> 在这里，BLE 配对是 Just-Works（机器人是 `NoInputNoOutput` 硬件，因此 MITM 保护的配对是不可能的）——因此我们在应用层进行加密，并将设备 PIN 混入密钥派生中。

同样的死胡同 `crate::pairing` 文档。当此页面得出结论为 *修复链路层* 时，他们得出的结论是 *停止要求链路层提供保密性，并密封一个关键的秘密*：`x25519-hkdf-sha256-aesgcm`，使用旋转的机器人密钥进行的临时 ECDH，PIN 作为 HKDF 的盐，AES-256-GCM 作为 AAD。它击败了被动嗅探器，但在设置过程中遇到活跃的 MITM 时不会被击败；他们如此说明，并将 PAKE 作为后续跟踪。

**因此 §8.1 有一个第三种候选修复方案，以及一个我们独有的注意事项。** 关键属性——旁观者无法恢复所有者的 WiFi 密码——来自于临时 ECDH，而不是 PIN。PIN 作为盐阻止了错误 PIN 的对等体生成可解密的数据包，而在 `000000` 时这里什么也买不到。他们为每个机器人设置的 PIN 是序列号的最后五个字符，印在机器人上，这有效是因为 *他们的* 广告是匿名的——每台机器人都广告为 `ReachyMini`。我们广告的是从序列号派生出的名称（§8.2），因此我们无法使用这种特定的技巧，这是出于更好的理由做出的选择。
**延迟、刻意且未被取消。**没有任何东西被发送，也没有任何人被赋予了机器人，因此链接保持开放状态，`--require-pairing`保持关闭且为默认状态。门仍未改变：这会在机器人发送给任何人之前关闭。

### 5.6 开放

- **解除绑定。** 无法手动解除手机的绑定；`bluetoothctl untrust` 是手动退出的方法。需要一个 API 和关于谁可以调用它的规则 —— 也许不是 BLE 本身。
- **速率限制仅在会话内有效。** 三次错误的 PIN 会关闭会话，但没有计数跨会话连接，因此一个有决心的对端可以在每次猜测失败后无限期地重试，每次三次猜测就会建立一个新的绑定。`btd` 中的会话间退避策略是显而易见的下一步，需要一个地方来保存这种状态。

### 2.3 伪造物是规范，而没有东西检查 NM 是否符合规范

因为现在它描述了三个错误而不是一个，所以值得明确地陈述。在板子上发现的每个 Wi-Fi 问题中，**`FakeNet` 已经具有了正确的行为，而 NetworkManager 的实现则偏离了它**：

| 行为 | `FakeNet` | NM 路径，如已发布 |
|---|---|---|
| 无线电无法看到的 SSID | `NotFound` | 报告 `connected`，命名了不同的网络 |
| 失败的尝试 | 无 | 留下了一个带有坏密钥的保存配置文件 |
| 重新配置 SSID | 代替 | 堆叠了一个第二个配置文件 |

因此，该特性不仅是一个测试接口；它是唯一的书面合同形式。问题在于检查的方向 —— 测试套件验证伪造物与合同的一致性，而没有任何东西验证 NM 与合同的一致性。两者都实现了 `Net`，因此相同的断言本可以同时针对两者运行；阻止它的原因是 NM 一侧需要一个真实的 NetworkManager 和一个真实的无线电，这意味着需要一个板子而不是 CI —— 参见 `install-path-gap.md` §"如何关闭它"，其中板子是按需提供的，并且故意不是 CI 运行器。

在那之前，诚实的总结是：`configd` 的 Wi-Fi 行为被测试了，而运行在机器人上的代码则没有。上述每个错误都是通过手工在硬件上在一个会话中发现的。

### 2.4 实际在板子上运行的内容

记录下来，因为“构建”和“工作”在文档中是同一个词用得太久了，而且四个“修复”都是基于从未运行的二进制文件进行验证的。
经过端到端验证，在 Radxa Zero 3 上与 Mac 作为客户端：发现、连接、版本读取、PIN 认证、`system.info`、`net.status`、`net.scan`，拒绝边界（`robot.move`、`system.pairingPin`、`update.select` 皆被 `btd` 本身以代码 14 拒绝），`update.check` 被路由至 `updaterd`，一个无线电无法看到的 SSID 被拒绝为 `NotFound`，以及 **一个机器人从未见过的网络通过 BLE 配置、连接并重新连接自身——这正是此路径存在的场景**。被拒绝的密码返回为 `BadKey`，携带 NM 的原因 7，这是手机会采取的回应：重新提示输入密码而不是显示通用失败信息。

`net.forget` 清除每个 SSID 的所有配置文件：五个重复的 `kek` 配置文件，由预置二进制文件遗留，通过一次调用完成。整个 `net.*` 表面现在已针对真实的 NetworkManager 进行了测试。

在没有无线电的板子上仍为假：连接未加密（§5.5）。这是此路径与可交付给某人的东西之间的唯一区别。

## 6. 无无线电的测试  · **度量**

测试套件在没有任何硬件、网络、D-Bus 和 Docker 的笔记本电脑上运行，并且必须保持这种状态。有两个缝合点使得这种情况得以实现：

- **`configd` 的 WiFi 是一个特性**，使用内存中的假体，就像 `duck-control` 有 `RobotIo` 一样。`--fake-net` 为整个 `net.*` 表面提供服务，包括按需产生错误密钥失败，这在针对真实接入点时很难引发。
- **`btd` 的无线电是两个通道，不是一个特性。** 一个 `GattLink` 特性需要异步 `recv` 和异步 `send`，而会话循环同时等待两者——这意味着需要关联类型或与借用检查器进行斗争。一个简单的结构体持有两个 `mpsc` 通道表达了同样的意思，测试构建了一个这样的结构体而不是实现任何东西。

因此，会话测试通过真实的 Unix 套接字驱动了一次完整的 BLE 会话：被拒绝的调用从未到达守护进程，`robot.*` 路由至 `robotd` 而不是 `updaterd`，并且每个订阅流的通知通过 23 字节的 MTU 到达。
`board-test.sh` 包含了仅在 Linux 上出现的内容：套接字模式、`--allow-user` 解析名称、组成员读取、非成员被套接字模式阻止、未命名成员被拒绝进行修改调用 **且拒绝的更改未生效**、拒绝的口令退出 5 而不是 1、PIN 保持其前导零、以及日志中无口令。此外还有 `btd --version`，这是一个真正的跨链接检查：`btd` 是唯一一个拉取 C 超过 `zstd` 的二进制文件，因为 `bluer` 通过 `zig cc` 编译了带有 vendored 源代码的 libdbus。

`duckctl` (`cargo run -p duckctl`) 是手机的替代品，也是唯一可以测试无线电的途径。这是一个 **示例，而非二进制文件**，因此 `btleplug` 从未达到机器人；选择 `btleplug` 而不是 `bluer`，因为必须在开发者的 Mac 上运行。它重用了 `duck_ble::framing`，因此分块是机器人自身代码的客户端部分，而不是自由重新实现并可以与之协商的部分。

### 6.1 未测试的内容

- 两种服务均未接触过 **真正的无线电** 或 **真正的 NetworkManager**。两者仅在 aarch64 上进行类型检查；此为全部内容。
- `migrate-network.sh` 中的 **切换** 只在新刷板上运行。曾手动一步步执行过此操作；然后重新运行脚本以确认幂等路径。首次刷板的人是真正的测试者。
- **约 73 秒后 BLE 响应。** `hci0` 仅在 `aic-bluetooth.service` 为 AIC8800 的 UART 附加后才存在，而 `bluetooth.service` 在 `dbus` 后面阻塞了 26 秒。`btd` 等待并重试，而不是退出——与 `robotd` 等待电机总线相同的一课——但一个围绕即时发现设计的手机应用会感到失望。
  
## 7. 承担的成本
- **artifact中包含两个D-Bus堆栈。**`btd`通过`bluer`链接libdbus；`configd`使用`zbus`。占用几兆字节。`bluer`被选择是因为它正好提供了一个GATT服务器、广告和配对代理，相比之下，手写的`org.bluez`对象管道行不足700行代码。如果`bluer`增加了`zbus`后端，值得重新考虑。
- **我们提供的libdbus**可以保持最新，而不是依赖发行版提供的版本。对于一个仅通过本地套接字由我们编写的守护进程访问的库来说是可以接受的。
- **`btd`故意不在`on_apply`的重启集中。**它可能是*更新请求的传输方式*：重启它会中断承载`update.subscribe`的连接，发起更新的手机将永远不会得知结果。同样的原因，`updaterd`在更新过程中也不会重启自己。成本是有限的而不是无止境的——排除会在回复发送后失效，因此引擎会在5秒后重启`btd`，而下一次`updaterd`启动会验证这一点（`restart-order.md` §1和§5）。

### 8.1 加密——阻塞点

全文§5.5。默认情况下，链接层是**未加密的**——`--require-pairing`存在且关闭，因为要求它会使每个客户端挂起——因此PIN和每个WiFi密码都以明文形式出现。关闭这一项意味着使机密配置生效 *并且* 使其成为默认设置；仅做前者会使每个板卡都处于不安全状态。

现在有三个候选修复方案，而以前这一节假设只有一个：

| | |
|---|---|
| **修复链路层** | 这一页面所假设的方案。如果有效，整个路由表面都将保密，而无需编写任何加密代码。反对理由：绑定只能始终工作，因此无论其他任何更改如何，`encrypt_authenticated_write`都是不可达的（§5.5） |
| **在应用层密封** | Reachy Mini的答案，在两个手机平台上均已投入生产并通过应用审核。它保护了在没有任何绑定的情况下，防止被动嗅探者获取密码。反对理由：它只保护了那些有人记得密封的内容，并且此传输现在携带设备代码、日志行和PIN本身（§3.1） |
| **密封会话而非通话** | 在`hello`之后建立一次加密，覆盖所有后续的帧。比上面的行更复杂，且唯一能覆盖`system.authenticate`的方法，因此后来添加的方法不可能是无人密封的方法
要求第一行的内容仍然未知——即是否存在一个连接（`bluetoothctl info <mac>`在机器人上）。*已连接但未加密*和*从未连接*需要不同的修复方法，发送错误的修复会使问题依然存在，而看起来已经解决了。§5.5 记录了iPhone运行的距离以及从何处继续。

### 8.2 识别机器人——三人，三台机器人，一个房间  · **已构建**

三个朋友拆开三台机器人。每个人都必须找到属于自己的那台，而在这一功能实现之前，他们无法做到：每块电路板都从一个图像中闪烁出`radxa-zero3`。

这是一个可用性问题。它还涉及安全问题——一部手机如果选择了错误的机器人，可以对其进行身份验证并将所有者的WiFi凭证写入其中，因为所有机器人的PIN码都是`000000`——但这个问题之所以值得修复，不是因为安全问题。你无法从列表中识别出一台机器人，那么没有人可以使用它，这就是问题所在。§8.1 单独跟踪，也不影响上述内容。

#### 机器人叫什么名字

**身份来自SoC序列号**，从`/proc/device-tree/serial-number`读取并通过`system.info`（`configd::identity`）报告。它被嵌入到芯片中并通过引导加载程序传递，因此在重新刷写后仍然存在，即使更换了无线电模块也是如此——不需要任何配置步骤即可存在，这也是手刷板能够工作的原因。它也是一个简单的文件读取：无需root权限，无需D-Bus，可以立即获取，而不是等待`hci0`在约73秒后出现。

这不是这个仓库中的新想法，值得说明：`updater-design.md` §5.6 已经选择了与更新日志中稳定设备ID相同的值，出于同样的原因——它有效且不需要任何配置步骤即可获取。重用它意味着机器人只有一个身份，而不是两个。

蓝牙适配器地址看起来更好，因为它在链路层上已经由对等方看到，因此从它派生出的名字不会泄露任何新的信息。它被证据否决了——参见§8.6。

**默认名称为`duck-`加上序列号的SHA-256哈希值的前四位十六进制字符**：`duck-c51b`。哈希而不是切片，因为没有任何保证芯片ID在不同芯片之间哪个部分会有所不同。SHA-256而不是`std`的哈希器，其输出在不同Rust版本之间不一致——工具链更新会重命名所有在野的机器人，而没有人会将这两件事联系起来。
四个十六进制字符有 65 536 种可能性，因此在一个房间中的三台机器人大约每 22000 次碰撞一次。这是一个默认设置，旨在使其 *可区分*，而不是一个唯一的键。

名称在 **扫描响应** 中传输，而不是在广告中，现在总是这样：标志（3）、128 位服务 UUID（18）和地址字段（8，见下文）占用了传统广告持有的 31 个字节中的 29 个字节。在地址之前是 21 个字节，一个 8 个字符或更少的名称可以与之并存——`duck-c51b` 是 9 个字符，多了一个，所以在实践中它从未并存。扫描响应是中央设备可以单独忽略的第二次交换，这就是为什么一个没有名称且没有服务的设备可能是机器人而不是需要过滤掉的东西。

#### 广告的名称是机器人被赋予的名称

`btd` 询问 `configd` 机器人叫什么名字，并每隔几秒钟就将其广告与答案进行协调。在此之前，它广告 `/etc/hostname`，而 `system.setName` 则向一个文件写入从未被读取的内容：重命名机器人并不会改变手机可以看见的东西，即使在重启之后也是如此，而且树中的三个注释描述了预期的行为，就好像它已经存在一样。

协调过程与适配器监视器在同一启动过程中并行运行，因此失去无线电会同时结束两者——而下一次启动会再次询问，这就是为什么在蓝牙关闭期间进行的重命名会被拾取的原因。

**一台机器人有两个名称，而且这两个名称都会被设置。** 广告携带本地名称；适配器单独提供一个 GAP 设备名称（`0x2A00`），BlueZ 从中获取 `Adapter.Alias` 并默认为主机名。仅设置第一个意味着重命名的机器人广告 `duck-c51b` 并回答 `radxa-zero3` 给任何读取特性的设备——而读取它正是中央设备在连接时所做的。BlueZ 然后将答案缓存到广告名称中，因此在 Linux 上，机器人在首次接触前是 `duck-c51b`，首次接触后是 `radxa-zero3`，`--name duck-c51b` 停止找到它；CoreBluetooth 保留两个名称并报告 `radxa-zero3 [duck-c51b]`。手机自身的蓝牙设置显示 GAP 名称，这是这里最关心的情况，也是树中没有工具可以看见的情况。`advertise` 会将别名与广告一起设置，因此每条发布名称的路径都会发布两者。缓存旧名称的客户端会一直保留它，直到被遗忘，这是一个客户端问题，需要客户端修复。
要求有选择地同步而非事件驱动，这是故意为之。`btd`会转发`system.setName`而不读取
回复——解释回复正是这个守护进程所避免的——并且在转发一个请求的瞬间重新询问。轮询拥有更少的移动部件，并且涵盖了通过`robotctl`进行的重命名，而这些重命名从不跨越`btd`。`--name`固定了*名称*用于测试——同步循环仍然运行，因为地址在名称变化与否的情况下都会移动。如果`configd`不可达，它会退回到主机名：`btd`处于恢复路径上，并且必须在机器人其余部分尚未启动时启动。

#### 广告携带了机器人的IPv4地址

`duckctl scan`连接到 nothing，这正是它成为当机器人不可达时要使用的命令的原因——这也是为什么列表只能报告广告所携带的内容。因此，列表最常被读取以回答的问题 *我在哪里ssh？* 并没有答案：地址在`net.status`中，而读取它需要一个连接、一个绑定和一个PIN，每个机器人一次。

IPv4的四个字节位于制造商数据字段下，公司ID为`0xFFFF`——这是蓝牙SIG保留用于内部和互操作性测试的ID，对于尚未分配ID的项目来说是正确的。任何人都可以使用这个ID，因此 **该字段不是一个身份验证检查**：它只能从也广告了服务UUID的设备中读取，这是区分器。

**SSID不在其中，也不能在其中。**一个SSID最多32字节，而预算上留下的6字节负载无法容纳它。它仍然是一个`wifi status`问题，当列表中的地址显示意外内容时，这就是要问的问题。

一个没有地址的机器人广告`0.0.0.0`而不是省略该字段，因此列表可以区分三种状态：一个地址、一个没有网络的机器人，以及一个在本机制存在之前发布的机器人，它根本不广播任何字段。将最后两种状态合并会导致读者去检查一个需要更新的机器人上的WiFi。

The 地址在与名称相同的时钟周期内进行校对，每隔几秒钟一次——比DHCP租约移动要快得多，而关键在于另一种情况：刚刚运行了`wifi connect`的人正在等待读取它生成的地址。如果`configd`未能回答，它会保留最后一个已知的地址，而不是清除它，否则`configd`重启会每时钟周期重新注销并重新注册广告，而一个有客户端监视地址闪烁的广告会不断重新注册。如果BlueZ ever 拒绝携带该字段的广告，`btd`会重新尝试不携带该字段的广告：一个没有地址的广告仍然可以被某人访问，而被拒绝的广告则表示该机器人已消失。

#### 分配可以为板子命名，但并非必须

`provision.sh --name`，`provision-board.sh --name`会传递给它，最终调用`robotctl system set-name`。出于目的考虑，它是可选的：派生的默认值已经能够区分板子，因此分配 *改进* 了现有的名称，而不是提供一个名称。这就是为什么这可以存活于手动刷写板子的情况下，而这是反对在分配时间分配身份的唯一论点。

#### 应用程序应该做什么

- **将序列号作为键存储起来。** 它是唯一能够在重命名和蓝牙地址更改后仍然存活的标识，也是“收藏”或用户选择的标签所依赖的。
- **也要存储外设标识符**，作为快速路径——在iOS上，`retrievePeripherals(withIdentifiers:)`可以完全跳过扫描。它是一个缓存，而不是身份：它会随着地址一起消失（§8.6），而序列号则是重新建立“收藏”所指代的机器人身份的关键。
- **RSSI是一个排序键，而不是身份。** 用于将最近的机器人排在前面是合适的。它不是证据：信号穿过身体或桌子会随意重新排序机器人。

一旦机器人被连接过一次，这个问题就解决了——应用程序会直接返回到它，并显示所有者给它起的名字。

#### 仍然悬而未决
- **我第一次拿起哪个才是我的。** 列表中的三个不同名称并不等同于知道哪个机器人是手中的那只鸭子。要跨越这个鸿沟需要一个物理信号：机器人上的标识、一个`identify`动作，或者接近度。最便宜的缓解措施不需要任何成本且不是代码——一次只给一个机器人通电，并在应用中说明这一点即可。
- **`identify`** — 让**这个**机器人点头、眨眼或鸣叫。树中的任何内容都不会驱动LED灯、扬声器或屏幕，而且出于设计原因，BLE不允许控制电机（§3.1），因此这是一个缺失的设备路径而不是看起来的策略问题。当它存在时，有两个决定要做出：它可以执行的动作，以及它必须在认证之前工作，因为要求在输入PIN之前进行认证是循环的，目标是将PIN对准正确的机器人。
- **一个标签，以及为每个机器人打印的PIN。** §5.3需要PIN；两者都在等待硬件，而没有人已经确定。请注意，PIN不能从身份推导出来：身份在广告中公布，因此从它计算出的任何内容都是公开的。
- **工厂重置做了什么。** 今天没有任何东西清除`configd`的配置——它设计上在更新和回滚中幸存，`update.resetToGolden`重置的是发布而不是配置——因此预置的名称和用户重命名是不可区分的。单独的“工厂名称”槽位只有在能够清除一个而不清除另一个时才有价值。

#### 测试未涵盖的内容

身份和派生名称是普通的单元测试。这种测试存在的场景——三个机器人同时广播并且客户端正确选择——无法在板子上进行测试，需要三个机器人或一个模拟外设。明确地说清楚这一点，而不是让绿色的测试套件暗示其他情况。

### 8.4 重新连接后的PIN尝试

§5.6. 三次错误的PIN会关闭会话；重新连接之间没有计数，因此对三次猜测的对端会无限期地重试，代价是每次三次猜测就失去一次连接。需要一个地方来保存每个地址的状态。

### 8.6 适配器地址不会保持不变 —— **未调查**

记录下来以免从头开始重新发现。这里没有任何内容被追查过，而且它被有意地停放而不是作为开放的工作。

一个板子在十六次启动中报告了两个不同的蓝牙地址，从`btd`自己的启动行（`serving BLE ... address=`）：
- `50:37:CD:16:2B:EC` — 两次 `btd` 在一次启动中开始，时间分别为 10:04 和 10:05
- `50:37:CD:16:1B:92` — 从第 10:18 个启动开始，共有十五个

在这两者之间：没有重新刷写。除了通过 `duckctl` 进行 BLE 连接和游戏手柄配对外，没有对板子进行任何操作。保持高位四位不变；只有低位两位发生变化，这符合一种生成地址的驱动，该地址在厂商前缀后面生成并缓存，而不是从模块中读取。`configd` 从未断电重启适配器——它只启动一个已关闭的适配器——因此配对手柄没有明显机制，这使其成为需要测试的对象，而不是需要指责的对象。

为什么这不仅仅是一个令人困惑的日志行：

- **每个绑定都存放在 `/var/lib/bluetooth/<地址>/` 下**，因此地址更改会使它们孤儿化。配对手柄和绑定的手机都会停止工作，重新配对手柄看起来像是修复一个无关故障的解决方案。
- **iOS 从设备地址中推导出从设备标识符**，因此应用程序保存的“我的机器人”会因为地址变化而失效。这就是为什么 §8.2 中的应用键喜好项依赖于 *序列号*。

这不再是一个身份问题——§8.2 不再依赖此值进行任何操作——这就是为什么这可以等待。

最便宜的下一步操作，当有人接手时。`sudo ls -la --time-style=long-iso /var/lib/bluetooth/` 可以确定第二个地址首次出现的时间，因为 BlueZ 会以每个适配器的名称命名一个目录。然后，在 `robotctl pad pair` 之前和之后运行 `bluetoothctl show | head -3` 可以在无需重启的情况下验证手柄假设。如果地址来自一个文件，可以故意将其固定——这也意味着它在重新刷写后会存活下来。
