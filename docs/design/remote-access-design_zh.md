# 远程访问 — 一个账号，以及背后的服务

状态：草稿 · 日期：2026-09-02 · 负责人：皮埃尔

如何从局域网外访问一只鸭子。`remote-webrtc.md` §7 描述了其形态 —— 从一个会话服务到已经在机器人上运行的信号服务器的桥梁 —— 而其形态描述是正确的。本页面拥有形态所需且自身不具备的两样东西：一个 **标识账号的凭证**，以及一个 **展示该凭证的服务**。

**目前构建完成**（2026-09-02）：§2 — 账号。`account.login`、`account.status` 和 `account.logout` 由 `updaterd` 提供服务，并且可以通过蓝牙低功耗（BLE）和 WebRTC 数据通道本地访问；`robotctl account login` 打印一个代码并等待，`duckctl account login` 打印一个代码后挂断。该凭证存储在 `/etc/robot/hf-token` 中，并会自动更新。目前还没有消耗它的内容 —— 这是 §3 的内容，也是下一个要实现的部分。

关于依赖服务的现状，通过探测而不是阅读文档来确定：

- **Hugging Face 实现了 OAuth 设备授权**，并且 `huggingface_hub` 提供了一个 **第一方公共客户端** (`DEVICE_CODE_OAUTH_CLIENT_ID`)，因此无需在任何地方注册 OAuth 应用。§2.3。
- **令牌有效期为 30 天**，附带一个刷新令牌，且 **每次刷新时刷新令牌都会轮换**。§2.7 记录了这一过程的成本。
- **令牌携带 Hugging Face 授予的所有权限** —— `write-repos`、`manage-repos`、`jobs`、`read-billing` —— 因为第一方客户端不接受 `scope` 参数。§2.4，这是在鸭子发布前需要更改的唯一事项。
- **`/oauth/userinfo` 在一次往返中返回身份信息**，因此无需解码 JWT。
- **会话服务归我们所有**，它是 `pollen-robotics/reachy_mini_central` —— 一个在 Space 中的 FastAPI 应用，可由我们读取和修改。本页面以下关于它的所有内容都是从该服务器读取的，而不是从客户端推断出来的。
- **其通信协议不是基于 WebSocket 的 gst 信号协议**。它使用 **HTTP** 的相同 JSON 封装 —— SSE 入站，`POST` 出站，`Authorization: Bearer` —— 并带有每跳的对等方和会话 ID。这纠正了 `remote-webrtc.md` §7 中的一个说法；§3.2 记录了这一过程的成本。

## 1. 使鸭子可访问需要满足的条件

四个条件，而机器人目前一个也没有满足：
1. 一个标识机器人所属账户的凭据（§2）；
2. 一个机器人向外访问的服务，该服务仅向其所有者展示（§4）；
3. 从该服务到 `ws://127.0.0.1:8443` 的桥梁（§3）；
4. 一个从某个客户端说话的服务的 wire 的服务端，该客户端可以从其可访问的地方获取（§5）。

此外还有 NAT 穿越，这是媒体路径的属性，而不是上述任何部分的属性（§6）。

四个部分都受到一个不变量的约束，而且这里不能妥协：**本地模式不能依赖于任何这些内容**。`architecture.md` 的第一个不变量是本地恢复保持独立，而 `remote-webrtc.md` §7 将其扩展到媒体——如果服务不可用，局域网客户端仍然可以连接。为了这个原因，每个可能的选择都选择了不通过服务路由本地会话，而 §3.1 则为此付出了代价。

## 2. 账户是一个针对 Hugging Face 的 OAuth 设备流

**该流程存在于 [`hf-robot-account`](https://github.com/pollen-robotics/hf-robot-account)**，
其独立的仓库，因为其中没有任何关于鸭子的内容：任何没有浏览器的机器人以同样的方式登录。保留在 `updater/src/account.rs` 中的是关于 *这个* 机器人的事实——令牌路径、`robot` 组、映射到 `proto` 的内容，以及每个拒绝应得到的 JSON-RPC 代码。关于该流程本身的一切描述都在该 crate 中；关于凭据落地和谁可以读取它的一切描述都在这个仓库中。

### 2.1 为什么选择设备授权，这也是 `reachy_mini` 的最终选择

`reachy_mini` **同时**拥有这两种方式。它最初使用授权码 + PKCE，将重定向 URI 指向机器人的 HTTP 服务器——`http://reachy-mini.local:8000/api/hf-auth/oauth/callback`，或对于有线版本则是 `localhost`——后来又添加了设备码流，该流程在其源代码中描述为“具有刷新能力、无重定向的登录”，现在其移动应用的设置向导使用的就是这种方式。选择这两种方式的原因如下。需要知道这并不是意见分歧：这是从不同方向得出的相同结论。

重定向流程带来了三个成本：
- **每个主机名一个注册的重定向URI。** 应用程序只有一个，因此移动应用携带一个回环HTTP桥接器，该桥接器在`127.0.0.1:8000`捕获HF的回调，并将其重写为自定义的`reachymini://`方案——这是一个整个组件，其声明的目的就是避免在HF侧进行配置更改（`features/auth/oauthLoopback.ts`）。
- **浏览器必须能够解析并访问机器人。** 回调是一个在机器人上的URL。因此登录需要在机器人的网络中，并且mDNS工作正常，这与`webrtc-console.md` §2中为一个页面所讨论的同一类问题相同。
- **这是一个没有浏览器的设备上的浏览器流程。** 机器人不是认证方；它只是托管了着陆垫。

设备授权则颠倒了这一点：机器人向HF请求一个代码，说“打开hf.co/oauth/device并输入M8HJ-FMGN”，然后进行轮询直到有人完成。没有重定向URI，没有主机名，没有要求授权设备能够访问机器人——一部在蜂窝网络上的手机就足够了。这正是为一个没有浏览器和键盘的设备指定的流程，而鸭子就是这样的设备。这也是唯一一个能够产生 **刷新令牌** 的流程，这使得机器人在第一个月之后仍然可达（§2.7）。

明确的成本：有人需要输入八个字符。这就是全部内容，而且比它移除的mDNS依赖要小。

**从`reachy_mini`的向导继承的三个不变量，其中没有一个是关于Python的，所有这些都是通过昂贵的方式学到的：**

- **以代码开头。是否打开浏览器是表面的属性，而不是规则。** 小型设备的应用程序了解到自动切换到Safari会隐藏代码，以至于任何人都无法阅读——但这是一部 *手机*：浏览器替代了唯一的屏幕并将应用程序置于后台，因此代码消失了。终端会将其保留在滚动缓冲区中，同样的推理在这里给出了三个不同的答案：
  - `robotctl account login` 在没有任何显示的机器人上运行，因此不会打开任何内容，只会打印代码并等待。
  - `duckctl account login` 会在打印代码之后打开页面，因为它是在你的机器上运行的——而 `duckctl open` 会自动启动浏览器。`--no-open` 选项可以抑制此行为，同样，如果 stderr 不是终端，也会抑制此行为，因为在一个脚本中打开浏览器窗口会让人感到意外。无法启动的浏览器会附在代码之后作为警告，而不是替换代码。
  - 一个手机应用会按照迷你机器人的规定行事，因为迷你机器人的原因如此。

  **打开页面带来的好处是导航，而不是输入。** 本节的早期版本声称机器人可以传递一个包含代码的 URL，这基于迷你设置文档中的一条注释，说明 `huggingface_hub` 会合成一个 `?user_code=` 形式的 URL。实际上并非如此——它会保持 `verification_uri` 不变——并且 HF 的设备页面会忽略该参数，这一点在本节发布后由浏览器确认。因此，`verification_uri_complete` 今天仍然是一个简单的页面，并且仅保留在回复中，因为一个服务器开始发送真正的页面时，无需进行线缆更改。
  - **客户端在中间流程中消失是预期行为，而不是错误。** 打开 HF 页面会后台运行一个手机应用，而 iOS 会在那个点断开 GATT 连接。到那时为止，传输已经完成了它的任务：守护进程正在轮询，客户端会回到 `status`。这就是为什么 `login` 返回的是代码而不是令牌，而 `robotctl` 的等待循环小心地不依赖于此。
  - **出现在会合点才是唯一的真正成功信号。** 存储的令牌意味着 *登录* 成功，而不是机器人可访问——他们的向导会将“具有我的硬件 ID 的机器人在列表中”视为完成，而其他情况则视为可恢复。§3 必须在这里提供这个检查，而 `account.status` 报告中继状态将是它所在的位置。

### 2.2 流程及其构建的对话记录
```
POST https://huggingface.co/oauth/device
     client_id=26be6b09-91c5-47da-9861-d2d2bb7a7e36

  → {"device_code":"41ad39ae-…","user_code":"A6MY-0314",
     "verification_uri":"https://hf.co/oauth/device","expires_in":300}

POST https://huggingface.co/oauth/token
     grant_type=urn:ietf:params:oauth:grant-type:device_code
     &client_id=26be6b09-…&device_code=41ad39ae-…

  → HTTP 400 {"error":"authorization_pending"}      until somebody approves it
  → {"access_token":"…","refresh_token":"…","expires_in":2591999,
     "token_type":"bearer","id_token":"…","scope":"manage-repos write-repos …"}

GET  https://huggingface.co/oauth/userinfo   Authorization: Bearer <access token>
  → {"name":"Rouanet","preferred_username":"PierreRouanet","orgs":[…], …}
```
No `scope`被发送，因为第一方客户端不需要（§2.4）。这回答了五个问题，每个问题都不需要现在做出决定：

- **没有`verification_uri_complete`，也没有合成一个的方法。** 没有携带代码的URL——HF的设备页面忽略了`?user_code=`——因此代码必须由**客户端**的人阅读，而不是守护程序。该字段以原始的`verification_uri`形式传递，这样稍后发送真实值的服务器无需进行任何更改。
- **没有`interval`。** RFC 8628中的五秒适用，`slow_down`增加了五秒。
- **`expires_in: 300`**在*代码*上。五分钟：足够长不会催促，但又足够短使得客户端可以显示剩余时间，这也是`account.status`倒计时而不是重复原始数字的原因。
- **`expires_in: 2591999`**在*令牌*上，带有`refresh_token`。§2.7。
- **`/oauth/userinfo`在一个往返中提供了身份信息**——`preferred_username`是用户名，`name`是显示名，可以是任何内容，因此存储和显示的是用户名。替代方案是解码`id_token`，这需要一个JWT解析器和一个相同的字符串的JWKS获取。
  **这是最后一次机会也是最不重要的一个，因此不能允许它影响登录。** 到运行时，有人已经在电话中输入了代码；因为代理返回502而导致丢弃令牌会使他们不得不重新进行整个流程以获取标签。因此，记录存储时没有名称，`account.status`回答`unknown`而不是“已注销”，下次`maintain`处理会填充这些信息——失败的网络正是这个板块预期拥有的网络。

一次登录，且门卫覆盖往返而不是检查之前。两个同时到达的调用者——一个控制台页面和一个电话，在设置期间这是正常情况——否则会同时收到一个代码，存储会保留最后一个批准，而有人阅读另一个代码并看着它无所事事。第二个调用者会收到`BUSY`，而第一个调用者正在飞行——因为它有自己的消息，因为“另一个更新正在进行中”是`BUSY`在其他地方说的内容，这会让人去错误的地方寻找。`account.status`携带代码，因此一个丢失了跟踪的客户端可以重新加入它而不是开始另一个。
**拒绝必须指出一条通过的方法，而在这里`force`就是那条路。**一段没有人会批准的代码——通常的情况，有人开始登录然后就走了——否则会让机器人等待五分钟，唯一的补救办法是`logout`，这会破坏一个有效的凭证以清除一个待处理的凭证。`force`已经意味着“替换这个机器人所属的内容”；替换一个*尝试*也是同样的权限，只是规模较小。

**这所付出的代价是，一个被放弃的流程仍然持有活生生的设备码**，如果有人最终批准它，Hugging Face 也会批准。这个流程存在于一个任务中，该任务的生命周期长于启动它的调用，因此`logout`也是如此：用空中一个代码签出一个机器人，一分钟后的批准会自行将其签入。因此，每个流程都携带它被启动时的生成信息，并在存储被触碰前后检查它是否仍然是当前的——因为写入等待——所以一个过时的登录保留其代码并丢弃其答案。这也正是`logout`能够兑现它承诺的原因。

### 2.3 OAuth 客户端是 Hugging Face 的——**封闭**

`huggingface_hub`提供了一个**第一方公共设备码客户端**，`DEVICE_CODE_OAUTH_CLIENT_ID` = `26be6b09-91c5-47da-9861-d2d2bb7a7e36`，这是`hf auth login`使用的。它是公开的——没有秘密，因此除了一个公共标识符之外不需要将任何内容嵌入到发布中——并且不需要在任何地方注册 OAuth 应用程序。`hf_robot_account::HUGGINGFACE_CLIENT_ID`就是这个常量，这也是这个决定的全部内容。

记录了两个替代方案，因为第一个看起来显而易见且被阻止了：

- **`reachy_mini`自己的应用** (`71146982-…`) 是一个**保密**客户端，因此设备端点拒绝它——*"如果你想在没有客户端秘密认证的情况下使用设备码流程，请从 OAuth 应用中删除秘密"*。将这个秘密嵌入到每一个鸭子中使其不再保密，而使应用公开则会改变 mini 的姿态以适应我们。

- **动态注册。**`POST /oauth/register`未经过认证并且支持`token_endpoint_auth_method: "none"`，因此一个机器人可以在首次登录时生成自己的公共客户端。这有效。现在这没有意义，而且每个机器人一个客户端将是一支无法枚举或撤销的身份舰队。
The first-party 客户端 不带 `scope` 参数，并且它发放的令牌包含了 Hugging Face 分配的一切：
```
manage-repos write-repos read-repos gated-repos contribute-repos write-collections
read-collections openid write-discussions inference-api jobs webhooks read-billing read-mcp
```
A 鸭子因此持有一个凭证，可以 **推送至其所有者的仓库、启动作业和读取其账单** —— 这个凭证的整个目的是向会面服务证明身份。每一只在野外的 Reachy Mini 都处于同样的位置；那是上下文，而不是一种防御。

实际上，该账号需要的是 `openid profile`，加上 `read-repos` 用于一件真实的事情：`policy.install` 从同一个令牌文件中的一个 **私有** 策略仓库获取，无需新的机制（`policy-channel-design.md` §7）。

因此，狭义版本是一个由 Pollen 拥有的公共设备代码客户端，带有 `openid profile read-repos` —— 一个 `Config::client_id` 和一次由 HF 组管理员点击。它不是阻塞的：流程今天就可以工作，权限范围的更改只需重新登录。在任何人带鸭子回家之前做这件事是值得的，因为失败模式是不对称的——一个一直能够写入的机器人无法被撤销，而一个稍后需要更广泛范围的机器人只需请求一个。

### 2.5 令牌存放在哪里，谁来写它

`/etc/robot/hf-token`，`root:robot`，`0640`。JSON：访问令牌、刷新令牌、一个绝对的 `expires_at`（响应提供了一个持续时间，而持续时间在重启后毫无意义）和用户名，因此 `account.status` 在没有网络的情况下也能回答——一个离线的机器人仍然知道它属于谁。

**写入时为 `0600`，设置组后放松为 `0640`**，而不是像其他此守护进程写入的内容那样通过 `fsutil::write_atomic`。那个辅助程序不会设置模式，一个以 `0644` 写入的令牌在稍后被 chmod 改变模式的瞬间是可世界读取的——这种窗口在测试中是看不见的，在 `ps` 和 `cat` 之后却是永久的。`account::write_private` 从一开始将临时文件打开为 `0600`，并测试断言落地文件对“其他人”没有任何信息。在没有 `robot` 组的板子上——开发者的笔记本电脑、半配置的板子——它保持为 root 只读，并且只说一次，而不是猜测。

**不在 `robotd.toml` 中。** 该文件中存在的一切机制都不适合用于秘密：`robotctl configure --list` 打印出机器人更改的内容，`policy-channel-design.md` 的全屏编辑器显示该文件，“在该机器人上已更改的内容”是我们现在生成的报告。一个授权令牌会在所有三个输出中出现。它自己的文件、它自己的模式，就是它能得到的全部保护——而 §7 说明了为什么这已经足够。
**`updaterd`拥有它。**它已经具备了HTTP客户端，已经替机器人访问网络，已经以`root`身份运行，并且其调用空间包括写系统状态的函数（`policy.*`）。`configd`拥有配置，没有HTTP客户端，为回答`system.info`请求的守护进程添加对外网络出口将是一种新的做法。`mediad`不能拥有它：它以`User=mediad`身份运行在`ProtectHome=yes`下，并且是远程对端与其通信的进程。

**`mediad`将读取它**——在每次连接尝试时，以及在没有连接时的慢速轮询（30秒），这也是它的“等待令牌”状态。未构建：在§3存在之前，没有任何内容会消费该凭证。没有跨守护进程的通知：`reachy_mini`有一个来自其认证路由器到其转发器的`notify_token_change`调用，而在即将发生的重新连接中重新读取文件是不必要的。代价是，一次新的登录需要最多一个轮询间隔才能成为活跃生产者，而没有人能够察觉。

### 2.6 调用及其可到达的传输方式

`account.login`，`account.status`和`account.logout`在`updaterd`上——出于`policy.*`相同的原因：它是具有网络堆栈的守护进程，`robotctl`不能链接一个（它处于恢复路径上），并且它存储的凭证也是通往私有Hub仓库的路径，这已经是该守护进程的工作。`configd`拥有配置，不拥有凭证，也没有HTTP客户端。`mediad`不能拥有它：它以`ProtectHome=yes`下未特权的身份运行，并且是远程对端与其通信的进程。

**`login`会返回一个代码并把等待交给守护进程。**没有进度通知也没有长连接；客户端会轮询`status`。这不是简化，而是要求——参见§2.1的第二个不变量。

**所有三个调用都会路由到所有三个传输方式**：本地、BLE和WebRTC数据通道。BLE最为重要且是最简单的调用——它是唯一一种能够到达刚从盒子中取出的机器人的方式，因为这种机器人没有网络，因此没有控制台也没有局域网可以打开一个，而且它已经有一个设置向导。本地是`robotctl`，这是开发人员做任何事情的方式。

**WebRTC是值得争论的，也是值得写下来而不是假设的。**控制台是放置“登录”按钮的显而易见的地方——一个页面上已经显示了机器人——而替代方案则是ssh或手机。相反：这是一次通过该传输进行的通话，其效果是以**其他任何事物都无法比拟的方式持久化**。局域网对端所做的其他一切都在会话范围内；`account.login`将“曾经在无线网络中出现过”转化为持久化的远程访问，而这种访问超出了在那里的存在。`remote-webrtc.md`的第4节接受网络上的任何人都可以拥有机器人及其摄像头。它没有考虑下个月来自另一个大陆的网络用户也能拥有它们。

有三件事使得这种情况是可以接受的，而不是仅仅被允许的：

- **一个已经属于某人的机器人会拒绝。**如果没有`force`的`account.login`会以`INVALID_PARAMS`命名账户作出回应，因此局域网对端不能默默地从其所有者那里夺取机器人——它必须明确表示，而一个行为良好的客户端必须先询问一个人。
- **它是可见的。**`account.status`从任何传输中命名账户，无需任何授权。“这个机器人属于哪个账户”这个问题任何人都可以问。
- **它是可撤销的**——可以从任何地方通过`account.logout`撤销，还可以在Hugging Face上撤销授权，而没有任何机器人端的门禁可以提供这样的功能。
  精确描述第一个部分，因为它有两个部分，只有一个部分是`updaterd`的。
  `logout`删除凭证，代理在一次心跳——十秒——内注意到并断开连接，在此服务中会立即驱逐生产者。因此，一个已注销的机器人将不再被列出且不再可被访问。它不会做的事情是撤销任何东西：**`logout`删除机器人的副本并向Hugging Face nothing。** 机器人停止成为生产者，这就是注销所追求的效果——但其持有的访问令牌在Hugging Face上仍然有效，直到它过期，最长为三十天，对于已经读取文件的任何内容都是如此。凭证是`0640 root:robot`，因此“任何内容”意味着该板上的root或`mediad`；被盗的板是需要考虑的情况，对于这种情况，答案是在hf.co上的账户的connected-apps页面，而不是在这里调用。从机器人发送撤销请求是一个§9的候选方案，并且在这一切片中故意不包括：它需要将端点与第一方客户端进行比对，而不是假设，而网络连接失败导致的`logout`仍然需要在本地忘记令牌。

**另一个文件中存在一个后果，并且它发现了一个错误。** `account.login`和`account.logout`是`Call::is_mutating`，这是`updaterd`针对对等方的uid授权的，因此`mediad`必须在`deploy/updater.toml`中与`btd`一起添加到`allow_users`中。

**精确描述它所授予的内容，因为它不仅仅是一个账户。** `allow_users`是针对调用者的门，而不是针对方法的：`updaterd`现在执行`mediad`发出的任何突变调用，包括`update.apply`。阻止远程对等方应用更新的是`mediad`自己的路由表，它拒绝转发——因此该表不是多个限制中的一个，它是唯一的，处于最暴露于陌生人流量的进程中。`btd`自BLE可以应用更新以来一直具有这种形状，并且同样的答案：边界是一个带有测试的命名列表，`mediad::route`的`only_these_mutating_calls_are_reachable_over_webrtc`，因此路由新的突变方法需要故意更改该列表并说明原因。`updaterd`中的每个方法门将使其成为两层而不是一层；它尚未构建，而这个注释说明了选择而不是被忽略。
Writing它下来立即发现了两个之前没有人注意到的错误方法：
**`policy.install` 和 `policy.fetch` 被路由到 WebRTC 而 `mediad` 没有在 `allow_users` 中，** 所以 `updaterd` 返回 `PERMISSION_DENIED` — 控制台可以提供一个 Hub 浏览器，但其安装按钮无法工作。这里为账号添加的 `allow_users` 行也修复了它们。这就是命名列表优于计数列表的理由：列表是传输的权限和配置文件的授予必须明确同意的地方。

### 2.7 令牌在30天后过期，刷新令牌会轮换 —— **已关闭**

设备码令牌返回 `expires_in: 2591999` — 三十天 — 并带有 `refresh_token`，刷新会 **轮换** 它：答案携带一个新的刷新令牌，旧的令牌作废。所以存储是两个字符串加上一个时钟，且有三个值得命名的后果。

**一个简单的机器人如果被闲置必须重新认证。** `hf_robot_account::maintain` 每六小时唤醒一次，刷新任何剩余时间不足一周的项 — 在令牌生命周期的三分之四处，留出一周的重试时间给网络状况不佳的板卡。它会无条件启动，不同于更新调度器，因为一个关闭了更新检查的机器人在一个月后仍然会停止工作。

**轮换留下一个无法关闭的窗口。** 在“Hugging Face 发布了一对新令牌”和“这对新令牌已写入磁盘”之间，旧的刷新令牌已经作废。在该窗口中突然断电会使机器人持有 Hugging Face 不会续期的凭据。没有写入顺序可以解决它 — 轮换发生在对方 — 所以它被处理而不是预防：写入是原子操作（读者看到旧的一对或新的一对，但从不会看到一半的一对），失败会在 `account.status` 的 `last_error` 中显现，修复方法是重新登录。提前一周重新认证使其成为不便而不是中断。

**一个超过30天未启动的机器人需要重新登录才能恢复**，没有任何余地可以挽救它。`account.token_expires_in` 变为负数，这是客户端用来表示这种情况的方式，而不是让某人等到机器人未出现时才发现。

## 3. 桥接

### 3.1 一个回环监听器，而不是 `webrtcsink` 内部的信号器
`webrtcsink` 接收一个自定义会话器（`Signallable` 接口），因此很容易实现一个可以直接与会话点进行通信的会话器：少一个跃点，没有 ID 转换，也没有本地 WebSocket 客户端。**被拒绝**，原因在于结构而非美学：一个 `webrtcsink` 只有一个会话器。将其指向服务意味着本地会话也会通过服务进行 —— 这破坏了 §1 的不变性 —— 保持两者意味着另一个 `webrtcsink` 从 T 型连接器上分叉出来，这意味着在预算有限的编码器上重复编码相同的帧。

因此，桥接器就是 `remote-webrtc.md` §7 所描述的，也是 `reachy_mini` 运行的：
```
  rendezvous  ──SSE──►  relay task  ──ws──►  127.0.0.1:8443  ◄──ws──  webrtcsink
  (HTTP)      ◄─POST──  (in mediad)  ◄──ws──  signalling server      (the producer)
```
The relay向服务注册为一个**`producer`**，向本地服务器注册为一个**`listener`**——在两边的角色是颠倒的，因为对服务而言它*是*机器人，而对管道而言它是一个请求会话的对等体。

### 3.2 它翻译了什么，以及对§7的修正

§7说“桥梁解析不了任何东西。它代理了gst信号协议，这与局域网客户端使用的协议相同。”实际上，载荷——SDP和ICE——确实是不透明的，并且保持这种状态。信封在三个方面有所不同：

| | 本地侧 | 会面侧 |
|---|---|---|
| 传输 | WebSocket | SSE入站，`POST /send`出站 |
| 认证 | 无（`remote-webrtc.md`的第4节） | `Authorization: Bearer <hf token>` |
| ID | 自己的`peerId`，自己的`sessionId` | 每跳不同，按跳 |
| 我们的角色 | `listener` | `producer` |
| 回复到达的位置 | 在套接字上，总是 | **`sessionStarted`和`list`在`POST`响应体中**；其他一切都在流中 |

最后一行花费了整整一个下午，应该放在表格中而不是某人的记忆中。在WebSocket中，每个答案都返回到套接字上，因此客户端自然地将发送视为“发送即忘记”。在这里，`handle_start_session`将`{"type":"sessionStarted","sessionId":…}`返回给`POST /send`的调用者——生产者通过SSE被通知，消费者在响应中得到答复——而一个丢弃了该响应体的页面收到了一个它从未被告知ID的会话的机器人提供的会话邀请，然后因null对等连接而失败。`list`也以同样的方式回答，并且在欢迎之后也通过流推送，这就是为什么列出的一半看起来健康而会话的一半却损坏了。

因此，桥梁在两个方向上都维护了一个会话表，并在每个`peer`消息中重写`sessionId`。这就是`reachy_mini`的relay需要最多疤痕的地方（§3.4），这也是诚实的描述：**一个带有不透明载荷的翻译器**，而不是一个relay。§7为`webrtcsink`相对于`webrtcbin`所声称的收益仍然存在——协议仍然存在而不是被发明，翻译是一个表格而不是解析器——但“代理，不解析任何东西”应该停止被说。

### 3.3 租约，以及心跳为何不可选

服务会在发送消息超过 `LEASE_SECONDS` 后驱逐一个生产者，无论其套接字状态如何。这并不是服务的过度防御性设计：半开的 TCP 连接——无线网络断开、NAT 重绑定、一个休眠的 captive portal——会默默地吸收服务器推送的保持连接消息数分钟之久，在此期间，机器人会认为自己是可达的并且不会被驱逐。

从服务器的数据来看：`PRODUCER_LEASE_SECONDS` 是 **30**，而 SSE 欢迎信息中广告了 `recommended_heartbeat_interval_seconds: 10.0`。租约仅基于入站 `POST /send` —— 一个健康的 SSE 流刷新 nothing。

因此，中继会以欢迎信息命名的频率重新发出 `setPeerStatus`，退而求其次为 5 秒，并且限制在 [1 秒, 60 秒] 之间，以便一个配置错误的服务既不会要求请求风暴，也不会让我们陷入比我们自己的驱逐频率还要慢的频率。`reachy_mini` 的梯子有一个中间台阶 —— `lease_seconds / 3` —— 用于发布租约但不发布频率的服务器。**这个服务器不发布 `lease_seconds`**，因此这里这个台阶是不可达的；不值得为一个不发送此字段的字段重复协商步骤。

**在 `GET /events` 之前 `POST /send` 会返回 400，因此顺序不是首选项。** 对方直到流存在时才存在——身份来自承载令牌，而令牌由 `/events` 连接绑定到一个对等体。§3.4 希望在任何报告机器人可达之前先进行注册，出于不同的原因；服务同样强制执行相同的顺序。

**每 60 秒每个对等体的请求数限制为 1200 次，滑动窗口。** 10 秒的心跳和 30 秒的轮询每分钟产生九次请求，因此它在此处不会限制任何东西——在有人缩短间隔以“安全起见”之前知道这是一个天花板就足够了。

**SSE 侧有自己的保持连接机制来衡量。** 在 30 秒内没有任何可交付的内容后，服务器会发出一个 `event: ping`，其唯一任务是阻止 Space 前面的 HTTP/2 代理因闲置而关闭连接。因此，我们这边的读超时必须比 30 秒多出一大截——`reachy_mini` 使用 60 秒，即两次错过的心跳，这就是我们要采用的数字。

### 3.4 已知的失败模式是主要原因，促使我们阅读其中继

四个，每个现在构建起来便宜，但重新发现起来昂贵：
- **分裂脑。** SSE 流是健康的并且服务不再列出我们 — 一个 `setPeerStatus` 往返在半途取消留下的就是这种情况。连接中的任何东西都没有注意到。他们的回答是每 30 秒轮询 `/api/robot-status`，并在连续两次错过之后强制重新连接。
- **并发会话。** 服务器对此进行了限制 — `handle_start_session` 以 `sessionRejected` 回应 `reason: "robot_busy"` 并推送 `sessionStateChanged` 到所有者的其他设备，使其 UI 在往返过程中翻转。因此，机器人端的限制是双重保险而不是一个变通方案，而且它应该保持不变：第二个对等体驱动同一个机器人是 `remote-webrtc.md` §9 的交错错误，两个远程写入者而不是一个垫子和一个对等体，这是一个需要检查两次的糟糕结果。
- **注册时的顺序。** 在报告 `connected` 之前先注册为生产者，或者每个观察者 — 一个状态调用、一个页面、一个人 — 都会看到“远程访问已启用”而服务还不知道机器人的存在。
- **带抖动的退避重试，上限。** 5 秒增长到 60 秒，加上约 10%。在服务重启后整个车队同步重新连接是一个自作自受的故障。
- **连接下更改的凭据。** 令牌在每次连接时只读取一次，因此 neither 一个 `logout` 还是另一个账户的 `login --force` 能单独达到运行中的中继 — 它会继续用其所有者已删除的凭据刷新租约。在心跳脉冲上重新读取，这使得延迟为一个节拍，而断开连接流是注销：一个干净的断开连接会立即驱逐对等体，而扫除仅针对从未报告关闭的套接字。还有一个显式的 `roles: []` 撤销，这是为了保持通道打开以稍后重新注册而并非这是想要的。
- **401 不是退避重试的情况。** 无论重试多少次都无法修复服务拒绝的令牌；需要登录。因此，这条路径与无人登录的机器人的 30 秒节拍一起等待令牌文件，而不是每五秒向别人的 Space 发送一个注定失败的请求。
Two 更多来自它们的源代码，关于服务器的行为而非如何操作它。**只有携带 `meta.hardware_id` 的生产者才会被清除**，因此没有它的生产者永远不会被驱逐 —— 一个崩溃的守护进程会一直徘徊在它的主人的机器人列表中，直到太空重启。这将§3.7 的 "应该" 变成了 "必须"。并且 **同一个令牌下的第二个 `/events` 覆盖了连接而没有驱逐对端**，因此一个守护进程在它之前的套接字半打开时重启会干净地重新连接 —— 这正是60秒的读取超时变得安全而不是仅仅勇敢的原因。

我们 **不** 复制它们的 `RobotAppLock`：它仲裁本地的应用程序与远程会话之间的争端，而鸭子没有应用程序。`remote-webrtc.md` §9 拥有这里的等效问题（一个便签和一个对端同时发送意图），并且故意推迟了它；第二个远程对端是同一个缺口，而不是一个新的缺口。

### 3.5 它是 `mediad` 中的任务，在不包含 GStreamer 的模块中

不是一个新的单元。一个 `relayd` 需要自己的一份生产者身份、自己的配置以及自己的重启故事，而且没有 `mediad` 运行的话它还是无用的 —— 这意味着增加了三个新的移动部件来隔离一个 websocket、HTTP 客户端和哈希映射的任务。

它会去 `session.rs` 所去的地方，出于同样的原因：**故意是传输无关的**，因此可以在笔记本电脑上针对一个假服务和一个假本地服务器进行测试。这使得控制通道可以在没有硬件的情况下进行测试，并且在这里的价值是双倍的，因为 §3.4 中的每一个失败都是一个时间上的失败，而手动硬件测试无法在需要时进行再现。

继承的一个规则：GStreamer 信号处理器中不能有任何导致程序崩溃的内容（`pipeline.rs` 的头部注释以及它所教给我们的过程终止）。继电器从不接触它 —— 但它最终会想要 *到达* 管道事件，这就是需要保持干净的边界。

### 3.6 一个桥接对端可以调用的：与局域网对端可以调用的完全相同

会话是同一个 `webrtcsink` 会话，`route.rs` 是同一个表。这是故意为之，并且这也是值得在它工作后重新审视的部分：§4 论证机器人不需要网关，因为服务已经对两端进行了认证，而在本页之后这个论点变得更加强大 —— 一个桥接对端已经证明了账户所有权，而一个局域网对端只证明了它在 WiFi 上。机器人可以通过源地址（§7 中提到）来区分它们，并且目前还没有任何东西会对此做出反应。保持这一点的真实性。

### 3.7 一个鸭子必须自己调用的，而且它并不是自由格式的

`meta` 是自由格式的，但服务器会读取其中的两个键，因此随意填写的鸭子会表现出微妙的错误行为，而不是明确的失败：

- **`hardware_id`**（或 `install_id`）是**稳定标识符键**。在 `setPeerStatus` 时，服务器会寻找同一位用户的另一个携带相同值的生产者，并将其移除——如果该生产者有会话，则结束其会话。它存在是因为重新刷写守护程序、复制 SD 卡或陈旧的托盘进程会以第二个机器人永久出现。

因此，鸭子**必须**放置一些稳定的信息，而显而易见的候选者已经存在：`producer.rs` 读取 SoC 串号以填充本地 `meta`，这正是“在重新安装和重命名后跨物理机器人保持稳定”的信息。如果省略该键，则重新连接并带有新令牌的机器人会被列出两次——并且，由于该字段上的扫掠键，它永远不会被移除；将 *名称* 放在那里意味着重命名机器人会分裂其身份。

如果没有可以读取的串号——例如开发者的笔记本电脑、设备树中没有串号的电路板——则会退回到 `/etc/machine-id`，该值在安装层面保持稳定，而不是在机器人层面。这虽然较弱但仍符合目的：一台机器被列出一次，生产者仍然可以被扫掠。`sounds` 已经出于同样的原因和同样的理由进行了这样的替换。
- **`simulated`** 是我们自己的，而不是服务器的，且服务器从未读取该键：在 MuJoCo 中注册的鸭子与机器人完全相同，如果无法区分它们的列表会导致有人在模拟中驾驶，而困惑为什么架子上的机器人仍然在工作。`configd --simulated <serial>` 是事实的声明之处，而 `docs/design/simulation.md` §8 是为什么仅在此处声明的原因。该序列号也是使模拟鸭子的 `hardware_id` 起作用的原因：`/etc/machine-id` 的退回到安装层面，因此共享同一台机器的鸭子会相互移除，而 macOS 完全没有这样的文件。
- **`name`** 是列表中显示给人的信息，而消费者的 `name` 是服务器报告给所有者其他设备的 `activeApp`。`transport`（`"wifi"` / `"usb"`）是一个鸭子可以忽略的小细节；`kind` 为 `microduck` 允许一个客户端同时列出两个家庭而无需打开会话。
**并且一个协议事实及其后果：节点由令牌键入。**`get_or_create_peer` 是一个 `token -> peer_id` 映射，且同一令牌上的第二个连接会取代第一个。因此，两个共享令牌的事物会轮流保持可达状态，且双方都不会看起来是断开的。每个鸭子都会运行自己的设备流程，因此没有两个机器人共享一个——图像是从头构建的而不是克隆的，因此没有途径将凭据复制到第二个板上。

  问题在于一个 **消费者**：一个云后端，它使用 *机器人的* 令牌进行身份验证会取代机器人的节点，并将其从列表中移除。一个空间消耗一个鸭子需要在同一个账户上使用自己的令牌，或者访客的令牌。§5的客户端使用访客的令牌，这就是为什么它从未遇到这种情况。

## 4. 会面是 `reachy_mini` 使用的 —— **决定**

`pollen-robotics-reachy-mini-central.hf.space`，即迷你队列已经注册的空间。决定而不是推导：它不需要后端工作，已经在实际机器人中得到了验证，而本页的整个内容都成为客户端项目。

机器人从它那里需要的东西很少：`GET /events`（SSE，`Authorization: Bearer <hf token>`），`POST /send`（相同），以及 `GET /api/robot-status` 以询问它是否仍然在列表中。它的 `meta` 是自由格式的，因此鸭子会注册任何标识它的内容——而 `producer.rs` 已经组装了列表所需的字段（名称、序列号、发布日期、`api_version`），这正是 `webrtc-console.md` §5 预测会面需要的内容。一个 `kind` 为 `microduck` 的字段会放在同样的结构中，因此一个列出用户机器人的客户端可以不打开会话就能区分鸭子和迷你机器人。

**我们拥有它**，这就是为什么这被视为重用而不是依赖的原因：`pollen-robotics/reachy_mini_central` 是一个在空间中的 FastAPI 应用，可以从这里读取和更改。由此引出两点：
- **协议是一个事实，而不是猜测。** §3 中的每一个数字——30秒基于 `POST /send` 的租约，10秒的广告周期，30秒的SSE心跳，`sessionRejected` 门限，`hardware_id` 的驱逐——都是从 `app.py` 中读取的。早期版本的页面曾说仓库是私有的；那是一个错误名称的401错误，被误认为权限错误，而客户端的通信则是无理由地反向读取的。
- **鸭子的需求是一个拉取请求，而不是一个分支。** 如果鸭子想要不同的租约时间，或者一个筛选器来列出不同的租约，或者一个不假设每个令牌对应一个机器人的驱逐规则，那么这些都是我们维护的服务器上的更改。这也意味着相反的情况：在服务器上为迷你版所做的更改可能会破坏鸭子，而在本文之后，迷你版上还有一个第二大家族的机器人。

唯一没有转移的是它的 **锁模型** —— `RobotAppLock`，本地应用与远程会话之间的区别，迷你版的继电器会将传入的会话转发到这个模型上。鸭子没有应用，因此 §3.4 中采取了重新连接的行为，而省略了那部分。

## 5. 客户端是一个带有 Hugging Face 登录的 Space —— **决定**

控制台是 `include_str!` 包含在 `mediad` 中，并由机器人（`webrtc-console.md` §1）提供服务，因为客户端在局域网内。**远程客户端无法从它无法到达的机器人那里获取页面**，因此远程客户端需要页面托管在机器人之外，并且需要一个第二信号传输通道。

**决定：`pollen-robotics` 组织中的一个 Space，`hf_oauth: true` —— `microduck-console`** — 该 Space 服务与机器人相同的页面，传输通道由打开方式决定。决定性因素不是托管，而是 **令牌**。

远程消费者与机器人以相同的方式认证到会合点——一个带有 `whoami-v2` 解析的凭据令牌，从答案中读取 `name`。它不做令牌类型检查，也不做范围检查，因此浏览器的 OAuth 令牌与机器人的设备流令牌享有同等地位。这使得整个问题变成了“页面如何获取 Hugging Face 令牌”，而 Space 回答了这个问题：`README` 中的 `hf_oauth: true` 创建了 OAuth 应用并注册了一个指向 Space 的重定向 URI，`@huggingface/hub` 的 `oauthLoginUrl` / `oauthHandleRedirectIfPresent` 完成了其余的流程 **客户端侧**，使用 PKCE，页面中没有秘密。

### 5.0 它是一个 Docker Space，这花费了一个下午
- 采用静态方式的空间应注入 `window.huggingface.variables.OAUTH_CLIENT_ID` — `huggingface.js` 正是读取这一点（`oauth-login-url.ts`），`reachy_mini_website` 也读取这一点，而 HF 也以 `huggingfacejs/client-side-oauth` 作为示例。但在 `microduck-console` 中从未出现过：无论是在元数据更改后、空间公开后、删除并重新创建后，还是在页面获得实际的 `<html><head>` 以供注入器工作后——直到那时，该页面一直是一个纯粹的文档类型。Hugging Face 的 API 将我们的空间和一个正常工作的空间报告为无法区分：两者都是 `sdk: static`，两者都是公开的，两者都有 `hf_oauth: true`，两者都是 `RUNNING`。

因此，控制台是一个 **Docker** 空间：`hf_oauth: true` 将 `OAUTH_CLIENT_ID` 放入容器的环境变量中——这是任何非静态内容的文档路径，也是 `grabette-*` 空间所使用的方式——并且八行 `sh` 代码在页面被服务时将其插入进去。一个不需要服务器的页面有一个，仅仅是因为这个原因。`OAUTH_CLIENT_SECRET` 也在同一环境中，从未接近页面。

在追踪这个问题的过程中，有两件事值得保留。页面 **记录自己的构建时间戳**（修订版本加上页面的哈希值），因为静态主机会缓存，浏览器也会更频繁地缓存，而一个小时花在了一个从未加载的修复上。每次登录的步骤都会 **与超时赛跑**：地址栏中遗留的 `?code=` 会使得 `oauthHandleRedirectIfPresent` 永远等待，而页面对此所能说的一切都在 `await` 的另一边。

在早期版本的这一部分内容中，GitHub Pages 也存在同样的问题：页面需要手动注册一个 OAuth 应用程序并设置自己的重定向 URI，这与 README 元数据到达的地方不同。这仍然是可能的——页面从 `?client_id=` 中获取客户端 ID，因此在写入之前会尝试一个——这与第 2.3 节中选择 Hugging Face 的设备码客户端而不是注册一个客户端的理由相同。

**这不是`reachy_mini_central`中的一个路由。**只有一个主机和一次部署，代价是将鸭子界面UI嵌入到迷你舰队依赖的服务中。§4中的“我们维护它，所以鸭子形状的需求是一个拉取请求”这句话也适用于反面情况：这意味着我们的页面变成了他们的运营风险。

Space是一个部署目标——`pollen-robotics/microduck-console`——而`scripts/publish-console.sh`是将页面部署到那里，同时部署`Dockerfile`和`entrypoint.sh`来提供服务。它从`duck-ipc-proto`中获取API版本，打上构建标签，并拒绝发布缺少任一令牌（端口令牌会使Space的副本尝试打开WebSocket，而客户端ID令牌会使它无法对任何人进行认证）的页面。手动部署时只有一个Space；当这种情况不再成立时，由CI来完成。

一个事情是确定的而不是首选的，它从早期草稿中存活下来：`EventSource`**不能设置头信息**，因此浏览器通过SSE流说话时必须将令牌放在查询字符串中，或者使用`fetch`读取流并手动拆分SSE。`reachy-mini-js`选择前者，**服务器正在移除它**——`_resolve_hf_token`接受`?token=`作为过渡性回退，为每个客户端IP记录一个弃用日志，并在其文档字符串中说明一旦已知客户端发送头信息，查询形式将被弃用。查询字符串中的令牌在Space的访问日志中以及每个代理之间都是一个令牌。因此，页面是`fetch`加上几行行分割的代码，这些代码是一次性编写的。
页面的内容，实际上是 `mediad::relay` 的镜像：SSE 输入，`POST /send` 输出，带有逐跳 ID 的 gst 信号封装，以及一个不透明的 SDP/ICE 载荷——这是另一个方向的相同翻译，这就是为什么在 §3.2 的表格值得在编写之前阅读。

### 5.1 一个在迷你客户端中的鸭子，这是一个对话而非提交

将鸭子放入与 `reachy_mini_mobile_app` 及其桌面版本的其他客户端进行的会合中，意味着鸭子可以在某人的迷你应用中出现——并以迷你应用的方式被操控，使用的方法名是此项目不提供的。视频会到达；其他内容不会到达，失败会被视为一个损坏的机器人。

`meta.kind` 存在以便客户端可以区分不同的家庭（§3.7），并且此页面会对其进行过滤。迷你客户端无法从这里被制作：这是一次与拥有它们的人的对话，并且这是 §4 没有考虑的方向——不是“鸭子需要从服务中得到什么”，而是“鸭子到达服务后会对现有客户端产生什么影响”。

**一个非浏览器消费者今天可以工作，但它的唯一问题是通道标签。**
`ReachyCentralConsumer` — 他们的 aiortc 客户端 — 通过会合连接到鸭子，并在两端都没有添加任何内容进行解码：`pip install "reachy_mini[central-consumer]"`，`robot_name="olducky"`，`latest_frame()` 返回 `(720, 1280, 3) uint8`。验证通过。它在经过时说 `ignoring unexpected data channel: 'control'`，因为它寻找迷你守护进程打开的标签，而我们的标签是 `control`（`remote-webrtc.md` §5）。对于一个感知消费者，它想要像素——而要为一个想要 *驱动* 鸭子的消费者修复的第一件事就是解决标签问题，标签是问题的一半，方法名是问题的另一半。§5.2 是这两半，从这一侧来看。

**他们的两个客户端选择 `meta.name` 并且都不读取 `kind`。** 主机壳的拾取器列出所有在线的项目，`ReachyCentralConsumer` 通过 `robot_name` 与 `meta.name` 匹配，**默认值**：无论其名称如何，只要有一个可见的生产者，就会使用它。因此，为迷你设计的云后端，在仅有一个在线机器人的账户上，选择了鸭子，并用此项目不提供的方法名操控它。在有人遇到它之前，告诉他们这是值得的，而这是他们需要做的两行更改 —— `kind` 已经在传输中。

### 5.2 一个驱动鸭子的消费者，以及它必须通过的一行代码

`spaces/policy-playground`是此仓库中的第二个消费者，也是第一个发送任何内容的消费者：登录、列出账户的鸭子、并从Hub中一键放置一个策略——`policy.fetch`、`robot.setSkill`、`robot.policies`、`robot.do`，这相当于`robotctl policy add`通过数据通道而非Unix套接字的命令顺序。

“驱动”与“观看”的整个成本只是一个标签。`ReachyCentralConsumer`处理`pc.on("datachannel")`，使用`if channel.label != "data": ignoring unexpected data channel`，而`mediad`打开`control`（参见`remote-webrtc.md` §5）——因此，想要像素的消费者不需要任何东西，而想要发送呼叫的消费者根本得不到通道。`RTCPeerConnection`是一个pyee发射器，因此`pc.on`追加而不是替换：一个子类覆盖`_build_pc`注册第二个监听器，他们的仍然运行并且仍然警告他们不知道的标签，而我们的则获取他们丢弃的通道。他们包中的任何内容都没有被重写，这就是为什么它能够存活于修复他们那一边的版本中——当他们的处理器接管`control`时，我们的停止成为第一个声称它的那一方，而补丁就变成了删除。

他们的`send_command`被重用而不是重新实现，并非出于懒惰：`RTCDataChannel.send`不是线程安全的，他们已经将每次发送都封装到拥有对等连接的循环中，而Gradio回调则在请求落脚的任何工作线程中运行。

**两个拒绝，哪一方拥有它们是写作此内容时主要解决的问题。** `policy.fetch`检查关于机器人的声明——`obs_len`、`action_len`、`model_api`、`robot.model`——并且它在下载之前就检查这些声明，因此客户端不应重复这些声明并且应显示机器人所说的内容。`robot.setSkill`不检查命令编码的任何内容：一个一次性安装的阶段策略被**接受**，然后机器人向一个基于阶段训练的网络提供一个恒定值，这可能是合理的动作也可能是错误的动作。这条规则存在于`robotctl`中，而`robotctl`并不在点击的路径中——因此`catalogue.refusal`是这条规则的第二次书写，任何需要增长此按钮的客户端都需要第三次书写。
**一个 `401` 来自rendezvous，只是令牌本身，而证明这一点则需要在猜测错误后阅读其 `app.py`。**最初，这个页面列出的机器人使用了 `GET /api/robot-status`，收到了一个 `401`，并得出结论该端点必须需要一个已建立的对等方——这在一定程度上是合理的，因为 `POST /send` 需要（§3.1 的注释中提到的），并且机器人仅在持有流时才轮询它。实际上并非如此：该路由依赖于 `_resolve_hf_token`，然后是 `validate_hf_token`，这只是一个 `whoami-v2` 调用，没有范围检查，没有令牌类型检查，也没有对等方要求，仅过滤为 `p.username == username`。它自己的文档字符串说明了它的存在——“一个被动的状态指示器，不消耗会话槽”。

这使得它比控制台的 `list` 调用更好，原因已经在§3.7 中说明：对等方是通过令牌键入的，因此浏览器打开的 `/events` 流会取代会话正在使用的流。以这种方式列出的页面无法刷新其列表而不放弃自己的会话。`/api/robot-status` 并未打开任何东西。

`401` 是 **Gradio 的模拟登录**。在没有空间的情况下 — `SPACE_ID` 未设置 — `gr.LoginButton` 表现正常，个人资料是真实的，`_get_mocked_oauth_info` 将 `access_token` 设置为字面字符串 `mock-oauth-token-for-local-dev`。通过 `whoami-v2` 解决令牌的服务拒绝了这一点，这是正确的，症状是一个页面显示“请重新登录”，旁边是控制台列出的同一只鸭子。因此，本地运行必须优先选择 `HF_TOKEN` 或 `hf auth login` 存储的内容，并且模拟是通过值来识别的，而不是通过 `SPACE_ID` 检查——一个真正到达空间外的令牌仍然是一个真正的令牌。

**而这个普遍的教训，这就是为什么现在页面同时记录两处。**四个层次在一个按钮中相遇——一个令牌，一个rendezvous，一个候选对，一个机器人的拒绝——并且所有四个都失败为“什么都没发生”。每个HTTP状态，每个信号帧，每个JSON-RPC行以及每个拒绝都被记录下来，令牌的 *来源* 被命名，而令牌从不被记录下来；`DUCK_LOG=DEBUG` 还添加了流式通知和每个候选的ICE行。面板同时出现在页面和终端上，因为一个空间有无人打开的日志，而浏览器没有stderr。每个层次也可以单独运行——`uv run rendezvous.py`，`uv run catalogue.py`，`uv run lan.py`——这将“它不起作用”转化为行号，而无需对话。
`IntentResult`是客户端在一次尝试中另一个常出错的地方：`robot.setSkill`、`robot.do`、`robot.init` 和 `robot.relax` 返回 `accepted: false` 并附带一个原因，而不是 JSON-RPC 错误，这是有意为之——安全起见，不允许在倒下的机器人上运行策略，并不意味着这是一个失败的调用。只捕获错误的页面会将所有这些情况都视为成功，并且会留下一个不动的机器人而没有解释。

**而传输层则是这一部分最依赖的领域。** 控制通道是通过候选对的同一对使用 SCTP 连接的，因此，如果中继不存在，点击也会随之消失：从数据中心开始的会话可能会协商但最终不携带任何内容。§6 的端点现在会作出响应，因此普通情况得到了覆盖——但计量依赖仍然是依赖，这就是为什么状态行会报告它达到的阶段而不是说“正在连接...”，以及为什么页面有第二种方式。

**`lan.py` 就是第二种方式，它是一个传输而不是第二种设计。** 机器人已经在 `ws://<robot>:8443` 为 `webrtcsink` 的信号服务器提供服务——这是控制台所连接的服务器——并且它携带与会面通过 SSE 和 `POST /send` 传递的相同的 gst 封装。因此，只交换了一跳，而上面的内容没有变化：相同的控制通道、相同的 JSON-RPC、相同的按钮，页面会持有其中任何一个消费者而不需要询问。§3.2 的表格就是全部的不同之处，而将方向转向局域网则移除而不是添加——没有账户，没有租约，没有会面，没有中继，两边都有主机候选者。

这实际上比为死掉的 DNS 记录提供一个替代方案更有价值，并且在§6 修复后保留它的论据就在于此：**它将传输与一切其他部分隔离开来。** 一个在局域网内有效但在会面中无效的点击告诉了你需要查看哪一层，而这个答案之前只是一个猜测。

它的唯一成本在于它是手写的，而会面的那一半是继承来的：从 `net/webrtc/protocol` 和控制台页面读取了十几种封装形状，出错时会保持沉默而不是产生错误。因此，`uv run lan.py` 在回环接口上建立了一个生产者，使用相同的协议并针对它驱动一个实际的会话——欢迎，列表，`startSession`，一个应答的要约，DTLS，SCTP，通道，一个呼叫匹配到其回复。两个 `127.0.0.1` 上的 aiortc 对象并不是鸭子；它们是相同的协议，这也是为什么它会安静地失败的部分。

### 5.3 从机器人发出的帧，这正是§6 所阻止的
- 翻译全文，保持忠实，不总结、省略或添加新内容。
The goal §5.2 的 Space 所追求的是处理这个相机在 Hugging Face 硬件上的能力，而这正是控制通道无法携带的一点：像素是媒体路径存在的意义。提取它们意味着 WebRTC，WebRTC 跨越两个 NAT 会生成一个中继候选，而 §6 说明没有这样的候选。`vision-demo` 的文档预期结果是“信令工作而媒体未工作”，原因正是如此。

**因此，机器人拨通 Space 并推送。** `media.stream {url}` — 由 `mediad` 自身响应，就像 `media.video` 一样，因为管道属于 `mediad`，没有服务拥有它 — 告诉机器人一个 `wss://` 地址去连接；它向外打开并发送帧。一个出站 WebSocket 是始终能工作的唯一事物，而机器人在所有可连接的每一秒都在证明这一点。没有中继，没有 ICE，**会话携带的是指令而非负载**，这是这种方案能扩展的原因，而通过服务迷你舰队依赖的服务中继像素则不会。

    Space ──media.stream {url}──► 会话 ──► 机器人
    机器人 ═══════ H.264, 出站 wss, 直接 ═══════► Space

**H.264 而不是 JPEG，最初是 JPEG。** 印刷电路板有硬件编码器，因此编码成本由 VPU 而不是核心承担，预测比一帧 JPEG 的字节数量要少一个数量级 —— 合成内容中为 0.5 KB 对比一帧 JPEG 的 6.5 KB，实际内容中更少，方向相同。为了确保安全，必须构建两件事情，而这两件事情都是隐形失败的：

- **一个中途加入流的接收器直到关键帧才能解码任何内容**，而 Space 在每次推送时都会重启，因此重新连接是常见情况而非例外。`h264parse config-interval=-1` 在每个关键帧前重复 SPS 和 PPS，打开阀门会发送一个上游的 `force-key-unit`，这样接收器首先接收到的是可解码的内容。
- **对于 JPEG 而不是这里，丢弃最旧的而保留最新的才是正确的。** 一个参考被丢弃的预测帧解码为看起来像是损坏相机的垃圾，而不是损坏传输。因此，一个间隙会将流丢弃到下一个关键帧，在两个地方：分支的队列和发送者的通道。

JPEG 在 `media.stream {"encoding": "jpeg"}` 上保持可达，因为对于频繁重新连接的接收器来说，每一帧独立是有价值的。
**分支是分流的，而不是条件性的。**`webrtcsink`拥有视频流的编码器，并故意接收原始视频——预编码输入会将编码器置于拥塞控制之外，这是此管道尝试并撤销的——因此没有可以窃取的部分，这是一个来自同一原始分流的第二个编码器。在一个编码器是预算，没有人流媒体时必须免费的板子上，分支只在`valve drop=true`后构建一次，并通过属性写入打开。在实时管道中添加和移除元素是另一种选择，`pipeline.rs`的历史记录中有关于`videoflip`的内容，这就是为什么这里不应该使用它。

这 **不** 做的是给浏览器一张机器人的图片、携带音频或关闭遥控回路。这些需要WebRTC和第6节仍然是它们所需要的；帧流是消费者是一个程序的情况。

## 6. NAT：两端都使用STUN，机器人提供中继 —— **决定**

`stun.l.google.com:19302`，这是`webrtcsink`自己的默认值，现在也是控制台在远程时请求的值。这一部分之前缺失了且很重要：一个只提供其`192.168.…`地址的页面与另一个网络上的机器人进行协商时会完美地建立会话，但因为没有可以工作的候选对，所以什么都不会携带。

**中继不是可选的，也不是对称的。**在家庭路由器后面的机器人和云提供商给容器的任何东西后面的消费者之间，srflx-to-srflx需要两个NAT来允许穿洞——通常它们会，但并不总是。中继总是有效，代价是某人的带宽，这就是ICE最后尝试的原因。

**一个中继候选者就足够了，而且不一定是机器人的。**一个连接需要*一个*，而不是两个，`aiortc`的STUN客户端在它的TURN客户端不起作用的地方可以工作——因此Python消费者不能是那个中继的侧，机器人必须是。`reachy_mini`的#1182确立了这种安排，`mediad::turn`也是同样的安排。
**那项论点遗漏了两端能否互相通信的问题**，而iPhone在移动网络上的情况就是它们不能互相通信的例子。它没有IPv4套接字：它通过DNS64/NAT64到达一个*主机名*，STUN服务器报告一个IPv4反射地址，手机收集了一个相应的候选地址。但是，ICE候选地址是一个裸露的字面量，而机器人的中继候选地址是一个裸露的IPv4字面量，且该板上没有任何全局IPv6地址——这正是那部手机无法向其发送数据包的地方。在olducky中测量：六个会话，每次`offering relay candidates relays=5`，每次`Ice connection state … failed`，每隔约八秒一次。

**这项测量无法承担赋予它的重量，且那部手机实际上具有IPv4。**`relays=5`统计了`webrtcbin`在`consumer-added`内部接受的 TURN服务器URI，而在此之前任何分配尚未尝试——而不是收集的中继候选地址。每次分配失败的机器人都会记录得与每次分配成功的机器人相同，因此这六个会话与普通解释一样一致：两端都没有中继候选地址。现在这条线被命名为`added TURN servers for this consumer servers=N`，以反映其实际意义，并在收集完成时每台消费者记录缺失的一半：`count_gathered_candidates`。
```
gathered ICE candidates host=2 srflx=1 prflx=0 relay=0 unparsed=0
TURN servers were added and no relay candidate came back …
```
`relay=0` 旁边是非零 `servers` 的情况是唯一的故障，且没有其他症状，第二行只在这一对上触发。直到有机器人产生这样的情况，上述原因尚未得到证实，因此 DNS64/NAT64 段应被视为假设，而非发现。

所以 **控制台提供自己的中继** (`refreshRelays` 在 `mediad/webclient/index.html` 中)，只有它自己的分配可以连接这一中继：`turn.cloudflare.com` 是一个名称，因此它会通过 IPv6 解析，而 Cloudflare 回传的中继地址是 IPv4，机器人可以访问。在写入之前，手机上已经确认了这一点——使用 `hf_oauth` 登录的浏览器持有的令牌在 Trickle ICE 页面中收集了一个带有 IPv4 地址的 `relay` 候选者，而机器人自己的候选者与之配对失败。

页面使用 **访客** 的令牌生成它们，而不是机器人的令牌，这是双重正确的：机器人的配额应该继续被监控而不是去监控，而且一个已用 `hf_oauth` 登录的浏览器已经持有自己的令牌。局域网会话不需要请求任何配额——两边都有主机候选者，且没有任何情况会使用中继。

这些凭据是 Cloudflare 的，由代理 Hugging Face 主机并用 **中继登录时使用的同一令牌** 进行认证——因此，属于某人的机器人可以提供中继，而没有归属的机器人则不能，这与第 2 条中的所有其他地方一致。它们是短暂的：任务在 600 秒寿命的一半处刷新，并在短暂失败后仅在 30 秒后重试。没有登录的机器人没有任何可重试的内容，而日志在守护进程的整个生命周期中每 30 秒发出一次警告，以防止日志不再被阅读。

**获取它们绝不能成为障碍。** 唯一的调用者是 GStreamer 的 `consumer-added` 处理程序，在此处理程序返回时，该消费者对应的 SDP 要约才生成，因此在此处发起 HTTP 请求会延迟每个连接——包括永远不会使用中继的局域网连接——直到代理返回为止。因此，`Relays::uris` 从缓存中读取，从不阻塞（返回一个 `try_read` 而不是等待，即使没有结果），从不失败。空回答是启动后的前几秒以及在没有任何账户的机器人上的普通状态，这意味着仅主机和 srflx，这正是同一网络上的任何事物所需要的全部。

What the mini 所有者 有而 `mediad` 没有的是一个 **协商看门狗**：从 `consumer-added` 到 `connection-state == connected` 之间有 12 秒，之后它会以一个命名的原因结束会话，而不是让客户端一直等待。它的注释命名了它所写的罪魁祸首——“`libnice` 在 `CHECKING` 中冻结（某些 `libnice` 版本已知的崩溃模式）”——这是会话协商完美且不携带任何内容的第二种方式，不同于没有可用的候选对。由于同样的原因，候选对的数量也是值得拥有的：它将两个从外部看起来相同的失败区分开来。

**代理是空间，它前面的名字是已死的部分。** `turn.fastrtc.org` —— `fastrtc` 代码指向的地方，也是 `reachy_mini` #1182 复制进这个安排的地方——是一个悬空的委派，而不是故障：`.org` 注册表为该区域命名了四个 Route53 域名服务器，注册状态健康且锁定至 2027 年，而所有四个域名服务器都对它们负责的区域返回 `REFUSED`，这是 Route53 说的当它们背后的托管区域不存在时。`fastrtc/turn-service`，这个悬空委派所指向的空间，从未停止回答。因此 `DEFAULT_TURN_ENDPOINT` 可以直接指向它，即 `https://fastrtc-turn-service.hf.space/credentials`，并且 vanity 记录不在路径中。

**这也关闭了一条令牌泄露路径，这才是比故障更重要的那一半。** 一个悬空的 Route53 委派是一个已知的接管模式——创建托管区域直到 AWS 分配给你其中一个已委派的域名服务器，一个就足够了，因为解析器只需要一个权威答案。无论谁接管了它，都会为该名称提供记录，通过 DNS 验证获取证书，并每五分钟从每次登录的机器人那里收到一次作为携带头的账户令牌。该令牌是机器人的全部凭证；§2.4 讲述了它的范围有多广。

**在令牌能够到达之前会检查端点。** `turn::parse_endpoint` 是一个 `clap` `value_parser`，用于 `--turn-url`：除非主机是回环地址，否则为 `https`，没有用户信息，没有查询和片段。错误的值会在参数解析时停止守护进程，而不是每三十秒变成一个警告。重定向不需要单独的防护——`reqwest` 在重定向跨越方案、主机或端口时会剥离 `Authorization`（`src/redirect.rs`，`remove_sensitive_headers`），因此令牌无法被带到第三方源。
**允许是机器人的拥有者，而且是有限的** — 每个月一个免费的 Hugging Face 账户有 10 GB 的配额。传输一个视频会话大约每小时占用 1 GB，因此如果一个机器人的传输活动频繁，它可能会耗尽配额，之后代理会回复没有传输服务器，并且 `turn.rs` 日志会在信息级别记录“传输代理未提供任何传输服务器”。这与从未提供传输服务器的机器人没有区别，这是一个值得在有人遇到这种情况时关闭的可读性缺口。这也是 `stream.rs` 用于发送帧而不是通过传输服务器的理由。

**现在有东西注意到了它死亡的情况，这就是为什么这个问题在三个月内未被注意到的原因。** 当 #1182 发布它时，端点已经失效了，唯一的症状是在日志中出现警告，并且没有被计算的候选类型。`/.github/workflows/turn-endpoint.yml` 每天运行一次：一次经过认证的 `GET` 请求针对 `DEFAULT_TURN_ENDPOINT`，断言返回 200 状态码并且至少有一个 `turn:`/`turns:` 条目。仓库中的其他所有检查都通过，因为它们中的每一个都配对了两个在同一网络中的对等体，而这些对等体从不查看传输服务器。

它的结构有三个刻意的设计。它通过 `sed` **从 `turn.rs` 中读取 URL** 而不是保留一份副本，因为持有自身端点的检查会测试它最后一次被告知的内容，并且可能会与守护进程编译的内容不同步——而且对于一个机器人从不使用的 URL 上的绿色检查比没有检查更糟糕，因为它会被视为证据。它 **不在 `pull_request` 中**：要防范的失败是“几个月没有人碰过这个”，而 PR 触发器看不到这一点，第三方的故障永远不应阻塞无关的工作。并且 **缺少 `HF_TOKEN` 秘钥会导致失败** 而不是跳过，因为一个会悄无声息地将自己静默成永久沉默的检查正是它存在的失败模式。
- **我们自己的代理。**此端点是一个小型服务，持有Cloudflare Calls密钥，并为持有有效HF令牌的呼叫者生成短期凭证，如果我们自己运行此服务，将结束对一个休眠项目Space的依赖——`--turn-url`已经是它所插入的接口。值得去做，但不值得因此推迟中继覆盖：`*.hf.space`是`{owner}-{space}`，因此如果`fastrtc`重命名或删除了Space，它就会失效，而且没有CNAME层可以重新指向。这就是残留的风险，被命名而不是被关闭。
- **机器人上的Cloudflare密钥**，直接使用`TURN_KEY_ID`和`TURN_KEY_API_TOKEN`。最快但最差：在每个板卡上使用长期API令牌，这正是§2.4存在的原因，旨在防止这种错误。

关于中继的问题并不致命。在`add-turn-server`被发出之前会先检查其存在性——在C闭包中的恐慌会终止进程而不是回溯，这已经是`pipeline.rs`曾经学到的一课——拒绝的URI会记录在日志中，而一个无法提供中继的机器人仍然可以从大多数地方访问，而不是完全无法访问。**一个TURN URI携带密码**，因此只记录主机部分。

## 7. 授权，现在有了账户后重新阐述

`remote-webrtc.md`的§4争论机器人不需要自己的门禁，因为一个桥接会话在到达之前已经被认证了两次——客户端到服务端，机器人向外使用令牌——因此信任因此转移到了服务端而不是消失。本页面并没有改变这一论点；它增加了§4无法命名的一件事，即**绑定发生的时间和执行者是谁**：
- 在 `account.login` 之前，鸭子从外部的局域网（LAN）无法被外部访问。没有什么可以攻击它。
- 之后，一个账号拥有了它，`account.login`/`account.logout` 是可以转移这种所有权的唯一调用。它们被路由到每种传输方式，包括 WebRTC，而 §2.6 是支持这一点以及使它成立的三个属性——一个已登录的机器人会拒绝，绑定信息对任何人都可读，并且可以从比机器人更多的地方撤销。
- **远程重新绑定机器人是一种比看起来更窄的风险**，并且值得精确说明原因：只有当前所属账号的客户端可以远程访问该机器人，因此远程的 `account.login` 实际上是账号所有者的客户端。真正的暴露是局域网内的，而这正是 `force` 存在的原因。
- 一个更换了主人的机器人必须被注销。这与配对 PIN 和校准——在 M6 中的移交过程——是一样的列表，而这也是列表中的一项，值得在列表仍在编写时添加，而不是在二手鸭子流到陌生人手中后再添加。
- 令牌是一个文件中的持有凭证，因此被盗的板子会泄露它。答案是 §2.4 的只读范围，而不是加密：机器人必须在启动时未受监督地读取这个文件，所以它能不依赖人类解密的任何东西，窃贼也能解密。这也是缩小范围的最尖锐论据——目前来看，被盗的鸭子会泄露一个可以写入其主人仓库的令牌。

## 8. 工作顺序

五个切片，前两个独立有用且无需客户端：
1. **`account login`** — 设备流程，令牌文件，`account status`。`updaterd`。**已完成**：
   三次调用，三次传输，两个命令行界面，以及一个可以自动续期的令牌。它本身可验证，这就是为什么它是第一个切片的原因：它打印出 Hugging Face 的用户名。
2. **仅注册的中继** — 生产者注册，协商心跳，重连和
   退避策略，分裂脑轮询。`mediad`。**已完成**：`mediad::relay`，一个不包含 GStreamer 的任务，直到 `/etc/robot/hf-token` 存在时才开始工作，并在存在时无需重启即可拾取。没有任何客户端的情况下也可以验证：服务的仪表板会统计生产者数量，`/api/robot-status` 列出鸭子。
3. **托管的客户端。** §5. 在会话翻译之前而不是之后进行，这是一个顺序上的改变，改变的原因是验证：服务本身不提供前端 —— `GET /` 是一个统计节点、生产者和会话的状态页面 —— 它的消费者是迷你机器的移动和桌面应用程序，这些应用程序会使用迷你机器的方法名称来驱动鸭子。因此，我们没有需要连接的任何东西，如果我们不编写，翻译会话首先会意味着构建只能在假货上测试的一半。
4. **会话翻译** — 远程消费者获取视频和 `control` 通道。**已完成**：`relay::bridge` 在请求会话时以 `ws://127.0.0.1:<--port>` 作为消费者打开连接，每跳重写 `sessionId`，不读取任何负载，拒绝同名的第二个会话，并在会话以任何方式结束时通知服务 —— 包括没有生产者可以桥接的情况，即机器人管道从未达到 PLAYING 状态。
5. **STUN 已决定；TURN 由机器人提供。** §6. **已完成**：两端均为 `stun.l.google.com:19302`，`mediad::turn` 保持 Cloudflare 资格认证信息新鲜，确保每个消费者的出价携带一个 `relay` 候选人 —— 来自 `fastrtc-turn-service.hf.space`，即 Space 本身，因为其前缀是一个悬空的委派。§6 提出了论点；需要带走的三个要点是：只有机器人需要凭据，读取它们必须从未阻塞线程构建出价，以及此仓库中的任何检查都不会注意到该端点再次死亡。

## 9. 什么可以打开，谁可以关闭它
| | 需求 |
|---|---|
| §2.4 范围宽度 | `pollen-robotics` HF 组织中的一个公共设备代码客户端，由具有组织管理员权限的人创建，具有 `openid profile read-repos` 权限。这不是阻塞项——权限更改需要重新登录——并且它不应在没有此权限的情况下发布 |

| 所有在网络上传输的内容都应在源处带有时间戳 | `remote-webrtc.md` 第11节：媒体上的 `abs-capture-time`，与浏览器和 `aiortc` 实际显示的内容进行比对；以及每个控制通道通知中的单调递增加时间戳字段，描述一个时刻。任何需要将机器人所见与所感相关联的消费者都需要它——视觉惯性 SLAM 是使其具体化的案例——并且它希望自己的版本更新而不是跟随传输 |
| §2.6 `logout` 不会撤销任何内容 | 检查 Hugging Face 是否接受第一方设备代码客户端的撤销请求，而不是假设撤销。这不是阻塞项——注销会停止机器人被访问，且被盗的板卡会在 hf.co 上得到回应——但它区别了“忘记”和“撤销” |
| §6 转发检查需要一个令牌 | `.github/workflows/turn-endpoint.yml` 存在并每日运行，直到在仓库上设置 `HF_TOKEN` 密文——一个仅用于签发 TURN 资格证书的 Hugging Face 令牌，其权限范围仅限于登录。大声失败是故意的；替代方案是一个会自我静默的检查 |
| §6 转发是别人的 Space | 一个我们自己的凭据代理，将 Cloudflare 的密钥存储在一个地方，而不是信任一个休眠项目的 Space 来保持其名称。`--turn-url` 是接口。这不是阻塞项——Space 会响应——但 `*.hf.space` 是 `{owner}-{space}`，如果它移动了就无法再指向别名 |
关闭本页面撰写时：OAuth客户端（§2.3 — Hugging Face提供一个），令牌是否过期（§2.7 — 三十天，带有旋转刷新令牌），使用哪个rendezvous（§4 — mini的），能否读取它（§4 — 我们维护它；早期草稿中的“私有仓库”是一个错误命名的401），客户端托管在哪里（§5 — 一个静态Space，使用`hf_oauth`，因为问题是从未托管而是页面如何获取令牌），以及应使用哪个relay端点（§6 — 本身Space；前面的别名是一个悬空的委托）。

本页面创建并关闭的一项内容：**令牌键入peer**，因此两个共享一个的peer会轮流可访问。这不是一个配置问题——图像从零开始构建，而不是克隆，所以第二个板子不会收到副本——但确实对消费者构成约束：云后端必须使用自己的令牌进行身份验证，而不是机器人的令牌，否则会将机器人从列表中移除。§3.7。

## 10. 不做

- **`teleop`数据通道。** `remote-webrtc.md` §6 拥有它；远程会话使头部阻塞更加明显，而不是更加紧迫。

- **多peer。** 一次一个媒体会话，与之前相同。
- **会话级同意。** 一个M5项，与本页面无关且因本页面而更加明确：可以从另一个大洲启动的流是`architecture.md` §7 所写的案例。
