# WebRTC客户端：从测试页面到机器人的控制台

状态：已合并 · 日期：2026-08-25 · 拥有者：pierre

`mediad/webclient/index.html` 证明了传输方式。这使其成为人们可以使用的功能：由机器人提供，而不是由 `python3` 提供，通过已经广播的地址 `btd` 找到，并且实际允许执行控制面 `route.rs` 的操作。

这是对 [`remote-webrtc.md`](remote-webrtc_zh.md) 的补充，后者负责传输——信号传输、会话模型、授权以及对等方可以调用的内容。在两者交汇的地方，该页面是所有者，而此页面则指向它。

**所有四个更改均已包含在内。** 在这些更改的第一行之前，此页面就已经写好了，因此这些决定是可争论的而不是由差异推导出来的；它被保留下来，因为替代方案是值得重新阅读的部分。在代码和此页面可能发生分歧的地方，代码是答案：`mediad/src/web.rs` 提供页面，`mediad/src/producer.rs` 填充 `meta`，`duckctl` 的 `ip` 和 `open` 找到机器人，而 `mediad/webclient/index.html` 是控制台。§7 说明了剩余的内容。

## 1. `mediad` 服务页面

**已实现** — `mediad/src/web.rs`，`--web-port`，默认 8080。

`mediad` 中的一个 HTTP 监听器，一个路由，返回页面。`http://<机器人>:8080/`，并且没有其他需要运行的内容。

这一步解决了四个问题，而不是一个：

- **无需 `python3`。** 指令变成了一个地址。
- **无需输入 URL。** 页面默认将信号目标设置为 `ws://${location.hostname}:8443` —— 它是由机器人提供的，因此它知道在与哪个机器人通信。
- **私有网络访问不再适用。** Chrome 会阻止来自 *公共或不透明* 原生的对私有地址的请求。从 `192.168.x` 提供的页面具有私有原生，因此 `file://` 的检查根本不会被触发。头部的警告块消失了，因为警告它的问题根本不会发生。
- **一个版本。** 页面和二进制文件一起打包（§1.2），因此从代码库获取的客户端不再可以指向来自发布版的机器人。

### 1.1 哪个 HTTP 服务器
**`axum`. 已决定。**它已经存在于`Cargo.lock`中——`updater`将其用作测试镜像的开发依赖项，因此该库在这个工具链和交叉构建中已知可用。

替代方案是一个手动编写的HTTP/1.1响应器：这在一个方法中提供了一个文件，因此可能只有六十行。六十行手动编写的请求解析器绑定到`0.0.0.0`，这是一个暴露在网络上的解析器，编写时避免了构建已经解决的依赖项——而`axum`底层的`hyper`是该语言中阅读量最大的那个解析器实现。

`mediad.service`中的`RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`已经允许了监听器；单元中的任何内容都没有改变。

### 1.2 页面嵌入，未安装

`include_str!("../webclient/index.html")`，从内存中提供。
- 将其安装在 `/opt/robot/daemon/current/webclient/` 下，并在请求时读取它 —— 这种方式需要在 `_build-release.yml`、`dev.yml`、`scripts/dev-push.sh` 这三个地方各添加一个 `--include` 行，而 `xtask` 的打包陷阱正是为了保持这些地方的一致性，而这正是之前已经出现过偏差的列表。它还会在运行 `ProtectSystem=strict` 的单元中将文件系统读操作隐藏在网络请求之后，并且使得“这个机器人正在服务哪个页面”成为一个有两个答案的问题。

嵌入则需要重新构建以更改样式表。对于一个属于守护进程界面的一部分的页面来说，这是一个正确的权衡。

## 2. 找到机器人：两个命令，其中一个已经现成的**Landed** — `duckctl ip` 和 `duckctl open`，广告先行，`net.status` 在其后。

`btd` 将机器的 IPv4 在其广告中以公司 ID `0xFFFF` 的形式记录下来，`duckctl` 已经解析了它 —— `Address::At`、`Unassigned`、`Unsaid` 三个答案而不是两个，并且 `scan` 今天打印了它。因此，这项工作是一个命令，而不是一种机制。

### 2.1 `duckctl ip`

机器的地址仅在标准输出中显示，因此 `ssh radxa@$(duckctl ip)` 可以正常工作 —— 这个工具已经保持了这种分割，诊断信息在标准错误中，数据在标准输出中。

**这不是这个仓库中的新想法；它已经以前被糟糕地写过一次。**
`scripts/dev-push.sh` 正需要这个功能，并且手写实现它：`resolve_board()` 调用 `duckctl wifi status`，并将 JSON 通过一个嵌入在 shell 脚本中的六行 Python 程序管道，从中提取 `result.ip4`。这就是那个命令，缺少一个家。

读取广告而不是调用 `net.status` 在三个方面都更好，所有这些都可以从 `dev-push.sh` 所需编写的代码中看到：
- **没有连接，就没有连接和PIN。** `resolve_board` 携带一个完整的失败分支，即“机器人拒绝 `net.status` — 大多数情况下是错误的PIN”。由于广告内容无法被拒绝，因此该分支不存在。
- **秒而不是几十秒。** `dev-push.sh` 每个机器人精确地缓存地址，因为“BLE发现需要十到二十秒”；一次扫描在找到第一个匹配的广告后大约需要一秒，因为 `duckctl` 会一直轮询直到出现结果，而不是等待 `SCAN_TIME`。
- **它不是过时的。** `btd` 的 `reconcile_advertisement` 每 `ADV_POLL`（5秒）重新读取 `net.status` 并重新广告，当答案发生变化时，广告就是带有五秒延迟的 `net.status` —— 这个延迟远远小于SSH新租约已经失效的时间窗口。
**带有一个非选项的备用方案。**与这台Mac绑定的机器人通常会停止向其广播服务——`duckctl`自身的扫描等级就是为了应对这种情况——因此，当未看到任何广播时，`ip`会连接并询问`net.status`，这正是`dev-push.sh`今天所做的。先进行廉价读取，再进行调用。如果没有备用方案，这条命令会在最常使用它的笔记本电脑上失败。

- `Address`的三态之一是`Unassigned`——机器人没有网络。修复方法是`duckctl wifi connect`，并且必须通过BLE进行，因为设计上`net.connect`不允许通过WebRTC配置（“一个从未见过网络的机器人不能通过该网络进行配置”）。
- `Unsaid`——在`btd`开始广播地址之前的一个版本。即使没有广播地址，备用方案也会给出响应；更新后会变得更快。

它的第三个调用者既不是上述两种情况之一：`install-dev.md`在打开时会询问“板子的**IP地址**”，并附带说明此图像上的mDNS不可靠，也没有获取IP地址的方法。

### 2.2 `duckctl open`
Resolve,然后在浏览器中打开 `http://<地址>:8080/`。`--print` 会打印出 URL，适用于没有浏览器的机器或脚本；`--port` 适用于使用非默认 `--web-port` 启动的机器人。

这是一个命令而不是文档中说明的 shell 替换，原因只有一个：**端口默认值应该只存在于一个人永远不会阅读的唯一一处地方。** `open "http://$(duckctl ip):8080"` 可以工作，并且是一行只写一次然后永远查阅的代码。

### 2.3 不是这些

- **`duckctl url`。** 这是 `open --print`。第三个命令的内容只是一个端口号。
- **`scan` 的 URL 列。** `scan` 列出耳塞，而机器人的行已经携带了地址。在列表下加一条指向 `open` 的注释就足够了。
- **任何需要连接的。** 两个命令都是广告读取，带有备用选项。这里需要连接的命令将是一种不同的命令，并且应该与 `wifi` 和 `update` 一起，而不是与找到一个机器人相关。

### 2.4 这个循环所关闭的，以及后续的一个
BLE提供网络，然后给你该网络的URL。这两种传输方式从替代关系变成了顺序关系——这一点值得说清楚，因为`route.rs`故意拒绝使用WebRTC的`net.connect`，这也是这一拒绝的另一面。

后续改动，单独来看而不是这四个改动：`dev-push.sh`的`resolve_board`变为`client --name "$1" ip`，删除了嵌入的Python和错误的PIN分支。这是分开处理的，因为它涉及到了推送路径，而且应该在手动使用`ip`几次之后再合并。

`duckctl`是为手机应用临时准备的，所以它仍然保持两个命令，没有引入新的机制。持久化的部分是那些会持续存在的：`btd`广播地址，`mediad`在已知端口上提供服务。应用将直接执行相同的两步操作。

## 3. 工具的名称反映了它即将停止使用的传输方式

已决定并合并——`duck-btctl`就是`duckctl`，在自己的crate中。本节其余部分是解释，保留这部分是因为备选方案是值得重新阅读的部分。
`open` 在 http URL 上打开浏览器，执行这个操作的工具名为 `bt`。这值得探究，因为结果发现它指向的远不止一个命令。

**`open` 本身并没有错。** 它的实质是蓝牙：它扫描广告以了解机器人的位置，而 `xdg-open` 只是一行代码。`duckctl open` 读作“使用无线电找到机器人，然后显示其控制台”，而这正是它所做的——就像 `wifi connect` 是一个 WiFi 命令，其整个机制是 BLE 一样。

**名称仍然不对，原因与 `open` 不同，而是与 `mediad` 相关。** 将会有第二种传输方式连接到这个机器人，两者的设计目的是不同的方法集：`robot.move` 通过 BLE 被拒绝，而通过 WebRTC 允许；反之亦然。因此，一个人需要两者，他们实际上想要的不是一个二进制选择——而是一个知道哪种传输方式可以提供服务的工具，并在两者都无法提供服务时给出提示：

> `wifi connect` 是蓝牙专用的，而这个机器人没有在广播。
那工具不能被称为`btctl`。而一个名为`btctl`的工具悄无声息地向所有人展示了
蓝牙是通往机器人的一种方式，就在这种途径不再唯一的时候。

### 3.1 这是一个改进，而不是重命名，并且这解决了两个现有问题

一个传输无关的客户端不能保持在`btd/examples/duck-btctl.rs`。它需要`btleplug`
*和*一个WebSocket客户端，而`btd`是BLE守护进程——这是它的错误归宿。因此，诚实地讲，它应该成为自己的工作空间成员，而两个今天显得笨拙的事情将在这一过程中不再显得笨拙。
- **安装命令。** `cargo install --path btd --example duck-btctl` 看起来有些奇怪，因此 `dev-push.sh` 为从未运行过它的克隆提供了一个备用方案——它会调用 `cargo run -q -p btd --example duck-btctl`。`cargo install --path duckctl` 并不需要备用方案。
- **真正的示例产品。** 它之所以被称为示例，是因为它的 dev-dependencies 从未包含在最终发布的文件中，这样可以避免将 `btleplug` 引入机器人。它自己的 crate 通过不作为任何守护进程的依赖来实现这一点，从而保持同样的保证，直接声明而不是作为文件位置的副作用。

### 3.2 `duckctl`

它与 `robotctl` 的使用方式相匹配：在机器人上使用 `robotctl`，在其他地方使用 `duckctl`。它保持了与仓库名称一致的 `duck-` 家族，并且足够短，无需别名即可快速输入。

单独的 `duck` 更容易输入，但已被占用：Cyberduck 已经使用了同名的 CLI，这在 Mac 上是可能的。`microduck` 是仓库名称，但太长，不适合每小时运行二十次的命令。

### 3.3 未重写的内容
196 条引用分布在大约二十个文件中，大多数是散文。**陈旧的记录保留了旧名称。** `update-over-ble.md` 和 `install-path-gap.md` 描述了一个时刻——一次更新会话，四个安装路径错误及其解决方式——将工具名称改写为描述工具在拥有该名称之前发生的事情，使记录略微失真。它们的 *链接* 被重新指向，仍然可以解析；而它们的散文部分则没有改变。

`roadmap.md` 位于同一目录中，是例外情况，因为它不是对某个时刻的记录：它描述了当前的 repo，包括每个 crate 的布局表。命名一个不存在的目录的布局表显然是错误的。

**没有兼容性桥接，也没有别名。** 一个用户和一个机器人：一个仍然可以工作的 `duck-btctl` 是保持两个名称同步的第二个名称，并且是旧名称在某人的 shell 历史中存活一年的原因。

### 3.4 为何将其排除在外
`cargo board --bins` — 在 `dev-push.sh` 和发布工作流中 — 为 aarch64 构建每个默认成员。例如，它在免费版本中被排除在外；作为一个 crate，它会被跨平台编译，这意味着在发布路径上为一种永远不会见到蓝牙堆栈的板子编译一个蓝牙堆栈。

**在工作区根目录下的 `default-members`，除了 `duckctl` 之外的所有内容。** 一个列表，而不是在两个 `--bins` 调用站点分别命名二进制文件并手动保持两者同步 — 这正是这个仓库一直在记录的失败。`--workspace` 未受影响，因此 CI 会像之前一样对其进行 lint 和测试。

## 4. 页面变成控制台

**已合并** — `mediad/webclient/index.html`，仍然只有一个文件且没有构建步骤。

允许的子集很大，几乎没有任何内容可以从页面访问。重新组织围绕人们来此的目的：
| | |
|---|---|
| **header** | 机器人名称、版本、API版本 — 从 `hello` 和 `system.info` 获取，当通道打开时会自动发送，未被点击 |
| **视频** | 加上 `getStats()` 的视频质量指标：比特率、帧率、丢包率、往返时延。今天的流媒体质量下降意味着画面变差且日志无提示 |
| **驱动** | 键盘和屏幕上的摇杆 → `robot.move` 以固定速率发送；拖动视频 → `robot.look` |
| **姿态** | `robot.enable`、`init`、`relax`、`stop`、`shutdown` — 最后两个需确认 |
| **do / sound** | `Do` 和 `Sound` 枚举作为菜单 |
| **遥测** | 以 2 Hz 的频率使用 `robot.subscribe` 到实时面板：模式、健康状态 |
| **控制台** | 原始 JSON 盒子、日志以及两个拒绝按钮 — 折叠显示，因为它们验证了路由表而非驱动机器人 |
- **停止按钮不得显示为紧急停止。** `route.rs` 允许 `robot.stop` 的原因是此通道可靠，并且死点已经能够在意图停止到达时停止机器人，然后用尽可能明确的语言指出，UI 不应暗示这是一个物理紧急停止。一个标签，而不是一个大大的红色圆圈。
- **版本差异只是一个横幅，而不是一道锁门。** `hello` 报告的偏差说的就是这个，并且页面仍然可以正常工作——同样的规则 `duck-btctl` 在 #102 中也确定了。
- **仍然只是一个文件，仍然没有构建步骤。** 这个约束就是客户端能够运行的原因，并且它能够存活下来。如果它超过一个文件，就会变成三个文件——`index.html`、`app.js`、`app.css`，三个 `include_str!`，仍然没有构建步骤，仍然没有 npm。

从页面驱动也是对 `remote-webrtc.md` 作出的两个断言的第一次真正测试，而没有任何事情能够验证：当会话断开时，死点是否能够停止机器人（§6），以及 `control` 上的排序是否足以让 `intents.rs` 保持诚实（§6 再次）。这两个断言都很容易被相信，但如果错了就会很昂贵。

## 5. 机器人在会话开始前自行命名

**已落地** — `mediad/src/producer.rs`。
`webrtcsink` 接收一个 `meta` 结构，并且信令服务器会将它传递给 `list` 中的每一个对端——页面已经记录了这些信息并且它们是空的。从 `configd` 中填充这些信息：名称、序列号、版本以及 `API_VERSION`。

小改动，但效果显著：页面可以在会话开始前命名机器人，一个找到两个生产者的客户端可以区分它们，而第 7 节中的 rendezvous 服务需要这个字段来进行路由。这是这里最经济的选择。

## 6. 它打开了什么，但不是什么

`remote-webrtc.md` 第 11 节推迟了“为服务器端程序提供的 WebSocket 表面——同样的 JSON-RPC，没有媒体堆栈，`get_frame` 返回一个 JPEG”，并在 §5 的路由存在后几行提到了它。一旦 `mediad` 中有了 `axum` 服务器，它就是一个已经在运行的服务器上的路由，帧也已经在那里了：`main.rs` 中的 `_frames` 是从 tee 分流出来的原始 NV12 摸板，目前还没有读取它。

这样命名是为了让结构可见，而不是在此提出。这是一个备用传输，而第一个传输已经足够了。

## 7. 顺序，以及剩余的工作

这四个更改各自独立且单独提交，按以下顺序：

1. **以包含信号URL的方式提供页面。** 删除了 Python 指令和警告块。改动很小，其他内容则更好。API 版本同样以这种方式替换，例如 §4 的横幅——页面中的字面量会是 `API_VERSION` 的第二个副本，在版本更新的那天是错误的，并且会报告一致。
2. **生成 `meta`。** 更小，且独立。
3. **`duckctl` 增加 `ip` 和 `open`。** 仅客户端改动，未触及守护进程。
4. **控制台。** 较大的那个，最后完成，位于已经可达的页面上。

**未完成且故意分离：** `dev-push.sh` 的 `resolve_board` 仍然通过 `duckctl wifi status` 和六行嵌入的 Python 代码（§2.4）手动实现这一点。它将变为 `duckctl ip`，删除了 Python 代码和错误的 PIN 分支——因为这涉及推送路径，且应在 `ip` 手动使用几次之后再提交。

## 8. 不做
- **控制台上的一个门。** §4 于 `remote-webrtc.md` 中拥有这一决定，并且这里没有改变其条款。为家庭场景提供一个 `--no-web` 标志以关闭页面是有价值的，而不是一个机制，一个标志。
- **一个 JS 框架、打包工具或 `gstwebrtc-api`。** 页面手动实现协议是因为需要 npm 的客户端是没有人运行的客户端。即使在四倍大小的情况下也是如此。
- **使用 TLS 服务。** §1.3 中说明了何时以及为何没有现在这样做。
- **教广告一个端口。** 它携带的是四个字节的 IPv4；一个在非默认 `--web-port` 上的机器人等同于在 `duckctl open` 上的 `--port`，而不是一种二进制格式的更改。
