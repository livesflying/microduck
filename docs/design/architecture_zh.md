# 机器人守护进程 — 整体架构

状态: 草案 · 日期: 2026-07-22 · 负责人: pierre

路线图详见 [`roadmap.md`](../project/roadmap_zh.md)。

与 [`updater-design.md`](updater-design_zh.md) 配套，后者详细介绍了更新系统。本文件则涵盖了服务拆分、服务间通信、状态存储位置以及机器人如何被本地、应用程序或远程控制。

范围说明：本文件描述的是第一个发布的版本的目标，而不是当前的原型（`microduck_runtime`，这是一个探索性的版本并将被重写）。v1 目标是单一且明确的硬件配置。

## 架构概览

一块板子上运行七个守护进程，通过 Unix 套接字通信。其中一个守护进程负责驱动机器人；其余三个守护进程的存在是为了在第一个守护进程失效时不会使板子变得不可达，剩下的则是传输和传感器，它们不拥有任何资源。
```text
   gamepad          phone          you, on a laptop     a peer, anywhere    a GitHub release
      │ BLE/USB        │ BLE             │ ssh                 │ WebRTC              │ https
      ▼                ▼                 ▼                     ▼                     │
  ┌────────┐      ┌────────┐       ┌──────────┐          ┌──────────┐                │
  │  padd  │      │  btd   │       │ robotctl │          │  mediad  │                │
  └───┬────┘      └───┬────┘       └────┬─────┘          └────┬─────┘                │
      │               │  a subset of the same API             │                      │
      │  robot.*      │  robot.health · update.* · net.* · pad.* · system.*           │
      ▼               ▼                 ▼                     ▼                      │
  ┌──────────────────────────────────────────────────────────────────┐               │
  │   one unix socket per service · JSON-RPC 2.0, one object a line  │               │
  └────┬──────────────────────┬─────────────────────────┬────────────┘               │
       ▼                      ▼                         ▼                            │
  ┌───────────┐        ┌─────────────┐           ┌─────────────┐                     │
  │  robotd   │        │  configd    │           │  updaterd   │◄────────────────────┘
  │ robot.*   │        │ net.* pad.* │           │ update.*    │
  │ 50 Hz     │        │ system.*    │           │ verify      │
  │ loop      │        │ wifi, name, │           │ swap        │
  │ safety    │        │ pad bonding │           │ health gate │
  └─────┬─────┘        └──────┬──────┘           └──────┬──────┘
        │ Dynamixel           │ D-Bus                   │ systemctl restart,
        ▼                     ▼                         │ then robot.health
  15 servos + IMU      BlueZ · NetworkManager           ▼
  on one UART                                    /opt/robot/daemon/current

  ┌ publishes, answers nothing ───────────────────────────────────────┐
  │  tofd — the head's 8×8 depth matrix, on /run/tofd/tof.sock.       │
  │         mediad and robotd read it; it reads no one.               │
  └───────────────────────────────────────────────────────────────────┘
```
**`robotd`是唯一接触机器人的部分。**十五个伺服电机和IMU板共享一个串行总线，50 Hz的控制循环占据着它。客户端发送*意图*——“以这个速度前进”，“朝那里看”，“站起来”——而`robotd`内的安全层决定哪些是可执行的。系统中的其他任何部分都不能命令电机（[`robotd-design.md`](robotd-design_zh.md)）。

**它们中的三个在`robotd`宕机后仍然存活。**`configd`、`updaterd`和`btd`都不依赖于`robotd`的systemd，没有机器学习运行时，也没有媒体堆栈，因为它们是恢复路径：一个控制循环无法启动的机器人正是需要重新配置、更新或回滚的机器人。这也是配置存储在`configd`而不是`robotd`（§1.1）的原因。`mediad`和`padd`依赖于`robotd`，这是可以接受的：一个没有摄像头和游戏手柄的机器人仍然是可以更新的机器人。
**`btd`, `padd` 和 `mediad` 拥有机器人的一切。**它们是运输者。`btd` 将 BLE 的一部分 API 前端转发给响应它的任意套接字；`padd` 读取游戏手柄并发送与应用程序相同的意图；`mediad` 通过 WebRTC 数据通道传输相同的调用，并仅拥有管道。这三个组件都可以在不触及机器人行为的情况下替换，并且每天都会被测试，因此应用程序将使用的 API 不能悄悄腐烂。`tofd` 是例外：它拥有一个传感器，发布帧，并不读取任何内容（§1）。

**发布是替换，不是打补丁。**一个构建作为一个完整的目录在 `/opt/robot/daemon/releases/<版本>/` 下落地；`updaterd` 验证其签名，移动 `current` 符号链接，重启单元，然后询问 `robotd` 是否健康。如果不健康，它会将旧的发布版本放回去。一个通过了这一步骤的崩溃循环会被启动计数器（`updater-design.md`）捕获。
| 服务 | 拥有 | 监听 | 连接到 |
|---|---|---|---|
| `robotd` | 电机控制、传感、策略、安全、`robot.health` | `/run/robotd.sock` | Dynamixel 总线 |
| `configd` | Wi-Fi、机器人身份和名称、配对 PIN、游戏手柄配对、重启 | `/run/configd.sock` | BlueZ 和 NetworkManager 通过 D-Bus |
| `updaterd` | 发行版：验证、安装、切换、健康门、回滚 | `/run/updaterd.sock` | GitHub 发行版、`systemctl`、`robotd` |
| `btd` | 无 — 用于 API 部分的 BLE 传输 | 一个 BLE GATT 服务 | `robotd`、`configd`、`updaterd` — 不包括 `padd` 或 `tofd`，这些组件的流此窄的无线电无法携带 |
| `padd` | 无 — 游戏手柄传输；提供原始输入插槽 | `/run/padd/pad.sock` (`pad.input` 仅此) | `/run/robotd.sock` |
| `mediad` | 相机和音频流水线；机器人本身——WebRTC传输和远程前门（§5.2） | TCP：控制台和PNG `GET /frame` 在 `:8080`，信令在 `:8443`；以及它自己的一个unix套接字 `/run/mediad/media.sock`，提供 `media.frame` 给本地记录器或感知进程——以及 `robotctl monitor` 的摄像头块，该块每打开一次每秒请求一次，关闭时从不请求。一个原始帧约为1.8 MiB，因此它特意不通过WebRTC控制通道传输 | `robotd`，`configd`，`updaterd` |
| `tofd` | 头部的ToF传感器：一个8×8深度矩阵，它发布但无人阅读 | `/run/tofd/tof.sock` (`tof.stream`) | HAT的I²C总线 |
| `robotctl` | 无——命令行界面，以及必须在损坏的机器人上工作的工具 | — | 上述所有套接字 |

状态存放在哪里，以及更新后会保留什么：
| | |
|---|---|
| `/etc/robot/robotd.toml`, `updater.toml` | 每块板的配置；安装程序只会写入一次且从不覆盖。`robotd.toml` 由 `robotd` 读取，仅对于 `[media]` 部分，即摄像机流媒体的内容，还会被 `mediad` 读取，因此更改会重启 `mediad` 而不是 `robotd` |
| `/var/lib/robot/config/config.json` | 机器人名称和配对 PIN — 一个文件加上 `flock`，由 `configd`（§3.1）拥有 |
| NetworkManager 配置文件 | Wi-Fi凭据；我们从不存储它们（§3） |
| `/opt/robot/daemon/releases/<ver>/` | 二进制文件、策略和预设默认值 —— 以原子方式替换 |
| `/opt/robot/daemon/current` | 指示当前运行版本的符号链接 |
| `/run/<service>/identity.json` | 每个守护进程实际运行的内容，在启动时发布 |

在 `releases/<ver>/` 之外的所有内容，在更新和回滚后都会保留。这就是全部规则，因此每块板的配置不会包含在发布的文件中。

从更改到达机器人的端到端过程：
```text
  push a branch ──► CI builds and signs a release ──► robotctl update apply
                                                            │
                                                            ▼
                                          updaterd: verify signature, unpack,
                                          move `current`, restart the units
                                                            │
                                                            ▼
                                          health gate: ask robot.health
                                            ├─ healthy  ──► keep it
                                            └─ not      ──► put the old one back
```
The rest of this document is the reasoning: the service split (§1), how services talk (§2),
who owns which state (§3), the API and its transports (§4), remote access (§5), and where
safety authority sits (§6)。

## 1. 服务

`systemd` 是 supervisor：生命周期、崩溃重启、顺序控制、看门狗机制。
| 服务 | 拥有 | 备注 |
|---|---|---|
| `robotd` | 电机控制、运动学、里程计、步态策略、传感器循环、安全 | 实时核心；对任何可能伤害机器人的事项拥有最终决定权。里程计是循环中的结构，而不是服务：它的输入正是循环已经读取的样本 |
| `mediad` | 摄像头/麦克风、编码、感知、WebRTC + 远程网关 | 最重的服务；也是远程 API 的前门入口（§5.2） |
| `btd` | BLE GATT 服务器 | **仅传输适配器** — 不拥有任何状态（§4.1）。参见 [`app-path-design.md`](app-path-design_zh.md) |
| `configd` | WiFi、机器人身份、电源、游戏手柄配对 | 配置必须在 `robotd` 死机时仍可访问（§3.1），且 `btd` 不拥有任何状态（§4.1）——因此不属于它们的业务，而是其自身的业务。游戏手柄配对放在 `padd` 之外，因为配对设备需要 root 权限和 BlueZ，而 `padd` 是故意无特权客户端（§4.1） |
| `tofd` | 头部ToF传感器：HAT I²C 总线上的 8×8 深度矩阵 | 感知相关，因此与 `robotd` 分开。拥有一个传感器并发布帧；不读取任何数据。即使没有安装传感器的板子也会运行它并说明情况 |
| `updaterd` | 更新引擎 | 请参见 `updater-design.md` |

将 `mediad` 从 `robotd` 中分离出来是故意为之：媒体/感知崩溃不能影响电机控制。`tofd` 是同样的规则应用于较小的传感器，并且具体的实现说明了这一点：将 VL53L5/8CX 上传固件大约需要通过 I²C 传输 90 KB 的数据，耗时数秒，该总线与音频编解码器共享，而且大多数鸭子根本没有安装传感器——对于这种情况的重试循环不应该包含在拥有电机的进程中。控制回路中的任何部分都不读取深度数据，因此将其移出不会造成任何损失。它故意不包含在 `mediad` 中：深度数据是通过总线上的传感器，而不是媒体管道的一部分，而且在有摄像头进行标注之前，它就有用处了。

消费者通过与垫子的原始流相同的方式访问它——通过拥有守护进程自己的套接字上的订阅 (`tof.stream`)，而不是通过 `robotd`。将一帧重新投影到机器人的自身坐标系中意味着需要通过 `kinematics` 箱子中的头前向运动学与 `robot.state` 中的关节状态结合；`tofd` 发布传感器的视图，并不假装可以计算它无法计算的几何关系。

### 1.1 不变量
1. **`btd`、`configd` 和 `updaterd` 在 `robotd` 死机后仍然存活。**它们是恢复路径；必须在某些东西出问题的情况下正常工作。`robotd` 不依赖任何 systemd，所有 IPC 为可选且带有超时限制，依赖面最小（无机器学习运行时，无媒体堆栈）。详情参见 `updater-design.md` §4.1。

   `configd` 存在有具体原因，而非为了对称性：当机器人损坏时，配置 WiFi 正是所需的功能，因此将配置放在 `robotd` 中会使它在最需要的时候不可用。

2. **`robotd` 是安全的权威。**任何远程或本地客户端都不能绕过跌倒检测、关节/热限或安全姿态逻辑。客户端发送 *意图*；`robotd` 决定哪些是可执行的。

3. **`robotd` 的控制循环从不因其他服务而阻塞。**所有跨服务读取均为最后值缓存，从不使用同步 RPC（§2.4）。

4. **每种状态只有一个写者。**每个值恰好有一个拥有服务；其他服务只能读取或订阅。

## 2. 服务间通信

### 2.1 控制面 vs 数据面
Two 种不同要求的流量。混淆它们是这里最常见的错误。

| | 控制面 | 数据面 |
|---|---|---|
| 内容 | 命令、配置、状态、感知事件 | 视频/音频帧 |
| 大小/速率 | 几十字节，≤100 Hz | 640×480 RGB @30 fps 时约为 27 MB/s |
| 机制 | Unix 套接字 RPC | **从未跨越套接字** |

### 2.2 控制面：Unix 套接字上的 JSON-RPC 2.0

- 每个服务拥有 **一个 Unix 套接字**。客户端直接连接。当 N=4 时，没有使用代理的必要——总线是另一个可能失败的组件，并且会与不变性（1）作斗争。
- **传输格式：JSON-RPC 2.0，每行一个对象（NDJSON）**。这是一种标准协议而非定制协议：标准请求/响应关联，标准错误对象，以及标准 **通知** —— 这正是推送进度和事件流的正确形状。分帧使用 `tokio_util::codec::LinesCodec`；消息类型是普通的 `serde` 结构体。
- **异步处理，处处带有超时，没有异常**。任何对端都可能是死的。关闭或沉默的套接字是一个正常且预期的答案。
- 订阅是在打开连接上的一系列通知流。
**Alternatives 测量**（唯一依赖项，ARM-Linux 目标）:

| 选项 | 依赖项 | 为什么不选择 |
|---|---|---|
| **JSON-RPC/NDJSON + tokio** | **30** | 选定 |
| `jsonrpsee-types` 仅（我们的传输） | 36 | 合理；拒绝 —— 以一个 `0.x` 依赖换取 frozen-spec 代码 |
| `varlink` | 24 | 精神相近；不那么熟悉，与 JSON-RPC 比起来几乎没有额外收益 |
| `zbus` (D-Bus, p2p+阻塞) | 66 | 见下文 |
| `axum` 通过 UDS | 66 | 可行；参见“HTTP/WS”下文 |
| `tarpc` | 71 | 人机可读的 Rust↔Rust，但不便于服务器推送 |
| `tonic` (gRPC) | 81 | 为少数几个方法需要 `.proto` 代码生成 |
| `jsonrpsee-server` | 112 | **无法提供一个 Unix 套接字** —— 仅限 HTTP/WS 传输；`jsonrpsee-ipc` 从未实现 |

依赖项计数仅供参考，非决定性因素。

**为什么选择 Unix 套接字而非 localhost HTTP/WS。** 功能上几乎相同；
区别在于访问控制和故障模式：
- **文件系统权限是自由授权。**一个模式为0660且有专用组的套接字仅可被允许进程访问。一个TCP端口可被盒子上的每一个进程和用户访问，因此需要构建一层认证来恢复到同等水平。
- **`SO_PEERCRED`** 提供调用者的uid/gid/pid，用于 *审计日志*（支持团队首先询问的是“谁触发了此回滚”）和 **执行**。两层的原因是因为它们回答不同的问题：
  - 套接字的组（模式0660）决定谁可以 **与守护进程通信**；
  - `allow_uids`/`allow_gids` 决定谁可以 **更改机器人** — 仅限变更调用。守护进程运行的uid总是被允许（它可以替换守护进程）；其他人需要被列出，未知的对端被拒绝。
  读取操作故意未加限制：支持团队必须能够检查它无权更改的机器人。仅凭组成员身份说“可以替换固件”对于一个BLE面向服务的设备来说过于粗略。
- **错误接口的错误类别将不再存在。** 通过误操作绑定 `0.0.0.0`，
  配置，或者通过一个“让其在我的笔记本电脑上工作”的补丁，都会将*固件更新控制*暴露给网络。通过Unix套接字，这种错误是不可表示的。权重最重——不是今天的安全威胁模型，而是失败模式。
- 对于计划中的**SDK**：如果第三方或用户代码在板卡上运行，一个本地主机端口将对其开放；一个组拥有权限的套接字则不会。

**为何不使用HTTP/WS作为控制平面**（独立于传输层——`axum`可以很好地服务于Unix套接字）：该协议需要服务器→客户端推送以进行进度更新。通过HTTP，这意味着调用需要POST *加上* WebSocket/SSE通知——两种机制，而`curl`无法消费流式部分，因此调试性优势仅覆盖请求/响应。通过WebSocket进行所有操作可以恢复一种机制，但增加了握手以到达分帧JSON，并再次失去`curl`。在持久的NDJSON连接上，调用和通知是一种机制且无需握手：**更少的概念，这才是实际的目标。**
**未来如果需要使用`curl`进行诊断,** 可以在同一个unix套接字上提供一个只读的HTTP端点 (`GET /status`, `GET /log`), 无需将控制操作迁移到HTTP或复制流式传输路径。诊断和控制有不同的需求; 将它们分开对双方都有好处。

**为什么不使用D-Bus:** BlueZ (通过`bluer`引入) 已经被包含在内，所以它已经在机器上了，`zbus`支持无总线的点对点通信。但是同样的消息类型还必须通过 **BLE和WebRTC/WebSocket** (§4.1, §5.2) 传输，而在这些地方，普通的serde结构体可以工作而D-Bus类型不行。一种定义，多种传输方式是目标，而JSON正是使其免费的关键。我们仅在操作系统要求的地方使用D-Bus (BlueZ, NetworkManager)。

**重新评估触发条件:** 如果`btd`最终在D-Bus方面对BlueZ进行了大量投资，那么通过`zbus`暴露更新接口几乎是免费的 *对`btd`而言*，同时还可以为调试提供`busctl`内省功能。更改成本很低 — 类型保持不变，只有封装方式改变。

### 2.3 异步等待，同步计算
Async (tokio) 用于服务真正需要等待的情况：在长时间操作运行时处理 IPC，超时 peer 查询或子进程，取消正在进行中的工作。

CPU 密集型和长时间的文件系统工作保持 **同步**，异步调用者会将其交给 `spawn_blocking`。在更新器中具体来说：SHA-256 校验 artifact，minisign 流验证，`zstd`+`tar` 解压，以及递归删除解压后的目录树。在 Pi 上这些操作运行几秒；如果交给异步工作者处理，将会阻塞那些在更新期间应该持续响应 `status`/`subscribe` 的 IPC 任务。

真正快速的文件系统操作——符号链接 `rename`，fsync，小规模追加——会直接调用。将这些操作分派到线程池会花费比节省更多的资源。

### 2.4 数据平面：功能，而非帧

`robotd` 不需要摄像头帧——它需要 *衍生特征*（“球在 (x,y)”、“检测到人”、“大声的声响”）。这些数据以十到三十赫兹，几十字节的频率传输，通过套接字传输非常简单。
**原则：将感知放置在传感器旁边。**`mediad`拥有摄像头，进行推理并发布特征。将帧传输给`robotd`以便其自行运行视觉处理会浪费大部分板载内存带宽。

**在控制回路中：**`robotd`仅订阅一次并读取本地缓存的*最新*快照——非阻塞，最新值获胜。如果`mediad`停滞不前，则会降低感知性能而不是增加对电机控制的抖动。

**如果帧必须跨越进程边界**（最后手段）：使用共享内存（shm/dmabuf环形缓冲区），套接字仅携带“帧N在偏移量X处准备好”。libcamera提供dmabuf，因此可以实现零拷贝。优先考虑特征而非帧，并尽量避免需要这种情况。

## 3. 状态所有权

三个不同的类别；详见`updater-design.md` §5.7中的更新/回滚影响。
| 状态 | 所有者 | 机制 |
|---|---|---|
| Wifi凭据 | **NetworkManager** | 我们从不存储它们。`configd`通过D-Bus驱动NM；NM以根用户权限保存配置文件并在自身重新连接。 |
| 机器人身份、用户偏好、可调参数 | **配置存储**（§3.1） | 文件+`flock`+`rename(2)`，由`configd`拥有 |
| 校准、学习状态、按设备生成的资产 | 所属服务 | 位于发布目录之外；在更新和回滚时均能生存 |
| 预装默认值、二进制文件、策略捆绑包 | 更新系统 | 位于`releases/<ver>/`下，原子交换 |

让NetworkManager拥有wifi凭据更少代码，更安全，并且减少了一个需要迁移的事物。
**A板并没有预装NetworkManager**，这原本是这一行所假设的。Armbian的无头镜像运行netplan + `systemd-networkd` + `wpa_supplicant`，netplan是一个配置*生成器*：它没有扫描API，`netplan apply`只会报告“配置已应用”而不是关联是否成功。这两点是为机器人进行手机配置时最需要的——“显示给我网络”和“密码错误”——因此决定保持不变，并且`scripts/migrate-network.sh`会在一次将一个板子迁移到NM上。关于这一决定的推理以及在板子上进行的测量结果，详见[`app-path-design.md`](app-path-design_zh.md) §2。

### 3.1 配置存储

一个普通的文件加上一个小巧的共享crate——**故意不使用服务**：

- `flock`用于写入序列化；使用写入临时文件再`rename(2)`进行原子性操作。
- `inotify`用于更改通知。
- 没有单点故障，即使任何服务都宕机时也能读取，且更新器从不修改它（参见`updater-design.md` §5.7）。
实现于 `configd/src/store.rs`，保存着机器人的名称及其蓝牙配对PIN。
`inotify` 目前 **尚未** 包含，这是故意为之：它只有在第二个进程读取该文件时才获得其位置，而今天 `configd` 是唯一的读取者。监视你唯一的写入文件是多余的。

配置 **必须** 在 `robotd` 死亡时可访问 —— 当一切出问题时，无线网络配置正是客户端所需要的 —— 这就是为什么它不能存放在 `robotd` 中。

**配置是状态，而不是动作。**“连接到这个无线网络”，“重启”，“应用更新”，“选择型号”都是动作，作为 RPC 分发给拥有服务。

## 4. 机器人的 API

### 4.1 一个定义，多种传输

`btd` **一无所有**。蓝牙只是几个前门之一。如果配置或配置文件存放在 `btd` 中，其他服务将依赖于它，SDK 将不得不无理地通过蓝牙进行操作。
```
        ┌──────── one API definition (shared crate: types + operations)
        │
   ┌────┴─────┬────────────┬──────────────┬────────────────┐
  BLE       unix socket   WebSocket     WebRTC datachannel
 (btd)      robotctl,     server-side   telepresence,
  subset    on-robot SDK  agents/LLM    full fidelity
```
Each transport是同一个API的薄适配器。BLE暴露了一个**子集**（配置、状态、更新触发/进度）——它对于完整表面来说太慢且太受限，且载荷从不通过它传输。

### 4.2 横切规则

- **每种传输的授权。** BLE意味着物理存在+配对；而网络传输需要一个令牌。相同的API，不同的授权——从一开始就决定检查点在哪里。
- **API版本握手。** SDK和守护进程版本*会*不一致。一个整数，版本不符时拒绝并给出清晰的消息（与`model_api`相同的方法）。
- **意图，而非电机写入。** 见§6。

## 5. 远程访问

### 5.1 要求

所有机器人和媒体数据必须通过**WebRTC**连接可达，以支持（a）远程存在和（b）一个服务器端程序（例如，一个LLM），该程序可以观察并控制机器人。后者必须是*容易的*。

### 5.2 WebRTC会话

一个PeerConnection承载一切：
```
peer (browser / phone / server)
   ├── video track(s)   ── camera
   ├── audio track(s)   ── mic + speaker (two-way for telepresence)
   ├── datachannel "control"   reliable, ordered      → the robot API (§4)
   └── datachannel "teleop"    unreliable, unordered  → input + high-rate telemetry
```
Two 数据通道，镜像 §2.1：电信操作输入和遥测数据变得**不可靠**(`maxRetransmits: 0`)，因为重传的80毫秒旧的摇杆命令比无用还要糟糕——总是选择最新的。

**`mediad` 拥有 PeerConnection。** 一个 PC 不能跨进程分割（轨迹和数据通道共享一个 DTLS/SCTP 关联），并且它需要编码后的媒体，因此它与 `mediad` 共存，`mediad` 通过它们的 Unix 套接字代理 `control` 消息到拥有服务。因此，`mediad` 是**远程网关**。

隔离成本是可以接受的：没有媒体，远程存在会变得毫无价值，因此共存不会失去任何分裂会保留的东西。本地恢复通过 BLE / `robotctl` 保持独立（不变量1）。

### 5.3 服务器端代理：不要强制它们通过 WebRTC

对于由 LLM 驱动的控制器，WebRTC 是更**困难**的路径。一个代理不需要每秒或每两秒解码一次30帧的 H.264 流——它需要每秒或每两秒一个帧加上一个状态块。首先要求 ICE/DTLS/SDP 和解码管道是不划算的交易。
| 消费者 | 传输 | 媒体 |
|---|---|---|
| 临场感（人类） | WebRTC | 轨迹，低延迟 |
| 服务器端代理 / 大型语言模型 | **WebSocket** | `get_frame` → 按需 JPEG，或 1–2 fps 推送 |
| 机器人 SDK，`robotctl` | Unix 套接字 | 截图 API |
| 应用 | BLE + WebRTC | 如需 |

所有这些都使用同一个 API。"在控制机器人的服务器上运行一个大语言模型"
变为：打开 WebSocket，请求一帧，发送意图 — 几十行代码，无需媒体栈。这正是它真正易于实现的原因。

另外，大语言模型的延迟（数百毫秒到数秒）意味着代理是一个 **高层** 控制器：“去厨房”，“看那个人”。反应式控制仍然保留在 `robotd` 中。无论传输方式如何，这都是正确的划分。

### 5.4 基础设施现实检查

“机器人有自己的 WiFi” **不** 等同于“可以从互联网访问”。远程 WebRTC 需要：

- 一个 **信令** 路径（SDP/ICE 交换），
- **STUN** 和 **TURN** 作为对称 NAT 的中继回退 — 真实的基础设施，有实际的带宽成本。

这与更新设计中的“零后端”前提相矛盾。**仅局域网的临场感可以完全避免这种情况；互联网临场感则无法避免。** 有待进一步探讨（§9）。### 5.5 实施注意事项

库的选择取决于硬件编码：如果我们需要 V4L2 M2M 硬件 H.264，则 GStreamer `webrtcbin` 更具实际意义；`webrtc-rs` 是纯 Rust 实现且更轻量，便于推理，但会让我们自行构建管道。这会显著影响 `mediad` —— 早期做出决定。

远程行走机器人在有损链路上的遥控。这些设计起来更便宜，而不是事后添加。

## 6. 安全性和权威性

通过有损链路远程控制行走机器人。这些设计起来更便宜，而不是事后添加。
- **死锁/心跳。** 如果命令停止到达或往返时间超过阈值，`robotd` 将自行停止机器人。不可协商：网络分割、LLM 在推理过程中停滞、笔记本电脑休眠。
- **意图，而非电机写入。** 远程客户端发送速度、注视目标、“坐下”—— 从不发送原始关节命令。`robotd` 对于跌倒检测、关节/温度限制以及安全姿态始终拥有最终决定权。一个困惑的代理不得能够命令机器人执行撞向墙壁的动作。
- **明确的权限仲裁。** 物理控制器、应用程序、远程对等方以及自主行为层都希望拥有控制权。定义优先级和交接流程，而非“后写者获胜”。本地/物理控制应能够优先于远程控制。
- **会话限制。** v1：一次仅一个媒体会话，加上 M 个控制仅客户端。多对等体视频（ simulcast、一次编码多次发送）暂未实现。

## 7. 隐私

这是一个家庭中的摄像头和麦克风。
- **明确同意**开始远程会话（每次会话前，或一个明确的持久性选择，用户可以撤销）。
- **始终可见的机器人指示器**，当流式传输激活时。
- DTLS-SRTP 保持媒体在通过 TURN 中继传输时始终加密——这一点值得直接告知客户端。
- BLE 配置文件传输携带 Wi-Fi凭据：该特性必须成对且加密。

## 8. 可观察性：日志和版本

横跨多个方面，因为家中的机器人无法通过附加调试器进行调试。支持方能请求的功能必须已经在机器人上实现。

部署细节——`journald` 配置文件、安装步骤、验证命令——位于
[`../deploy/README.md`](../../deploy/README.md)。本节是每个服务必须满足的合同。

### 8.1 每个服务将日志输出到 stderr

`tracing` → stderr → journald，日志级别通过 `RUST_LOG`（在预装单元中为 `info`）。没有
任何服务写入自己的日志文件：一种机制，一种保留策略，一个查看日志的地方。

每个守护进程写入的第一行是其自身的身份信息，级别为 `warn`，以确保在长时间运行的板卡上 `RUST_LOG=warn` 时仍然可见：

> 每个守护进程写入的第一行是其自身的身份信息，级别为 `warn`，以确保在长时间运行的板卡上 `RUST_LOG=warn` 时仍然可见：
```
WARN starting service="robotd" build=0.2.0 (rev a1b2c3d, built 2026-07-28T13:50:00Z)
     exe=/opt/robot/daemon/releases/0.2.0/bin/robotd pid=814
```
`exe` 赢得了它的位置：它指出了进程实际启动的发布目录，这区别于“更新生效”和“符号链接移动但systemd仍在运行旧路径”。

**日志容量是一个保留决策，而不是一个装饰性的决策。**`robotd` 的每跳心跳在 `debug` 级别；在 `info` 级别时，每五分钟记录一次总结，包含达到的跳数百分比。在 `info` 级别时的每跳记录将从一个空闲的机器人那里产生大约每天 86,000 条条目，而在日志大小受限的情况下，这些条目正是需要 *驱逐* 事故日志的。总结也提供了更多信息：一个运行在目标速度 60% 的循环是活着并且通过了健康检查的，而其他任何东西都无法显示这一点。

### 8.2 两条记录，故意不同的持久性

| | 存储位置 | 能够在断电后存活 | 由...限制 |
|---|---|---|---|
| 服务日志 | journald | 只有在配置的情况下，参见 `deploy/README.md` | `SystemMaxUse` |
| **更新历史** | `/var/lib/robot/updater/update-log.jsonl` | **是** | 200 条记录 |
更新历史故意不在日志中记录。它存放在引擎的 `state_dir` 下的 `/var/lib` 中，每次追加时都会 `fsync`，重写也是原子操作（临时文件 + 重命名 + 父目录 `fsync`）。因此，“这个机器人安装了什么，发生了什么”在日志易失或被擦除的机器人上是可以回答的——这是现实中的支持案例，而不是理想情况。

### 8.3 运行版本和已安装版本是两个不同的问题

`updaterd` 不能在更新过程中重新启动自身（`updater-design.md` §4.1），因此在每次更新后的几秒钟内，运行中的二进制文件确实会滞后于已安装的版本。任何工具在此窗口期内报告的版本号都是错误的，并且会朝着使正常工作的机器人看起来有问题的方向出错。

不是“直到重新启动”：引擎会在回复后自己安排重新启动，并在 5 秒后重新启动 `btd`，下一个 `updaterd` 启动会检查这些是否已落地，并重新启动未完成的部分（`restart-order.md` §5）。

`robotctl version` 会报告两者并指出它们之间的差异：
- `updaterd` 在安装的版本之后 → 预期会短暂出现，并且不会有任何偏差：继任者会报告它而不是重新启动自己，因此如果它持续存在，说明计划中的重启并未发生；
- `robotd` 在其后 → 不应出现，因为它在 `on_apply` 的重启集合中，所以重启并未生效。

这些是不同的诊断结果，不能共享一条消息。`--json` 会给出相同的內容用于支持包，并且当 `updaterd` **宕机** 时该命令仍然有效——它会报告该状态而不是退出，因为这是人们会去检查它的时候。

四个独立的地方可以恢复版本，因此丢失一个是可以生存的：启动日志行；通过 IPC 的 `robotctl version`；每个二进制文件的 `--version`；以及每个发布目录内的 `version.toml`（加上 `robotctl update list`，它显示了每个安装版本所构建的修订版本）。
`revision` 是从 `DUCK_REVISION` 编译进来的 —— 由 CI 设置，在本地不存在时，二进制文件诚实地报告 `rev unknown, not a CI build`。在编译时读取，从不从 git 在运行时读取：已发货的机器人没有仓库。它比看起来更重要：一旦分支安装落地（路线图 M2），多个构建共享一个版本号，而修订号是区分它们的唯一标识。

### 8.4 健康是一个问题，所以是一个命令

`robotctl health` 从 `robotd` 报告硬件状态，从 `updaterd` 报告软件状态，在一个答案中给出。这不仅仅是为了方便：“这台机器人的哪里出了问题”直到回答之后才会分为硬件和软件，而一个小时之前回退了一个版本的机器人与伺服未供电的机器人在屏幕上分开之前，看起来完全一样。分开它会让调用者在不知道哪个部分出问题之前就做出选择。
It **退出非零状态当机器人不健康或无法访问**，因此它可以作为脚本——
任何构建在其之上的合约依赖的门控。其他任何事情都不会影响退出代码：一个平装版、一个热电机和一个锁定的组件都会被报告，而不是判断。代码库绝不能因为其所在的板卡状态而回滚。

`--json` 为支持包携带相同的内容。

## 9. 未决问题
1. **v1中的互联网可访问远程会诊，还是仅局域网？** 大问题：区别在于没有后端和运行信令 + TURN（§5.4）。
2. **SDK是团队内部使用的还是分发给最终用户？** 决定了API兼容性承诺的难度（§4.2）。
3. **当应用程序、远程对等体和自主行为发生冲突时的权限优先级** —— 即使是一个粗略的固定顺序，但也是决定好的而不是自发形成的（§6）。
4. **感知功能是在`mediad`中还是独立的`perceptiond`中？** 将推理功能与摄像头捆绑在一起更简单；分离意味着感知崩溃不会杀死视频流。这取决于视觉功能的重量。
5. **行为/大脑层**（驱动、情绪、习惯）：是`robotd`的一部分，还是独立的服务和更新通道？无论哪种方式，其学习状态都是`updater-design.md` §5.7 的内容。
6. **通过蓝牙低功耗撤销绑定。** 没有什么可以解绑手机；`bluetoothctl untrust` 是手动退出的方法。需要一个API和关于谁可以调用它的规则（[`app-path-design.md`](app-path-design_zh.md) §5）。
7. **每个设备的配置状态** —— 现在是每个机器人的配对PIN，除此之外没有其他内容。序列号
   是另一方的主张方，现在不再需要分配插槽：它已融合到SoC中，并从
   `/proc/device-tree/serial-number`（`updater-design.md` §5.6，
   [`app-path-design.md`](app-path-design_zh.md) §8.2）读取。PIN不能共享身份，这原本是计划中的：身份在广告中发布，因此任何从中派生的内容都是公开的。
   仍然需要生成一个秘密，记录并打印在制造过程中。

## 10. 构建顺序

`updaterd` 首先构建，然后用于分发此架构的每个后续版本。这将更新系统的风险前置加载，因为此时失败成本较低（没有客户端，没有有价值的东西可以破坏），并且意味着更新路径在机器人发货前会被执行数百次。

在执行时需要注意的后果：

- `updaterd` 是基于对 `robotd`（健康探测，安全重启）的 **接口** 构建的，而不是实现——最初是用模拟对象实现的，这也是使其可测试的原因。
- 早期的健康探测将是弱探测（“进程存活”）。随着 `robotd` 的成熟，自动回滚的信心会逐渐增强；**保持在整个早期开发过程中都有手动恢复路径（SSH / 重新刷写）**。更新程序既未经过验证又在快速变化，并且它会包含在要更新的软件包中——不要让它成为唯一的返回路径。
- 无法回退的 Schema 字段（`min_supported`、`schema_version`、`model_api`）即使未使用也会从第一个版本开始包含在内。
