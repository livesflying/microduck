# 手机应用 — 它由什么构成

状态: 已构建 · 日期: 2026-09-17 · 所有者: pierre

所有者的应用: 竖起机器人，将其放在Wi-Fi网络上，更新它，登录它，驾驶它，看看它是否正常，然后让它执行它所知道的任务。它是用什么语言编写的，它从我们已经为另一款机器人提供的应用中借用了一些什么，以及机器人还欠它什么。

它存在于 **[`pollen-robotics/microduck-app`](https://github.com/pollen-robotics/microduck-app)** 中，
这是代码和操作的一半——构建它、签名它、将其安装到手机上——所在的地方。本页面是其理由：它为何如此设计，以及哪些决策带来了成本。

与 [`app-path-design.md`](app-path-design_zh.md) 相配套，后者负责机器人一侧——GATT界面、路由表、车道、配对、身份以及它们的每一个开放问题。当两者交汇时，后者是所有者，而本页面则指向它。
[`remote-webrtc.md`](remote-webrtc_zh.md) 负责另一种传输方式，而第1.2节则是它们之间的分界线。

## 1. API 是规范；应用是客户端
`btd/src/route.rs` 决定手机可以请求什么，而 [`duckctl.md`](../robot/duckctl_zh.md) 是应用最接近功能规范的东西——里面每一个命令都是应用可以通过同一无线网络发出并收到相同回复的调用。

| 屏幕 | 调用 |
|---|---|
| 选择机器人 | 广告——名称和IPv4，然后 `hello` 和 `system.authenticate` |
| 机器人 | `system.info`，`robot.health`，`system.services`，`system.setName`，`system.reboot`，`robot.init`，`robot.enable` |
| 驾驶 | WebRTC：视频，`robot.move`，`robot.subscribe` |
| 移动 | `robot.skills`，`robot.do`，`robot.policies`，`robot.loadPolicy`，`policy.check`，`policy.search`，`policy.fetch`，`policy.install` |
| wifi | `net.status`，`net.scan`，`net.connect`，`net.forget` |
| 更新 | `update.check`，`update.apply`，`update.subscribe`，`update.status`，`update.listInstalled`，`update.log`，`update.rollback`，`update.select` |
| 日志 | `system.logs` |
| 账户 | `account.login`，`account.status`，`account.logout` |

如果发现需要添加但未路由的内容，则只需对 `route.rs` 进行一行更改，并决定它是否属于无线电——这就是 §3.1 存在的目的。该应用现已测试了该属性四次：`update.rollback` 和 `update.select`，然后是 `robot.init`，最后是 `robot.enable`，每次打开都是因为使用应用时发现了拒绝带来的成本，而这种成本拒绝本身的推理并未考虑到。

### 1.1 这是机器人的接口，而非设置工具

曾经路由的子集包括 Wi-Fi、更新、健康和名称。现在它几乎涵盖了一个人使用鸭子所做的一切，并且 `route.rs` 的每一臂上的参数都押韵：**十米的无线电范围意味着点击它的人正在查看机器人，而连接是通过 PIN 校验的**——因此，BLE 是最佳的传输方式，因为它回答了 *谁在观看* 这个问题，这也是该文件中大多数拒绝所关注的问题。

这就是为什么下面的机制不是过度工程。一个设置工具可以仅通过一个调用和一个加载项来实现；而一个接口则不能。

What stays off the radio: continuous intent and anything streaming (`robot.move`, `robot.subscribe`,
`tof.stream`, `pad.input`), the pairing PIN, `update.pin` and `update.resetToGolden`, and the two
calls whose failure mode is the floor — `robot.relax` and `robot.rebootMotors`。第一组属于另一种传输方式；其余的属于机器人终端上的人。

### 1.2 两种传输方式，并非竞争对手

除了 `drive` 之外的所有内容都通过 BLE 传输。**BLE 是应用程序的通道，原因在于机器人页面 §2.2 所述的内容**：无需网络即可工作的设置。一块电路板到达一个新地方，它所知道的 WiFi 并不存在，而网络上的任何东西都无法达到它——一个需要局域网来更改设置的应用程序无法修复保持机器人离线的设置。

`drive` 从定义上需要一个网络，并从 `net.status` **通过无线电** 获取用于连接的地址。这就是它们作为一个整体而非两个独立实体工作的原因：总是可用的传输方式告诉您如何连接到快速的那一个。机器人的控制台也不是竞争对手——它也需要一个地址，这意味着它需要一个网络，这意味着它需要应用程序所提供的东西。

## 2. `reachy_mini_mobile_app` 是一个参考，而不是基底

Pollen 为 Reachy Mini 发送了一个 Tauri 2 应用 —— React 19, MUI, `tauri-plugin-blec`, TestFlight 和 Play Internal。它通过 BLE 配置一个机器人，然后通过局域网和 Hugging Face 做其他一切事情。

它的 BLE 层使用了一种不同的方言 —— 四个特征，命令以字符串形式发送，回复通过子字符串解析 (`ERROR:`, `OK:`, 和 `ECHO:` 表示“你的固件版本太旧，无法识别此命令”)，其源代码称之为一个弃用的测试表面。并且它的蓝牙仅用于运行一次，这就是我们无法继承的原因。第二个决定的是这个应用的形态，而不仅仅是传输方式。

值得借鉴的是其底层架构，其中包含了昂贵的知识：
| 以代码为准 | 以规则为准 | 删除 |
|---|---|---|
| `tauri-plugin-blec` 的布线 —— 但 **不** 包括其打包的 `btleplug` 修补程序和 npm 绑定。CoreBluetooth 连接时的崩溃修补程序 (deviceplug/btleplug#397) 在 `btleplug` 0.13 中已修复，`blec` 0.14 是基于此构建的；而他们的 0.8 版本则早于此。他们保持的 crate 到 npm 的同步步调从未达到由 Rust 驱动的客户端，因为 webview 不调用 BLE | 未过滤地扫描并自行筛选候选项 —— 他们的扫描核心和 §3.3 是独立得出的，这证明它是真实的 | TanStack Query：它通过 HTTP 缓存服务器状态，而此应用没有服务器状态 |
| Android 蓝牙低功耗运行时权限处理，这是选择 `blec` 而不是 `btleplug` 的原因 | 通过轮询候选项而不是在睡眠后取一个快照 (§3.4) | 设置向导状态机 —— §4 |
| 全屏，`viewport-fit=cover`，安全区域填充，锁定纵向模式 | 每个错误都携带恢复步骤，因此“重试”不会重新启动流程 | 字符匹配错误分类：`configd` 返回 `BadKey` 和 `NotFound` 作为类型，而缺少的方法会自我命名为 `METHOD_NOT_FOUND` |
| 他们的App Store合规和审查备注，这些备注只写一次但会导致一次拒绝才能学到 | 当应用处于后台时，预期会发生一次BLE掉落，这不是故障：iOS会断开GATT连接 | |
| `x25519-hkdf-sha256-aesgcm` 密码封装方案，如果机器人页面的§8.1部分关注的是封装而非链路层——线路上的格式已在他们那边文档化，并且有一个可用的客户端可以用来测试实现 | 连接失败可能会表现为成功，然后在订阅时挂起；通过断开连接再重新连接来强制进行一次新的发现 | |

## 3. 协议运行在 Rust 中

`tauri-plugin-blec` 暴露了一个 Rust 处理程序以及一个 JS 处理程序，这两个处理程序是相同的——从任一端打开的链接可以从另一端驱动。因此，应用依赖于 `duck-ipc-proto` 用于线上的数据类型、依赖于 `duck-ble` 用于分块和 GATT UUID，从 Rust 驱动无线电，并向 WebView 提供类型化的命令。React 从不解析机器人回复；它调用一个返回 `NetStatus` 的函数。
This 是值得重用的部分，也是 Reachy Mini 无法拥有的：**应用程序不能偏离守护进程。** 协议更改会像影响 `btd` 的路由表一样影响应用程序的构建 —— 这种情况已经发生过两次，每次都因为应用程序在错误的时机从机器人那里学到了一个本应从守护进程那里学到的字段。

这也是选择 Tauri 而不是其他替代方案的理由，但不是通常的理由。每个跨平台工具包都能提供一个代码库；只有这个工具包能让客户端使用服务器自身的类型。

**`duck-ble` 存在的原因就是这个应用程序。** `gatt`、`framing` 和 `adv` 都是 `btd` 的，而且每个都已经被标记为传输合约 —— `adv` 明确指出，客户端单独编写的解码器只会与自身一致，而这个应用程序通过在 crate 之前手动编写一个解码器证明了这一点。提取这些代码停止了手机二进制文件携带 `clap` 和 `tracing-subscriber` 仅为了一个模块的情况，并停止了 `duckctl` 编译一个 Linux 守护进程 —— 而在 Linux 上，`bluer` 和一个 vendored 的 libdbus —— 以达到三个平台无关的文件。

### 3.1 媒体的位置，以及为什么这并不是一个漏洞
The 协议在 WebRTC 数据通道上并非全部使用 Rust 编写，而且只有一半是。一个对等连接和一个 `<video>` 元素是 WebView 的固有部分；手机屏幕上没有相应的 Rust 等效物可以将帧显示出来。但是数据通道携带的是 *相同的* JSON-RPC，因此在 TypeScript 中手动编写这些信封会重新引入本节安排防止的漂移。

所以 WebView 负责传输字节，而 Rust 决定这些字节的含义：每一行都是由 `proto::Request` 从 `proto::Call` 构建的，应用程序的信号模块根本不包含任何方法名。`.ts` 文件中的 `{vx, vy, vyaw}` 对象字面量会继续编译并开始错误地控制方向。

Reachy Mini 的传输会发送一条命令，同步读取响应特征值，如果回复是 `OK: working` 确认，则等待携带实际载荷的通知：这就是为什么一次 WiFi 搜索返回空结果，同时却传递了上一个命令的密钥交换对象。修复方法是在每个命令的顶部清除过时的 backlog。

## 4. 蓝牙是永久通道，不是设置步骤

唯一结构上的不同之处，决定了应用的形态。

Reachy Mini 的 BLE 代码仅运行 **一次** — 一个具有终端状态的向导，之后局域网接管，蓝牙再也不会被使用。Duck 的 BLE 是机器人接口的驻地，只要机器人存在，它就会一直存在。
So 这不是一个带有设置选项卡的巫师。该应用有一个会话层，在不告知的情况下重新连接并重新认证，因为§3.2中有 `btd` 在中央消失且重新连接的电话开始未认证时丢弃会话。每个屏幕都能容忍其下的连接断开并重新连接——包括在更新过程中，`btd` 在回复发出后五秒重启（参见[`restart-order.md`](restart-order_zh.md) §1），而在用户在浏览器中批准设备代码期间，`account.login` 回复的是一个代码而不是令牌。

机器人在会话层的中间位置：`updaterd` 为每个组件保持最新的进度，并将其重播给新的订阅者，而 `update.status` 在更新过程中从缓存快照中回答。因此，在更新过程中重新连接的电话会重新认证、重新订阅并被告知进度到了哪里。
**那层是应用的实际核心，而且出乎意料地是可以测试的。**§8.2中的机器人页面说，值得测试的场景在板子上是不可测试的——对于房间里的三台机器人来说是这样，但对于断开链接的情况则不是这样。`tauri-plugin-blec` 提供了一个进程内模拟，可以断开链接并在需要时挂起操作，因此重新连接、重新认证和重新订阅都是普通的测试。它们已经发现了三个真正的缺陷：在打开链接的调用中，订阅被发送了两次；重新连接时找不到自己的机器人，因为发现缓存已经清空；以及一个从未上线的链接的`Down`事件。

## 5. 专属的仓库

守护进程工作区因为其中的一切都打包在一个文件中而共享版本。应用程序以不同的节奏发布到应用商店，并不属于这个版本线，因此它有自己的版本。

`microduck` 是公开的，因此 `duck-ipc-proto` 和 `duck-ble` 是普通的 git 依赖项，不需要凭证。依赖项故意跟踪 `main` 而不是固定版本：协议更改导致应用程序构建失败是这种安排存在的信号。
## 6. 版本底线，即与守护进程规则相反的规则

**应用程序在握手时拒绝版本低于 `API_VERSION` 31 — 机器人 0.14 — 的机器人。**

这与守护进程遵循的规则不同。`app-path-design.md` 第 3 条明确指出，版本差异应报告但不应拒绝，这是正确的，因为守护进程是为没有网络连接的机器人而存在的传输方式，`net.connect` 是解决偏差的方法。

应用程序做出了不同的权衡，这种权衡为每个屏幕带来了好处。一个检查过的底线，意味着一个屏幕可以将一个字段视为存在，一个方法视为已路由，一个回复视为守护进程定义的形状——而不是每个字段都带着自己对较旧机器人可能发送的内容的猜测。在握手时发现这一点比在四屏之后从一个不存在的方法中发现要好。

**这种权衡的实际成本在于拒绝本身的话语**：低于底线的机器人无法从手机更新，因为手机不会与它通信。`duckctl update apply` 通过相同的无线电到达它，消息中会这么说。
A机器人*更新*于应用时被服务。协议只会增加字段，而拒绝不认识的客户端则需要与每个机器人的更新同步进行。

| | |
|---|---|
| **使机器人站立** — #301, #303 | `robot.init` 被拒绝，因为“希望执行者面对机器人而不是屏幕”，这是 `route.rs` 为路由 `robot.do` 和 `policy.install` 而提出的论点。`robot.enable` 也被拒绝，因为它不是自动控制——一次请求，而不是每秒五十次。没有这两项，应用程序可以向机器人展示所有关于自己的信息而不让它移动，出路是去找游戏手柄。|
| **通知携带512字节** — §3.6, #292 | 由该应用程序发现并用 `duckctl` 复制：`btd` 的回复大小为 `mtu - 3`，在 CoreBluetooth MTU 为 517 的情况下，比一个特征值所能容纳的多出两个字节。中心设备保留了前 512 个字节并默默地丢弃了其余部分，因此 `{"security":…}` 作为 `{"serity":…}` 到达——或者，当丢失的那对包含换行符时，作为从未接收到的呼叫。|
| **三个机器人中哪个是我的** — §8.2 | 名字来自SoC序列号，而广告则携带IPv4，因此第一个屏幕会列出名称和地址，而不进行任何连接。该应用会基于序列号进行操作，并将地址视为缓存，这正是§8.2的规定：另一个板卡重用的地址将被名称拒绝，而不是默默接受|

## 8. 开放
- **开机屏。** 工厂预设PIN为`000000`并在本仓库中公开，因此今天的PIN步骤要求一个保护不了任何东西的秘密，并在唯一一个增加摩擦成本的流程中增加了一个屏幕。应用会默默地发送这个步骤。当有为每个机器人打印的PIN需要输入时，这个屏幕就会出现，而“错误PIN，还剩两次机会”也会出现在这里。
- **来自手机的游戏手柄。** `pad.pair`、`pad.forget`、`pad.bind`和技能表编辑都被路由并且未被触及。`route.rs`说明`pad.bind`的存在是为了BLE连接——谁拿着机器人谁拿着手柄——而上述故障3就是为什么从手机配对比路由显示的要难。
- **一个应用是否最终服务于两个机器人。** 现在不是这样——这意味着在一个发布的代码库中增加第二种方言，而它们之间共享的只是传输方式。如果它成为目标，前提条件是*协议*的统一，而不是用户界面的统一。
- **用户界面组件库。** 并没有一个这样的库：应用的CSS代码行数大约为三百行。MUI显然是一个候选方案，但并未被采用，迄今为止也没有什么需要它的地方。如果某个屏幕需要一个样式表无法提供的组件，值得一看，但不值得再次考虑。
