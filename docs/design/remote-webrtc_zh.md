# WebRTC: 会话、信令和控制通道

电话、浏览器或服务器端程序如何通过 WebRTC 驱动和观察机器人。
[`architecture.md`](architecture_zh.md) §5 规定了这一要求；本节描述了机制。

仅限 **本地信令**：以下内容在机器人上运行，并在局域网内工作，没有后端。从局域网外访问机器人与之相同，只是前面有一个代理（§7）——故意不是首先构建的内容，因为本地情况是其他所有情况的基础定义。

## 0. 状态：正在硬件上进行开发

一个 Radxa Zero 3W 通过硬件编码将 `videotestsrc` 流式传输到局域网内的浏览器，浏览器同时获得一个 `control` 数据通道。2026-08-25 证明了端到端功能：

| | |
|---|---|
| 信令 | `mediad` 在进程中运行服务器；生产者注册，消费者列出并启动会话 |
| 视频 | `mpph264enc` → `webrtcsink` → 浏览器，协商为 `profile-level-id=42e01f` —— 限制基线，这是 §2 的全部要点 |
| 绑定 | `a=group:BUNDLE video0 application1`，`a=sctp-port:5000` —— 一个传输用于媒体和数据 |
| 数据通道 | `control` 到达对端 |
Two 事情从没运行过，但都在第一次尝试时出错了，记录下来是因为它们是这种设计所招致的错误形态，而非偶然：

### 摄像头，以及导致35%帧率损失的两个独立原因

主摄像头以 **29.3 fps** 通过硬件编码器进行流式传输。达到这一点花了两个不相关的修复，而耗时的原因是每个单独的修复都无法提高帧率——这使得每个修复看起来都无效。

**捕获池深度。** rkisp 不实现 `V4L2_CID_MIN_BUFFERS_FOR_CAPTURE`，因此 `gst_v4l2_object_decide_allocation` 从零开始计算 `own_min` 并最终确定为两个缓冲区。三个缓冲区是一个悬崖，而不是一个斜坡：在主路径上使用 `v4l2-ctl --stream-mmap=N`，两个缓冲区时为 19.7 fps，三个或更多时为 29.2 fps。提高捕获池深度需要在 ALLOCATION 查询中包含一个 `GstVideoMeta`（或者 `can_share_own_pool` 为假且读取查询的 `min` 的分支从未被取到），并且需要一个 `min` 非零的初始池（任何下游元素提出的池会设置 `update` 并放弃 `+2` 的奖励——`GstVideoEncoder::propose_allocation` 正好提出这一点）。
**像素格式。**rkisp 提供了一个非连续的双平面 `NM12` 以及单平面格式。两者都映射到 GStreamer `NV12`，`v4l2src` 偏好使用多平面版本，但在任何池深度下都无法以全速率驱动：

| caps | 2 个缓冲区 | 4+ 个缓冲区 |
|---|---|---|
| `NV12`（选择 `NM12`） | 19.5 fps | 19.6 fps |
| `UYVY`（单平面） | 19.7 fps | **29.3 fps** |

`mpph264enc` 在其 sink 端口上列出 `UYVY` 并在 RGA 上进行转换，因此从 4:2:2 转换到 4:2:0 不会消耗 CPU。

**通过测量而不是争论排除的内容** —— 每个选项都是一个合理的嫌疑人：`v4l2-ctl` 在同一节点上以每种格式均能达到 29.2 fps；传感器子设备报告 1/30 的间隔；驱动程序未实现 `S_PARM`；`mpph264enc` 以 130 fps 的速度无限制地编码 720p；`v4l2src` 在未受约束时偏好的 DMABuf caps 并非其在未受约束时快速的原因。
**这个方法论上的教训，代价比上述任何一项都高。**四种不同的速率各自被用于捕获速率，但它们都不是：`rkvenc` 中断计数的是编码器实际消耗的速率，位于 `webrtcsink` 队列之后以及其转换器模块中的 `videorate drop-only` 之后；`v4l2src` 的 `lost frames detected` 计数的是由于驱动序列号中的间隙而检测到的丢失帧，并且当源只是较慢时会保持静默；tee 的原始分支上的计数器位于故意泄漏的一缓冲区队列之后；而 `/dev/video1` 是ISP 自身的路径，而不是守护进程使用的主路径。`mediad` 现在在 tee 之前计量了管道，这是唯一一个从它到驱动之间没有任何压缩的地方。

暴露了两个尚未解决的问题：`rtpgccbwe` 占用大约 40% 的一个核心，而 GStreamer 自身的 `INFO` 级别日志从未通过桥映射到 `tracing::info!` 达到日志记录，这就是为什么这些问题中的几个是通过较慢的方式回答的。

尚未测试的内容：通过桥传输的任何内容。

What the stream是——摄像头或测试图案，帧大小，帧率，码率——是在`/etc/robot/robotd.toml`中定义的`[media]`。这个每块板子的配置文件`robotd`已经读取了。`sudo robotctl configure`可以编辑它，并提供所需的`systemctl restart mediad`；`mediad`在启动时会读取一次，就像这里其他每个守护进程读取其配置一样。

**一个`quality`键命名一个梯级——`1080p30`，`720p30`，`720p15`，`360p30`——而不是宽度，高度和帧率。**这三个参数并不独立变化：捕获路径不能生成的组合会导致管道无法启动，这也会导致控制通道和视频一起失效，因为数据通道与视频轨道捆绑在一起（§2）。每个梯级都是16:9，这是传感器自身的宽高比，因此“较小”的永远意味着“裁剪”。`bitrate`是唯一可以单独设置的数字，如果不设置，它会跟随梯级——在720p30时为2 Mb/s，这是所有测量所采用的速率。
The 数字原来是 `ExecStart` 标志在 `mediad.service` 中，直到该部分存在。发布安装程序会重写该单元文件，所以更改一个意味着使用 `systemd` 下载配置 — 一种用于电路板 *连接* 不同的机制，而不是解释为什么图片模糊。

### 拥塞控制也是一个 CPU 设置

`[media] congestion_control` — `gcc`、`自制` 或 `禁用` — 是 `webrtcsink` 的 `congestion-control` 属性，设置而不是继承。`gcc` 是该元素的默认值，因此命名它不会有任何改变；它购买的是上游改变默认值的那一天，并不是每一个机器的发送速率都会随之改变的那一天。

**这是该进程最大的单一 CPU 消耗者。** 每个线程，与板上连接一个对等体时：

| 线程 | 占用 CPU（一个核心） |
|---|---|
| `rtpgccbwe1:src` | 7.6 |
| `queue1:src` | 6.0 |
| `mpph264enc2:src` | 5.0 |
| … | |
| `v4l2src0:src` | **0.3** |
| `queue3:src`（原始分支） | **0.3** |
~25%的一核总占用率，且其形状为点：捕获和原始分支框架拷贝——这两者是唯一与*像素*相关的缩放项——之间相差0.6%。其余部分是包工作，其与比特率相关。这就是为什么选择较小的阶梯不会降低CPU占用率：在一个从未饱和的链路上，估计器会将360p流调整到大约720p流所使用的比特率，并将资源用于每个像素的质量上。

`disabled` 删除了 `rtpgccbwe` 线程。这会牺牲适应性，而这正是 `webrtcsink` 被给予原始视频而不是预编码的 H.264（§1）的原因——在链路劣化的情况下，它能保持画面而不是停滞。这也使得 `bitrate` 的含义变得明确：它不会移动，因此表示的是速率而不是起始点。

**720p30是唯一测量过的阶梯。** 传感器固定在30帧每秒的1920x1080模式上，ISP从该模式向下缩放，因此1080p30不需要任何缩放；没有人测量过捕获路径和编码器是否能在上述表格中像素的2.25倍下保持30帧每秒。无法保持的阶梯会运行得更慢——这并不是开始的失败。

## 1. 这不是什么
`webrtcbin` 没有被使用。`mediad` 使用了 **`webrtcsink`** 从 `gst-plugins-rs`，而两者之间的区别正是这份文档简短的原因：`webrtcsink` 带来了会话协议、会话模型以及每个消费者端的编码管理，因此剩下的设计工作是控制面而非媒体管道。

如果使用 `webrtcbin`，就需要自己编写这三部分。它在 Debian 中可用而 `webrtcsink` 不可用（[`media-bringup.md`](../project/media-bringup_zh.md) 介绍了该插件的构建和分发方式），这是支持使用 `webrtcbin` 的一个理由——但因为免费带来了协议，而这个协议正是远程桥接代理所依赖的（§7），所以这个理由并不成立。

## 2. 一个会话，四路流
```
peer (browser / phone / server-side program)
   ├── video track      camera, hardware H.264 (mpph264enc, constrained-baseline)
   ├── audio track      mic; two-way for telepresence
   ├── datachannel "control"   reliable, ordered      → the robot API (§5)
   └── datachannel "teleop"    unreliable, unordered  → input and high-rate telemetry
```
Two 数据通道而不是一个，原因如 `architecture.md` §5.2 所述：重传80毫秒前的joystick命令比无用更糟糕，因此teleop设置为 `maxRetransmits: 0` 并总是采用最新的数据。

**第一个版本仅打开 `control`。** teleop不是短期内的优先事项，将其省略不仅仅是推迟——§6描述了它所移除的内容。

**`webrtcsink` 在其sink端口接收预编码的H.264**，因此编码器从未参与协商。已在硬件上验证；四个编码器属性中，有四个是决策而非默认值，详见[`media-bringup.md`](../project/media-bringup_zh.md)。

**管道在编码器之前分流原始的NV12数据**，这种放置是故意的：
```text
                              ┌─ queue ─ mpph264enc ─ h264parse ─ webrtcsink
capture ─ NV12 ─ capsfilter ─ tee
                              └─ queue(leaky, 1) ─ appsink ─ a frame on request
```
§5.3 要求服务器端程序按需获取一个框架 — “它每秒或几秒想要一个框架，再加上一个状态数据包”，而不是一个 30 帧每秒的 H.264 流来解码 — 而 `architecture.md` §2 要求传感器旁边进行感知，提取特征而不是将像素传输到 `robotd`。两者都需要 *像素*，如果将它们从编码分支中移除，就意味着需要解码刚刚编码的内容。

全程使用 NV12，因为这是 rkisp 路径发出的格式，也是 `mpph264enc` 接受的格式，所以没有任何地方需要进行转换。每个分支都有自己的 `queue` —— 没有它们的 `tee` 会从一个线程运行，所以慢速的读取器会阻塞视频流 —— 而原始数据的 `queue` 是泄漏性的且只有一块缓冲区，这正是 `architecture.md` §2 所要求的最新快照，而不是一串过时的快照。阻塞的读取器会丢失帧，而不是编码器。
**一帧只有在读者请求时才会从 appsink 中复制出来。**在这个分支上的读者每秒之间想要获取两帧——自动曝光计每 500 毫秒一个，当启用时鸭子检测器每秒查看两次——一帧在 720p30 分辨率下大小为 1.84 MB。捕获所有三十帧需要 55 MB/s 的 memcpy 和每秒 30 次 1.8 MB 的内存分配，从启动开始，每台机器人上都会发生这种情况，而这些帧实际上并没有被读者读取。每个缓冲区仍然会到达 appsink 并在那里被丢弃；对于不需要的帧，其成本只是放松了负载。

读者的请求是由 *下一个* 捕获来回答的，而不是由最后一个交付的捕获来回答。返回当前闲置的任何内容会再次更便宜，并且会将读者自己的轮询周期纳入测量中——一个基于半秒前亮度进行曝光环控制的循环是一个在寻找的循环。读者会阻塞，直到其帧到达，受到超时的限制，而当相机停止时，它会到达与总是相同的“没有帧”路径相同。

这个分支从一开始就存在，而不是在有东西读取它时才添加进去：在实时管道中插入一个 tee 是一个比始终存在的 tee 更困难的问题。
## 3. `mediad` 自行运行 signalling 服务器

`webrtcsink` 有 `run-signalling-server`，带有 `signalling-server-host` 和 `signalling-server-port`（gst-plugins-rs 0.15.3）。因此，服务器在 `mediad` 的 **自身进程中运行**，不需要额外构建、分发或监督二进制文件——这很重要，因为我们要分发的插件是一个 `.so`，而 `gst-webrtc-signalling-server` 是同一个上游 crate 的独立 Rust 二进制文件。不分发它是一个真正的简化，而不是捷径。

`webrtcsink` 自身的 signaller 默认为 `ws://127.0.0.1:8443`，并连接到它刚刚启动的服务器。局域网客户端直接连接到同一个服务器——`mediad/webclient/index.html` 就是一个例子，它是一个单文件，没有构建步骤，通过手写协议与服务器通信，而不是通过 `gst-plugins-rs` 的 JS 库，这样尝试它不需要安装任何东西。
[`webrtc-console.md`](webrtc-console_zh.md) 拥有该页面的后续处理——提供该页面的机器人、找到该机器人以及它应该达到的控制面。
**绑定地址是一个决定，而不是默认设置。**仅使用回环地址意味着局域网对等方无法访问它，所有会话都将通过桥接进行，这违背了本地模式的意义。因此它绑定在所有接口上，§4 就是对此的说明，说明谁可以操作。

## 4. 授权：机器人上没有门禁，以及为何这一点在本地和远程都适用

**第一版没有门禁。**能够到达信令服务器的对等方可启动会话、操作机器人并透过其摄像头观看。这是一个决定，而不是疏忽。

此时易用性优先于加固，而这里的权衡差距甚远。机器人的配对PIN码是共享的 `000000` —— 每个认证机器人上的相同PIN码实际上认证不了任何人，因此在WebRTC上要求输入PIN码只会增加每次首次连接的步骤，却没有任何安全保障。一个令人不悦的首次连接确实是一个成本；这种特定的门禁没有任何好处，却是一个真正的成本。

明确地说出它所付出的代价，以免任何人不得不去发现它：同一网络上的任何人都可以操作机器人及其摄像头。在实验台上和办公室里可以接受。**在家中则不行**，这是在发货前需要重新考虑的事情。
### 作者权限的实际位置：桥梁，它已经在那里

远程路径也不需要在机器人上设置一个门，因为它在到达一个门之前就已经进行了身份验证——在两边都是如此：

- **客户端** 使用 OAuth 向会合服务进行身份验证，服务只会向其展示客户端账户拥有的机器人。到达通往特定机器人部分的桥梁部分即是证明。
- **机器人** 向外进行身份验证：其中继持有账户令牌，并使用该令牌连接到服务（§7）。因此，机器人也证明了它属于该账户。

因此，服务正在匹配两个已经进行了身份验证的实体，通过它的会话已经被授权两次。额外的 `system.authenticate` 就像是对已经回答的问题进行第二次回答——而且是一个更差的答案，因为共享的 `000000` 密码比账户令牌证明的内容要少。
**这意味着信任并没有消失，而是转移了**，值得明确指出它去了哪里：机器人没有独立的验证机制，因此机器人与账户的绑定现在是必须正确无误的部分，它存在于服务中而不是这里。这是一个可以接受的位置——它是唯一能够知道答案的组件——但它是一个依赖关系，而不是缺失的关系。

这种安排没有涵盖的情况是，一个直接通过端口转发而非通过桥接将信号端口暴露到互联网上的机器人。在这种情况下，没有桥接进行认证，§4中的局域网逻辑也不适用，因为能够访问它的群体不再是大楼里的人。这是一个部署错误而不是设计决策，值得明确说出来，因为机器人本身不会注意到这一点。

### 如果需要的话，钩子

`system.authenticate` —— BLE已经使用的方法，从 `API_VERSION` v4开始添加。一个控制通道会为这个方法服务，并在通过认证前拒绝其他所有请求，PIN将通过unix套接字从 `configd` 读取，而不是通过正在认证的通道。
- 该名称只是为了答案的存在，而非计划中的内容。它的理由十分狭窄：它并未为桥接路径增添任何价值，而桥接路径已经得到了更好的验证；在局域网中，它每增加一个连接就需要增加一个步骤，而仅能证明对端读取了每个机器人上打印的数字。如果将来需要它，成本低廉——第5节的路由表已经需要一种概念来表示传输可以到达哪些方法，“在认证之前的方法”只是该表的一个子集而非新的机制。

## 5. 控制通道是对现有API的一个管道

`control`上的帧是**JSON-RPC 2.0，每行一个对象**，这正是[`duck-ipc-proto`](../../duck-ipc-proto/src/lib.rs)已经定义并`robotctl`和`btd`已经使用的格式。没有新的东西被发明：`mediad`将调用路由到拥有该服务的Unix套接字，并将回复回传。

`btd`是当前的工作范例，应当成为共享的范例：
| `btd` 今天 | `mediad` 需要什么 |
|---|---|
| `route.rs` — 哪些调用可以通行，哪个套接字回应，哪条通道承载它们 | 同一张表，但有 *不同的允许子集* |
| `session.rs` — `system.authenticate` 的门 | 同一个门 |
| `upstream.rs` — 建立套接字连接，超时一切 | 同一事项 |
| `framing.rs` — BLE MTU 分段 | **不需要**；SCTP 自身进行帧处理 |

所以四个文件中有三个是传输无关的，一个不是。**将路由表提升为两者共用的内容**，并通过传输可以达到的子集进行参数化。

值得保留的属性不是代码，而是详尽匹配。`route.rs` 明确地说：向 `proto::Call` 添加一个变体会使文件无法编译，因此新方法无法到达无线电，因为有人忘记了这个文件的存在。使用 `_ => None` 通配符会无声地拒绝新方法，第一个症状将是无法看到某个功能的应用程序，而这个功能没有人记得要路由。这种保证必须 **对每个传输** 都成立，否则 WebRTC 就成了这个保证的漏洞。

### WebRTC 可以到达的内容及其为什么不是 BLE 的子集
BLE的子集较窄，因为无线电传输速度较慢，几米范围内的任何人都可以与其通信。
这里不适用，因此WebRTC可以获得更多——但“更多”不等于“全部”，仍有两类情况被排除在外：

- **`system.pairingPin` 和 `system.setPairingPin`**。这并不是因为它们会损害这种传输——§4 本身已经留有余地——而是因为它们授权了不同的传输。能够重写配对PIN的局域网对端可以将手机从BLE中锁定，这是恢复路径。将PIN从每个网络传输中移除的规则与使其无法通过BLE本身路由的规则相同。

- **`update.*` 变更**。目前仅此而已，且原因不同于PIN：应用更新会重启`mediad`并断开会话。以后可能需要；§8 才是实现它的必要条件。
And 一个类别是值得在这里命名的，而不仅仅是在路由表中：
**`account.*`**，将这个机器人绑定到 Hugging Face 账户的调用。它们是这个传输携带的第一个
变更调用，而控制台是有人会为机器人进行登录的地方。这也是这里唯一一个其效果像账户一样超越会话的东西——[remote-access-design.md](remote-access-design_zh.md) §2.6 是论据和使其成立的三个属性，而 `mediad::route` 携带了简短版本。

### 回复不相关，故意为之

`btd` 将套接字发出的任何内容直接转发而不解析，且测试固定了这一点：订阅是一个在打开连接上的通知流，而每一个通知都必须到达客户端。将回复与请求相关联会破坏这一点。`mediad` 继承了同样的规则，这也意味着 **在添加方法时 `mediad` 中没有针对方法的额外工作** — 管道保持愚蠢，`duck-ipc-proto` 仍然是唯一定义方法的地方。
The 车道概念同样适用，也很容易假设它不会。每个守护进程在同一连接上一次请求服务一个请求，因此在同一个连接上 `update.subscribe` 之后的任何其他操作都会挂起——这就是 `app-path-design.md` §7 记录的确切错误。一个数据通道是一个有序流，具有相同的危险，`btd` 的答案未作更改：通过方法路由到一个车道套接字，每个套接字回泵，从不相关联。

## 6. 为什么 `control` 只读先来，以及 `teleop` 上岸会付出什么代价

`intents.rs` 中的每个意图都存储在一个 `ArcSwap` 中，并采取最后写入者获胜。今天这是正确的，因为每个写入者都通过一个 Unix 套接字到达，其中后来的消息不能在更早的消息之前到达。

**一个可靠且有序的数据通道保持这一点不变。** 在这种模式下，SCTP 按定义顺序交付，因此通过 `control` 到达的意图保留了 `intents.rs` 已经依赖的属性。因此，从一个通道开始并不是一种妥协，不会积累工作——它意味着在第一个版本中根本不存在排序问题。

### 为此付出的代价，以免大家感到意外
头端阻塞。在可靠通道中，丢失的数据包会阻塞其后面的所有内容，包括控制RPC，因此一个差的连接会表现为**一切暂停**，而不是过时的操纵杆。以适度的速率在`control`上驾驶是可以的，但随着速率和丢包率的增加，情况会变得更糟——这也是为什么`architecture.md`第5.2节指定了第二个通道，以及为什么“机器人在差的连接下感觉延迟”时的答案是手动操作而不是调整。

### 而当手动操作着陆时，它需要序列号

**SCTP在`maxRetransmits: 0`下会重新排序。** 80毫秒前的一个转折可以落在一个更新的数据包之后并赢得最后写者赢的规则，然后机器人会基于一个过时的命令驾驶，而没有任何地方报告问题。这并不是罕见的竞态条件：这是通道的正常行为，是故意选择的结果。

因此，手动操作帧携带**每个流的单调序列号**，写入者会丢弃任何比它上次应用的更新的数据。这是传输层的属性，因此它属于`mediad`而不是`robotd`——`robotd`应该接收它能信任顺序的意图，这使得`intents.rs`保持简单。
在信道存在之前而不是之后记录下来：这种失败是无声的，看起来像是调优不当而不是一个 bug，如果在设计时就考虑到这一点，修复起来很简单，但如果需要先诊断一个过时的扭曲，修复起来就显得很繁琐。

死锁者无论哪种情况都不需要额外的操作：`safety.gate(command, twist_age)` 已经是基于时间的，因此分区会停止机器人而无需新代码。

## 7. 连接不在本地局域网的机器人

**远程路径是通往本地信号服务器的桥梁，而不是另一种设计。** 一个中继进程连接到一个会面服务，并将相同的协议代理到 `ws://127.0.0.1:8443`。机器人的信号服务器、会话模型、授权和控制通道保持不变；DTLS-SRTP 通过中继也能保持媒体端到端加密，这一点值得向客户端明确说明。

由此衍生出两个特性，这两个特性就是这种设计的原因：
- **本地模式从不依赖桥接。**如果会合服务不可用，局域网客户端仍然可以连接。`architecture.md`中的不变量1——本地恢复保持独立——扩展到了媒体。
- **桥接不发明任何协议。**信封使用的是gst signalling协议，这是局域网客户端已经使用的协议，因此负载——SDP和ICE——通过透明的方式传递。这就是使用`webrtcsink`而非`webrtcbin`的具体收益。

这并不意味着桥接只是一个纯中继，这个项目标过去曾说过它是。`reachy_mini`的会合服务通过HTTP——SSE入站，`POST`出站——而不是通过WebSocket来传递这些信封，并且对等和会话ID是逐跳的。因此，桥接会重写信封，并在两个方向上维护一个会话表：一个带有透明负载的翻译器。
[`remote-access-design.md`](remote-access-design_zh.md) §3.2将两部分并列展示。
- **桥梁进行认证，因此机器人无需进行认证。** 中继连接 *外部* 并持有账户令牌，服务仅向客户端展示其账户拥有的机器人——因此在会话到达之前，双方都会进行授权。第4节讨论了这会留下怎样的信任问题。

一个有用的推论是：由于中继是一个连接回环接口的机器人端进程，机器人可以通过源地址区分桥接对端和局域网对端，尽管它目前并不处理这种差异。如果这种情况发生变化，也不会有任何限制。

`reachy_mini` 正是按照这种安排与 Hugging Face Space 进行交互，机器人注册为 `producer`，而 Space 则通过心跳保持 TTL 租约更新。本地模式现在可以工作，因此这一节留下的两个问题——我们是否采用该服务以及机器人如何绑定到一个账户——已经不再悬而未决，因为这些问题已经得到了解答：
[`remote-access-design.md`](remote-access-design_zh.md) 包含了这两个问题的答案，账户采用的是 Hugging Face OAuth **设备** 流程，而不是 `reachy_mini` 使用的重定向流程（第2.1节解释了原因）。

### 信号协议，由谁编写桥梁时使用
从 `gst-plugins-rs` 0.15.3 开始，`net/webrtc/protocol` — 传输的数据是 JSON 格式，带有 `type` 标签，
camelCase：

| 同步 → 服务器 | 服务器 → 同步 |
|---|---|
| `setPeerStatus` (`roles`, `meta`, `peerId`) | `welcome` (`peerId`) |
| `startSession` (`peerId`, 可选 `offer`) | `sessionStarted` (`peerId`, `sessionId`) |
| `endSession` (`sessionId`) | `startSession`, `endSession` |
| `peer` (SDP `offer`/`answer`，或 `ice`) | `peer`, `error` (`details`) |
| `list`, `listConsumers` | `list` (`producers`), `listConsumers` (`consumers`) |

角色是 `producer`，`listener`，`consumer`。机器人是 `producer`；`meta` 是自由格式的 JSON，
并且是机器人身份信息所在的地方。

## 8. 通过 WebRTC 更新机器人：尚未实现，以及需要哪些条件

不在第一个允许的子集中，**这是一个延期而不是原则** — 通过 WebRTC 更新机器人是后来的需求，
因此本节讨论的是必须满足的先决条件，而不是为什么不能这样做。
What 使它今天显得笨拙：应用更新会重启 `mediad`，这会导致客户端正在观看进度的会话中断。`update-over-ble.md` 记录了“启动更新并观看它”失败已发生过一次，而会话在更新过程中消失同样是同样的问题。因此，第一个子集将 `update.*` 的变更排除在外，BLE 保持为在重启后能存活的传输方式。从一开始就引入只读的 `update.*` 调用——通过远程会话查看版本和历史记录是有用的，且不会产生任何成本。

对于变更本身，有两件事需要改变，而且都是小而具体的：
- **客户端必须能够应对重启。** 协议本身已经支持这一点：进度以 JSON-RPC *通知* 的形式推送，`duck-ipc-proto` 详细记录了这一点，以便客户端在中断更新过程中重新连接时可以重新订阅并继续接收这些通知。因此，工作的重点是客户端的重新连接和重新订阅，而不是对传输格式进行更改。
- **`RobotRemoteSessionActive` 必须更加具体。** `updater/src/preflight.rs::check_no_remote_session` 在远程会话处于活动状态时拒绝更新，这是正确的，因为此时会话只是一个旁观者——有人正在进行远程存在通话，不应在他们不知情的情况下重启机器人。当会话是请求者时则是错误的。目前还没有设置该标志为真，因此可以设计这种区分而不是事后补上：检查需要知道即将断开的会话是否是请求这次更新的会话。

现在记录这一点是有价值的，因为目前还没有设置该标志。当 `mediad` 如实报告时，通过 WebRTC 请求的更新将被拒绝，这看起来更像是更新路径中的一个 bug 而不是这里缺少这种区分。
## 9. 权限：这一特性打破的前提，被指出但未采取行动

`intents.rs` 中说其槽位是“实际上的单写者”，因此“后写者胜”就是它的意思。这在只有一个手柄的情况下是真的。**一旦手柄和远程对端同时驱动，情况就不再成立**，而且失败并不是竞争——而是两个写者以50 Hz的频率交错写入同一个槽位，产生一个既不听从任何一个写者命令的机器人。

**这里故意不解决这个问题**。记录下来是为了给一个令人困惑的机器人提供一个解释，并且因为最终解决这个问题的标志在有两套传输之前设计会更便宜。`architecture.md` §6 拥有这个需求——定义优先级和交接，本地物理可以优先于远程——并且路线图中它在M6阶段。

到了适当的时候，一个简单的解决方案是一个**单写者令牌**：一个对端持有写入意图的权利，其他对端是观察者，交接令牌是明确的。这比§6中的全部仲裁要少得多，并且移除了交错写入，这是产生无意义而非仅仅是错误的获胜者的部分。优先级排序——无需询问直接优先本地物理——可以之后再做，基于同一个令牌之上。
这一部分的目的：知道两个同时运行的驱动程序是一个已知的缺口而不是一个谜，以及第一个症状是机器人忽略所有输入而不是执行错误的输入。

## 10. 构建 `mediad`

`gstreamer-rs` 箱是 pkg-config 箱，因此在目标平台上跨编译它们需要在开发者的机器上安装目标平台的头文件、`.pc` 文件和共享库。`cargo board` 使用 `cargo-zigbuild` 从 macOS 跨编译，而之前用于提供其唯一 C 依赖项的多架构脚本曾提到它“是那个例外的成本，而且在添加另一个之前值得阅读”。这是第二个，也是更大的一个——它完全取代了那个脚本，因为 Ubuntu 的多架构可以提供 libudev 但无法诚实地提供 GStreamer：它会给开发者机器上的 Ubuntu 提供，而机器人运行的是 Debian 特里奇的。

**`scripts/cross-sysroot.sh` 将机器人的 Debian 包解压到一个 sysroot 中** —— 经验证明：整个工作空间的跨编译都针对它进行，`gstreamer`、`gstreamer-app` 和 `gstreamer-webrtc` 都解析为 1.26.2 版本，与板子运行的版本相同。

在接触它之前，有三件事值得了解：
- **它服务于整个工作区，而不仅仅是 `mediad`。** `PKG_CONFIG_LIBDIR` *替代* pkg-config 的搜索路径，而不是添加到路径中，因此仅携带 GStreamer 的 sysroot 打破了 `padd` — 其中 `gilrs` 需要 libudev — 并在 `libudev-sys` 中这样做，远离任何关于媒体的内容。替代仍然是正确的：`PKG_CONFIG_PATH` 是对 *宿主机* 的补充，这就是为什么 pkg-config 会回答一个 macOS 库并生成一个无法在机器人上运行的二进制文件。
- **包列表是明确的，而不是解析后的。** 从显而易见的根节点遍历 Debian `Depends` 拉取了 543 个包，因为 `libgstreamer-plugins-bad1.0-dev` 声明了每个可选后端的开发包，闭包达到了 Qt、Vulkan 和 OpenEXR。只有十九个包满足实际所需。
- **单独的 `-dev` 包对于实际链接来说是不够的。** 它将 `libfoo.so` 作为符号链接指向运行时包中的 `libfoo.so.N`，因此 `-lfoo` 需要两者。仅出现在 `Requires.private` 中的库只需要 `-dev`。
The 替代方案是在一个 arm64 运行器上构建 `mediad`，就像在 [`media-bringup.md`](../project/media-bringup_zh.md) 中的插件一样。但因为这将 daemon 的构建分成两部分，并且没有人能够在笔记本上构建 `mediad` —— 对于那个需要最多针对真实硬件进行迭代的 crate 来说，这是一个错误的权衡。

### `media.video` 规定了图片的几何信息

宽度、高度、安装旋转——以及相机的 **内参**，这是消费者需要将像素转换为方向的信息。没有这些信息，单目重建将是尺度无关的，并且其角度是错误的；SLAM、视觉里程计和“那有多远”都始于这里。
四个数字和一个标志：`fx`、`fy`、`cx`、`cy` 和 `calibrated`。它们描述了 **发送时** 的框架——因为机器人不会旋转像素，所以这些值是未旋转的，因此对应用了 `rotate` 的消费者来说，需要同时旋转这些值，交换 `cx` 和 `cy`。标志并非装饰：`false` 表示 IMX219 模块的设计参数（3.04 毫米的焦距，1.12 微米的间距，主点假设居中，没有畸变模型），这在几百分比的精度内是有效的，足以测绘一个房间；`true` 表示一个测量值：*这台* 机器人的，写在 `[media.intrinsics]` 中，或者——由于摄像头和镜头是阿尔法家族的一部分，因此是默认值——随 `robotd-params` 一起提供的家族解决方案。需要进行计量的消费者可以据此判断需要进行询问。
**关键是当几何形状未知时不存在，而不是存在且错误。**那是一个正在传输测试模式的机器人，或者一个 `media-ctl` 无法设置传感器模式的机器人——在这种情况下，传感器处于其 3280×2464 的启动模式，其视野覆盖整个阵列而不是 1920×1080 的裁剪区域，因此每一个固有的参数都会偏离大约 1.7 倍。`mediad::camera` 包含了所需的算术和模式表，包括从传感器读取 720p 会将视野 *变窄* 为 27° 而不是节省任何东西。

## 11. 所有通过网络传输的数据都应携带发生的时间 —— **待实现**

今天，此传输方式所携带的数据均未在源头进行时间戳标记。一帧图像在到达时被打上时间戳，一个 `robot.state` 通知在到达时被打上时间戳，而一个想要知道机器人在何时看到或感受到某事物的消费者只能依靠自己的时钟——而在另一个大陆的中继传输中，这个时钟与实际时间相差未知的路径延迟。
That 是用来驱动你正在观察的机器人，但对于远程消费者感兴趣的其他一切而言，它的形状是不对的。**SLAM 是使其具体化的案例**：在没有捕获时间的流上进行单目 SLAM 可以运行，而当有人想要视觉惯性（即，这个机器人已经拥有的、频率为 50 Hz 的 IMU，且在同一控制通道上）时——两组数据系列除了猜测外无法关联。远端应用的时间戳衡量的是网络，而不是机器人。

两个部分，它们并不是同一个问题：
- **媒体。**RTP时间戳相对于随机偏移量是相对的，因此它们只能排序帧而不能确定它们的时间。这种机制是`abs-capture-time` RTP头部扩展，它携带每个分组的时钟捕获时间，这是接收器需要将视频与任何其他内容对齐所需的信息。`webrtcsink`是否会协商这一点，以及浏览器和`aiortc`会暴露多少，是首先要检查的内容——一个接收方不显示的头部扩展没有任何价值。
- **控制信道。**这是我们自己的且成本低廉的机制：一个单调递增的读数，加上用于跨进程可比性的启动时间戳，每次通知描述一个时刻。成本是一个字段每条消息和关于使用哪个时钟的争论——答案必须与媒体路径最终用于给帧打时间戳的时钟相同，否则两个时间序列仍然无法合并。

未实现，且有意不在远程路径中构建或开始：它会改变每条通知的外观，因此需要自己的决策和版本号，而不是附带在传输上。`remote-access-design.md` §9将其列为开放项。

## 12. 推迟，有理由
- **一个用于服务器端程序的WebSocket界面** (`architecture.md` §5.3)。使用相同的JSON-RPC，没有媒体栈，`get_frame`返回一个JPEG。一旦§5的路由存在，它就只有几十行代码，并且这就是“一个LLM驱动机器人”变得容易的原因——但它是一个备用传输，第一个传输应该有效。
- **`teleop`数据通道**。这不是短期内的优先事项；§6涵盖了推迟它的利弊，以及它在短期内会带来的成本，以及它所需要的序列号。
- **多对视频**。一次一个媒体会话，加上控制客户端。同时进行多路传输和一次编码多次发送是真正的项目。
- **同意和流媒体指示器**。`architecture.md` §7希望每个会话都有明确的同意和一个可见的指示器，并且现在便宜但以后昂贵。它们需要硬件支持——一个由软件控制的LED——这尚未确定。
- **TURN**。仅限局域网不需要它。一个桥梁需要它，并且会带来实际的带宽成本；这个决定应属于会话服务，而不是在这里做出。
