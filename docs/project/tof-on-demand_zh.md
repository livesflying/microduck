# 无人注视时的头部传感器

`tofd` 在每次装有头部模块的鸭子从启动到关闭的过程中，对激光进行了测距并读取了IMU数据，无论是否有进程订阅了任一数据流。这最初是“仅在需要时启动单元并在之后停止”，最终在每一步都进行了测量：**深度流本身并不消耗任何成本，真正有成本的是那个没有任何消费者的数据传感器，而且其内部循环中的任何内容都不值得优化。**因此，激光和单元被保留了下来，头部IMU增加了一个开关，默认关闭。

这接着[`idle-cpu.md`](idle-cpu_zh.md)，后者将`tofd`的轮询从每秒约100次I²C读取减少到约45次，并留下了“为何要进行轮询”的问题。

## 测量的成本

在旧ucky（Radxa Zero 3，RK3566）上，一个空闲的板子，没有任何数据流的订阅者：
On olducky (Radxa Zero 3, RK3566), an idle board with nothing subscribed to either stream:
```text
$ ps -L -o tid,comm,pcpu -p "$(pidof tofd)"
    TID COMMAND         %CPU
  12209 tofd             0.0
  12212 tof-sensor       0.5
  12213 head-imu         4.5
```
百分比基于一个核心，所以`top`显示的约5%是该SoC的1.25%——并且它是**九部分头部IMU之一部分深度**。为套接字服务的运行时，由于没有东西需要服务，因此不产生任何成本。

这个划分是本文档的全部内容。从中可以得出两方面的结论。

**IMU的数量是指一个样本采集两次读取。** 而不是唤醒次数，也不是融合。该crate的`bench_imu`以五种方式运行循环，在100 Hz下每种方式持续10秒，此时`tofd`被停止：
```text
  sleep only  (0 reads)   cpu  0.69 %
  filter only (0 reads)   cpu  1.00 %
  update      (2 reads)   cpu  3.35 %
  update_all  (2 reads)   cpu  3.86 %
  three-reads (3 reads)   cpu  4.20 %
```
Being 每秒被唤醒一百次是0.69分；Madgwick更新增加0.31分；剩下的约2.4–2.9分来自两个I²C交易。一个陀螺仪样本和一个加速度计样本*是*十二字节，位于两个地址，因此没有任何完整样本的成本低于两次交易——这就是为什么此循环中的任何内容都不值得优化。

关于这些数字有两个注意事项，因为它们是决策的基础。`update`和`update_all`执行相同的工作（一个委托给另一个），它们之间相差0.51分，因此噪声底限约为半分——可能是A55上的CPU频率缩放。而在`tofd`仍然持有总线的早期运行中，相同的三种读取模式被压缩到4.44/4.46/4.53，使第三个读取看起来是免费的。这些变化不影响形状：读取操作占主导地位，底限较小，第三个读取值在0.3到0.9分之间。

**没有任何订阅者。**`head_imu.stream`在这个树中没有消费者：`btd`拒绝代理它（`btd/src/route.rs:412`），更新器的降级IPC拒绝它（`updater/src/ipc.rs:819`），也没有守护进程订阅。它是为了映射工作而添加的，但该工作尚未到来。因此，此守护进程最大的重复成本是一个无人订阅的传感器读取。

明确地说，这并不是指行走策略的IMU：它是一个不同的芯片，连接在不同的总线上——`imu_to_dxl` v2板在Dynamixel总线上以50 Hz `sync_read`读取，与十五个伺服机相同（`duck-control/src/bus.rs`，`duck-control/src/model.rs:76`）。这里没有触及它，也没有任何内容会为此策略的IMU样本造成成本。

## 所作决定

**`[head_imu] enabled`，默认关闭。**循环中的任何内容都没有带来收益，因此开关就是答案：一个没有订阅者的流不应在启动时耗费核心的约4%。它存在于`robotd.toml`中，`mediad`已经在读取`[media]`，因此`robotctl configure`会写入它并提供`tofd`重启；`tofd --imu`在一次会话中读取芯片而不触碰文件，而当开关关闭时，一个订阅者会得到一个命名键的原因，而不是一个不匹配传感器给出的沉默。在映射工作读取流时打开它。
**第三个冗余读取还是进行了**, 因为 bmi088-rs#1 和一个 `tofd`，它从一次调用中获取样本。这个读取值为 0.3–0.9 分，这在上面的表格噪声范围内，因此它是因为其他原因而被接受的：发布的 `accel` 成为了四元数计算所用的样本，而不是在大约 200 µs 后的另一个读取，而且读取可以在一个地方失败而不是两个地方。

**读取速率是剩余的杠杆，它是线性的** — `--imu-hz 50` 将读取成本减半。将其保留为一个标志而不是配置键：第一个真正的消费者决定需要什么速率，现在猜测一个数字是没有意义的。

**如果消费者将来需要以低廉的成本获得 100 Hz 的数据，答案是使用 FIFO。** 两个芯片都有一个 FIFO，因此十个样本可以在一次事务中到达而不是二十个 — 这是唯一攻击真正占主导地位的术语的变化。这会增加一帧解析、水印配置和最多 100 ms 的延迟成本，这就是为什么不会为不存在的消费者构建它。

## 设计的门控机制，现在已经不再需要

保留这些是因为推理过程导致了切换，并且第一步是一个 bug，无论怎样都是一个 bug。

### 1. 让“有人想要这个”成为事实 — 无论以何种方式都是一个 bug

`accept` 在读取请求字节之前（`tof/src/main.rs:612`）将连接订阅到 **两个** 通道，因此 `receiver_count()` 统计的是连接数而不是兴趣：一个请求 `head_imu.stream` 的客户端持有深度接收器，而一个连接并保持沉默的客户端则持有两个。

将 `subscribe()` 调用移入 `subscriber()` 匹配臂中，这样接收器仅在方法已知的地方存在，并将两个 `Sender` 传递给函数而不是两个 `Receiver`。单独来看，这样做是有价值的 — 一个没有请求任何东西的连接不应被视为想要深度数据 — 而且这是下面所有内容的前提。

### 2. IMU 线程可以在第一个订阅者时打开，在最后一个订阅者离开时关闭

没有需要保留的昂贵内容：`open_imu` 只是一些寄存器写入，没有固件和探针。因此线程可以等待 IMU 租约，打开，当有人在监听时以 `imu_hz` 速率读取，然后在他们离开时关闭 — 这同样节省了 4%，而无需操作员知道切换的存在。
**未构建，因为开关已经到位且只是十分之一的设备。**这在有任何消费者时便成为更好的答案：一只同意参与的鸭子在没有任何东西在读取时会支付4%的费用。两个细节将决定是否做得正确：

两个细节决定是否做得正确：

- **订阅答案必须不撒谎。**`ImuStatus`初始为`unavailable: "no reading yet"`，`head_imu.stream`的答案在第一个样本之前写入。冷启动时，该答案会读作"no BMI088 fitted"，这是它在有该设备的板子上绝不能说的一件事。因此，处理器会向线程发送信号并等待打开操作解决——有界，大约几百毫秒——之后再回答`found`或`lost`。（开关也有同样的问题并以相同方式解决：`ImuStatus::off`是其自身的一句话，命名了关键点。）
- **冷启动的`quat`是一个收敛的`quat`。**Madgwick融合在大约一秒内稳定下来（`tof/src/imu.rs:43`），因此订阅者获得的朝向仍然在移动，而今天获得的是自启动以来已经收敛的朝向。`gyro`和`accel`是原始的且未受影响。在`method::HEAD_IMU_STREAM`上记录它；第一个真正的消费者可以决定是否需要一个预热的滤波器，这在那时很容易添加，现在猜测是没有意义的。

### 3. 不要封禁测距，也不要改动单位

在测量之前，两者都是计划的一部分，现在也都已关闭：

- **按需测距节省0.5%的CPU核心。**这是`tof-sensor`线程保持激光开启、轮询并每秒发布15帧所花费的成本，减去`idle-cpu.md`中的轮询工作。停止和启动测距本身是便宜的——`start(hz)`/`stop()`每次都是一个事务（`tof/src/sensor.rs:293`，`:181`）——但这意味着在拥有共享I²C总线的一个进程中需要一个状态机，需要正确的恢复路径，并且是一个没有人测试过的硬件假设（即停止然后启动不会重新上传固件）。0.5%并不值得为此付出。
- **`robotd`的 theremin 可以在启动时继续订阅。**它的深度读取器只连接一次并保持连接（`robotd/src/theremin.rs:237`），在有测距封禁的情况下会为恰好在演奏音符的鸭子固定激光。没有测距封禁时，没有什么需要固定，因此它在启动时连接的原因——使得第一次武装窗口只需等待帧——没有受到挑战。
The 一个用于限制激光的参数是VCSEL自身的功率，这与CPU无关，并不会在`ps`中显示。如果有人希望关闭这一限制，数字可以在VL53L8CX的数据表中找到；在毫安级别时它会保持关闭，这个项目可以移除。

## 为什么不启动和停止该单元

保留该条目，因为它回答了这个问题的起始问题，并且原因是一个持久的事实，而不是一个测量结果。

**启动过程是秒级的，且是按进程进行的。** `Sensor::open` 会探测设备ID，然后上传ULD固件 — 大约90 KB通过I²C传输，“大约几秒，400 kHz”（`tof/src/sensor.rs:226`） — 在进行距离测量之前，每个进程只会进行一次。如果在`t`时刻启动了该单元的`monitor`，它会在几秒内显示一个空网格，并且`robotctl theremin`直到上传完成都无法开始武装。

**没有“关闭”的拥有者。** 两个客户端可以同时需要深度数据，因此在退出时停止需要一个存活于客户端被`SIGKILL`杀死后的引用计数，而systemd对此没有为手动启动的单元提供支持。一个被Ctrl-\杀死的`monitor`会使得传感器无限期地进行测量。

**它需要一个没有客户端拥有的权限。** `monitor`以`robot`组的操作员身份运行；`systemctl start`需要root权限或一个polkit规则授予该组对该单元的`manage-units`权限 — 这是一个新的安装路径的附加项，一个在安装板卡之前不会静默包含的项目。

**一个单元，两个传感器。** 停止`tofd`也会停止头部IMU，这是本文最终关心的传感器。

套接字激活可以免费解决权限和泄漏问题 — 一个`tofd.socket`单元拥有`/run/tofd/tof.sock`，连接即为启动信号，systemd拥有生命周期管理。但它无法解决固件问题，它会在每次会话的第一个连接时移动固件，并在每次空闲退出时重复此操作。这是在进程成为我们想要终止的对象时的正确机制；但这不是对一个投票问题的答案，在测量之后也没有值得回答的投票问题。

## 板卡上剩余的内容

- 一只鸭子运行切换开关时，`ps -L`显示完全没有`head-imu`线程。
- 如果有人希望第三次读数的精度优于半个百分点，可以再次回到测试台，将CPU调度程序固定并交错使用模式。但现在这已经无关紧要了。
- 在空闲状态下，十分钟内SoC的温度，启动前后的数据。一个核心的4%不会在其中显现，这是应该记录的真实预期，而不是去发现：这并不是为了没有人而读取传感器，而是关于温度。
