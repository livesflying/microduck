# 通过蓝牙更新机器人

状态：已实现，尚未在板上运行 · 日期：2026-08-19 · 负责人：皮埃尔

通过蓝牙的更新路径已经基本完成，但还没有人驱动它。`btd`已经路由了更新子集，`updaterd`已经向请求者流式传输进度，而`duck-btctl`可以通过`call`访问所有这些内容。驱动它发现了一个缺陷，使得应用程序自身的流程——启动更新，监视它——没有执行更新，两个较小的更新在`updaterd`中，以及一个需要输入的客户端界面。

这记录了发现的内容和所做的决定。这些机制紧邻着代码：
[`app-path-design.md`](../design/app-path-design_zh.md) §3.5 拥有连接通道，§3.1 拥有路由子集，而 `btd/src/route.rs` 携带了每条路由的推理，这些路由使得手臂能够做出这些决定。

## 1. 已经工作的部分，未重新构建

**路由子集覆盖了读取和触发。** `hello`，`update.check`，`update.apply`，`update.status`，`update.subscribe`，`update.log` 和 `update.listInstalled` 已经到达 `updaterd`，`robot.health` 和 `robotd`。这里没有向协议添加任何方法。

**应用已经流式传输了自己的进度。** `updaterd` 的 `run_mutating` 在回复之前将 `update.progress` 通知写入了应用到达的连接；`btd` 将每行从上游泵入会话而不读取它们；`duck-btctl` 打印了无 ID 的行并继续等待。因此，在应用过程中没有任何订阅的情况下，进度在 BLE 客户端期间到达了应用——而 `duck-btctl.md` 声称相反，“一个单独连接的应用在完成之前是静默的”——这被纠正了。

**在更新过程中重新连接的客户端不会丢失。** `updaterd` 为每个组件保留最新的 `Progress` 并将其重放到新的订阅者，而 `update.status` 在更新过程中从缓存快照回答时会用实时阶段进行修补。这些都是在链路断开后手机所需要的。

**并且回复在传输死亡前发出。** `updaterd` 和 `btd` 是更新过程中永远不会重启的两个单元，而两者都在回复后约五秒重启（参见 [`restart-order.md`](../design/restart-order_zh.md) §1）。

## 2. 问题所在

### 2.1 长时间的调用静默了整个会话 · `btd` · **已修复**
`Pool` 每个服务每个会话持有一个连接，它背后的两个守护进程每次仅处理一个连接的一个请求。因此，`update.subscribe` 跟随 `update.apply` 写入了一个 `stream_progress` 已停止读取的套接字流中：它从未运行，从未回复，也从未出错。当房主点击“更新”时，机器人没有任何反应，而且在任何地方都找不到错误。`update.apply` 跟随 `update.status` 也有同样的缺陷，只是症状较轻——在机器人正常运行和更新期间超时的状况下，状态查询超时了。

现在，调用按它们保持连接的时间分组，每个组都有自己的连接：
`app-path-design.md` §3.5 说明了车道，为什么在发生时共享一个连接是正确的，以及为什么每个调用一个连接被拒绝。这两个失败都有测试在修复前会失败。

这是唯一一个移动应用无法绕过的变更。

### 2.2 进度信息如同消防水龙对着20字节的管道 · `updaterd` · **修复**

源代码报告每次它写入的每个HTTP块——对于一个发布包来说，可能是成千上万个——并且每个订阅者都为此付费。一条进度行大约有一百个字节，这相当于在20字节的地板 `btd` 帧中发送五到六个通知，当客户端落后时，`btd` 会丢弃行，因此手机看到的百分比是任意的子集，进度条从12%跳到61%再跳到34%。

现在最多每整百分之一发送一个通知，每秒最多四个，合并于生成数字的引擎中，因此 `robotctl update watch` 也获得同样的流。被间隙抑制的百分比在下载结束时仍然发布，或者在快速下载时在97%时明显完成。

### 2.3 `update.check` 被引擎锁阻塞 · `updaterd` · **修复**

`ipc.rs` 在其自身头部声明了规则——只读请求使用 `try_lock`，因此 `status` 和 `subscribe` 在更新期间仍然可回答——而 `check` 并未遵循此规则。在应用期间被询问时，它在应用完成时回答，几分钟后，这在手机上与一个停止回答的机器人无法区分。现在它立即回答 `BUSY`，`update.pin` 也是如此。
`update.apply` 已经被路由并且是这三个选项中更为重要的一个——它安装了从未在该板上运行过的代码，从网络获取——而 `rollback` 和 `select` 则转向昨天在该板上运行的发布，下载 nothing，并且像其他任何过渡一样被自动回滚。引擎自身的自动回滚覆盖了未通过健康检查的发布，但这并不是用户拿起手机时的情况：那是一个安装了发布、通过了检查但随后表现 *更差* ——一项蹒跚前行的政策，而不是完全不执行的政策，一个停止重新连接的垫子。除了一个人类，没有任何东西会回滚，而这个人类正在拿着手机并且没有 ssh。

两者都被打开而不是仅仅 `rollback`，因为 `update.listInstalled` 已经被路由：一个应用可以显示板上的所有发布，而不能选择一个发布的能力是不完整的另一半。`select` 需要从列表中选择一个版本，这比误击键多出更大的出错表面，而这正是我们接受的成本。

`pin` 是有趣的拒绝。一个错误的 `select` 只需一个发布就可以被撤销，并且机器人会指出是哪个发布；一个因误击键被固定的机器人拒绝所有后续更新，并报告自己为最新版本，这是唯一一个看起来正确的行为但实际上是错误的行为。

### 2.5 由手机触发的更新被记录为 `btd` · **记录，未修复**

`updaterd` 在每次变更时都从 `SO_PEERCRED` 记录调用者的 uid 和 pid，这是支持回答“谁触发了这次回滚”的方式。通过 BLE，答案总是 `btd`，对于每部手机都是如此。`btd` 会原封不动地转发参数，并添加一个“谁”字段会使它成为请求的作者而不是管道。除非支持需要区分两部手机，否则不值得重新打开。

### 2.6 客户端截止时间是全面的，不是空闲的 · `duck-btctl` · **修复**

一个固定的预算要么中断一个正在工作的更新，要么等待一个死掉的机器人，而有用的信号已经存在：每次进度通知都是机器人正在工作的证明。截止时间现在是沉默——更新需要三分钟，这是合法的最大间隔（一个安装后挂钩），而不是最长的可能时间。手机应用继承了这一原则，而不是代码。

### 2.7 一个守护进程应用回复后大约五秒后链路会断开

这不是缺陷——§1 的排序，正在工作——但每个客户端都必须预期这种情况，而机器人宣布的断开连接不能被解读为更新失败。构建顺序如下：
1. `update.apply`会返回其结果。这就是答案；更新已完成。
2. 大约五秒后，`btd` 重启并且连接断开。
3. 重新连接，并读取 `update.status`。`last_attempt` 携带结果，因此一个错过了步骤1中回复的客户端仍然可以报告结果。

`duck-btctl` 在步骤2发生前打印出来。

### 2.8 开放，故意地：`from_dir` 通过蓝牙

`ApplyOptions.from_dir` 指定了机器人上的一个目录，这对手机来说毫无意义，但在实验台上却很有用。过滤它意味着 `route.rs` 会决定参数而不是方法，而 `btd` 并不会检查参数。预检已经拒绝了那些会出问题的情况——并且明确表示了这一点——因此保持现状，这里命名它是为了让下一个开发者能找到一个决策而不是一个疏忽。

## 3. `duck-btctl` 现在提供了什么

`version`，以及 `update` 的 `check`，`apply`，`status`，`versions`，`log`，`rollback`，`select` 和 `watch` —— 这些词与 `robotctl update` 使用的相同，因此在机器人上学会的命令可以通过无线电使用。参数是从 `duck_ipc_proto` 的自身类型构建的，而不是手写的 JSON，这正是 `call` 留给任何正在输入的人的：`update.apply` 的目标是一个外部标记的枚举，因此 `--ref` 和 `--version` 是不同的 JSON *形状*，错误的一个会导致解析错误且没有任何可以执行的内容。[`duckctl.md`](../robot/duckctl_zh.md) 包含了每个命令。

进度以每事件一行的形式打印到 stderr，这正是该页面已经承诺的，而工具却没有做到。

`duck-btctl` 是一个临时解决方案，这一点很重要：§2.1，§2.2 和 §2.3 是机器人侧的，因此应用程序继承了修复，而 §2.6 的截止形状是客户端侧的，因此工具做对了，而应用程序自己的注释将不得不说明原因。

## 4. 剩下的工作

**这一切都没有在板子上运行过。** 上面的内容都经过了测试，而测试无法看到手机所看到的内容：是否进度能够平滑地通过实际的 20 字节链路传输，`btd` 重启前 `apply` 的回复是否已经到达客户端，以及每个服务的第四个套接字是否会对 Zero 3W 造成任何成本。这些是下一阶段的内容，使用 `duck-btctl update apply --ref` 对抗开发板。

**`duck-btctl.md` 中过时的声明是通过阅读代码而不是通过板子来修正的。** 如果蓝牙上的应用最终证明是无声的，那么需要检查的是 `btd/src/link.rs` 中的传出队列机制，而不是路由。

## 5. 这里故意不做的事情
**不支持取消。**引擎没有这个功能，而且半途而废的更新比缓慢的更新更糟糕。已经离开的客户端：更新会完成。

**不支持手机端的自动应用开关。**`deploy/updater.toml` 明确没有将客户端机器人纳入无人值守重启的选项中，而在没有一个可以推理的机群之前，不应将此作为开关暴露出来。

**不支持加密。**`app-path-design.md` §8.1 指出了这一点，它并未阻碍此处的任何事情，而且上述关于在无线电范围内的一方能做的事情的所有声明都假设加密仍然处于关闭状态。
