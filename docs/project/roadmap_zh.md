## 第一个路线图达到了目标
M1 到 M4 是一个序列，目标是一个能够行走、空中更新且不会被砖死的机器人。这个目标实现了。从 `0.2.0` 版本以来的每次发布都通过 M1 和 M2 构建的机制到达了某个板卡，而 `0.9.x` 是一个能够行走、滚动、看见、说话和唱歌的机器人。

接下来的内容不是那个序列的延续。剩下的工作是独立的轨道，彼此之间没有顺序关系，因此 **下面的数字是标识符，不是序列** — [工作的顺序](#工作的顺序)将是一个单独的部分。

**创始声明只对了一半。** *产品化才是难点，而不是能力* 正确地判断了难度：更新路径、健康门、恢复网和 BLE 表面都已构建并保持完好。它判断了规模错了。自 `0.5` 版本以来，几乎所有内容都是能力——运动学、里程计、ToF、注视、语音、合唱、摄像头——而最大的单一组件，自主大脑，仍未移植。

## 里程碑

每个里程碑都有一个测试标准，即“完成”，因为没有测试标准的里程碑会漂移。

### M1 — 关闭循环 · **完成**
。
更新器有了真正可以阻挡的东西，团队得到了一个共享的 crate 边界：
一个 `robotd` 骨架，其状态为原子变量而非互斥锁（一个循环被卡住的机器人仍然能够回答“我不健康”），`duck-ipc-proto` 被提取出来，使得恢复路径上没有任何东西链接引擎的 http/tar/crypto 树，一个真实的套接字探测作为健康门，`robotd` 套接字的单一真相来源，每个守护进程在任何事情发生前都会记录一条警告级别的身份行，以及通过普通引擎进行首次安装的初始化。

**完成：** `robotd/tests/updater_gate.rs` 通过一个真实的套接字与一个真实的 `robotd` 进程进行更新门控并提交；`robotd --unhealthy` 会撤销 `current` 后面的内容。

### M2 — Dev 渠道 · **完成**
`sudo robotctl update apply daemon --ref my-分支` 安装一个分支构建，而 `scripts/dev-push.sh` 则通过 ssh 安装一个笔记本构建，完全不进行 CI 运行。两个特性使得每次推送都安全：首先，一个开发构建 **不能成为 `latest`**（版本是 semver 预发布版本，`version_under` 拒绝将开发标签读作发布版本），其次，它 **不能安装在客户机器人上**（`allow_dev_keys` 为假，只有文件名为 `.dev.pub` 的受信任密钥才被视为开发密钥）。

**已完成：** 通过实际仓库验证 — `dev.yml` 发布，`--ref main` 通过网络安装，并且客户机器人拒绝相同构建。

**还留有一个问题，现已决定：** 私有仓库的发布资源可以通过令牌访问，而客户机器人没有任何访问权限，因此，虽然这个仓库是私有的，现场的机器人也无法下载任何内容。**决定发布它**，这解决了该问题且不改变任何代码 — 引擎使用的 API 路径同样适用于公共仓库（参见 `[updater-design.md]`（../design/updater-design.md）§6.1）。

### M3 — `robotd` 正式上线 · **已完成**，分为两个部分
`robotd` **替换** `microduck_runtime`，通过将其控制核心提取到 `duck-control` 而不是重新实现它，因此相容性是由于提取而来的结果，而不是与移动的目标竞争的结果。第一片断是一个实际的 50 Hz Dynamixel 循环保持其姿态——这就是为什么 `robot.health` 的含义是 *循环满足了其时间限制*。第二片断是一个 61-D 观测构建器，主要加站立策略、意图表面以及一个通过其中的游戏手柄客户端。

**安全主管** 位于此处而不是 M6，持有对总线的唯一写权限，因此没有任何策略和客户端能够命令电机绕过它：关节夹紧、跌落 → 虚弱、以及意图死锁。

**硬件优先，仿真之后** —— 而电路板产生了测试无法捕捉到的一个错误：`ort` 在运行时低于其最低要求时 *惊慌失措* 而不是出错，这杀死了控制线程并使健康状况归咎于错误的事物。

**完成**：所有这些都在一个 Radxa Zero 3W 上实现。它通过意图 API 被驱动行走；使用 `robotctl` 应用更新可以干净地重启它；一个上线后不健康的发布会自动回滚。

### M4 — 硬件启动 · **结束**
A 测量里程碑，而非功能之一：它存在是为了将猜测转化为实际的数字。几乎所有的答案都是在发货过程中作为副产品得到的——循环保持在50.0 Hz（在非RT内核上，`missed=3`在15022跳动中），总线和`imu_to_dxl`板在`/dev/ttyS2`上响应，热传感器在每个区域都有实际读数，`on_apply`中的`systemctl restart`在实际的systemd上有效，而网关的提交和撤销都是真实的。

**日志保留问题通过决定而非测量来解决。** `/var/log` 在此镜像中是一个zram设备，因此`Storage=persistent`将journald指向一个本身在内存中的目录：它在干净的`reboot`后存活，在断电时丢失最近的日志。这是预期的安排——持久的记录是在`/var/lib`下的更新历史，每条记录都经过`fsync`（参见`[deploy/README.md]`([../../deploy/README.md])）。因此，原始的“日志在断电后存活”标准被废弃：它要求一个该项目决定不具有的属性。
**完成条件:** 它在硬件上运行，通过 `robotctl` 应用更新后可以干净地重启 `robotd`，门禁通过后，`journalctl --list-boots` 可以报告重启后的上一个启动记录。前两项已完成；最后一项是一个板上的命令，是唯一未完成的事。

**故意留下的两个未测量的数字**，因为它们没有等待项：eMMC 写入时间以及负载下的电池情况。它们属于 M7，这是关于了解一块板子在做什么的里程碑。

### M5 — `mediad`，WebRTC，SDK · **进行中**

**已在硬件上实现。** `mediad` 作为独立单元包含在发布版本中。相机通过 VPU 与局域网中的浏览器相连 —— `mpph264enc` → `webrtcsink`，使用受限的基本编解码器，并且 `control` 数据通道携带与其它传输相同的 JSON-RPC，控制台由机器人本身提供，因此有 URL 而无需安装任何内容（参见 [`remote-webrtc.md`](../design/remote-webrtc_zh.md) 第 0 节，[`webrtc-console.md`](../design/webrtc-console_zh.md)）。为了实现这一点，必须从源代码构建两个 GStreamer 插件（参见 [`media-bringup.md`](media-bringup_zh.md)），并且相机已经通过 `rkaiq` 获得了 3A。

**有三项保持其开放。**
**在外网。**与§7中所述的设计相同，但在此设计中，rendezvous服务和TURN在前，有意为之地排在第二位。[`remote-access-design.md`](../design/remote-access-design_zh.md) 现在拥有它：一个通过OAuth设备流到达的Hugging Face账户，以及从rendezvous Space——mini的舰队已经使用的信号服务器——到机器人上已经存在的信号服务器的桥梁。

**账户**是构建的，是第一步——`robotctl account login`打印出一个代码，有人在hf.co/oauth/device处批准它，然后机器人持有并自行更新凭证；这三次调用在BLE上工作，这是没有Wi-Fi的机器人唯一的传输方式，也在数据通道上工作。目前还没有消耗凭证：**桥梁**是下一步，也是rendezvous Space的协议被发现为HTTP而不是LAN客户端使用的WebSocket的地方。

在随鸭子一起发货之前需要解决一件事：令牌携带了Hugging Face授予的每个范围，因为第一方设备码客户端不接受`scope`参数。将其限制为`openid profile read-repos`是一个组织内的公共OAuth应用，并且是一个常量。
**SDK，以及一个小的Python客户端。** §5.3 将其设计为WebSocket加上快照：相同的JSON-RPC，没有媒体栈，`get_frame`返回一个JPEG，只有几十行代码——而`mediad`的会话层构建得使得表面可以未变地重用它（`mediad/src/session.rs`）。一个通过**WebRTC**的Python客户端可以获取实时视频和`control`数据通道，代价是需要`aiortc`，ICE协商和一个信号传递往返，对于只想发送意图并读取一帧的调用者来说。**调查的问题是，一个客户端是否可以同时覆盖这两方面**——WebSocket用于控制和快照，WebRTC仅在调用者要求流媒体时使用——或者一个脚本只需要WebSocket表面而不涉及实时视频，让实时视频保留在控制台中。在编写任何内容之前，先回答这个问题，因为它决定了SDK是五十行代码还是一个项目。
**隐私，现在是两个项目而不是一个。** *同意* — 在流开始前的每会话明确批准 — 是一个 `mediad` 会话层更改，并未受任何限制。*可见指示器*需要一个由软件控制的LED，而此硬件上并不存在（参见 [`remote-webrtc.md`](../design/remote-webrtc_zh.md) §11）；这是一个硬件问题，应该向硬件提出而不是将其搁置在软件里程碑上。`architecture.md` §7 指出两者现在便宜但以后昂贵，因此同意不应等待LED。

**完成条件：** 从局域网外进行的临场感工作正常，并且服务器端脚本可以获取一帧并在几行代码中发送意图。

### M6 — 发布准备

陌生人所需的内容。预购已开放，因此按 **前置时间** 而非难度进行排序 — 代码最少的项目前置时间最长。
- **配对PIN码。** BLE配对安全依赖于每个机器人的PIN码；工厂默认值是`000000`并在本仓库中公开，因此开箱即用的配对仅证明了物理存在而不会更多。必须生成一个PIN码，打印出来并记录下来——这是一个工厂流程，而不是一个补丁。它不能来自身份信息，因为身份信息在广告中已公布。
- **校准**，配置的另一半。身份不再等待它：机器人从自己的SoC序列号中推导出一个并将其命名为`duck-c51b`。
- **恢复网络，在电路板上进行测试。** 它被构建并发货，从未与任何无法启动守护进程的版本进行过测试，这是唯一重要的路径。这里最便宜的项目：一块电路板，一个故意损坏的版本。
- **同意**，来自M5。
- **清单陈旧性报告**（§8.4.2）。
- **权威仲裁**，已完成——包括边缘问题#52：`Call::is_mutating()`不涵盖`robot.enable`，因此启动行走机器人上运行策略的调用被归类为`hello`。
- **应用程序**。#107设计它并构建 nothing。阻碍因素是一个手机原型——扫描，连接，
  `hello`, 认证, `system.info` 并启用 `--require-pairing` 选项, 在真实的 iPhone 和真实的 Android 设备上 —— 因为 §5.5 当前是一个关于 CoreBluetooth 在笔记本上的事实。

一项项目在 M6 中被决定: 客户端机器人下载的来源。决定是发布此仓库, 以便发货的机器人在没有令牌和没有第二个主机的情况下达到其版本。它留下的后续问题是预算而不是阻碍 —— 匿名的 GitHub API 请求每小时每个 IP 限制为 60 次, 一只鸭子远远达不到, 而一个房间里二十只鸭子在同一 WiFi 下也不达到 (§6.1)。

**完成标准:** 非开发人员从手机更新机器人, 并且一个故意砖掉的版本能够无需笔记本电脑恢复。

### M7 — 了解板子在做什么

在他人手中的鸭子会发展出故障, 而今天, *哪个部分* 的答案是一个开发者通过 SSH 读取日志。目前还没有这种形状; 这是一个开放的研究, 而问题就是它拥有什么。
**已存在的情况**比看上去的要多：`robotctl health` 报告总线、IMU、电池、每个电机的温度和 SoC；`robotctl monitor` 绘制循环、垫片流、ToF 矩阵、3D 机器人和电源行；`scripts/pad-stack-report.sh` 是收集一个子系统完整故事的一个先例，使其可以粘贴；`board-test.sh` 运行 60 项检查，但这些检查在 CI 中以 emulated aarch64 而不是在你面前的板子上进行。

**缺失的内容，以问题的形式：**
- **一个支持包。** 一个命令，在故障后生成一个文件，有人可以发送。它不收集健康状况、版本信息、日志、更新历史和单元状态。`robotctl update show` 是其在单一子系统中的形式——一个持久化的运行记录，包含该时间段的日志——仅涵盖更新内容。
- **一个非开发人员可以运行的硬件通过/失败测试。** 总线扫描和每个伺服的回答，IMU 的合理性，ToF 感应器存在，摄像头存在，NPU 存在，麦克风和扬声器，负载下的电池。它更接近于 `board-test.sh` 的精神，旨在测试硬件而非发布版本。
- **历史记录，因为瞬时故障在快照中是看不见的。** 总线读取失败，丢失的时钟，伺服温度峰值，欠压重启。日志设计上不会在断电时幸存（M4），因此这里任何重要的内容需要依赖更新历史的持久性，而不是日志的持久性。
- **与 #52 的重叠。** IPC 监控设计是这个问题的软件部分，其崩溃记录——最后一次刷新到 `/var/lib` 目录下的固定大小文件中，位于发布目录之外，因此在更新和回滚时可以幸存下来——正是这种持久性特性。
硬件故障报告需要。两者应该一起决定，而不是各自生成两个答案。

M4的两个未测量数值记录在此：eMMC写入时间以及负载下电池状态。

**完成时间:** 非开发人员可以在故障后运行一个命令并生成一个命名故障部件的报告，或者声明硬件正常。

### M8 — 政策通道：来自Hub的策略

每个策略过去都包含在**daemon软件包中**，因此一个新的步态需要daemon的发布，并且一个在笔记本上训练的策略只能通过CI或整个daemon的侧载才能到达鸭子。此里程碑的要点在于，一个在`microduck_rl`——训练仓库（这是一个私有仓库）——中训练的策略可以被发布、安装并单独尝试，而且有人可以尝试一个他们没有训练过的策略并获得反馈。
**设计**，在[`policy-channel-design.md`](../design/policy-channel-design_zh.md)中，拥有本节留待日后决定的决策。简而言之：一个插槽可以从三个来源之一填充——官方（`pollen-robotics/*`，重置目标），社区（任何其他Hub仓库，未签名，已报告但从未自动应用）或本地（电路板上的路径）；`policy load`写入配置键，`policy reset`移除它，因此持久性和撤销机制已经存在；并且官方集以一个`policies`组件的形式打包，而不是每个插槽一个。

**大部分引擎已经构建完成**：`hf_hub`源解析和验证，组件自带版本号、回滚、锁定、启动试验和已知不良历史记录，`on_apply = reload`已存在，`xtask sign`为任何目录的文件打上签名。

**三个独立有用的部分：**
1. **本地环回，无网络。** `robot.loadPolicy` 加上本地姿态重载，以及 `robotctl policy list` / `load` / `reset`。提供了一种“尝试一个策略而不编辑 toml 文件”的完整流程，不涉及 Hub 和发布决策。`API_VERSION` 17 → 18。
2. **官方策略会留下制品。** *已完成* `robotd` 读取 `/opt/robot/policies/current`，由 `scripts/seed-policies.sh` 通过从 `pollen-robotics/microduck-policies` 下载固定集填充 —— 这种安排与 `setup-board.sh` 用于 ONNX Runtime 的方式相同。`policies/` 目录及其三个 `--include` 列表已被移除，更新 `[workspace.metadata.policies]` 现在就是整个发布步态的过程。
3. **超越固定版本。** *已完成* `policy.*` 在 `updaterd`、`robot.reloadPolicies` 和 `robotctl policy check` / `update` 中 —— 重新训练的步态现在可以到达没有守护进程发布的板子上，这正是该里程碑的全部目标。每个集合记录了其来源仓库，因此不会重复配置。
4. **社区库。** *已完成* `policy load <slot> <org/repo>` 从任何 Hub 仓库中获取一个策略到 `/var/lib/robot/policies/<org>/<name>/<rev>/` 中，`origin` 报告为 `community`
   对于陌生人的贡献，`policy search` 列出了可用的内容。迄今为止发布的 repos 已经包含了 `manifest.json`，其中包含 `obs_len`、`action_len` 和 `model_api`，因此无法在此运行的策略在下载之前就被拒绝——这也是 `model_api` 停止设计并实现的地方。

`reset` 在所有三个版本中都意味着“移除覆盖并重新解析”，因此第一片断提供了一个针对发布版的正确 `reset`，而第二片断则更改了它所解析的内容而不触碰命令。

**真正缺失的是** 在两端，而不是中间：
- **`robotd` 不能按需重新加载。** 机制是存在的 — `robot.setMode` 已经在家庭姿态下重建了每个 ONNX 会话 — 但没有针对每个插槽的触发器，且加载失败必须保留运行中的控制器，而不是让机器人陷入无动作状态。
- **没有任何内容发布一个捆绑包。** `xtask package --channel` 差不多；它会将 `--version` 与 crate 版本进行比对，而一个政策设定没有这样的版本，且 HF 仓库布局并不存在。
- **`model_api`** 在双方都设计但未实现。`robot.modelApi` 回答问题，但没有任何内容咨询它。
- **训练循环。** `microduck_rl` 导出了 ONNX；但没有任何内容将结果带到一个板子上。切片 1 是让“训练它并尝试它”变成一分钟而不是 CI 运行的关键。

**完成标准：** 在 `microduck_rl` 中训练的政策被发布到 Hub，安装在一只鸭子上，尝试后撤销，撤销操作通过 `robotctl policy reset` 完成 — 控制循环在整个过程中从未丢失对电机的控制 — 并且没有参与训练的人可以从机器人中找到它并尝试。

### M9 — 自动化大脑
要求最大的未跟踪缺口：运行时的 `autonomous.rs` 在守护进程的任何地方都不存在，也没有任何设计文档拥有它。[`ideas/autonomous_behavior.md`](../ideas/autonomous_behavior_zh.md) 是它的临时存放地——一个基于能量/情绪模型的16状态机，新颖性网格探索，ToF 避障，惊吓反应，球类游戏，小憩周期，以及被抚摸。

它现在所需的所有输入都已存在，还有一些它从未有过的：环境声音事件，深度帧，分类的躯干帧障碍点，语音标签，通过稳定ID识别的附近鸭子，共享节拍，RSSI 作为粗略距离，实时合成音，以及手与ToF之间的距离。

**形状比状态更重要。** 呈现、情绪和节拍是 *输入到一个大脑* 的内容，而不是旁边的不同模式。合唱和 theremin 成为了显式的模式，因为没有大脑可以挂载它们——合唱是55 KB的 `robotd`——这就是这个里程碑存在的模式，旨在停止重复。它会在获得代码之前先获得设计文档。

**完成标准：** 当一只鸭子独自在一个房间里做了值得观察十分钟的事情，且合唱是由它自己决定的而不是由命令启动的。

## 工作顺序
The 数字上面是标识符。这是顺序。

1. **M8，策略通道。** 下一个功能。它没有阻塞其他任何内容，并且它解开了产生机器人实际行为的循环：训练，发布，安装，尝试，回滚。
2. **M5的运输调查。** 便宜，它的答案决定了Python客户端是五十行代码还是一个项目。
3. **M6，随着发货临近**，按交货时间：客户机器人下载的地方，然后是PIN，接着是恢复网络的硬件测试。同意可以随时到来，应该尽早到来。
4. **M7** —— 一个没有日期的调查。它会在某个鸭子在他人手中出现故障但无人能命名时获得优先级，而最便宜的准备方式是将其与#52一起决定，而不是在其之后决定。
5. **M9，大脑** —— 后期，故意如此。它是剩余最大的工作部分，也是最有可能在构建过程中增长的部分。
