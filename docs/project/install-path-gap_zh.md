## 保留的内容

所有四项都在一天内提交成功，同时将`btd`和`configd`安装到开发板上。（计数器显示为“三”直到下方添加了第4节。）
**1. `on_apply` 使用一个命令重启几个服务单元。`systemctl restart robotd configd` 如果其中任何一个服务单元未知，则会整体失败——并且不会重启已存在的那个。因此，引入新守护进程的发布版本无法重启任何服务，因为该服务单元文件随着发布版本一起到来，但没有任何内容安装它。回滚的原因是 `not healthy within 30s: unreachable`，这个原因既没有命名服务单元也没有命名命令。**

**由于电路板保留自己的 `/etc/robot/updater.toml`，这是一个潜在的问题而不是致命的。**
Fixed 两次，第二次才是真正的修复。首先，防御性地：每次只重启一个服务单元，对于系统未知的服务单元会被跳过。然后正确地：**`hooks/postinstall` 安装了发布的服务单元。** 引擎一直有一个后安装钩子点 —— `extract → [pre_install] → swap → [post_install] → apply → health gate` —— 这个钩子点在 `current` 移动之后运行，因此 `ExecStart` 可以解析，且在重启之前运行，因此 `on_apply` 可以找到一个存在的单元。之前没有用到它；只有 `scripts/install.sh` 曾经将单元从一个发布中复制出来，因此每一个新的服务在每一个板上都需要一个手动步骤，永远如此。指出这种机制存在且未被使用的是代码审查，而不是我自己发现的。

**2. 构件中不包含新的单元。** 打包工作流程会通过显式的 `--include` 来命名每一个发布的文件，而单元被添加到了 `install.sh` 中，但没有在其中添加。手动发现：在板上运行 `ls current/systemd/`。
**3. 构件中未包含新的二进制文件。**Package步骤通过显式的`cp`逐个复制二进制文件。`cargo board --bins`构建了`btd`和`configd`；但没有任何步骤将它们放置在待处理区。`btd.service`失败于`203/EXEC`，这表明它是一个损坏的服务而非不完整的构件。

Bug 3 属于与 Bug 2 同一类问题，出现在同一文件中，**两个提交之后增加了一个测试以防止 Bug 2 重现**——该测试检查的是单元而非它们执行的二进制文件。每次修复都是正确的，但都过于狭隘，这才是值得攻击的模式，而不是具体的错误。

**4. `on_apply`的重启列表保存在板上，因此新服务永远不会被重启。**·
**测量**：最昂贵的一个，也是这里已经记录为“潜在而非致命”的问题。

`[component.daemon.on_apply].units`从`/etc/robot/updater.toml`读取——这是*操作员*的文件，`install.sh`特意保留了它。`configd`在引入它时被添加到了打包的`deploy/updater.toml`中，因此在那之前设置的板将永远保持`units = ["robotd"]`。每次`configd`的发布都会替换二进制文件但保留旧进程。
What 使它花费了两小时而不是两分钟的是失败的形态：

- 更新报告 **成功** — 更新完成，健康门限通过了，没有失败；
- `robotctl update apply` 然后报告 **`already_current`** 并不做任何事情，因此显而易见的恢复命令成了空操作；
- 代理程序在旧代码上继续响应，因此看起来修复是错误的而不是缺失的。四次 wifi 修复被验证为在从未运行的二进制文件上失败。
  `robotctl version` *确实* 能诊断这种情况，用词如下：“configd 运行的是 X，但安装的代理程序版本是 Y … 或者重启没有发生，或者失败了”。没有人运行它。存在的诊断工具如果没有被使用，其价值等同于不存在的工具，这表明更新本身应该注意到这一点而不是增加更多的诊断信息。
**Fixed** (`engine.rs::units_to_restart`): 重启集是从发布的 `systemd/*.service` 文件中推导出来的，然后与配置中命名的项进行并集运算，但不包括 `updaterd` 和 `btd` — 这两者从一种由测试强制执行的配置惯例，变成了代码中的 `NEVER_RESTART` 常量，因为它们是这些守护进程的属性，而不是操作员的选择。一块板的 `updater.toml` 如果早于某个守护进程，那么即使这样也会重启该守护进程，无需进行编辑。接下来是推导的逻辑，保留下来是因为它是这类列表应归属之处的理由。

**从发布的版本中推导重启集，而不是从板卡中。** 发布版本会包含 `systemd/*.service`，因此它已经声明了提供哪些单元 —— 这与将 `hooks/postinstall` 作为安装它们的正确答案是一样的。引擎可以重启发布的版本提供的单元，减去两个已文档化的排除项（`updaterd`，正在执行更新；`btd`，可能是请求的传输方式）。这样，添加了守护进程的发布会在每个板卡上重启该守护进程，无需操作员编辑，也不会让板卡的配置默默过时。
Two 更小的选项 被注意到作为上述选项的补充而不是替代：
`apply` 可以增加一个 `--force` 选项，用于在已经是最新的发布版本时重新运行挂钩和重启
（这有先例 — `install --force` 用于同一类的鸡和蛋问题），并且
`already_current` 可以比较 *运行中的* 版本而不是仅比较已安装的版本，这样它在出现问题时才不会成为无效操作。

**第二个问题的答案不在最初提出的地方。** 它真正提出的问题是
运行中的版本与已安装的版本不匹配时是否应该报告并拒绝还是修复，答案是
修复 — 通过 `updater/src/reconcile.rs` 实现，该文件在每次 `updaterd` 启动时运行而不是在 `apply` 内部运行。每个单元的运行版本来自其进程发布的身份文件，与该组件当前激活的版本进行比较，任何过时的版本都会被重启。由于 `updaterd` 在每次应用更新后的五秒内重启自身，因此每次 `apply` 后几秒内都会运行此检查，所以本节讨论的状态现在会通过 `Engine::apply` 保持不变。
What 剩下的部分比任何一种选项都要窄，并且现在已经关闭了。`reconcile` 有意不修复一种偏差 — `updaterd` 自身的偏差，因为拥有恢复过程的自重启循环是唯一无法解决的失败 — 而这仅在单一情况下遇到了 `apply` 返回 `AlreadyCurrent`：一个过时的 `updaterd`，操作员尝试使用 `apply`，`already_current`，没有计划重启，且没有任何办法修复它，除了手动运行 `systemctl restart updaterd`。

**已修复**（`engine.rs::restarts_owed`，`reconcile::stale_units`）。`apply` 和 `select` 在它们的已知路径上读取相同的标识文件，在 `already_current` 结果中命名正在运行的单元为其他名称，并像更新调度其延迟配对那样安排这些重启。这并不是启动检查所防范的循环：它仅在请求时触发一次，并通过 `systemd-run` 而非从正在重启的进程中触发。
**And `apply --force` 被移除而不是推迟。** 它的整个任务是重新运行重启操作，前提是当前版本已是最新版本；现在，`apply` 只在并且只有在有东西实际上过期时才会执行这一操作。增加一个标志会提供第二种方式来请求这一操作，但需要一个相当长的段落来正确地设计这一标志：`install --force` 拒绝执行，而 `robotd` 则会回答，因为它会禁用健康检查门，`apply` 保留了这一门，因此通过对称复制这一保护措施会恰好在机器人处于运行状态且数据倾斜时禁用该标志。现在，这已经不再需要回答了。
**固定了，之前这段话曾说相反的情况。**`btd` 被排除在 *在飞行中* 重启之外，因为重启它会中断承载更新进度流的 BLE 连接 —— 这部分之前正确且仍然正确。从这里得出的结论则不是这样的：之前说 `btd` 的修复“需要手动重启或重启……这在由手机驱动的流程中是一个真正的缺口”，而现在这种情况已经不存在了。排除 `btd` 的状态在结果传输到网络上后即告失效，因此 `btd` 和 `updaterd` 五秒后都会通过 `systemd-run --on-active=5s`（`RESTART_AFTER_REPLYING`）重启。客户端会看到其结果然后连接中断，对于 BLE 来说，这只是一个普通的重新连接。
**Also fixed,和这一段之前的说法相反。**可观测性部分被说成会幸存下来：`robotctl version` 无法看到 `btd`，因为 `btd` 没有提供套接字，所以没有可以询问的东西。前提是答案必须通过套接字传输。现在不是这样了——每个守护进程现在都会在启动时将自己的身份信息写入一个文件，`btd` 和 `padd` 也包括在内，因此 `robotctl health` 会读取每个进程启动时的版本，并在与安装的版本不一致时发出警告。没有守护进程因为这个原因而不可观测。

### 一个值得关注的后果：单位文件比安装它们的版本更持久

`hooks/postinstall` 安装了发行版随带的单位文件，并且出于设计原因，在回滚时会保留这些单位文件——替代方案是记录添加了什么以便撤销，但该钩子自身的注释认为这样做不值得，因为下一次成功的更新会重新安装发行版自带的内容。
That reasoning 适用于回滚。它不适用于 **回退到早于守护进程的发布版本**：单位保持不变，其 `ExecStart` 指向一个在较早版本中不包含的二进制文件，守护进程会因 `203/EXEC` 而失败。一旦该守护进程也被包含在 `on_apply` 的重启集中，失败的重启会阻止 *更新*，从而导致回滚。

观察到的情况正是如此：在运行开发构建的板子上执行 `robotctl update apply daemon`，该命令最终解析为稳定的 `0.2.0` 版本，而该版本早于 `configd`；`configd.service` 无法启动；引擎进行了回滚并报告了这一情况。结果是正确的——板子不应在未引入当前运行的守护进程的版本的情况下默默回退——但并没有说明规则，错误信息指出了一个 systemd 失败，而不是根本原因。
**现在明确表述而非 emergent。** `updater/src/orphan.rs` 拒绝一个缺少二进制文件的候选项，一些已安装的单元执行文件，拒绝的理由会指出该单元、缺失的二进制文件以及拒绝的方式 —— 移除该单元，`systemctl disable --now configd.service && rm /etc/systemd/system/configd.service`。没有 override 标志：移除单元正是操作员的意思，因为引入守护进程的板子不应运行该守护进程，而下一次更新会重新安装该单元。

关于它运行的位置。它 **不在** 预启动阶段，预启动阶段无法看到候选文件列表 —— 两次预启动通过都发生在 artifact 下载之前 —— 所以它在解压之后且在交换之前运行，此时 staging 仍然可以废弃且没有任何内容被武装。并且 **没有目标可以豁免**，不同于 `Error::WouldDowngrade`，它仅在 `Latest` 上触发：这个防护措施是关于镜像提供过时的 manifest，而这个则是关于一个无法启动的单元，`Ref` 正是它被观察到的方式。
It 不在回滚、重置为黄金版或 `select` 中运行。这些操作故意向后移动，是让电路板摆脱不良版本的方式，因此一个可以拒绝的检查不应位于恢复路径中（`docs/design/architecture.md` §1.1）——回滚到孤儿单元保持了上述文档的行为，并保持了自我纠正性。

## 什么是关闭它的机制

修订于 2026-08-11，在下面的重启机制实现之后，并且增加了一个之前未提及的约束条件：**CI已经是迭代中最慢的部分，因此该计划将根据它增加的等待时间来评估，而不仅仅是它覆盖的内容。** 因此，这里的一切都指明了新测试运行的位置。

### 预算，首先

CI会在每次推送和每次修改代码的拉取请求中运行，作为并行任务，因此等待绿色的结果取决于最慢的任务——而不是总时间。这一单一事实决定了新测试应放置的位置：

| 任务 | 使其变慢的原因 |
|---|---|
| `check` | 格式检查、clippy、`cargo test --workspace`、安装程序检查以及真实的 `xtask package` |
| `board` | 从源代码安装 `cargo-zigbuild`，以及 aarch64 的 QEMU 模拟 |
| `coverage` | 完整的带仪器的构建 |

因此，添加到 `cargo test` 的毫秒级测试不会产生任何注意的成本，而任何进入 `board` 或 `coverage` 的内容都会在每次推送时产生成本。接下来有三条规则，它们是本节的重点：
- **默认的 `cargo test --workspace` 只包含进程内测试。**没有打包文件，没有 `systemd`，没有网络连接，也没有睡眠。
- **任何需要解压一个 artifact 或驱动一个服务的操作都按需运行**，作为脚本或一个 `#[ignore]` 标记的测试 —— 从不运行在拉取请求路径上。
- **没有新的 CI 作业。**如果一个检查需要一个 artifact，它会挂靠在 `xtask package` 步骤中已经运行的 `check` 步骤，并重用该步骤已经构建的 tarball。

这两个数字以前更糟糕，而解决它们的两个移除正是这一部分所主张的形状 —— **从 CI 中移除工作比任何下面的测试增加的价值更大**：
- **`coverage` 运行了整个仪器化套件两次**在一个拉取请求中，分别针对头和基，只是为了打印出差异。移除了：`--fail-under-lines` 是用来检测退步的，而这个任务从超过七分钟缩短到了大约两分钟。成本被明确指出而不是被轻描淡写——现在，覆盖率有所下降但仍超过底线的变化不再被提及，而底线现在是一个单向的机制。
- **一个仅涉及文档的更改就支付了全部费用。** `on:` 没有过滤路径，因此编辑此文件时在 QEMU 下交叉编译了 aarch64 并在仪器化下构建了工作空间。在制定此计划期间，连续三个文档拉取请求都做了同样的事情。移除了一个 `paths-ignore` 项，其内容为 `docs/**` 和 `*.md`。

### 框架在途中发现的缺口——已修复

**一次失败的更新报告了一个机器人回滚失败，但实际上它已经成功恢复了。** 由上面的缺失用户版本重现，`RollbackFailed`是设计中认定最严重的结果——因此值得记录。

- 翻译全文，不要省略或添加内容。
The cause is not the rollback. `hooks/postinstall` 覆盖单元文件，并且设计上不会恢复它们：该钩子认为，未完成的发布会使得服务在下次发布前处于失败状态，无论是否回滚，情况都是一样的。这种推理依然有效且未改变。它没有预料到的是，单元文件在被回滚的发布中处于重启集里——然后回滚会重新运行相同的重启操作并继承相同的失败。这可以通过普通的不良发布而不是仅通过上面提到的降级情况来实现：两个连续的发布使用相同的单元名称，而新的那个是损坏的。

**修复方案是将交换操作与应用操作分开，因为只有一个是恢复操作。** 在 `swap_to` 之后且试运行被清除后，机器人 *确实* 回到了它原本所在的发布；随后单元文件无法重启是一个独立的事实，而不是对第一个事实的反驳。因此 `Error::RollbackFailed` 保持其含义——机器人根本无法恢复——并且在回滚过程中失败的应用操作会被记录为 `error`：
```text
not healthy within 30s: …; the release was reverted, but restarting robotd failed: …
`Restart=` may have brought it back since — `robotctl health` says whether it did.
```
Both 事实，按顺序排列：为什么更新失败在先，然后是未随撤销一起恢复的单元。

那句话的后半部分曾经是“所以这个机器人的某个东西宕机了”，它错误的频率足够高，值得单独指出。这里的每个守护进程都运行着 `Restart=always`，并且一个立即退出的守护进程在健康门的三十次尝试用完之前就已经被 systemd 拒绝重启了——因此，撤销的重启通常会被 `Start request repeated too quickly` 拒绝，并且单元在几秒钟后再次独立运行。一块测试板直接在其自身的 `机器人健康` 行下方印出了该宕机声明。`restart_one` 现在通过 `reset-failed` 清除了计数器，并再次尝试，这移除了原因；结果报告了它观察到的拒绝，并指出了它无法回答的命令。
The 两个被拒绝的替代方案，因为两者都不明显错误。使 `postinstall` 可逆是钩子明确拒绝的变更；它需要超出发布范围的状态，并在恢复路径中增加了一种失败模式，而这正是必须保持单调的地方。容忍失败的重启 *无处不在* 会削弱 `restart_one` 特意做出的区分——一个存在但无法启动的单元是捕获故障发布的方式，这在进入过程中仍然是致命的。

### 1. 在`HealthResult`中添加了一个必填字段
`main` 将 `consecutive_stale_blocks` 添加到了 IMU 部分，并从 `main` 分支发布了 0.2.0 版本。在那之前已经合并了 `main` 的分支没有发送该字段。`robotd` 运行得完美无缺——它服务了套接字，加载了两个策略，并以 50 Hz 的频率运行循环——而驻留的 0.2.0 版本 `updaterd` 因缺少字段而拒绝了它的回复。`RobotIo::health` 将无法解析的答案映射为 `Health::Unreachable`，因此网关报告了一个完全健康的机器人在 30 秒内未达到健康状态：不可达，从而回退了一个良好的发布。

修复了两个问题，都是小问题，而且 **都已解决**：

- **在新的 `HealthResult` 字段上添加了 `#[serde(default)]`**，这样较新的 `updaterd` 仍然可以解析较旧的 `robotd`。每次使用 `--ref` 安装一个在添加健康字段之前的分支都会遇到这个问题，而这正是整个开发工作流的一部分。

  这个问题中的一半是嵌套的问题：每个顶级字段已经带有 `#[serde(default)]`，包括 `imu`，而嵌套的 `ImuHealth` 中的 `consecutive_stale_blocks` 没有。`ImuHealth` 和 `BusHealth` 现在在容器级别携带了它，因此添加到任一者中的字段默认值而不是导致整个解析失败。
  `LoopHealth`, `Battery` 和 `MotorThermal` 故意不使用 **不**，唯一的例外是
  有用的修复部分：这些部分包含 *测量值*，默认的零值是一个不诚实的谎言，一个较旧的发送者从未说过——默认的 `percent: 0.0` 在一个满电的机器人上表现为一个平板包装。规则是“默认一个遗漏所真正意味着的内容”，而不是“默认一切”，而 `ImuHealth` 的文档注释则是逐字段进行论证的。
- **一个独特的 `Health::Incompatible`** 而不是重用 `Unreachable`，因此原因读作“回答了一个此更新器无法理解的形状”而不是暗示机器人已下线。纯粹是诊断信息，它会在一分钟内找到上述问题。

  已完成。在添加过程中还发现了它的邻居：`safe_to_restart` 也是以同样的方式压缩了一个不可读的回复，而 `permits_restart` 则将其读作 *safe* —— 这与它自己的注释承诺的恰恰相反。这变成了 `SafeToRestart::Incompatible` 和 #68。

### 2. `API_VERSION` 不一致问题在 `robotctl` 和 `updaterd` 之间
`robotctl` 是一个指向 `current` 的符号链接，因此它会跟随安装的版本。`updaterd` 则不会。因此，一旦版本变更了 `API_VERSION`，两者 **保证** 会不一致，直到 `updaterd` 重启——而停止工作的命令正是 `robotctl update apply`，这恰恰是你用来解决这个问题的命令。

这通过普通使用来展示，而不是通过刻意制造的情况：安装分支 A，等待 CI 安装分支 B，此时每次调用 `robotctl` 都会失败，提示 `client speaks API v2, daemon speaks v3`。唯一的解决办法是从一个版本与运行中的守护进程匹配的发布目录中调用 `robotctl`，或者重启 `updaterd`——这两种方法都无法从错误信息中发现。

握手至少 **捕捉** 了这个问题，并指出了两个版本，这比情况 1 做得更多。
The first提出的修复方案是**`hello` 应该只在客户端比守护进程** *新* **时拒绝连接**，
但这个方案被**否决了**(#77)：它假设版本更新是累加的，但实际上并非如此 — v5 添加了 `pad.*` 并且是累加的，而 v4 使 `system.authenticate` 成为必需并且不是累加的。仅仅依赖一个常量不跟踪的模式来接受较旧的客户端会承诺向后兼容性，但实际上却没有东西来保证这一点。
**固定问题的方法是直接移除那个门。**那个拒绝的前提仍然存在——一个突起承诺不了什么——但结论并不由此得出。打破一个不匹配的对等体的是它*无法到达的路径*或*参数形状的变化*，而这两个问题已经在无法服务的唯一调用中拒绝了自己：`Request::as_call`中的`METHOD_NOT_FOUND`，以及参数解码中的`INVALID_PARAMS`。握手阶段的门在其他所有调用中也触发了——事实上，在所有调用中，因为`hello`在它们之前——这就是一个位数差异同时拿走了`update apply`和`version`的原因。因此，`updaterd`现在记录这对版本并处理调用；差异通过`HelloResult::api_version`传递给客户端，而`robotctl`每次运行时打印一行警告信息。

在门可以移除之前，必须满足两个条件，而第二个条件是有用的部分：
- **拒绝必须是冗余的，而不仅仅是令人讨厌的。** 它是：`robotd`、`configd` 和 `padd` 完全没有检查这个数字，而 `updaterd` 在 `update.status` 之前也不需要握手。`duck-btctl` 已经从链路的另一端得出了相同的结论（#102）。
- **必须停止存在一个被默默地忽略的参数。** `serde` 会忽略它不认识的内容，这使得门体感觉像是承重的：v7 添加了 `ApplyOptions::from_dir`，而一个忽略它的 v6 代理会在操作者认为自己在侧载目录时从其配置的源进行安装。现在每个参数类型都拒绝未知字段，所以这被称为 `INVALID_PARAMS`，并命名了该成员。它只向前传递 —— 在此之前构建的代理仍然会忽略它不认识的内容 —— 这就是为什么仍然值得进行 `API_VERSION` 升级。

消息在此次更改前已经被重写，现在已经随着门体一起消失了。它曾说 `client speaks API v2, daemon speaks v3` 并未指出任何出路；它成长起来的补救措施（重试，或者使用 `/usr/local/bin/robotctl` 的符号链接）现在存在于 `robotctl` 的警告中，而没有任何内容被拒绝。

### 为什么这些不是安装路径错误
以上计划中的任何内容都无法检测到这个问题。该文件在两次都是正确的；出错的是同一时刻运行的 *版本对*，这仅存在于已更新的机器上。第4项（本地真实的systemd）可以检测到容器中运行较旧的`updaterd`时case 1的 *健康门* 结果，但故意构建这种偏差是一种不同的测试——更接近于兼容性矩阵而非安装测试，因此值得单独保留。
